# Learning more about Effect

This repository uses the Effect Typescript library: the server (`app/server/`) and the API definition it shares with the web (`packages/webui-shared/src/api/`) are written with it.

Before writing any Effect code, first read `repos/effect/LLMS.md` **completely**, and follow the links in the file when required (they are relative to `repos/effect/`).

If you need to learn more about particular Effect apis and concepts that the guide doesn't cover, search through the source code in `repos/effect/packages/effect/src` (`repos/effect/packages/` for the `@effect/*` packages). `repos/effect` is the same version as the installed packages: read it rather than `node_modules`.

Les règles du serveur sont dans `docs/superpowers/poc-effect/conventions.md` : où va chaque partie d'un domaine, le régime des diagnostics Effect, les requêtes et les réponses, les programmes, les processus longs et l'état autour d'eux, le SQL, les caches, l'ajout d'un groupe, d'un service, d'une étape d'arrêt, d'un message `/ws`, d'un cas de contrat ou d'une page, les tests et les commandes. Le lire avant d'écrire du code du serveur. Le serveur Nitro qui l'a précédé se lit dans git (`git show 8f6fe3581^:app/server/<chemin>`) ; le comportement porté et ce qui a changé sont dans `docs/superpowers/poc-effect/behaviours.md` et `defects.md`, le bilan dans `report.md`.

# llama-webui

L'app tourne sur Node (≥ 26.13, un seul processus) ; pnpm installe et lance les scripts. Un seul package `app/` : le client React (`app/src/`) et le serveur Effect (`app/server/`, point d'entrée `app/server/main.ts`), qui partagent la définition de l'API (`packages/webui-shared/src/api/`).

- Lancer : `pnpm dev` (`vite dev` dans `app/` : HMR de l'UI, serveur depuis les sources sous `node --watch`, relancé à chaque sauvegarde d'un fichier qu'il importe), `pnpm start` (build puis production) ; un fichier TS se lance par `node <fichier>` (syntaxe effaçable).
- Tests : Vitest (`pnpm test`, voir « Testing ») ; type check : `pnpm check` (le `typecheck` de chaque package, en parallèle) ; build : `pnpm build` (`vite build` puis `node build/server.ts` dans `app/`).
- Install : `pnpm install` (voir « Installation (pnpm) ») ; un outil ponctuel : `pnpm dlx`.
- `.env` du dossier courant : `main.ts` l'applique par `loadDotEnv` (`app/server/config/DotEnv.ts`, `parseEnv` de `node:util`) avant de lire la configuration : l'environnement l'emporte, sauf avec `--env-override` ou `LLAMA_WEBUI_ENV_OVERRIDE=1|true` dans l'environnement ou le `.env`. Pas de `dotenv`, seul `.env` est lu (pas de `.env.local`, pas d'expansion de `$VAR`). En dev, `vite.config.ts` l'applique de la même façon et le serveur lancé par Vite hérite du résultat.
- Le dépôt ne tourne que sur Node : aucune API ni commande Bun.

## Installation (pnpm)

L'app, ses tests et son build tournent sur Node ; pnpm installe et lance les scripts.

- `pnpm install` à la racine installe tout le dépôt, `site/` compris : un seul `pnpm-lock.yaml` (à commiter avec tout changement de dépendance ; la CI fait `pnpm install --frozen-lockfile`). Workspaces (`packages/*`, `app`, `site`), catalogue et réglages pnpm dans `pnpm-workspace.yaml` (pas de champ `workspaces` dans `package.json`, pas de réglage dans `.npmrc`).
- Le `catalog:` de `pnpm-workspace.yaml` fixe les versions qui doivent bouger ensemble (`"react": "catalog:"`) : pour une de ses entrées, changer la version là, pas dans les `package.json`. D'autres dépendances partagées (`@types/react`, `lucide-react`, `shadcn`…) ont encore leur version dans chaque `package.json` : candidat de refactoring (backlog de `docs/superpowers/plans/2026-11-12-node-migration-notes.md`), à ne pas migrer au passage.
- `allowBuilds` (absent tant qu'aucun paquet n'en a besoin) liste les scripts d'installation autorisés ; un paquet non listé qui en a un fait échouer l'installation : décider `true` (une fonctionnalité en a besoin) ou `false`. Garder les entrées `minimumReleaseAgeExclude` que pnpm ajoute.
- `effect` et les `@effect/*` (`platform-node`, `sql-sqlite-node`, `vitest`) sont épinglés à la même version exacte dans le `catalog:`, celle de la copie de référence `repos/effect` (submodule git, superficiel : `git submodule update --init` après un clone) : une montée de version change les deux ensemble (le commit du submodule et le `catalog:`), et se fait seule, suites vertes (presque tout Effect hors du cœur est `@stability unstable`). Le script `prepare` racine (`effect-tsgo patch`) installe le language service d'Effect dans le `tsc` de `node_modules` à chaque `pnpm install`.

## Serveur (Effect)

Les règles détaillées et leurs exemples sont dans `conventions.md` (voir plus haut) ; cette section en donne la carte.

- **Un domaine** : ses schémas dans `packages/webui-shared/src/<domaine>.ts`, son groupe d'API (endpoints, erreurs `Schema.TaggedError` avec leur statut `httpApiStatus`) dans `packages/webui-shared/src/api/<Domaine>Api.ts`, ajouté à `Api` (`api/Api.ts`) ; son service dans `app/server/<domaine>/<Nom>.ts` (un `Context.Service`, ses layers en statiques), ses handlers dans `app/server/<domaine>/http.ts`, ajoutés à `ApiRoutes` (`app/server/http/HttpLive.ts`), son layer à `Services` (`app/server/App.ts`) et à `ServicesTest` (`app/server/testing/services.ts`).
- **HTTP** (`app/server/http/HttpLive.ts`, `NodeHttpServer` sur `node:http`) : l'API (`HttpApiBuilder.layer(Api)`), le WebSocket `/ws` (`app/server/ws/WsHub.ts` ; sans upgrade : 426) et l'UI (`http/Static.ts` : `/assets/*` en `immutable`, un asset manquant en 404, `index.html` en `no-cache` pour tout autre chemin). Autour des routes de l'API et de `/ws` (`Guarded` de `http/Guard.ts`, fourni à `ApiRoutes` et à `WsHub.route` : un middleware des routes, pas du serveur, donc appliqué quelle que soit l'écriture du chemin que le routeur accepte, `/API/…`, `//api/…`, `/%61pi/…`, `/ws;x` ; une route ajoutée hors de `Api` le reçoit par `Layer.provide(Guarded)`), la garde (Host localhost ou IP, Origin de la page, corps d'écriture en `application/json` ; refus `RequestRefused`), puis le 308 d'un slash final (`http/TrailingSlash.ts`) ; un défaut d'un handler est loggé et répond 500 sans son message. Une erreur répond `{ _tag, message }` (et `issues` pour une validation) ; le web la reconnaît à son `_tag`, jamais à son texte. Tout autre chemin sous `/api`, ou une méthode qu'un chemin n'a pas (pas de 405), est un 404 `RouteNotFound` `Unknown route`.
- **Requêtes** : chaque endpoint déclare `params` (un id est `IdParam`), `payload` et `query` en schémas ; un handler ne lit jamais un corps lui-même. Les corps se décodent strictement (une clé inconnue est une erreur) ; un corps, une query ou un en-tête invalide est un 400 `RequestInvalid` `Invalid data: <premier problème> (<chemin>)` avec `issues`, un paramètre de chemin invalide un 404 `RouteNotFound` (`http/RequestErrors.ts`). Un fichier à télécharger : `attachment(schema)` (`http/attachment.ts`) ; un flux SSE : `HttpApiSchema.StreamSse` et `sseResponse` (`http/Sse.ts`, `: ping` toutes les 15 s), handler `handle`, jamais `handleRaw`.
- **Démarrage** (`main.ts`) : `.env`, la ligne de commande (`config/Cli.ts` : `--help`, `--version`, `--host`, `--port`, `--data-dir`, `--env-override` ; une option l'emporte sur sa variable `LLAMA_WEBUI_HOST`/`PORT`/`DATA_DIR`, `config/AppConfig.ts`), puis l'adresse vérifiée (`http/Address.ts` : un port pris sort en code 1, `llama-webui: cannot listen on <hôte>:<port>: the port is already in use`, avant de toucher au dossier de données), puis `Layer.launch(App)` : les services sont construits par étages (`App.ts`, la base en premier), et le port n'est ouvert qu'ensuite. Il n'y a donc pas de fenêtre « starting » : une requête trouve toujours un serveur prêt, un démarrage raté sort en code 1.
- **Arrêt** (`runtime/runApp.ts`, `runtime/Shutdown.ts`) : SIGINT ou SIGTERM lance d'abord les étapes d'arrêt (`Shutdown.before` : une réponse du chat enregistrée « stopped », un run ou un sweep « interrupted », le dernier message du hub), puis le serveur HTTP ferme (sockets en 1001, 500 ms de grâce), puis les services se défont dans l'ordre inverse de leur construction (le watcher externe, le bench, le monitor et les réponses du chat, la file de téléchargements avec son `.part`, llama-server arrêté par le superviseur, la base en dernier) ; sortie 0. Un second signal pendant l'arrêt sort tout de suite. Un échec sort en code 1 avec `llama-webui: <message>` sur stderr.
- **Requêtes sortantes** : jamais `fetch`. Toute requête à un llama-server passe par `LlamaHttp` (`app/server/llama/LlamaHttp.ts` : `node:http` sans limite de temps sur les en-têtes ni le corps, une socket par requête), toute requête à Hugging Face (API du Hub et téléchargements) par `HfHttp` (`app/server/hf/HfHttp.ts` : HTTP/1.1 sur ses propres agents, le proxy de l'environnement `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` posé sur eux) ; chaque appelant borne son attente et suit lui-même les redirections qu'il accepte.
- **Programmes** : par `effect/process` (`ChildProcess.make`, `ChildProcessSpawner`), jamais `node:child_process`. Un programme qui dure (llama-server, llama-bench, `nvidia-smi`, l'échantillonneur NVML) passe par `followProgram` (`app/server/process/followed.ts`). L'échantillonneur NVML est un programme Effect (`app/server/collectors/nvml/worker.ts`, `node:ffi`) à qui le serveur parle en NDJSON sur stdin et stdout (schémas de `protocol.ts`, les mêmes des deux côtés) ; il sort à la fin de son stdin, tourne tel quel en dev et en `.output/server/nvml-worker.mjs` en production. Le bench et les sweeps passent par `BenchRunner` (`app/server/bench/` : la réservation, le gate qui arrête puis relance llama-server, llama-bench et le llama-server d'essai, la boucle d'un sweep).
- **Fichiers et plateforme** : `FileSystem` et `Path` d'Effect ; un chemin écrit par une personne passe par `expandHome` (`config/Home.ts`, `~` et `~/…`). Les règles de la plateforme du language service refusent `node:*`, `fetch`, les timers et `JSON` dans le serveur : quatre imports `node:*` sont permis, chacun avec sa directive et sa raison (`conventions.md` › Diagnostics).
- **SQLite** : `SqlClient` de `@effect/sql-sqlite-node` (sur `node:sqlite`), ouvert par `app/server/db/Db.ts`, migrations dans `app/server/db/migrations.ts`. Ni `bun:sqlite` ni `better-sqlite3`.
- **Caches** : dans les services (les GGUF lus par `GgufReader`, les flags de `--help` par `Flags`, le matériel du bench, la table `model_cache`) ; l'API ne met rien en cache.
- **Réglages de test**, lus par le runtime : `LLAMA_WEBUI_TEST_MONITOR=stub` (valeur exacte, `Monitor.layer` : ni collecteurs, ni snapshot, historique vide), `LLAMA_WEBUI_TEST_OFFLINE=1` (valeur exacte, `HfHttp.layer` : toute requête échoue en `fetch failed`, d'où le 502 `HfUnreachable` des routes du Hub), `LLAMA_WEBUI_NVML_LIB` et `LLAMA_WEBUI_NVIDIA_SMI` (`Collectors.layer`, pour tester leur absence). En dev, `LLAMA_WEBUI_DEV=1` (posé par `vite dev`) envoie les spans aux Effect DevTools quand elles écoutent (`LLAMA_WEBUI_DEVTOOLS_URL`, `ws://localhost:34437` par défaut).
- **Client typé** : le web importe `Api` de `@llama-webui/shared` et l'appelle par `call((api) => api.<groupe>.<endpoint>({ params, payload, query }))` (`app/src/lib/api.ts` : la réponse décodée, ou l'erreur taguée de l'endpoint, `ApiUnreachable` sans réponse ; un corps que le client refuse d'envoyer donne le même `RequestInvalid` que le serveur) et un flux par `callStream(…, onEvent, { signal })`. Jamais de `fetch('/api…')` ni de cast sur une réponse : une réponse brute comme `/api/server/props` se restreint par des guards (`app/src/lib/props.ts`). Une erreur se distingue par son `_tag` (`errorTag`), une erreur de type se corrige dans le schéma partagé. Le web n'importe rien de `app/server/` (`app/server/build.test.ts` refuse un `node:*` dans le bundle client).

## Testing

`pnpm test` lance toutes les suites : `test:unit` (`vitest run`), puis `pnpm --filter llamacpp-js test` (`node --test`).

```ts#index.test.ts
import { expect, test } from 'vitest';

test('hello world', () => {
  expect(1).toBe(1);
});
```

**Dans ce projet :** `vitest.config.ts` (racine) définit un projet Vitest par base de code (`server` = `app/server/**`, `app/build/**` et `scripts/`, `shared`, `web` = `app/src/` et `site` avec leur alias `@`), `environment: 'node'`, imports explicites (pas de globals), `oxc: { target: 'esnext' }` pour garder `using` natif. Le projet `server` a un **globalSetup** (`app/server/testing/build.ts`) : un build de production (`app/.output`) par run, pour les suites qui le lancent ; `LLAMA_WEBUI_TEST_BUILD=0` réutilise le build existant (un fichier lancé seul après un `pnpm build`). Un fichier lancé seul : `pnpm exec vitest run <chemin>`, un nom : `-t '<regex>'`. `pnpm exec vitest run --changed` (ou le mode watch) ne relance que les fichiers qui importent un fichier modifié : les suites boîte noire et `dev.test.ts` lancent le build ou `vite dev` sans importer le serveur, il ne les choisit donc pas pour un changement du serveur ; boucle rapide pendant le travail, jamais à la place de `pnpm test` avant un commit. En CI, `test:unit` tourne en deux moitiés parallèles (`--shard=1/2`, `2/2`, chacune son build), à côté des jobs lint et types, build et paquet, site. Vitest échoue sur un `.resolves`/`.rejects` non attendu : toujours `await expect(…).rejects`.

- **Code Effect** : `layer(L)('Nom', (it) => { it.effect(…) })` de `@effect/vitest` (le test reste un effet, pas d'`Effect.runPromise` ; les finalizers du layer tournent après le bloc). `it.effect` tourne sur le `TestClock` ; un test sur le temps réel (processus, sockets, plannings) prend `layer(L, { excludeTestServices: true })` ou `it.live`. Les services d'un test viennent de `ServicesTest` (`app/server/testing/services.ts`, base en mémoire, monitor stub, délais raccourcis par les `layerWith` de chaque service) ; les dépendances sont des layers, pas de `mock.module`. Un faux llama-server, `freePort`, `httpStub`, `chatStub` : `app/server/testing/llama.ts` (faux programmes de `testdata/fake/`) ; un test qui lance un processus vérifie qu'il est mort à la fin ; un port de test n'est jamais 7860, 7861 ni 8080.
- **Suites boîte noire**, en Node simple contre le build : `launch({ dataDir, port?, env? })` (`app/server/testing/launch.ts`) lance le build comme un utilisateur (sans `CI`, `TEST`, `NODE_ENV` ni `LLAMA_WEBUI_DEV`, le réglage `port` de la base sur un port libre), attend `/api/health`, et `await using` l'arrête (SIGTERM). `app/server/lifecycle.test.ts` : port pris (code 1, sans toucher aux données d'une instance sur le même dossier), `.env` et `--env-override`, SIGTERM avec l'UI ouverte, llama-server lancé, une réponse en cours, un benchmark, un téléchargement (moins de 2 s, 1001, « stopped », « interrupted », `.part` repris), un dossier de données du serveur Nitro ouvert tel quel. `app/server/build.test.ts` : `.output` (lanceur depuis un dossier vide, serveur sans autre import que `node:*`, client sans `node:*` et découpé par page, licences, échantillonneur NVML à côté du serveur et qui démarre depuis le bundle). `app/server/dev.test.ts` : la boucle de dev sur une copie de `app/` sous `.cache/` (une sauvegarde du serveur le relance, une du web le garde, SIGINT, double SIGINT, SIGHUP, `.env`, les DevTools).
- **Suite de contrat** (`app/server/contract/`) : chaque endpoint rejoué en HTTP réel contre le build de production (réglages `LLAMA_WEBUI_TEST_MONITOR=stub` et `LLAMA_WEBUI_TEST_OFFLINE=1`), comparé à `golden.json` (hachages des assets remplacés par `<hash>`, chemins de la machine par `<repo>`, `<tmp>`, `<home>`). Sa matrice est générée depuis la définition de l'API (`HttpApi.reflect` dans `cases.ts` : chaque méthode qui manque à un chemin, le mauvais id et l'id inconnu de chaque `:id`, les cinq corps cassés de chaque payload) ; puis les cas écrits à la main (un succès pour un endpoint que la matrice n'atteint pas, sinon le test de couverture échoue, une `violation`, un `refusal`, un cas de garde) ; puis les cas qui tiennent une connexion (`runStreams` : `/ws` hello et pong, un profil lancé sur le faux llama-server, la réponse SSE du chat lue par `readSse` de `wire.ts`). Un changement de comportement voulu → `UPDATE_GOLDEN=1 pnpm exec vitest run app/server/contract/contract.test.ts`, puis relire le diff du golden.

## Type checking

`pnpm check` = `pnpm -r --parallel --include-workspace-root typecheck` : le script `typecheck` de chaque package du workspace, tous en même temps (`tsc` ; racine : `tsc -p scripts` ; `app` : `tsc && tsc -p server` ; `site` : `react-router typegen && tsc`). TypeScript 7 (`tsc` natif), version dans le `catalog:`. Les projets qui portent du code Effect (le serveur, `app/server/tsconfig.json`, et `packages/webui-shared`) étendent `tsconfig.effect.json` : le language service d'Effect (`@effect/tsgo`, plugin `@effect/language-service`) y sort ses diagnostics dans `tsc` (`effect(<règle>)`, sévérités dans `diagnosticSeverity`). Ils sont bloquants, warnings compris : `pnpm check` n'affiche aucune ligne `effect(` (`pnpm check 2>&1 | grep -c 'effect('` donne 0). `unstableApiUsage` et `apiStabilityLeak` sont coupées (`off`) : presque tout Effect hors du cœur est `@stability unstable` (`effect/http`, `effect/sql`, `effect/process`, les `@effect/*`…), d'où la version exacte dans le `catalog:`.

**Dans ce projet :** pas de `tsconfig.json` racine ni de project references : chaque base de code a son `tsconfig.json` (`packages/llamacpp-js` en types Node seuls et résolution NodeNext, tests compris, `packages/webui-shared`, `scripts`, et deux pour `app/` : `app/tsconfig.json` pour `src/`, `build/` et `vite.config.ts` (DOM + Node), `app/server/tsconfig.json` pour le serveur et ses tests (Node seul)), qui étend `tsconfig.base.json` (options communes : `noEmit`, `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` (une propriété optionnelle `x?: T` ne prend pas `undefined` : `x?: T | undefined` ou `Schema.optional` quand un appelant en relaie un), `erasableSyntaxOnly`, imports relatifs en `.ts` par `rewriteRelativeImportExtensions`), directement ou par `tsconfig.effect.json`, et n'ajoute que ses types et ses fichiers. Un projet qui importe un autre package en vérifie les sources avec ses propres options. Nouveau package → un `tsconfig.json` qui étend la base, un script `typecheck` (`tsc`) et `typescript` (`catalog:`) en devDependency ; pas de `paths` vers des sources d'un autre package.

## Format (oxfmt) et lint (oxlint)

oxfmt (devDependency épinglée, config dans `oxfmt.config.ts`, où se lit le style) gère le format, le tri des imports et celui des clés des `package.json` ; il formate aussi tous les `.md` (le `docs/` de la racine compris) et les pages `.mdx` du site, sans toucher au code de leurs blocs (`embeddedLanguageFormatting: 'off'`) ; il ignore ce que liste `.gitignore`, ainsi que `repos/`, les `testdata` et `pnpm-lock.yaml`.

oxlint (devDependency épinglée, avec `oxlint-tsgolint` pour les règles qui lisent les types, `typeAware`) gère le lint du TS et du TSX (pas du CSS, du Markdown ni du MDX). Une config par projet, toujours `oxlint.config.ts` : celle de la racine exporte `base` (plugins, catégories `correctness`, `suspicious` et `perf`, règles choisies par nom) et couvre `scripts/`, `app/build`, `app/bin`, `packages/webui-shared` et les fichiers de la racine ; `app/server`, `app/src`, `site` et `packages/llamacpp-js` ont la leur, qui étend `base` et les fragments dont le projet a besoin, `oxlint.react.ts` (React et `jsx-a11y`, pour `app/src` et `site`) et `oxlint.tests.ts` (Vitest sur `*.test.ts(x)`, sauf `llamacpp-js`, testé sous `node:test`). Chaque fichier prend la config la plus proche, qui remplace celle de la racine sans s'y ajouter ; les `ignorePatterns` ne passent pas par `extends` et sont relatifs à leur config : chaque config de projet répète ceux de son dossier. Ni lintés ni formatés : ce que liste `.gitignore`, `repos/`, `**/src/components/ui` (shadcn généré, app et site, pour rester comparable aux mises à jour shadcn), `**/testdata`, `app/server/contract/golden.json` (généré) ; oxlint saute aussi le `docs/` de la racine et les sorties de build. `.eslintignore` (`/repos/`, lu avant les configs imbriquées) empêche oxlint de charger `repos/effect/.oxlintrc.json`, ce que les `ignorePatterns` ne font pas. Toute règle active est en `error` ; une règle coupée ou avec options porte sa raison en commentaire dans la config (`require-yield` coupée dans `app/server/oxlint.config.ts` : un générateur d'Effect n'a pas toujours de `yield`). Les règles qui signalent sur le code d'aujourd'hui sont coupées dans deux blocs « dette » (`--- Debt: off until its milestone ---`, dans `oxlint.config.ts` et dans l'override Vitest de `oxlint.tests.ts`), chacune avec son compte et le jalon qui l'allume (L4, L5) : un bloc ne fait que diminuer, on n'y met pas une règle pour faire passer le lint. Config effective d'un projet : `pnpm exec oxlint -c <projet>/oxlint.config.ts --print-config` (`--print-config <fichier>` ignore le chemin et affiche celle de la racine). Les diagnostics Effect restent dans `tsc` (« Type checking » ; `prepare` : `effect-tsgo patch --typescript --no-oxlint`).

- `pnpm lint` (`oxfmt --check && oxlint --deny-warnings --report-unused-disable-directives`) : vérifie format + imports + lint (lecture seule ; un warning ou une suppression qui ne sert à rien le fait échouer) ; `pnpm lint:fix` (`oxlint --fix && oxfmt`) applique les corrections sûres puis formate ; `pnpm format` (`oxfmt`) formate seulement.
- **Avant de clore un jalon / milestone / lot de travail** (et avant de commiter ou d'ouvrir une PR), tout doit être vert : `pnpm lint`, `pnpm check`, `pnpm test`. Zéro erreur et zéro warning d'oxlint.
- Ne pas désactiver une règle ni la baisser en `warn` pour faire passer le lint. Si une règle est un faux positif, `// oxlint-disable-next-line <règle> -- <raison>` (`{/* … */}` en JSX) ciblé et motivé, la règle sous le nom qu'affiche le rapport, un `/` à la place des parenthèses et sans le préfixe `eslint` (`react-hooks(exhaustive-deps)` s'écrit `react-hooks/exhaustive-deps`, `eslint(no-control-regex)` s'écrit `no-control-regex`) : sans raison (`directives/require-reason`, plugin local `scripts/oxlint/directives.ts`), sans règle (`unicorn/no-abusive-eslint-disable`) ou sans rien à taire, la suppression fait échouer le lint. Une dépendance « déclencheur » d'un effet (listée, jamais lue) n'est pas signalée par `react-hooks/exhaustive-deps` : un commentaire dit qu'elle est voulue ; quand la règle signale un tableau de dépendances voulu, la suppression va au-dessus de ce tableau : elle tait tous les rapports du hook, une dépendance absente comprise, même si le rapport affiche la ligne où la valeur est lue ; un hook sans tableau (un effet relancé à chaque rendu) la prend au-dessus du hook. Pour lire la dernière valeur dans un effet sans le relancer, préférer `useEffectEvent` (React 19) à une suppression ; pour réinitialiser un état au changement d'identité, un `key` sur le composant plutôt qu'un effet.

## Langue

L'UI, les messages du serveur (erreurs, validations des schémas, logs, `--help`), les commentaires, les noms de tests, les messages de commit et les PR sont **en anglais**. Nombres, dates et unités passent par `app/src/lib/format.ts` (`LOCALE = 'en-US'` de `packages/webui-shared/src/format.ts`, `num`, `fmt`, `plural`, `formatBytes` en KiB/MiB/GiB…), côté serveur par `fmtInt` et, pour une taille, `fmtBytes` (`packages/webui-shared/src/format.ts`, avec `MiB` et `GiB`) : pas de locale codée en dur. Le web ne compare jamais un texte de message du serveur : utiliser le `_tag` de l'erreur ou un helper partagé (`isOomError`, `isDefaultTitle`).

## Packages (`packages/`)

`packages/webui-shared/` (`@llama-webui/shared`) : les schémas (Effect `Schema`) et la logique pure partagés par le serveur et le web, et la définition de l'API (`src/api/` : `Api`, un groupe par domaine, les erreurs de chaque endpoint). `packages/llamacpp-js/` : tout ce qui parle à llama.cpp (API HTTP de `llama-server`, métriques, `--help`, sortie de `llama-bench`, `/proc`), destiné à être publié sur npm. `packages/webui-theme/` (`@llama-webui/theme`, privé) : le thème Obsidian Aurora en un seul `theme.css` (tokens clair et sombre, fond aurora, styles de base), importé par `app/src/index.css` et `site/src/styles/app.css`, qui n'y ajoutent que leur calibrage ; un changement du thème redéploie le site (`paths` de `site-deploy.yml`). Règles de `llamacpp-js` (vérifiées par `tests/package.test.ts`, son projet TS et ses tests, sous Node en CI) :

- **Cible :** Node ≥ 24, donc uniquement des API web et `node:*` dans `src/` (`fetch`, `node:child_process`, `node:fs/promises`) ; son projet TS n'a que les types Node. Ses tests sont dans `tests/` (hors de `src/`) et utilisent `node:test` + `node:assert/strict`, sous Node (`pnpm --filter llamacpp-js test` = `node --test 'tests/*.test.ts'`, en CI sous Node 26 et, dans un job à part sans installation, sous Node 24, la version minimale). Les contrôles de bundling de `tests/package.test.ts` passent par Rolldown (devDependency) et passent `{ skip }` sans installation.
- Aucune dépendance ni import de `@llama-webui/*` ; ce qui est un choix de llama-webui (superviseur, `buildCommand`, formulation des erreurs pour l'utilisateur, caches) reste dans l'app.
- TS exécutable tel quel par Node : imports relatifs avec extension `.ts`, `import type`, syntaxe effaçable (`erasableSyntaxOnly` : pas d'`enum`, de `namespace` ni de propriétés de paramètre).
- Tree-shakeable : ESM, `"sideEffects": false`, aucun état ni effet au chargement d'un module, un export par module dans `package.json` ; seul `llamacpp-js/node` utilise des API Node, le reste tourne aussi dans le navigateur.
- Erreurs : classes `Llama*Error` avec un `name` fixe ; l'app les traduit en messages.

## Build, dev et distribution

`app/vite.config.ts` construit le client (`app/src/`, React, Tailwind par `@tailwindcss/vite`, alias `@`) dans `.output/public` ; `app/build/server.ts` (Rolldown) construit ensuite le serveur.

**Dans ce projet :** un seul process Node sur le port 7860 sert l'API, le WebSocket et l'UI (`LLAMA_WEBUI_HOST`, `127.0.0.1` par défaut, `LLAMA_WEBUI_PORT`, `LLAMA_WEBUI_DATA_DIR`, ou leurs options). `pnpm dev` = `vite dev` dans `app/` : Vite garde l'adresse publique (`strictPort`) et sert l'UI en HMR ; son plugin `app/build/devServer.ts` lance le serveur depuis les sources (`node --watch server/main.ts`, `LLAMA_WEBUI_DEV=1`) sur un port libre de loopback, dans son propre groupe de processus, et lui passe `/api` et `/ws` en proxy (`changeOrigin: false` : la garde lit le Host et l'Origin du navigateur ; une requête de l'API attend que le serveur réponde pendant qu'il (re)démarre). Arrêt de Vite (SIGINT, SIGTERM, SIGHUP) : le serveur reçoit SIGTERM et Vite l'attend (une page ouverte reçoit son 1001), un second signal le tue ; un SIGKILL de Vite est la seule fin qui laisse le serveur tourner. Version (`app/server/config/AppInfo.ts`, barre d'état, `/api/health`) : `dev` depuis les sources, `git describe --tags --always --dirty` au build (`LLAMA_WEBUI_VERSION`, défini par `build/server.ts`), la version du `package.json` sans git.

**Rechargement (dev) :** une sauvegarde d'un fichier que le serveur importe (`app/server/`, `packages/`) le relance (`node --watch`) : le runtime est défait comme à un arrêt (llama-server arrêté, un sweep en cours passe « interrupted », bouton Resume, une réponse du chat « stopped », un téléchargement reprendra son `.part`) puis reconstruit, nouveau `bootId`. Une sauvegarde sous `app/src/` reste du HMR, le serveur et llama-server sont gardés.

`pnpm build` = `vite build && node build/server.ts` dans `app/` → `app/.output/` : `public/` (client découpé par page, assets hachés), `server/index.mjs` (le serveur, un seul fichier qui n'importe que `node:*`), `server/nvml-worker.mjs` (l'échantillonneur NVML), `llama-webui.mjs` (le lanceur, `app/bin/llama-webui.ts`, `#!/usr/bin/env node`, qui importe `./server/index.mjs` : la ligne de commande est lue par le serveur) et `server/THIRD-PARTY-LICENSES.md` (`app/build/licenses.ts`, depuis les modules embarqués dans le serveur et l'échantillonneur). `pnpm start` = build puis `node app/.output/llama-webui.mjs`. `node scripts/smoke.ts` vérifie le build (CI). **Distribution :** le paquet racine est le paquet publié (`bin` `llama-webui` → `app/.output/llama-webui.mjs`, `files` `app/.output` seulement, `os` linux ; `pnpm pack` refuse sans build, `scripts/prepack.ts`) ; il n'a **aucune dépendance** : le build est autonome (`scripts/package.test.ts`). `.output` est ignoré par le `.gitignore` racine et non par un `app/.gitignore` : npm appliquerait ce dernier au tarball malgré `files`. `node scripts/smoke.ts --tarball [fichier.tgz]` : `pnpm pack`, `npm install` dans un préfixe vide, puis les vérifications du smoke par `node_modules/.bin/llama-webui` (CI). `release.yml` (tag `v*`) : `node scripts/release.ts --check`, build, `pnpm pack`, smoke du tarball, `SHA256SUMS`, `gh release create` ; la version de tous les `package.json` s'aligne par `pnpm release <version>` (PR, `master` est protégée) ; `scripts/release.test.ts` échoue s'ils divergent.

## Site web et documentation (`site/`)

Le site public (page d'accueil, doc utilisateur, doc développeur) vit dans `site/` et est publié sur GitHub Pages (`https://sharkezz.github.io/llama-webui/`, base `/llama-webui/`). Plan et jalons : `docs/superpowers/plans/2026-11-08-website.md`.

- **Pile :** `site/` utilise Vite + React Router (mode framework, `ssr: false` + prérendu statique) + Tailwind 4 + shadcn + MDX. C'est un projet du workspace pnpm (installé par le `pnpm install` racine, sans lockfile propre), ses scripts lancés par pnpm et exécutés par Node (`node scripts/<nom>.ts`, mêmes règles que `app/server/` : `node:*`, imports avec extension `.ts`), ses tests dans le projet Vitest `site`. Il n'importe aucun code de `app/` : les composants repris (verre, jauges…) sont copiés et adaptés ; les tokens, le fond aurora et les styles de base viennent du paquet partagé `@llama-webui/theme` (voir « Packages »).
- Mêmes règles qualité que l'app (oxlint sans warning, type check, tests verts) ; le contenu est en anglais, URLs avec slash final. Les scripts racine couvrent le site : `pnpm check` lance aussi le `typecheck` de `site` (`react-router typegen` puis `tsc`), `pnpm test` inclut `site/` (projet Vitest `site`), et la CI (`.github/workflows/ci.yml`, sur chaque PR et chaque push sur `master`, ou à la main par `gh workflow run ci.yml --ref master`) construit le site. oxfmt formate les `.mdx`, qu'oxlint ne lit pas ; tous deux ignorent `site/src/components/ui/**` (shadcn).
- **Commandes :** après le `pnpm install` racine, depuis la racine `pnpm site:dev` (Vite + HMR sur `0.0.0.0:5173`, ouvrir `http://192.168.0.20:5173/llama-webui/`), `pnpm site:build` (prérendu + `scripts/postbuild.ts` → `site/dist/`) et `pnpm site:preview` (`scripts/serve.ts`, `node:http`, sert `dist/` comme GitHub Pages sur le port 4173, `--port` pour un autre : sous `/llama-webui/`, redirection vers le slash final, `404.html`).
- **Pages :** chaque `.mdx` de `site/content/{docs,developers}/` devient une route prérendue (`src/routes.ts`, `src/lib/content.ts`). Les liens internes s'écrivent sans basename (`/docs/…/`) : React Router ajoute `/llama-webui`. Le prérendu écrit sous `build/client/llama-webui/` ; `postbuild` remonte ces pages à la racine de `dist/` et transforme le fallback SPA en `404.html` (route `*`). Le déploiement (`.github/workflows/site-deploy.yml`) part à chaque push sur `master` qui touche `site/` (ou à la main, `workflow_dispatch`) : une PR fusionnée publie aussitôt sa doc.
- **Écrire une page :** front matter YAML `title` + `description` obligatoires (le build échoue sinon ; le titre `h1` vient de là, ne pas en écrire dans le corps), entrée dans `site/content/nav.ts` (`site/src/docs/nav.test.ts` échoue si une page n'y est pas ou si une entrée n'a pas de fichier), sections en `##` / `###` (sommaire). Composants MDX disponibles sans import (`site/src/docs/mdx-components.tsx`) : `Callout` (`note`, `tip`, `warning`, `important`), `Steps` / `Step`, `Tabs` / `Tab`, `Screenshot`, `Kbd`, et pour la doc développeur `Endpoint` (méthode + chemin d'une route, sous le titre qui la nomme), `FileTree` (liste Markdown, nom entre backticks, `/` final pour un dossier) et `ArchitectureDiagram` ; le contenu Markdown d'un composant de bloc (`FileTree`, `Steps`, `Step`, `Tabs`, `Tab`, `Callout`) est séparé de ses balises par une ligne vide (sinon oxfmt le colle en un seul paragraphe), et une ligne d'un paragraphe ne commence pas par un composant en ligne comme `<Kbd>` (oxfmt y coupe le paragraphe) ; `title="…"` après le langage d'un bloc de code (`bash title="Terminal"`) lui donne un titre. Après `pnpm site:build`, `pnpm --dir site check-links` vérifie chaque lien interne et ancre (bloquant en CI). La recherche (Pagefind, index écrit par `postbuild`) n'existe qu'après un build : `site:preview` pour la tester.
- **Captures d'écran (`site/public/screenshots/<nom>-<dark|light>[-800].webp`) :** elles viennent d'une **instance démo** (jamais l'instance de tous les jours), lancée avec un home neutre pour qu'aucun chemin personnel n'apparaisse : `env -u HF_TOKEN HOME=/home/demo PATH="/home/demo/llama.cpp/build/bin:$PATH" pnpm start --host 0.0.0.0 --port 7861` (`/home/demo/models` → dossier des modèles, `/home/demo/llama.cpp/build/bin` en liens physiques : l'app fait un `realpath` du binaire). `pnpm --dir site demo-seed setup bench sweep start chat` remplit l'instance (vrais modèles sur les GPU : demander à l'utilisateur de les libérer), puis `pnpm --dir site screenshots [nom…]` capture en Chromium headless (sombre et clair) ; `demo-seed generate` puis `screenshots --live` pour Dashboard/System/Topology. Liste et mise en scène des écrans : `site/scripts/shots.ts`. Une modification d'UI qui change un écran capturé → refaire sa capture (et `pnpm --dir site og` si c'est le Dashboard : image Open Graph). La page d'accueil reproduit aussi en React des écrans de l'app, avec leurs vraies valeurs (Dashboard animé du hero, éditeur d'arguments, recommandation Tuning, etc. dans `site/src/landing/`) : les mettre à jour avec eux.
- **Synchroniser la doc avec le code (obligatoire) :** toute modification d'une fonctionnalité, de l'UI, d'une route API, d'un message WebSocket, d'un flag CLI, d'un réglage ou de l'architecture met à jour, **dans la même PR**, la ou les pages correspondantes de `site/content/` (la référence API est écrite à la main : elle dérive si on l'oublie). Correspondance code → pages : le tableau de « Keep the docs in sync » dans `site/content/developers/contributing/workflow.mdx` (seule copie), à lire avant de commiter un changement de code ; une ligne s'y ajoute quand un nouveau dossier de code a sa page.
