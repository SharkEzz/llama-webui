# llama-webui

L'app tourne sur Node (≥ 26.13, un seul processus) ; pnpm installe et lance les scripts. Elle est construite sur **Nitro v3** (h3 v2, srvx, crossws), dans un seul package `app/` : le client React (`app/src/`) et le serveur (`app/server/`, le `serverDir` de Nitro).

- Lancer : `pnpm dev` (`vite dev` dans `app/` : HMR de l'UI, serveur dans le worker de dev de Nitro, réévalué à chaque sauvegarde), `pnpm start` (build puis production) ; un fichier TS se lance par `node <fichier>` (syntaxe effaçable).
- Tests : Vitest (`pnpm test`, voir « Testing ») ; type check : `pnpm check` (le `typecheck` de chaque package, en parallèle) ; build : `pnpm build` (`vite build` dans `app/`).
- Install : `pnpm install` (voir « Installation (pnpm) ») ; un outil ponctuel : `pnpm dlx`.
- `.env` du dossier courant : en production, le lanceur (`app/bin/llama-webui.ts`) le charge par `loadDotEnv` (`app/server/lib/env.ts`, `parseEnv` de `node:util` : l'environnement l'emporte, sauf avec `--env-override` ou `LLAMA_WEBUI_ENV_OVERRIDE=1` dans l'environnement ou le `.env`) ; pas de `dotenv`, seul `.env` est lu (pas d'expansion de `$VAR`). **En dev**, `vite.config.ts` charge `.env` de la même façon, mais le plugin Vite de Nitro lit aussi `.env.local`, `.env.development` et `.env.development.local` (liste codée en dur dans `nitro/vite`, aucune option ; `app/server/dev.test.ts` le vérifie). `useEnvProxy()` (même fichier, appelé par `boot()`) fait passer `fetch` par `HTTP_PROXY`/`HTTPS_PROXY` s'il y en a un (`http.setGlobalProxyFromEnv`, loopback toujours en direct) : le `fetch` de Node les ignore sinon.
- Le dépôt ne tourne que sur Node : aucune API ni commande Bun.

## Installation (pnpm)

L'app, ses tests et son build tournent sur Node ; pnpm installe et lance les scripts.

- `pnpm install` à la racine installe tout le dépôt, `site/` compris : un seul `pnpm-lock.yaml` (à commiter avec tout changement de dépendance ; la CI fait `pnpm install --frozen-lockfile`). Workspaces (`packages/*`, `app`, `site`), catalogue et réglages pnpm dans `pnpm-workspace.yaml` (pas de champ `workspaces` dans `package.json`, pas de réglage dans `.npmrc`).
- Le `catalog:` de `pnpm-workspace.yaml` fixe les versions qui doivent bouger ensemble (`"react": "catalog:"`) : pour une de ses entrées, changer la version là, pas dans les `package.json`. D'autres dépendances partagées (`@types/react`, `lucide-react`, `shadcn`…) ont encore leur version dans chaque `package.json` : candidat de refactoring (backlog de `docs/superpowers/plans/2026-11-12-node-migration-notes.md`), à ne pas migrer au passage.
- `allowBuilds` (absent tant qu'aucun paquet n'en a besoin) liste les scripts d'installation autorisés ; un paquet non listé qui en a un fait échouer l'installation : décider `true` (une fonctionnalité en a besoin) ou `false`. Garder les entrées `minimumReleaseAgeExclude` que pnpm ajoute.
- `nitro` est épinglé en version exacte (une RC) dans `app/package.json` : une montée de version se fait seule, suites vertes.
- Biome ne détecte pas React depuis une version `catalog:` (même avec `javascript.resolver.experimentalPnpmCatalogs`) : le domaine `react` est activé explicitement pour `app/src/**` et `site/**` dans `biome.jsonc`.

## APIs

- HTTP : le serveur de Nitro (preset `node_server`, srvx) sert l'API (routes fichiers sous `app/server/routes/api/`), le WebSocket `/ws` (`app/server/routes/ws.ts`, `defineWebSocketHandler`, crossws par `features.websocket`) et l'UI : les assets hachés de `.output/public` (cache `immutable`, natif) et `index.html` pour tout autre chemin (renderer SPA de Nitro). Les middlewares de `app/server/middleware/` passent dans l'ordre : `00.ready.ts` (l'API et `/ws` attendent le démarrage ; 503 `llama-webui is starting`), `01.guard.ts` (garde de `lib/security.ts` sur `/api/*`, puis la table des 405 + `Allow` et le 404 `Unknown route` ; `/ws` sans upgrade → 426), `02.cache.ts` (`cache-control: no-cache` sur les pages HTML ; la réponse du renderer arrive en `HTTPResponse` de h3, pas en `Response`). `app/server/error.ts` (`defineErrorHandler`) répond par `appError(error)` (`lib/http.ts` : l'erreur d'origine si elle arrive enveloppée, jamais le `cause` d'un `HTTPError` de h3, qui porte ses détails). Le SSE du chat par `createEventStream` de h3 (`lib/chat/sse.ts`, `: ping` toutes les 15 s, `Connection: close`). Pas d'`express`, pas de Hono.
- SQLite goes through `Database` from `app/server/lib/db/sqlite.ts` (`node:sqlite`). Don't use `bun:sqlite` or `better-sqlite3`.
- `WebSocket` (client) et `fetch` sont globaux dans Node. Le `fetch` de Node abandonne après 300 s sans en-têtes de réponse, et après 300 s entre deux chunks, sans réglage possible : une requête à llama-server qui peut rester muette plus longtemps (flux du chat, requêtes du bench) passe par `llamaFetch` (`app/server/lib/llamaFetch.ts`, `node:http`, même signature et mêmes erreurs). Le `fetch` de Node négocie aussi HTTP/2 avec Hugging Face et son CDN, dont la fenêtre de contrôle de flux plafonne un flux à ~22 MiB/s : les téléchargements de modèles passent par `downloadFetch` (même fichier, `node:https` en HTTP/1.1, agents globaux donc proxy de l'environnement).

**Dans ce projet :** fichiers, processus, pauses et hachages passent par `node:*`, jamais `Bun.file`/`Bun.write`/`Bun.spawn`/`Bun.sleep`/`Bun.which`/`Bun.CryptoHasher`/`Bun.$`/`Bun.argv`/`import.meta.dir`. Côté serveur, `app/server/lib/proc.ts` : `spawnProc` (flux web typés par les options `stdout`/`stderr`, `pipe` par défaut, `exited`, lève une erreur tout de suite si le lancement échoue), `readText`, `fileExists` (faux pour un dossier), `fileRange`, `which` ; pauses `setTimeout` de `node:timers/promises` (une pause qui ne fait que borner une attente, `Promise.race([proc.exited, sleep(ms)])`, en `{ ref: false }` : elle ne retient pas le processus), sha256 `createHash` de `node:crypto`, `import.meta.dirname`. Les tests écrivent avec `writeFileDeep` (`app/server/lib/testing/write.ts`, crée les dossiers parents) et écoutent avec `listen(server)` (`app/server/lib/testing/listen.ts`, port libre → URL de base). SQLite : `Database` de `app/server/lib/db/sqlite.ts`, enveloppe de `DatabaseSync` (`node:sqlite`) avec la surface qu'utilisent les dépôts (`query()` en cache, `get()` → `null`, `run(sql, params)` pour une instruction et `exec(sql)` pour plusieurs (migrations, pragmas : `query()`/`run()` lèvent une erreur sur plusieurs instructions), `transaction(fn)`, booléens et `undefined` liés en 1/0/NULL, nombre de valeurs vérifié, clés étrangères coupées par défaut : `openDb()` les active). NVML : `node:ffi` (expérimental, sans flag) dans un processus enfant (`fork`, `app/server/lib/collectors/nvml/sampler.ts` : pas un worker thread, dont un appel bloqué dans le pilote retiendrait la sortie de Node), handles en `bigint` ; le sampler (`worker.ts`, imports avec extension `.ts`) tourne tel quel en dev, `.output/server/nvml-worker.mjs` en production ; `LLAMA_WEBUI_NVML_LIB` (comme `LLAMA_WEBUI_NVIDIA_SMI`) pour tester son absence (repli `nvidia-smi`). Les caches restent dans `lib/` (GGUF parsés, flags `--help`, matériel du bench, table SQLite `model_cache`) : `nitro/cache` dépend des modules virtuels de Nitro, que `lib/` et ses tests unitaires n'ont pas. L'API ne met rien en cache.

**Routes API (Nitro) :** une route = un fichier sous `app/server/routes/api/`, méthode en suffixe (`profiles/[id]/index.put.ts` → `PUT /api/profiles/:id`), `export default defineHandler(async (event) => …)` de `nitro`. Le code métier vit dans `app/server/lib/` (ignoré par le scan de Nitro : `ignore: ['lib/**']`) ; un handler y accède par `deps()` (`lib/context.ts`). Helpers de `app/server/lib/http.ts`, mêmes messages et même ordre qu'avant : `idParam(event, 'Profile')` (`:id` entier positif, sinon 404, avant le corps), `readBody(event, Schema)` (zod : `Invalid JSON`, `JSON object expected`, puis `Invalid data: …` + `issues`), `readJson(event, check)` (vérification impérative, `object`, `passthrough` : un handler qui cherche ou répond 409 avant de valider le corps le passe tel quel), `queryOf(event, 'clé', …)` (première valeur de chaque clé, ne refuse rien) ; réponses `reply<T>(data, status?)`, `noContent()`, `attachment(nom, corps)` ; erreurs `HttpError(status, message, code?)`, `notFound('Profile')`. Signal : `event.req.signal`. Une route qui lit un corps ou une query exporte `type Body` / `type Query`. Le routeur de Nitro est un radix : un chemin statique et un `[id]` voisins (`downloads/clear.post.ts`, `downloads/[id]/…`) ne se masquent pas. **Client typé :** `app/server/api.gen.ts` (généré, ne pas éditer) donne `ROUTES` (méthode + chemin, la table des 405) et le type `Api` : réponse = type de retour du handler (`reply<T>()`), corps et query = `Body`/`Query` du fichier. `app/build/apiTypes.ts` l'écrit depuis le scan de Nitro (`nitro.scannedHandlers`) au hook `build:before` (démarrage du dev et chaque build), puis en dev à chaque sauvegarde sous `routes/api/` (un fichier modifié tout de suite, un fichier ajouté ou supprimé une fois que Nitro a rescanné). Le web appelle l'API par `api('METHOD /api/chemin', { params, query, body, signal })` (`app/src/lib/api.ts` : corps typé, `ApiError` hors 2xx) ou `request(…)` pour la `Response` brute (SSE du chat) : jamais de `fetch('/api…')` ni de cast sur une réponse (une réponse brute comme `/api/server/props` se restreint par des guards, `app/src/lib/props.ts`) ; une erreur de type se corrige côté serveur (`reply<T>()`, type de retour d'un check, `Body`). Le web n'importe de `server/` que des types (`import type`) : son projet (`app/tsconfig.json`) vérifie donc aussi les sources du serveur que `api.gen.ts` atteint, d'où les types Node à côté du DOM (une API Node y compile : `app/server/build.test.ts` refuse un `node:*` dans le bundle client). Tests de routes : `routeApp([[méthode, chemin, handler], …])` (`lib/testing/routes.ts`, une app h3 qui répond aux erreurs comme l'app) et `using _ = provideDeps(deps)` (`lib/context.ts`) pour que `deps()` réponde des doublures.

## Testing

`pnpm test` lance toutes les suites : `test:unit` (`vitest run`), puis `pnpm --filter llamacpp-js test` (`node --test`).

```ts#index.test.ts
import { expect, test } from 'vitest';

test('hello world', () => {
  expect(1).toBe(1);
});
```

**Dans ce projet :** `vitest.config.ts` (racine) définit un projet Vitest par base de code (`server` = `app/server/**`, `app/build/**` et `scripts/`, `shared`, `web` = `app/src/` et `site` avec leur alias `@`), `environment: 'node'`, imports explicites (pas de globals), `oxc: { target: 'esnext' }` pour garder `using` natif. Le projet `server` a un **globalSetup** (`app/server/lib/testing/build.ts`) : un build de production (`app/.output`) par run, pour les suites qui le lancent ; `LLAMA_WEBUI_TEST_BUILD=0` réutilise le build existant (un fichier lancé seul après un `pnpm build`). Un fichier lancé seul : `pnpm exec vitest run <chemin>`, un nom : `-t '<regex>'`. Vitest échoue sur un `.resolves`/`.rejects` non attendu : toujours `await expect(…).rejects`. `vi.fn()` pour un callback enregistré (pas de `mock.module`, les dépendances sont injectées). `launch({ dataDir, port?, env? })` (`lib/testing/launch.ts`) lance le build comme un utilisateur (sans `CI`, `TEST` ni `NODE_ENV`), attend `/api/health`, et `await using` l'arrête (SIGTERM) ; `seedDataDir()`, `startLlama()`, `bootId()`, `isAlive()` dans `lib/testing/seed.ts`. **Suite de contrat** (`app/server/lib/contract/`) : chaque route rejouée en HTTP réel contre le build de production (`launch()`, réglages de test `LLAMA_WEBUI_TEST_MONITOR=stub` et `LLAMA_WEBUI_TEST_OFFLINE=1` lus par le runtime), comparée à `golden.json` (hachages des assets remplacés par `<hash>`) ; une route ajoutée va dans `ROUTES` de `cases.ts` (comparé au `ROUTES` d'`api.gen.ts`) ; un changement de comportement voulu → `UPDATE_GOLDEN=1 pnpm exec vitest run app/server/lib/contract/contract.test.ts` puis relire le diff du golden. `app/server/build.test.ts` vérifie `.output` (client découpé, three.js seulement dans les chunks de Topology, aucun `node:*` côté client, serveur sans autre import que `node:*`, licences, sampler NVML à côté du module qui le nomme et qui démarre depuis le bundle) ; `app/server/lifecycle.test.ts` l'arrêt (SIGTERM avec l'UI ouverte et une réponse en cours : moins de 2 s, 1001, « stopped »), le port pris (code 1, sans toucher aux données d'une instance sur le même dossier), un asset manquant (404) et les en-têtes de cache ; `app/server/dev.test.ts` la boucle de dev, sur une copie de `app/` sous `.cache/` (le dépôt et un `pnpm dev` en cours ne sont pas touchés) : une route sauvegardée garde llama-server, du code métier sauvegardé reconstruit le runtime, SIGINT et double SIGINT, `.env.local`, et `.env` qui l'emporte sur lui ; `app/server/api.gen.test.ts` le générateur (table = scan de Nitro, ajout et suppression en dev).

TypeScript 7 (`tsc` natif), version dans le `catalog:`.

## Format et lint (Biome)

Biome (devDependency épinglée, config dans `biome.jsonc`) gère le format, le lint et le tri des imports. Style : 2 espaces, guillemets simples (doubles en JSX), 120 colonnes, point-virgules partout (`app/`, `packages/`, `scripts/`). Règles : preset `recommended` et domaines `tailwind`, `test`, `project` (graphe de modules) et `types` (inférence de types) en `recommended`, plus `react` pour `app/src/**` et `site/**`. `**/src/components/ui` (shadcn généré, app et site) est ignoré par Biome (ni format, ni lint, ni tri des imports) pour rester comparable aux mises à jour shadcn ; `app/server/api.gen.ts` et `golden.json` (générés) aussi. Ces exclusions s'écrivent `!` dans `files.includes` (le fichier reste indexé pour les domaines `project` et `types`), pas `!!` (réservé aux sorties de build).

- `pnpm lint` : vérifie format + lint + imports (lecture seule) ; `pnpm lint:fix` applique les corrections sûres.
- **Avant de clore un jalon / milestone / lot de travail** (et avant de commiter ou d'ouvrir une PR), tout doit être vert : `pnpm lint`, `pnpm check`, `pnpm test`. Zéro erreur et zéro warning Biome.
- Ne pas désactiver une règle ni la baisser en `warn` pour faire passer le lint. Si une règle est un faux positif, `// biome-ignore lint/<groupe>/<règle>: <raison>` ciblé et motivé (voir `useExhaustiveDependencies` : les dépendances « déclencheur » sont volontaires). Pour lire la dernière valeur dans un effet sans le relancer, préférer `useEffectEvent` (React 19) à un ignore ; pour réinitialiser un état au changement d'identité, un `key` sur le composant plutôt qu'un effet. Une correction `--unsafe` d'imports inutilisés emporte le commentaire rattaché au premier : relire le haut du fichier.

## Langue

L'UI, les messages du serveur (erreurs, validations zod, logs, `--help`), les commentaires, les noms de tests, les messages de commit et les PR sont **en anglais**. Nombres, dates et unités passent par `app/src/lib/format.ts` (`LOCALE = 'en-US'` de `packages/webui-shared/src/format.ts`, `num`, `fmt`, `plural`, `formatBytes` en KiB/MiB/GiB…), côté serveur par `fmtInt` (`packages/webui-shared/src/format.ts`) : pas de locale codée en dur. ## Packages (`packages/`)

`packages/webui-shared/` (`@llama-webui/shared`) : types, schémas zod et logique pure partagés par le serveur et le web. `packages/llamacpp-js/` : tout ce qui parle à llama.cpp (API HTTP de `llama-server`, métriques, `--help`, sortie de `llama-bench`, `/proc`), destiné à être publié sur npm. Règles de `llamacpp-js` (vérifiées par `tests/package.test.ts`, son projet TS et ses tests, sous Node en CI) :

- **Cible :** Node ≥ 24, donc uniquement des API web et `node:*` dans `src/` (`fetch`, `node:child_process`, `node:fs/promises`) ; son projet TS n'a que les types Node. Ses tests sont dans `tests/` (hors de `src/`) et utilisent `node:test` + `node:assert/strict`, sous Node (`pnpm --filter llamacpp-js test` = `node --test 'tests/*.test.ts'`, en CI sous Node 26 et, dans un job à part sans installation, sous Node 24, la version minimale). Les contrôles de bundling de `tests/package.test.ts` passent par Rolldown (devDependency) et passent `{ skip }` sans installation.
- Aucune dépendance ni import de `@llama-webui/*` ; ce qui est un choix de llama-webui (superviseur, `buildCommand`, formulation des erreurs pour l'utilisateur, caches) reste dans l'app.
- TS exécutable tel quel par Node : imports relatifs avec extension `.ts`, `import type`, syntaxe effaçable (`erasableSyntaxOnly` : pas d'`enum`, de `namespace` ni de propriétés de paramètre).
- Tree-shakeable : ESM, `"sideEffects": false`, aucun état ni effet au chargement d'un module, un export par module dans `package.json` ; seul `llamacpp-js/node` utilise des API Node, le reste tourne aussi dans le navigateur.
- Erreurs : classes `Llama*Error` avec un `name` fixe ; l'app les traduit en messages.

## Frontend

Vite : `app/vite.config.ts` construit le client (`app/src/`, React, Tailwind par `@tailwindcss/vite`, alias `@`) et, par le plugin `nitro()`, le serveur (preset `node_server`, `serverDir: './server'`, `features.websocket`, `errorHandler`).

**Dans ce projet :** un seul process Node sur le port 7860 sert l'API, le WebSocket et l'UI (`server.host` depuis `LLAMA_WEBUI_HOST`, `127.0.0.1` par défaut, `server.port` depuis `LLAMA_WEBUI_PORT`, `strictPort`). `pnpm dev` = `vite dev` dans `app/` : HMR de l'UI, serveur dans le worker de dev de Nitro (un worker thread). `app/server/plugins/runtime.ts` lance le runtime par `start()` (`lib/context.ts`) ; `boot()` (`lib/boot.ts`) construit tout sur un `AsyncDisposableStack` (`await using`) : chaque partie y enregistre ce qui la défait dès sa création, la pile défait dans l'ordre inverse (intervalle du watcher externe, `chatRuns`, `benchRunner`, `downloads`, hub (1001), placement, monitor, `supervisor.stop()`, base) ; un échec avant la fin défait ce qui était construit. Les options viennent de l'environnement (`LLAMA_WEBUI_HOST`/`PORT`/`DATA_DIR`) : le worker n'a pas d'argv. Arrêt : en dev, Nitro envoie au worker un message `shutdown`, sans délai (3.0.261103-rc, nitrojs/nitro#5133) : le worker attend que chaque connexion finisse avant d'appeler le hook `close`, et le socket amont du `/ws` d'une page ouverte ne finit jamais seul (« Dev worker did not shut down in time » au bout de 5 s, runtime jamais défait) ; le plugin écoute donc ce message (`parentPort`) et appelle `stop()` aussitôt (à la montée de version qui corrige #5133, retirer cette écoute si `dev.test.ts` reste vert sans elle), le hub coupe (`terminate()`) au bout de 500 ms un client qui ne répond pas à son 1001 (Ctrl+C : Nitro ferme Vite puis sort en 130) ; `stop()` ne défait le runtime qu'une fois, un appel suivant attend le même ; en production, le hook `shutdown` (appelé dès que le serveur commence à fermer, pendant que les connexions se vident) défait le runtime **d'abord** (sockets 1001, réponses « stopped », llama-server arrêté), puis srvx ferme le serveur HTTP sans attendre la fin de son délai de grâce (5 s) ; un second signal force la fermeture de srvx. Nitro 3.0.261103-rc n'appelle pas encore `shutdown` (nitrojs/nitro#5099, non publié) : le plugin le déclare (augmentation de `nitro/types`) et l'émet depuis son propre handler SIGINT/SIGTERM, enregistré avant celui de srvx (`waitUntil`, 5 s au plus) ; à la montée de version, retirer ce handler et la déclaration. `process.on('exit')` tue llama-server en dernier recours. Les requêtes attendent le démarrage dans `middleware/00.ready.ts` ; un démarrage raté sort en code 1 en production. Version (`app/server/lib/version.ts`, barre d'état, `/api/health`) : `dev` en développement, `git describe --tags --always --dirty` au build (`define`), la version du `package.json` sans git.

`pnpm build` = `vite build` dans `app/` → `app/.output/` : `public/assets/*` (client découpé par page, hachés), `server/index.mjs` et ses chunks (autonome : n'importe que `node:*`, `index.html` embarqué pour le renderer), `server/nvml-worker.mjs` et `llama-webui.mjs` (construits par Rolldown au hook `compiled`), `server/THIRD-PARTY-LICENSES.md` (`app/build/licenses.ts` : `build.license` de Vite n'atteint pas la sortie de Nitro). `app/bin/llama-webui.ts` est le lanceur (`#!/usr/bin/env node`) : `.env`, `cliOptionsOrExit()` (`--help`, `--host`, `--port`, `--data-dir`, `--env-override`), puis `NITRO_HOST`/`NITRO_PORT` et `LLAMA_WEBUI_*` reçoivent les options résolues (un `PORT` ou `HOST` de l'environnement ne l'emporte donc jamais sur `--port`/`--host`), puis `import('./server/index.mjs')`. Le lanceur vérifie l'adresse **avant** d'importer le serveur (le runtime démarre en même temps que l'écoute et toucherait sinon le dossier de données d'une instance déjà lancée) : un port pris sort en code 1 avec un message qui le nomme. `pnpm start` = build puis `node app/.output/llama-webui.mjs`. `node scripts/smoke.ts` vérifie le build (CI). **Distribution :** le paquet racine est le paquet publié (`bin` `llama-webui` → `app/.output/llama-webui.mjs`, `files` `app/.output` seulement, `os` linux ; `pnpm pack` refuse sans build, `scripts/prepack.ts`) ; il n'a **aucune dépendance** : le build est autonome (`scripts/package.test.ts`). `.output` est ignoré par le `.gitignore` racine et non par un `app/.gitignore` : npm appliquerait ce dernier au tarball malgré `files`. `node scripts/smoke.ts --tarball [fichier.tgz]` : `pnpm pack`, `npm install` dans un préfixe vide, puis les vérifications du smoke par `node_modules/.bin/llama-webui` (CI). `release.yml` (tag `v*`) : `node scripts/release.ts --check`, build, `pnpm pack`, smoke du tarball, `SHA256SUMS`, `gh release create` ; la version de tous les `package.json` s'aligne par `pnpm release <version>` (PR, `master` est protégée) ; `scripts/release.test.ts` échoue s'ils divergent.

**Rechargement (dev) :** le runtime vit sur `globalThis` (`lib/context.ts`) et survit au worker qui se réévalue. Une sauvegarde d'un **fichier de route** garde le runtime et llama-server (même `bootId`). Une sauvegarde de **code métier** (un module que `boot()` atteint, donc `lib/context.ts` réévalué) défait l'ancien runtime puis en construit un nouveau : llama-server arrêté, un sweep en cours passe « interrupted » (bouton Resume), une réponse du chat « stopped », un téléchargement reprend son `.part`, nouveau `bootId`. Une sauvegarde sous `app/src/` reste du HMR. Deux sauvegardes du même fichier à quelques ms d'intervalle : le watcher de Vite peut ignorer la seconde.

## Site web et documentation (`site/`)

Le site public (page d'accueil, doc utilisateur, doc développeur) vit dans `site/` et est publié sur GitHub Pages (`https://sharkezz.github.io/llama-webui/`, base `/llama-webui/`). Plan et jalons : `docs/superpowers/plans/2026-11-08-website.md`.

- **Pile :** `site/` utilise Vite + React Router (mode framework, `ssr: false` + prérendu statique) + Tailwind 4 + shadcn + MDX. C'est un projet du workspace pnpm (installé par le `pnpm install` racine, sans lockfile propre), ses scripts lancés par pnpm et exécutés par Node (`node scripts/<nom>.ts`, mêmes règles que `app/server/` : `node:*`, imports avec extension `.ts`), ses tests dans le projet Vitest `site`. Il n'importe aucun code de `app/` : les composants repris (tokens, verre, jauges…) sont copiés et adaptés.
- Mêmes règles qualité que l'app (Biome sans warning, type check, tests verts) ; le contenu est en anglais, URLs avec slash final. Les scripts racine couvrent le site : `pnpm check` lance aussi le `typecheck` de `site` (`react-router typegen` puis `tsc`), `pnpm test` inclut `site/` (projet Vitest `site`), et la CI (`.github/workflows/ci.yml`) construit le site. Biome ignore les `.mdx` (non supportés) et `site/src/components/ui/**` (shadcn).
- **Commandes :** après le `pnpm install` racine, depuis la racine `pnpm site:dev` (Vite + HMR sur `0.0.0.0:5173`, ouvrir `http://192.168.0.20:5173/llama-webui/`), `pnpm site:build` (prérendu + `scripts/postbuild.ts` → `site/dist/`) et `pnpm site:preview` (`scripts/serve.ts`, `node:http`, sert `dist/` comme GitHub Pages sur le port 4173, `--port` pour un autre : sous `/llama-webui/`, redirection vers le slash final, `404.html`).
- **Pages :** chaque `.mdx` de `site/content/{docs,developers}/` devient une route prérendue (`src/routes.ts`, `src/lib/content.ts`). Les liens internes s'écrivent sans basename (`/docs/…/`) : React Router ajoute `/llama-webui`. Le prérendu écrit sous `build/client/llama-webui/` ; `postbuild` remonte ces pages à la racine de `dist/` et transforme le fallback SPA en `404.html` (route `*`). Le déploiement (`.github/workflows/site-deploy.yml`) part à chaque push sur `master` qui touche `site/` (ou à la main, `workflow_dispatch`) : une PR fusionnée publie aussitôt sa doc.
- **Écrire une page :** front matter YAML `title` + `description` obligatoires (le build échoue sinon ; le titre `h1` vient de là, ne pas en écrire dans le corps), entrée dans `site/content/nav.ts` (`site/src/docs/nav.test.ts` échoue si une page n'y est pas ou si une entrée n'a pas de fichier), sections en `##` / `###` (sommaire). Composants MDX disponibles sans import (`site/src/docs/mdx-components.tsx`) : `Callout` (`note`, `tip`, `warning`, `important`), `Steps` / `Step`, `Tabs` / `Tab`, `Screenshot`, `Kbd`, et pour la doc développeur `Endpoint` (méthode + chemin d'une route, sous le titre qui la nomme), `FileTree` (liste Markdown, nom entre backticks, `/` final pour un dossier) et `ArchitectureDiagram` ; `title="…"` après le langage d'un bloc de code (`bash title="Terminal"`) lui donne un titre. Après `pnpm site:build`, `pnpm --dir site check-links` vérifie chaque lien interne et ancre (bloquant en CI). La recherche (Pagefind, index écrit par `postbuild`) n'existe qu'après un build : `site:preview` pour la tester.
- **Captures d'écran (`site/public/screenshots/<nom>-<dark|light>[-800].webp`) :** elles viennent d'une **instance démo** (jamais l'instance de tous les jours), lancée avec un home neutre pour qu'aucun chemin personnel n'apparaisse : `env -u HF_TOKEN HOME=/home/demo PATH="/home/demo/llama.cpp/build/bin:$PATH" pnpm start --host 0.0.0.0 --port 7861` (`/home/demo/models` → dossier des modèles, `/home/demo/llama.cpp/build/bin` en liens physiques : l'app fait un `realpath` du binaire). `pnpm --dir site demo-seed setup bench sweep start chat` remplit l'instance (vrais modèles sur les GPU : demander à l'utilisateur de les libérer), puis `pnpm --dir site screenshots [nom…]` capture en Chromium headless (sombre et clair) ; `demo-seed generate` puis `screenshots --live` pour Dashboard/System/Topology. Liste et mise en scène des écrans : `site/scripts/shots.ts`. Une modification d'UI qui change un écran capturé → refaire sa capture (et `pnpm --dir site og` si c'est le Dashboard : image Open Graph). La page d'accueil reproduit aussi en React des écrans de l'app, avec leurs vraies valeurs (Dashboard animé du hero, éditeur d'arguments, recommandation Tuning, etc. dans `site/src/landing/`) : les mettre à jour avec eux.
- **Synchroniser la doc avec le code (obligatoire) :** toute modification d'une fonctionnalité, de l'UI, d'une route API, d'un message WebSocket, d'un flag CLI, d'un réglage ou de l'architecture met à jour, **dans la même PR**, la ou les pages correspondantes de `site/content/` (la référence API est écrite à la main : elle dérive si on l'oublie). Correspondance code → pages : le tableau de « Keep the docs in sync » dans `site/content/developers/contributing/workflow.mdx` (seule copie), à lire avant de commiter un changement de code ; une ligne s'y ajoute quand un nouveau dossier de code a sa page.
