# Learning more about Effect

This repository uses the Effect Typescript library: the server (`app/server/`) and the API definition it shares with the web (`packages/webui-shared/src/api/`) are written with it.

Before writing any Effect code, first read `app/node_modules/effect/CLAUDE.md` **completely**.

It is the installed version: prefer it over web search results or any other copy of Effect, and never edit it.

# llama-webui

L'app tourne sur Node (≥ 26.13, un seul processus) ; pnpm installe et lance les scripts. Un seul package `app/` : le client React (`app/src/`) et le serveur Effect (`app/server/`, point d'entrée `app/server/main.ts`), qui partagent la définition de l'API (`packages/webui-shared/src/api/`).

- Lancer : `pnpm dev` (`vite dev` dans `app/` : HMR de l'UI, serveur depuis les sources sous `node --watch`, relancé à chaque sauvegarde d'un fichier qu'il importe), `pnpm start` (build puis production) ; un fichier TS se lance par `node <fichier>` (syntaxe effaçable).
- Tests : Vitest (`pnpm test`, voir « Testing ») ; type check : `pnpm check` (le `typecheck` de chaque package, en parallèle) ; build : `pnpm build` (`vite build` puis `node build/server.ts` dans `app/`).
- Install : `pnpm install` (voir « Installation (pnpm) ») ; un outil ponctuel : `pnpm dlx`.
- `.env` du dossier courant : `main.ts` l'applique par `loadDotEnv` (`app/server/config/DotEnv.ts`, `parseEnv` de `node:util`) avant de lire la configuration : l'environnement l'emporte, sauf avec `--env-override` ou `LLAMA_WEBUI_ENV_OVERRIDE=1|true` dans l'environnement ou le `.env`. Pas de `dotenv`, seul `.env` est lu (pas de `.env.local`, pas d'expansion de `$VAR`). En dev, `vite.config.ts` l'applique de la même façon et le serveur lancé par Vite hérite du résultat.
- Le dépôt ne tourne que sur Node : aucune API ni commande Bun.

## Installation (pnpm)

L'app, ses tests et son build tournent sur Node ; pnpm installe et lance les scripts.

- `pnpm install` à la racine installe tout le dépôt, `site/` compris : un seul `pnpm-lock.yaml` (à commiter avec tout changement de dépendance ; la CI fait `pnpm install --frozen-lockfile`). Workspaces (`packages/*`, `app`, `site`), catalogue et réglages pnpm dans `pnpm-workspace.yaml` (pas de champ `workspaces` dans `package.json`, pas de réglage dans `.npmrc`).
- Le `catalog:` de `pnpm-workspace.yaml` fixe les versions qui doivent bouger ensemble (`"react": "catalog:"`) : pour une de ses entrées, changer la version là, pas dans les `package.json`. Toute dépendance que plusieurs packages du workspace nomment y est (`@types/react`, `shadcn`, `rolldown`…) : une dépendance qu'un deuxième package ajoute passe dans le catalogue.
- `allowBuilds` (absent tant qu'aucun paquet n'en a besoin) liste les scripts d'installation autorisés ; un paquet non listé qui en a un fait échouer l'installation : décider `true` (une fonctionnalité en a besoin) ou `false`. Garder les entrées `minimumReleaseAgeExclude` que pnpm ajoute.
- `effect` et les `@effect/*` (`platform-node`, `sql-sqlite-node`, `vitest`) sont épinglés à la même version exacte dans le `catalog:` : une montée de version les change tous ensemble et se fait seule, suites vertes (presque tout Effect hors du cœur est `@stability unstable`). La documentation à lire avant d'écrire du code Effect (`CLAUDE.md`, `ai-docs/`, `src/`, voir plus haut) vient avec le paquet installé : elle suit la version sans rien à mettre à jour. Le script `prepare` racine, à chaque `pnpm install`, installe le language service d'Effect dans le `tsc` de `node_modules` (`effect-tsgo patch`).

## Serveur (Effect)

Les règles détaillées et leurs exemples sont dans `conventions.md` (voir plus haut) ; cette section en donne la carte.

- **Un domaine** : ses schémas dans `packages/webui-shared/src/<domaine>.ts`, son groupe d'API (endpoints, erreurs `Schema.TaggedError` avec leur statut `httpApiStatus`) dans `packages/webui-shared/src/api/<Domaine>Api.ts`, ajouté à `Api` (`api/Api.ts`) ; son service dans `app/server/<domaine>/<Nom>.ts` (un `Context.Service`, ses layers en statiques), ses handlers dans `app/server/<domaine>/http.ts`, ajoutés à `ApiRoutes` (`app/server/http/HttpLive.ts`), son layer à `Services` (`app/server/App.ts`) et à `ServicesTest` (`app/server/testing/services.ts`).
- **HTTP** (`app/server/http/HttpLive.ts`, `NodeHttpServer` sur `node:http`) : l'API (`HttpApiBuilder.layer(Api)`), la doc OpenAPI 3.1 (`http/OpenApiDocs.ts` : `GET /api/openapi.json` et l'UI Scalar hors ligne `GET /api/docs`, fusionnées dans `ApiRoutes`), le WebSocket `/ws` (`app/server/ws/WsHub.ts` ; sans upgrade : 426) et l'UI (`http/Static.ts` : `/assets/*` en `immutable`, sa copie `.br` ou `.gz` à un client dont l'`Accept-Encoding` l'accepte, sauf pour un `Range`, un asset manquant en 404, `index.html` en `no-cache` pour tout autre chemin ; le JSON de 1 KiB ou plus part en gzip, `compressJson` de `HttpLive.ts`, jamais un flux SSE). Autour des routes de l'API et de `/ws` (`Guarded` de `http/Guard.ts`, fourni à `ApiRoutes` et à `WsHub.route` : un middleware des routes, pas du serveur, donc appliqué quelle que soit l'écriture du chemin que le routeur accepte, `/API/…`, `//api/…`, `/%61pi/…`, `/ws;x` ; une route ajoutée hors de `Api` le reçoit par `Layer.provide(Guarded)`), la garde (Host localhost ou IP, Origin de la page, corps d'écriture en `application/json` ; refus `RequestRefused`), puis le 308 d'un slash final (`http/TrailingSlash.ts`) ; un défaut d'un handler est loggé et répond 500 sans son message. Une erreur répond `{ _tag, message }` (et `issues` pour une validation) ; le web la reconnaît à son `_tag`, jamais à son texte. Tout autre chemin sous `/api`, ou une méthode qu'un chemin n'a pas (pas de 405), est un 404 `RouteNotFound` `Unknown route`.
- **Requêtes** : chaque endpoint déclare `params` (un id est `IdParam`), `payload` et `query` en schémas ; un handler ne lit jamais un corps lui-même. Les corps se décodent strictement (une clé inconnue est une erreur) ; un corps, une query ou un en-tête invalide est un 400 `RequestInvalid` `Invalid data: <premier problème> (<chemin>)` avec `issues`, un paramètre de chemin invalide un 404 `RouteNotFound` (`http/RequestErrors.ts`). Un fichier à télécharger : `attachment(schema)` (`http/attachment.ts`) ; un flux SSE : `HttpApiSchema.StreamSse` et `sseResponse` (`http/Sse.ts`, `: ping` toutes les 15 s), handler `handle`, jamais `handleRaw`.
- **Démarrage** (`main.ts`) : `.env`, la ligne de commande (`config/Cli.ts` : `--help`, `--version`, `--host`, `--port`, `--data-dir`, `--env-override` ; une option l'emporte sur sa variable `LLAMA_WEBUI_HOST`/`PORT`/`DATA_DIR`, `config/AppConfig.ts`), puis l'adresse vérifiée (`http/Address.ts` : un port pris sort en code 1, `llama-webui: cannot listen on <hôte>:<port>: the port is already in use`, avant de toucher au dossier de données), puis `Layer.launch(App)` : les services sont construits par étages (`App.ts`, la base en premier), et le port n'est ouvert qu'ensuite. Il n'y a donc pas de fenêtre « starting » : une requête trouve toujours un serveur prêt, un démarrage raté sort en code 1.
- **Arrêt** (`runtime/runApp.ts`, `runtime/Shutdown.ts`) : SIGINT ou SIGTERM lance d'abord les étapes d'arrêt (`Shutdown.before` : une réponse du chat enregistrée « stopped », un run ou un sweep « interrupted », le dernier message du hub), puis le serveur HTTP ferme (sockets en 1001, 500 ms de grâce), puis les services se défont dans l'ordre inverse de leur construction (le watcher externe, le bench, le monitor et les réponses du chat, la file de téléchargements avec son `.part`, llama-server arrêté par le superviseur, la base en dernier), puis `Otlp.layer` vide les derniers spans et métriques (1 s max) si OTLP est activé ; sortie 0. Un second signal pendant l'arrêt sort tout de suite. Un échec sort en code 1 avec `llama-webui: <message>` sur stderr.
- **Requêtes sortantes** : jamais `fetch`. Toute requête à un llama-server passe par `LlamaHttp` (`app/server/llama/LlamaHttp.ts` : `node:http` sans limite de temps sur les en-têtes ni le corps, une socket par requête), toute requête à Hugging Face (API du Hub et téléchargements) par `HfHttp` (`app/server/hf/HfHttp.ts` : HTTP/1.1 sur ses propres agents, le proxy de l'environnement `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` de `app/server/http/proxyEnv.ts` posé sur eux) ; l'export OTLP (`app/server/runtime/Otlp.ts`) réutilise le même `proxyEnv`. Chaque appelant borne son attente et suit lui-même les redirections qu'il accepte.
- **Programmes** : par `effect/process` (`ChildProcess.make`, `ChildProcessSpawner`), jamais `node:child_process`. Un programme qui dure (llama-server, llama-bench, `nvidia-smi`, l'échantillonneur NVML) passe par `followProgram` (`app/server/process/followed.ts`). L'échantillonneur NVML est un programme Effect (`app/server/collectors/nvml/worker.ts`, `node:ffi`) à qui le serveur parle en NDJSON sur stdin et stdout (schémas de `protocol.ts`, les mêmes des deux côtés) ; il sort à la fin de son stdin, tourne tel quel en dev et en `.output/server/nvml-worker.mjs` en production. Le bench et les sweeps passent par `BenchRunner` (`app/server/bench/` : la réservation, le gate qui arrête puis relance llama-server, llama-bench et le llama-server d'essai, la boucle d'un sweep).
- **Fichiers et plateforme** : `FileSystem` et `Path` d'Effect ; un chemin écrit par une personne passe par `expandHome` (`config/Home.ts`, `~` et `~/…`). Les règles de la plateforme du language service refusent `node:*`, `fetch`, les timers et `JSON` dans le serveur : quatre imports `node:*` sont permis, chacun avec sa directive et sa raison (`conventions.md` › Diagnostics).
- **SQLite** : `SqlClient` de `@effect/sql-sqlite-node` (sur `node:sqlite`), ouvert par `app/server/db/Db.ts`, migrations dans `app/server/db/migrations.ts`. `better-sqlite3`, `bun:*` et, hors de `db/` et des tests, `node:sqlite` : `no-restricted-imports` de `app/server/oxlint.config.ts`.
- **Caches** : dans les services (les GGUF lus par `GgufReader`, les flags de `--help` par `Flags`, le matériel du bench, la table `model_cache`) ; l'API ne met rien en cache.
- **Réglages de test et télémétrie**, lus par le runtime : `LLAMA_WEBUI_TEST_MONITOR=stub` (valeur exacte, `Monitor.layer` : ni collecteurs, ni snapshot, historique vide), `LLAMA_WEBUI_TEST_OFFLINE=1` (valeur exacte, `HfHttp.layer` et `Otlp.layer` : toute requête échoue en `fetch failed`, d'où le 502 `HfUnreachable` des routes du Hub), `LLAMA_WEBUI_NVML_LIB` et `LLAMA_WEBUI_NVIDIA_SMI` (`Collectors.layer`, pour tester leur absence). En production comme en dev, `OTEL_EXPORTER_OTLP_ENDPOINT` (et les autres variables `OTEL_*` standard, `app/server/runtime/Otlp.ts`) exporte spans et métriques en OTLP/HTTP (désactivé par défaut ; pas de logs) ; en dev, `LLAMA_WEBUI_DEV=1` (posé par `vite dev`) envoie aussi les spans et métriques aux Effect DevTools quand elles écoutent (`LLAMA_WEBUI_DEVTOOLS_URL`, `ws://localhost:34437` par défaut).
- **Client typé** : le web importe `Api` de `@llama-webui/shared` et l'appelle par `call((api) => api.<groupe>.<endpoint>({ params, payload, query }))` (`app/src/lib/api.ts` : la réponse décodée, ou l'erreur taguée de l'endpoint, `ApiUnreachable` sans réponse ; un corps que le client refuse d'envoyer donne le même `RequestInvalid` que le serveur) et un flux par `callStream(…, onEvent, { signal })`. Jamais de `fetch('/api…')` ni de cast sur une réponse : une réponse brute comme `/api/server/props` se restreint par des guards (`app/src/lib/props.ts`). Une erreur se distingue par son `_tag` (`errorTag`), une erreur de type se corrige dans le schéma partagé. `app/server/`, et `node:*` ou `llamacpp-js/node` hors des tests, depuis le web : `no-restricted-imports` de `app/src/oxlint.config.ts` (`app/server/build.test.ts` refuse en plus un `node:*` dans le bundle client).

## Testing

`pnpm test` lance toutes les suites : `test:unit` (`vitest run`), puis `pnpm --filter llamacpp-js test` (`node --test`).

```ts#index.test.ts
import { expect, test } from 'vitest';

test('hello world', () => {
  expect(1).toBe(1);
});
```

**Dans ce projet :** `vitest.config.ts` (racine) définit un projet Vitest par base de code (`server` = `app/server/**`, `app/build/**` et `scripts/`, `shared`, `web` = `app/src/` et `site` avec leur alias `@`), `environment: 'node'`, imports explicites (pas de globals), `oxc: { target: 'esnext' }` pour garder `using` natif. Le projet `server` a un **globalSetup** (`app/server/testing/build.ts`) : un build de production (`app/.output`) par run, pour les suites qui le lancent ; `LLAMA_WEBUI_TEST_BUILD=0` réutilise le build existant (un fichier lancé seul après un `pnpm build`). Un fichier lancé seul : `pnpm exec vitest run <chemin>`, un nom : `-t '<regex>'`. Le rapport cache ce qu'un test écrit sur la console (`onConsoleLog`) : `VITEST_ENABLE_CONSOLE_LOG=1` l'affiche ; chaque fichier est listé avec son tas (`logHeapUsage`). `pnpm exec vitest run --changed` (ou le mode watch) ne relance que les fichiers qui importent un fichier modifié : les suites boîte noire et `dev.test.ts` lancent le build ou `vite dev` sans importer le serveur, il ne les choisit donc pas pour un changement du serveur ; boucle rapide pendant le travail, jamais à la place de `pnpm test` avant un commit. En CI, `test:unit` tourne en deux moitiés parallèles (`--shard=1/2`, `2/2`, chacune son build), à côté des jobs lint et types, build et paquet, site. Une promesse d'un test est attendue (`await expect(…).rejects`) : le lint l'impose (`vitest/valid-expect` pour un `.resolves`/`.rejects` non attendu, `typescript/no-floating-promises` pour toute autre promesse ni attendue, ni rendue, ni traitée, ni jetée par `void`). Un fichier de test ne laisse rien en attente : `detectAsyncLeaks` signale une promesse jamais réglée, un timer ou un handle, et le reporter `failOnAsyncLeaks` (`vitest.config.ts`) fait échouer le run (Vitest seul l'affiche et sort en 0) ; une fuite peut n'apparaître que quand son test tourne seul (`-t`). Donc : le corps d'une réponse `fetch` est lu ou annulé (`await res.body?.cancel()`), une attente bornée passe par `orAfter(promesse, ms, valeur)` (`app/server/testing/orAfter.ts`), jamais par un `Promise.race([promesse, sleep(ms)])` nu, et une assertion relancée par `vi.waitFor`, jamais `expect.poll` (un poll qui réussit laisse en attente la promesse de délai de Vitest).

- **Code Effect** : `layer(L)('Nom', (it) => { it.effect(…) })` de `@effect/vitest` (le test reste un effet, pas d'`Effect.runPromise` ; les finalizers du layer tournent après le bloc). `it.effect` tourne sur le `TestClock` ; un test sur le temps réel (processus, sockets, plannings) prend `layer(L, { excludeTestServices: true })` ou `it.live`. Les services d'un test viennent de `ServicesTest` (`app/server/testing/services.ts`, base en mémoire, monitor stub, délais raccourcis par les `layerWith` de chaque service) ; les dépendances sont des layers, pas de `mock.module`. Un faux llama-server, `freePort`, `httpStub`, `chatStub` : `app/server/testing/llama.ts` (faux programmes de `testdata/fake/`) ; un test qui lance un processus vérifie qu'il est mort à la fin ; un port de test n'est jamais 7860, 7861 ni 8080.
- **Suites boîte noire**, en Node simple contre le build : `launch({ dataDir, port?, env? })` (`app/server/testing/launch.ts`) lance le build comme un utilisateur (sans `CI`, `TEST`, `NODE_ENV` ni `LLAMA_WEBUI_DEV`, le réglage `port` de la base sur un port libre), attend `/api/health`, et `await using` l'arrête (SIGTERM). `app/server/lifecycle.test.ts` : port pris (code 1, sans toucher aux données d'une instance sur le même dossier), `.env` et `--env-override`, SIGTERM avec l'UI ouverte, llama-server lancé, une réponse en cours, un benchmark, un téléchargement (moins de 2 s, 1001, « stopped », « interrupted », `.part` repris), un dossier de données du serveur Nitro ouvert tel quel. `app/server/build.test.ts` : `.output` (lanceur depuis un dossier vide, serveur sans autre import que `node:*`, client sans `node:*` et découpé par page, licences, échantillonneur NVML à côté du serveur et qui démarre depuis le bundle). `app/server/dev.test.ts` : la boucle de dev sur une copie de `app/` sous `.cache/` (une sauvegarde du serveur le relance, une du web le garde, SIGINT, double SIGINT, SIGHUP, `.env`, les DevTools).
- **Suite de contrat** (`app/server/contract/`) : chaque endpoint rejoué en HTTP réel contre le build de production (réglages `LLAMA_WEBUI_TEST_MONITOR=stub` et `LLAMA_WEBUI_TEST_OFFLINE=1`), comparé à `golden.json` (hachages des assets remplacés par `<hash>`, chemins de la machine par `<repo>`, `<tmp>`, `<home>`). Sa matrice est générée depuis la définition de l'API (`HttpApi.reflect` dans `cases.ts` : chaque méthode qui manque à un chemin, le mauvais id et l'id inconnu de chaque `:id`, les cinq corps cassés de chaque payload) ; puis les cas écrits à la main (un succès pour un endpoint que la matrice n'atteint pas, sinon le test de couverture échoue, une `violation`, un `refusal`, un cas de garde) ; puis les cas qui tiennent une connexion (`runStreams` : `/ws` hello et pong, un profil lancé sur le faux llama-server, la réponse SSE du chat lue par `readSse` de `wire.ts`). Un changement de comportement voulu → `UPDATE_GOLDEN=1 pnpm exec vitest run app/server/contract/contract.test.ts`, puis relire le diff du golden.

## Type checking

`pnpm check` = `pnpm -r --parallel --include-workspace-root typecheck` : le script `typecheck` de chaque package du workspace, tous en même temps (`tsc` ; racine : `tsc -p . && tsc -p scripts` ; `app` : `tsc && tsc -p server` ; `site` : `react-router typegen && tsc`). TypeScript 7 (`tsc` natif), version dans le `catalog:`. Les projets qui portent du code Effect (le serveur, `app/server/tsconfig.json`, et `packages/webui-shared`) étendent `tsconfig.effect.json` : le language service d'Effect (`@effect/tsgo`, plugin `@effect/language-service`) y sort ses diagnostics dans `tsc` (`effect(<règle>)`, sévérités dans `diagnosticSeverity`). Ils sont bloquants, warnings compris : `pnpm check` n'affiche aucune ligne `effect(` (`pnpm check 2>&1 | grep -c 'effect('` donne 0). `unstableApiUsage` et `apiStabilityLeak` sont coupées (`off`) : presque tout Effect hors du cœur est `@stability unstable` (`effect/http`, `effect/sql`, `effect/process`, les `@effect/*`…), d'où la version exacte dans le `catalog:`.

**Dans ce projet :** pas de project references. Le `tsconfig.json` racine ne couvre que les fichiers de config de la racine (`./*.config.ts`, `./oxlint.*.ts`), avec ses propres options, et le `typecheck` racine le lance avant `scripts`. Chaque base de code a son `tsconfig.json` (`packages/llamacpp-js` en types Node seuls et résolution NodeNext, tests compris, `packages/webui-shared`, `scripts`, et deux pour `app/` : `app/tsconfig.json` pour `src/`, `build/` et `vite.config.ts` (DOM + Node), `app/server/tsconfig.json` pour le serveur et ses tests (Node seul)), qui étend `tsconfig.base.json` (options communes : `noEmit`, `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` (une propriété optionnelle `x?: T` ne prend pas `undefined` : `x?: T | undefined` ou `Schema.optional` quand un appelant en relaie un), `erasableSyntaxOnly`, imports relatifs en `.ts` par `rewriteRelativeImportExtensions`), directement ou par `tsconfig.effect.json`, et n'ajoute que ses types et ses fichiers. Un projet qui importe un autre package en vérifie les sources avec ses propres options. Nouveau package → un `tsconfig.json` qui étend la base, un script `typecheck` (`tsc`) et `typescript` (`catalog:`) en devDependency ; pas de `paths` vers des sources d'un autre package.

## Format (oxfmt) et lint (oxlint)

oxfmt (devDependency épinglée, config dans `oxfmt.config.ts`, où se lit le style) gère le format, le tri des imports, celui des clés des `package.json` et celui des classes Tailwind (`sortTailwindcss`, dans `className`, `cn(…)` et `cva(…)` ; une chaîne de classes ailleurs, une constante, reste telle quelle) ; il formate aussi tous les `.md` (le `docs/` de la racine compris) et les pages `.mdx` du site, sans toucher au code de leurs blocs (`embeddedLanguageFormatting: 'off'`) ; il ignore ce que liste `.gitignore`, ainsi que les `testdata` et `pnpm-lock.yaml`.

oxlint (devDependency épinglée, avec `oxlint-tsgolint` pour les règles qui lisent les types, `typeAware`) gère le lint du TS et du TSX (pas du CSS, du Markdown ni du MDX). Une config par projet, toujours `oxlint.config.ts` : celle de la racine exporte `base` (plugins, catégories `correctness`, `suspicious` et `perf`, règles choisies par nom) et couvre `scripts/`, `app/build`, `app/bin` et les fichiers de la racine ; `app/server`, `app/src`, `site`, `packages/llamacpp-js` et `packages/webui-shared` ont la leur, qui étend `base` et les fragments dont le projet a besoin, `oxlint.react.ts` (React, `jsx-a11y` et dix règles du plugin JS `oxlint-plugin-react-doctor`, la dixième pour `site` seul, pour `app/src` et `site`), `oxlint.tests.ts` (Vitest sur `*.test.ts(x)`, sauf `llamacpp-js`, testé sous `node:test`) et `oxlint.tailwind.ts` (`app/src` et `site` : le plugin JS `oxlint-tailwindcss`, chaque projet y ajoute sa feuille de style, `settings.tailwindcss.entryPoint`). Un rapport Tailwind se corrige sans changer le rendu, par une forme équivalente : une classe du thème qui n'est pas un utilitaire s'ajoute à l'`allowlist` de `tailwindcss/no-unknown-classes` (`oxlint.tailwind.ts`), jamais supprimée pour faire taire la règle ; une couleur sans token de la même valeur exacte garde la sienne sous une suppression motivée, sans ajouter de token (détail dans `conventions.mdx` › Tailwind classes). Le plugin met en cache le design system de chaque feuille de style dans `$TMPDIR/oxlint-tailwindcss-<uid>`, par version du paquet et non par contenu du thème : après une modification de `packages/webui-theme/theme.css`, supprimer ce dossier (ou lancer avec un `OXLINT_TAILWINDCSS_CACHE_DIR` neuf) avant de croire `pnpm lint` ou l'éditeur, la CI partant toujours à froid. Les frontières entre projets sont des `no-restricted-imports` (un motif par frontière, sur le nom du paquet et les chemins relatifs qui mènent au même dossier ; `import`, `import type`, `export … from` et `import('…')` littéral), doublées des mêmes motifs par `imports/no-restricted-calls` (plugin local `scripts/oxlint/imports.ts` : `require`, `require.resolve`, `createRequire(…)(…)`, `import()` d'un template, `vi.mock` et sa famille ; un chemin connu seulement à l'exécution est refusé, sauf suppression motivée) : chacune dans la config du projet, par `bans([…])` de `oxlint.config.ts` (les deux règles, mêmes motifs), qui relâche, pour ses tests, un refus de `node:*` ; le tableau est dans `conventions.mdx` › What the linter enforces. `import/no-cycle` (dans `base`) refuse un cycle d'imports. Chaque fichier prend la config la plus proche, qui remplace celle de la racine sans s'y ajouter ; les `ignorePatterns` ne passent pas par `extends` et sont relatifs à leur config : chaque config de projet répète ceux de son dossier. Ni lintés ni formatés : ce que liste `.gitignore`, `**/src/components/ui` (shadcn généré, app et site, pour rester comparable aux mises à jour shadcn), `**/testdata`, `app/server/contract/golden.json` (généré) ; oxlint saute aussi le `docs/` de la racine et les sorties de build. Toute règle active est en `error` ; une règle coupée ou avec options porte sa raison en commentaire dans la config (`require-yield` coupée dans `app/server/oxlint.config.ts` : un générateur d'Effect n'a pas toujours de `yield`). Config effective d'un projet : `pnpm exec oxlint -c <projet>/oxlint.config.ts --print-config` (`--print-config <fichier>` ignore le chemin et affiche celle de la racine). Les diagnostics Effect restent dans `tsc` (« Type checking » ; `prepare` : `effect-tsgo patch --typescript --no-oxlint`).

- `pnpm lint` (`oxfmt --check && oxlint --deny-warnings --report-unused-disable-directives`) : vérifie format + imports + lint (lecture seule ; un warning ou une suppression qui ne sert à rien le fait échouer) ; `pnpm lint:fix` (`oxlint --fix && oxfmt`) applique les corrections sûres puis formate ; `pnpm format` (`oxfmt`) formate seulement.
- **Avant de clore un jalon / milestone / lot de travail** (et avant de commiter ou d'ouvrir une PR), tout doit être vert : `pnpm lint`, `pnpm check`, `pnpm test`. Zéro erreur et zéro warning d'oxlint.
- Ne pas désactiver une règle ni la baisser en `warn` pour faire passer le lint. Si une règle est un faux positif, `// oxlint-disable-next-line <règle> -- <raison>` (`{/* … */}` en JSX) ciblé et motivé, la règle sous le nom qu'affiche le rapport, un `/` à la place des parenthèses et sans le préfixe `eslint` (`react-hooks(exhaustive-deps)` s'écrit `react-hooks/exhaustive-deps`, `eslint(no-control-regex)` s'écrit `no-control-regex`) : sans raison (`directives/require-reason`, plugin local `scripts/oxlint/directives.ts`), sans règle (`unicorn/no-abusive-eslint-disable`) ou sans rien à taire, la suppression fait échouer le lint. `react/hooks` et `react/exhaustive-effect-dependencies` sont actives comme `react/exhaustive-deps` (écrite `react-hooks/exhaustive-deps` dans ses rapports et ses directives). `react/exhaustive-deps` signale, dans tout hook, une valeur lue mais non listée (et un effet sans tableau qui pose un état) ; une valeur listée mais non lue, seulement dans un `useMemo` ou un `useCallback`. `react/exhaustive-effect-dependencies` signale le tableau d'un effet : une dépendance manquante (« missing effect dependencies ») ou en trop (« extra effect dependencies », le cas d'une dépendance « déclencheur », listée, jamais lue). Une dépendance « déclencheur » voulue prend la suppression de la règle que nomme le rapport, ciblée, avec ce qu'elle déclenche en raison, au-dessus du tableau de dépendances (`// oxlint-disable-next-line react/exhaustive-effect-dependencies -- current.id is a trigger: …`). Une directive `react-hooks/…` fait sauter tout le composant aux règles fondées sur le React Compiler (`react/hooks`, `react/exhaustive-effect-dependencies`, `react/set-state-in-effect`, `react/immutability`…), comme le Compiler lui-même : à éviter (le code n'en a aucune ; une valeur lue sans relancer l'effet passe par `useEffectEvent`). Quand une règle signale un tableau de dépendances voulu, la suppression va au-dessus de ce tableau : elle tait tous les rapports du hook, une dépendance absente comprise, même si le rapport affiche la ligne où la valeur est lue ; un hook sans tableau (un effet relancé à chaque rendu) la prend au-dessus du hook. Pour lire la dernière valeur dans un effet sans le relancer, préférer `useEffectEvent` (React 19) à une suppression ; un état recopié ou remis à zéro dans un effet, c'est `react/set-state-in-effect`, `react-doctor/no-mirror-prop-effect` et `no-reset-all-state-on-prop-change` : la correction et ses idiomes (un `key`, l'ajustement pendant le rendu, `useDraft`) sont dans `conventions.mdx` › React. Les autres règles react-doctor signalent : un `setState` après un `await` dans un effet sans drapeau d'annulation (`no-set-state-after-await-in-effect`), un indicateur de chargement remis hors d'un `finally` (`no-loading-flag-reset-outside-finally`), un effet de bord dans une fonction de mise à jour d'état (`no-impure-state-updater`), un état jamais rendu, à tenir dans un `useRef` (`rerender-state-only-in-handlers`), un store Zustand lu en entier plutôt que par sélecteurs (`zustand-no-whole-store-destructure`), un Entrée sans garde de composition IME (`no-enter-submit-without-ime-composition-guard`), une route racine sans élément d'erreur (`react-router-require-root-error-boundary`) et, pour `site` (prérendu), `window`, `document` ou `navigator` lu pendant le rendu ou l'état initial d'un hook (`no-unguarded-browser-global-in-render-or-hook-init`) ; leur tableau est dans `conventions.mdx` › react-doctor.

## Profiling

`pnpm profiling <scénario…|all> [--name <run>] [--compare <run> | --base <ref>] [--profile <id>]` mesure l'app comme on l'utilise (build avec source maps cachées, serveur sur le port de l'instance, qui doit être libre, Chromium headless avec compositing GPU, un profil lancé sur les GPU pour les scénarios avec modèle), puis annule tout ce qu'il a créé ; `pnpm profiling:report <run> [--compare <run>]` réécrit un rapport depuis son `results.json`. Code dans `scripts/profiling/`, chaque run dans `.cache/profiling/<run>/` (`report.html`, `results.json`, données brutes). Pour vérifier un correctif, la même commande avant et après (`--name before`, le correctif, `--name after --compare before`), pas une comparaison avec une passe complète. `--base <ref>` mesure une ref git puis l'arbre de travail dans le même run (la base dans un worktree sous `.cache/profiling/<run>.base/src`, chaque côté sur sa copie du dossier de données, tous deux retirés à la fin) et écrit aussi `summary.md` ; un commentaire `/profiling [scénarios] [--profile N]` sur une PR le lance sur un runner auto-hébergé (`.github/workflows/profiling.yml`, label `profiling`, propriétaire et collaborateurs seulement, jamais un fork ; les mots du commentaire passent par `scripts/profiling/comment.ts`, jamais tels quels dans un shell) et répond par ce résumé, avec un lien vers le `report.html` publié en artifact du run. Un scénario avec modèle est refusé tant qu'un `llama-server` tourne. Aucun test ne le lance (les tests ne couvrent que ses options, son annulation, sa comparaison, son rapport et l'analyse du commentaire) ; il occupe les GPU et le port 7860. Doc : `site/content/developers/contributing/profiling.mdx`.

## Packages (`packages/`)

`packages/webui-shared/` (`@llama-webui/shared`) : les schémas (Effect `Schema`) et la logique pure partagés par le serveur et le web, et la définition de l'API (`src/api/` : `Api`, un groupe par domaine, les erreurs de chaque endpoint) ; `app/` et, hors des tests, `node:*` ou `llamacpp-js/node` : `no-restricted-imports` de `packages/webui-shared/oxlint.config.ts`. `packages/llamacpp-js/` : tout ce qui parle à llama.cpp (API HTTP de `llama-server`, métriques, `--help`, sortie de `llama-bench`, `/proc`), destiné à être publié sur npm. `packages/webui-theme/` (`@llama-webui/theme`, privé) : le thème Obsidian Aurora en un seul `theme.css` (tokens clair et sombre, fond aurora, styles de base), importé par `app/src/index.css` et `site/src/styles/app.css`, qui n'y ajoutent que leur calibrage (après une modification, vider le cache du lint Tailwind : « Format et lint ») ; un changement du thème redéploie le site (`paths` de `site-deploy.yml`). Règles de `llamacpp-js` (vérifiées par `tests/package.test.ts`, son projet TS, son `oxlint.config.ts` et ses tests, sous Node en CI) :

- **Cible :** Node ≥ 24, donc uniquement des API web et `node:*` dans `src/` (`fetch`, `node:child_process`, `node:fs/promises`) ; son projet TS n'a que les types Node. Ses tests sont dans `tests/` (hors de `src/`) et utilisent `node:test` + `node:assert/strict`, sous Node (`pnpm --filter llamacpp-js test` = `node --test 'tests/*.test.ts'`, en CI sous Node 26 et, dans un job à part sans installation, sous Node 24, la version minimale). Les contrôles de bundling de `tests/package.test.ts` passent par Rolldown (devDependency) et passent `{ skip }` sans installation.
- Aucune dépendance (`tests/package.test.ts`) ; un import de `@llama-webui/*`, `effect` ou `@effect/*`, ou de `node:*` hors de `src/node.ts` et des tests : `no-restricted-imports` de `packages/llamacpp-js/oxlint.config.ts`. Ce qui est un choix de llama-webui (superviseur, `buildCommand`, formulation des erreurs pour l'utilisateur, caches) reste dans l'app.
- TS exécutable tel quel par Node : imports relatifs avec extension `.ts`, `import type` (`typescript/consistent-type-imports`), syntaxe effaçable (`erasableSyntaxOnly` : pas d'`enum`, de `namespace` ni de propriétés de paramètre).

## Build, dev et distribution

`app/vite.config.ts` construit le client (`app/src/`, React, Tailwind par `@tailwindcss/vite`, alias `@`) dans `.output/public` ; `app/build/server.ts` (Rolldown) construit ensuite le serveur.

**Dans ce projet :** un seul process Node sur le port 7860 sert l'API, le WebSocket et l'UI (`LLAMA_WEBUI_HOST`, `127.0.0.1` par défaut, `LLAMA_WEBUI_PORT`, `LLAMA_WEBUI_DATA_DIR`, ou leurs options). `pnpm dev` = `vite dev --bypass-lock` dans `app/` : Vite garde l'adresse publique (`strictPort`) et sert l'UI en HMR ; son plugin `app/build/devServer.ts` lance le serveur depuis les sources (`node --watch server/main.ts`, `LLAMA_WEBUI_DEV=1`) sur un port libre de loopback, dans son propre groupe de processus, et lui passe `/api` et `/ws` en proxy (`changeOrigin: false` : la garde lit le Host et l'Origin du navigateur ; une requête de l'API attend que le serveur réponde pendant qu'il (re)démarre). Arrêt de Vite (SIGINT, SIGTERM, SIGHUP) : le serveur reçoit SIGTERM et Vite l'attend (une page ouverte reçoit son 1001), un second signal le tue (d'où `--bypass-lock` : sur SIGINT, le verrou de processus de Vite se libère en se renvoyant SIGINT, qui compterait pour le second ; le plugin refuse de démarrer sans) ; un SIGKILL de Vite est la seule fin qui laisse le serveur tourner. Version (`app/server/config/AppInfo.ts`, barre d'état, `/api/health`) : `dev` depuis les sources, `git describe --tags --always --dirty` au build (`LLAMA_WEBUI_VERSION`, défini par `build/server.ts`), la version du `package.json` sans git.

**Rechargement (dev) :** une sauvegarde d'un fichier que le serveur importe (`app/server/`, `packages/`) le relance (`node --watch`) : le runtime est défait comme à un arrêt (llama-server arrêté, un sweep en cours passe « interrupted », bouton Resume, une réponse du chat « stopped », un téléchargement reprendra son `.part`) puis reconstruit, nouveau `bootId`. Une sauvegarde sous `app/src/` reste du HMR, le serveur et llama-server sont gardés.

`pnpm build` = `vite build && node build/server.ts` dans `app/` → `app/.output/` : `public/` (client découpé par page, assets hachés, ceux de texte de plus de 1 KiB avec leurs copies `.br` et `.gz` : `app/build/precompress.ts`), `server/index.mjs` (le serveur, un seul fichier qui n'importe que `node:*`), `server/nvml-worker.mjs` (l'échantillonneur NVML), `llama-webui.mjs` (le lanceur, `app/bin/llama-webui.ts`, `#!/usr/bin/env node`, qui importe `./server/index.mjs` : la ligne de commande est lue par le serveur) et `server/THIRD-PARTY-LICENSES.md` (`app/build/licenses.ts`, depuis les modules embarqués dans le serveur et l'échantillonneur). `pnpm start` = build puis `node app/.output/llama-webui.mjs`. `node scripts/smoke.ts` vérifie le build (CI). **Distribution :** le paquet racine est le paquet publié (`bin` `llama-webui` → `app/.output/llama-webui.mjs`, `files` `app/.output` seulement, `os` linux ; `pnpm pack` refuse sans build, `scripts/prepack.ts`) ; il n'a **aucune dépendance** : le build est autonome (`scripts/package.test.ts`). `.output` est ignoré par le `.gitignore` racine et non par un `app/.gitignore` : npm appliquerait ce dernier au tarball malgré `files`. `node scripts/smoke.ts --tarball [fichier.tgz]` : `pnpm pack`, `npm install` dans un préfixe vide, puis les vérifications du smoke par `node_modules/.bin/llama-webui` (CI). `release.yml` (tag `v*`) : `node scripts/release.ts --check`, build, `pnpm pack`, smoke du tarball (`--expect-version` du tag : un build qui rapporte une autre version, `-dirty` par exemple, n'est pas publié), `SHA256SUMS`, `gh release create` ; la version de tous les `package.json` s'aligne par `pnpm release <version>` (PR, `master` est protégée) ; `scripts/release.test.ts` échoue s'ils divergent.

## Site web et documentation (`site/`)

Le site public (page d'accueil, doc utilisateur, doc développeur) vit dans `site/` et est publié sur GitHub Pages (`https://sharkezz.github.io/llama-webui/`, base `/llama-webui/`). Plan et jalons : `docs/superpowers/plans/2026-11-08-website.md`.

- **Pile :** `site/` utilise Vite + React Router (mode framework, `ssr: false` + prérendu statique) + Tailwind 4 + shadcn + MDX. C'est un projet du workspace pnpm (installé par le `pnpm install` racine, sans lockfile propre), ses scripts lancés par pnpm et exécutés par Node : `dev`, `typecheck` et la première étape de `build` sont des commandes React Router (`react-router dev`, `react-router typegen`, `react-router build`), les autres des scripts `node scripts/<nom>.ts` (mêmes règles que `app/server/` : `node:*`, imports avec extension `.ts`), ses tests dans le projet Vitest `site`.
