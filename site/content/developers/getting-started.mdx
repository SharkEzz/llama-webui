This page gets a working copy of llama-webui running for development: prerequisites, installation, the two ways to run
the server and the package, every script, the repository layout, how to work without GPUs or without llama.cpp, and the checks every
change must pass.

## Prerequisites

| Tool | Why |
| --- | --- |
| **Linux** | Hardware discovery and telemetry read `/proc` and `/sys`. |
| **[Node.js](https://nodejs.org) 26.13 or later** | The runtime of the app, its tests, its build and the website's scripts. CI pins 26.13. |
| **[pnpm](https://pnpm.io) 12** | Installs the workspace and runs the scripts (`npm install -g pnpm`, into a prefix you own: [Install Node.js](/docs/getting-started/installation/#install)). |
| **`setpriv`** (util-linux) | Every `llama-server` and `llama-bench` process is launched as `setpriv --pdeathsig KILL -- …`, so it dies with llama-webui. |
| **Git** | To clone the repository; the build reads its version from `git describe`. |
| A llama.cpp build (optional) | Needed to run real models. Without it, use the [fake binaries](#without-llamacpp). |

The [user requirements](/docs/getting-started/requirements/) list the optional pieces (NVIDIA driver, `amdgpu`,
`perf`) and what each one unlocks.

## Install

```bash title="Terminal"
git clone https://github.com/SharkEzz/llama-webui.git
cd llama-webui
pnpm install
```

`pnpm install` installs the whole pnpm workspace, declared in `pnpm-workspace.yaml`: `packages/*` (`webui-shared`,
`llamacpp-js`), the app, `app/`, and the website, `site/`, all from one `pnpm-lock.yaml`. The same file holds the
`catalog:` of the versions that move together (React, Vite, TypeScript, zod…): change a version there, not in a
`package.json`. A dependency change commits its `pnpm-lock.yaml`; CI installs with
`--frozen-lockfile`.

## Run llama-webui

<Tabs>
  <Tab title="Development">

```bash title="Terminal"
pnpm dev
```

`pnpm dev` runs `vite dev` in `app/`: one Node.js process, one port. Vite serves the UI with hot module replacement,
and Nitro's Vite plugin runs the server in its dev worker, on the same port. Saving a route file keeps the runtime and
`llama-server`; saving business code under `app/server/lib/` or `packages/` rebuilds the runtime, `llama-server`
included ([Development restarts](/developers/architecture/#development-restarts)). Once the runtime is up, it prints:

```text
[llama-webui] ready (dev)
```

  </Tab>
  <Tab title="Production">

```bash title="Terminal"
pnpm start
```

`pnpm start` is `pnpm build && node app/.output/llama-webui.mjs`. `vite build` writes Nitro's output to
`app/.output/`: the UI, split per page, in `public/`, the server, every dependency bundled, in `server/`, and the
launcher, `llama-webui.mjs`. It has no HMR and no file watching. It prints its version,
`git describe --tags --always --dirty` at build time:

```text
[llama-webui] ready (v0.3.1-23-gc5e88eb)
```

  </Tab>
</Tabs>

The production launcher takes the launch options (`--host`, `--port`, `--data-dir`, or their `LLAMA_WEBUI_*`
variables), listed by `pnpm start --help` and documented in [Launch options](/docs/configuration/), and reads the
`.env` file of the repository's root. `pnpm dev` does not read the launch flags: it takes the same variables from the environment, or
from `.env`, `.env.local`, `.env.development` and `.env.development.local` in `app/`, its working directory. Two
habits keep development away from your everyday instance:

- Use a separate data directory. `data/` and `*.sqlite` are ignored by Git, so `LLAMA_WEBUI_DATA_DIR=$PWD/data pnpm dev`
  keeps a development database inside the clone.
- Use another port if an instance already runs on 7860: `LLAMA_WEBUI_PORT=7861 pnpm dev`.

A save of business code stops the `llama-server` that `pnpm dev` manages, and a running sweep ends as `interrupted`
(Resume button). Edit the server's business code between benchmarks rather than during one; a route file can be edited
at any time.

### The package

A release is the npm package of the repository's root ([Distribution](/developers/architecture/#distribution)):

```bash title="Terminal"
pnpm build                          # app/.output
node scripts/smoke.ts               # starts the build and checks the API, the UI and the WebSocket
pnpm pack                           # llama-webui-<version>.tgz (refused without a build)
node scripts/smoke.ts --tarball     # packs, installs with npm into an empty prefix, checks the installed command
```

To try the installed command by hand, install the tarball into a folder of its own rather than your global prefix:
`npm install -g --prefix /tmp/lw ./llama-webui-<version>.tgz`, then `/tmp/lw/bin/llama-webui`.

## Scripts

The root `package.json` defines the app's scripts; the website has its own, in `site/package.json`.

| Script | Runs | What it does |
| --- | --- | --- |
| `pnpm dev` | `pnpm --filter @llama-webui/app dev` | `vite dev` in `app/`: the UI with HMR and the server in Nitro's dev worker; a save of business code rebuilds the runtime. |
| `pnpm build` | `pnpm --filter @llama-webui/app build` | `vite build` in `app/`: the UI in `app/.output/public/`, the server in `app/.output/server/` (with the NVML sampler, `nvml-worker.mjs`), the launcher `app/.output/llama-webui.mjs`. |
| `pnpm start` | `pnpm build && node app/.output/llama-webui.mjs` | Builds, then runs the production server. |
| `pnpm test` | `pnpm test:unit && pnpm --filter llamacpp-js test` | Every Vitest project (`server` with `app/build/` and `scripts/`, which starts with one production build, then `shared`, `web`, `site`), then the `llamacpp-js` tests on `node --test`. |
| `pnpm test:unit` | `vitest run` | The Vitest projects only. |
| `pnpm check` | `pnpm -r --parallel --include-workspace-root typecheck` | Runs the `typecheck` script of every workspace package at once (`packages/*`, `app/` with its client and server projects, `site/`, and the root for `scripts/`), each with its own `tsconfig.json`: [Type checking](/developers/contributing/testing/#type-checking). |
| `pnpm typecheck` | `tsc -p scripts` | The root package's share of `pnpm check`: type checks `scripts/`. |
| `pnpm lint` | `biome check` | Format, lint and import order, read-only. |
| `pnpm lint:fix` | `biome check --write` | Applies Biome's safe fixes. |
| `pnpm format` | `biome format --write` | Formats only. |
| `pnpm release` | `node scripts/release.ts` | Sets the version of every `package.json` before a release tag ([Releases](/developers/contributing/workflow/#releases)). |
| `pnpm site:dev` | `pnpm --filter llama-webui-site dev` | Website dev server (Vite, HMR) on `0.0.0.0:5173`. |
| `pnpm site:build` | `pnpm --filter llama-webui-site build` | Prerenders the website into `site/dist/`. |
| `pnpm site:preview` | `pnpm --filter llama-webui-site preview` | Serves `site/dist/` the way GitHub Pages does, on port 4173. |

`pnpm pack` also runs `prepack` (`node scripts/prepack.ts`), which refuses to pack without a build. The website has
more scripts of its own (`check-links`, `demo-seed`, `screenshots`, `og`, `typecheck`), run with
`pnpm --dir site <script>`; [Docs, commits and PRs](/developers/contributing/workflow/) covers them.

## Without GPUs

llama-webui runs on a machine without a GPU: the GPU collectors find no card, and the CPU, memory and disk readings
still work. A few things help when you work on telemetry code:

- The **collectors** switches in [Settings](/docs/settings/) turn NVML, the system sampler and the disk sampler on or
  off.
- NVIDIA cards are read through NVML, with `nvidia-smi` as the fallback. `LLAMA_WEBUI_NVML_LIB` overrides the NVML
  library the worker opens and `LLAMA_WEBUI_NVIDIA_SMI` the `nvidia-smi` binary the fallback runs, which lets you test
  either one missing (`LLAMA_WEBUI_NVML_LIB=/nonexistent pnpm dev` reads NVIDIA cards through `nvidia-smi`).
- Hardware parsers are tested against captured files in `testdata/` (`nvidia-gpu.csv`, `fdinfo-*.txt`,
  `metrics-*.txt`, `slots-*.json`…), so most collector changes can be covered by a test without the hardware.

## Without llama.cpp

`testdata/fake/` holds two stand-ins that the tests launch instead of the real binaries. Each is a small shell
wrapper that runs a TypeScript fake with `node`:

- `fake-llama-server` answers `--version`, listens on `127.0.0.1` at the `--port` it receives (8080 without one),
  returns `503` on `/health` while it "loads", then serves `/health`, `/slots`, `/metrics` and `/props` from the
  fixtures next to it, `/completion`, and `/v1/chat/completions` (a streamed, simulated Markdown reply with
  reasoning, or a whole reply when `stream` is not `true`).
- `fake-llama-bench` prints `--list-devices` from `testdata/llama-bench/list-devices.txt`, writes `llama-bench`-style
  progress on stderr, and prints the JSON of `testdata/llama-bench/ok.json`.

llama-webui finds `llama-bench` by replacing `llama-server` with `llama-bench` in the binary's file name
(`benchBinary()` in `llamacpp-js/node`), so the two fakes pair up the same way the real binaries do.

The server wrapper's comment notes it can be used as the binary setting. Point **llama-server binary** in
[Settings](/docs/settings/) at the absolute path of `testdata/fake/fake-llama-server` to drive the UI without
llama.cpp. Keep in mind that the fake:

- ignores the model: a profile still needs a `model` value, but the file is never opened;
- has no `--help`, so the argument editor has no flag catalogue;
- listens on `127.0.0.1` whatever `--host` says.

Environment variables change the fakes' behavior. The supervisor passes llama-webui's environment and the profile's
environment variables to `llama-server`, so you can set them in either place.

| Variable | Fake | Effect |
| --- | --- | --- |
| `FAKE_LOAD_MS` | server | Loading time before `/health` answers `200` (default 300 ms). |
| `FAKE_SLOW_ARG`, `FAKE_SLOW_MS` | server | Loads for `FAKE_SLOW_MS` (default 5000 ms) when one of its arguments equals `FAKE_SLOW_ARG`. |
| `FAKE_FAIL_ARG` | server | Logs an out-of-memory error and exits with code 1 when one of its arguments equals this value. |
| `FAKE_EXIT_LINES` | server | Logs these lines (separated by `\|`) and exits with code 1 at startup. |
| `FAKE_EXIT_AFTER_MS`, `FAKE_EXIT_CODE` | server | Exits after a delay, with `FAKE_EXIT_CODE` (default 1). |
| `FAKE_IGNORE_TERM` | server | `1` ignores `SIGTERM` (tests the `SIGKILL` path). |
| `FAKE_CRASH_ON_PREDICT` | server | Dies in the middle of a `/completion` request with this `n_predict`. |
| `FAKE_N_CTX` | server | Context size of the simulated chat (default 40192 tokens); a larger prompt gets `llama-server`'s context error. |
| `FAKE_CHAT_DELAY_MS`, `FAKE_CHAT_LINES` | server | Delay between streamed chunks (default 60 ms), extra lines appended to the reply. |
| `FAKE_DRAFT` | server | `1` adds draft statistics (speculative decoding) to `/completion` and non-streamed replies; the streamed chat reply always has them. |
| `FAKE_PP`, `FAKE_TG` | both | Prompt and generation speed reported, in tokens per second (server: `/completion` and non-streamed replies). |
| `FAKE_TG_BY_ARG` | bench | Generation speed per argument fragment, the first match wins, for example `-ncmoe 8=30;-ncmoe 16=20`. |
| `FAKE_BENCH_OOM`, `FAKE_BENCH_OOM_ARG` | bench | Reproduces a load failure: always with `FAKE_BENCH_OOM=1`, or when the arguments contain the `FAKE_BENCH_OOM_ARG` fragment. |
| `FAKE_BENCH_STEP_MS` | bench | Delay between progress steps (default 100 ms). |

[Testing](/developers/contributing/testing/) explains how the tests use the fakes and the other captures.

## Quality gate

Before you close a piece of work, commit, or open a pull request, these three commands must pass from the repository
root, with zero errors and zero Biome warnings:

```bash title="Terminal"
pnpm lint
pnpm check
pnpm test
```

CI (`.github/workflows/ci.yml`) runs the same commands, then `pnpm build`, the two smoke tests, the website build and
its link check, and runs the `llamacpp-js` tests again on Node 24, the package's minimum. Do not disable a Biome rule
or lower it to a warning to get a green run: for a genuine false positive, add a targeted
`// biome-ignore lint/<group>/<rule>: <reason>` comment. `app/src/components/ui/` (generated shadcn components) is
ignored by Biome. [Conventions](/developers/contributing/conventions/) has the full rules.
