`@llama-webui/shared` (`packages/webui-shared/src/`) holds what the server and the web app must agree on: the
definition of the HTTP API (`src/api/`), the Effect schemas of every response, request body, setting and WebSocket
message, and pure functions that both sides run. It has no build step and two dependencies: `effect`, and
[llamacpp-js](/developers/llamacpp-js/) for llama.cpp's own formats.

## The package

`packages/webui-shared/package.json` exports its TypeScript sources directly (`"exports": { ".": "./src/index.ts" }`). The app
(`app/`, both its server and its client) depends on it as `workspace:*` and resolves it through its `node_modules`. `index.ts` re-exports every module, so both sides import from the package root and never from a
file path:

```ts title="app/src/lib/logs.ts"
import { EMPTY_LOG_VIEW, type LogLine, type LogView, mergeLogs, onBoot } from '@llama-webui/shared';
```

Tests sit next to their module (`packages/webui-shared/src/<module>.test.ts`) and run with Vitest on Node
([Testing](/developers/contributing/testing/)). `node.test.ts` checks that Node imports the package from its sources,
without a build. Its project extends `tsconfig.effect.json`, so the Effect language service checks it as it checks
the server.

### Re-exported from llamacpp-js

Part of the API both sides share is llama.cpp's own format, so it lives in `llamacpp-js` and `index.ts` re-exports it:
the whole flag catalogue (`llamacpp-js/flags`: `Flag`, `FlagCatalog`, `parseHelp()`, `catalogFrom()`, `flagOf()`,
`complete()`, `flagSuggestions()`, `unknownFlags()`, `describeFlag()`), `SseParser` and `SseEvent` (`llamacpp-js/sse`),
and through `monitor.ts` the `SlotView`, `Health`, `RequestStats`, `SpecStats` and `RequestRecord` types. The web app
keeps importing them from `@llama-webui/shared`. `bench.ts` builds on `BenchMeasure` and `BenchDevice` of
`llamacpp-js/bench` (`Measure` is the same type; `BenchDevice` adds `otherUsedMib`), `chat.ts` on `LlamaTimings` of
`llamacpp-js/client` (`LlamaTimingsSchema` decodes it).

## The API definition

`Api` is the one description of the HTTP API. Each group lists its endpoints with their path, `params`, `query`,
`payload`, `success` and `error` schemas:

```ts title="packages/webui-shared/src/api/ProfilesApi.ts"
export class ProfileNameTaken extends Schema.TaggedError<
  ProfileNameTaken,
  { readonly ProfileNameTaken: unique symbol }
>()('ProfileNameTaken', { message: Schema.String }, { httpApiStatus: 409 }) {}

export class ProfilesApi extends HttpApiGroup.make('profiles').add(
  HttpApiEndpoint.get('list', '/api/profiles', { success: Schema.Array(Profile) }),
  HttpApiEndpoint.post('create', '/api/profiles', {
    payload: ProfileInput,
    success: Created, // Profile.pipe(HttpApiSchema.status(201))
    error: ProfileNameTaken,
  }),
  // …
) {}
```

The server implements it (`HttpApiBuilder.group(Api, 'profiles', …)` in `app/server/profiles/http.ts`): a handler
gets its inputs decoded and can only fail with the errors its endpoint declares. The web app derives its client from
the same value (`call((api) => api.profiles.create({ payload }))`, `app/src/lib/api.ts`): the reply comes back decoded,
and an error comes back as the tagged class, told apart by its `_tag`. A change of an endpoint is a type error on
both sides until both follow. The [API overview](/developers/api/overview/#how-routes-are-registered) shows how a
group is added.

## Why the schemas live here

A schema is written once and gives three things: the server decodes with it, the web app's client decodes the
replies with it, and both sides get its TypeScript type.

```ts title="packages/webui-shared/src/settings.ts"
export const Settings = Schema.Struct({
  binary: Required.pipe(Schema.withDecodingDefaultKey(Effect.succeed(DEFAULTS.binary))),
  // …
  pollIntervalMs: IntBetween(250, 60_000, 'Between 250 and 60000 ms').pipe(
    Schema.withDecodingDefaultKey(Effect.succeed(DEFAULTS.pollIntervalMs)),
  ),
  historySeconds: IntBetween(30, 1800, 'Between 30 and 1800 s').pipe(
    Schema.withDecodingDefaultKey(Effect.succeed(DEFAULTS.historySeconds)),
  ),
  // …
});
export type Settings = typeof Settings.Type;
```

- **The server decodes.** A request's body, query and path parameters are decoded by `HttpApi` before the handler
  runs, strictly (an unknown key is an error) and reporting every issue; a failure is a `400` `RequestInvalid` with
  its `issues` ([Validation errors](/developers/api/overview/#validation-errors)). The repositories decode what they
  read back: `SettingsRepo` with `Settings`, `BenchRunsRepo` a run's spec with `StoredBenchSpec`, the lenient form
  that still reads the rows of earlier versions.
- **The web app decodes the replies.** `call()` decodes each reply with the endpoint's `success` schema, and a
  request body the client refuses to send gives the same `RequestInvalid` as the server. The forms show the
  `issues` next to the matching field.
- **Defaults and messages live in one place.** The defaults come from the schema (`withDecodingDefaultKey`, so a
  missing key decodes to its default), and the validation messages the user reads ("Port between 1 and 65535",
  "expected an absolute path") are written in the schema.

Shared rules are shared through the schema too. `serverArgsField` (`packages/webui-shared/src/bench.ts`), used by both
`BenchSpec` and `SweepSpec`, rejects the flags llama-webui sets itself (`RESERVED_FLAGS`: `--host`,
`--port`, `--metrics`, `--slots`, `--props`, `-m`, `--model`, `-mm`, `--mmproj`) at the index of the offending argument,
the same rule `ProfileInput` applies to a profile's `args`.

## Pure logic used on both sides

Functions that both sides need to compute the same way live here rather than being written twice:

| Function              | On the server                                                                                                                          | In the web app                                                                                |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `rankRuns()`          | Picks a sweep's best run and the runs to validate with a real server (`app/server/bench/BenchRunner.ts`).                              | Ranks the same runs on the Tuning page (`features/tuning/RankingTable.tsx`).                  |
| `benchArgs()`         | Builds the `llama-bench` arguments (`app/server/bench/execute.ts`).                                                                    | Shows a run's arguments in the benchmark history and comparison (`features/bench/`).          |
| `shellQuote()`        | Builds the displayed command line of a launch (`app/server/supervisor/command.ts`) and of a benchmark (`app/server/bench/execute.ts`). | Formats arguments in the profile editor, the benchmark form and history, and the Tuning page. |
| `SERIES`              | Names the history series the monitor records (`app/server/monitor/tick.ts`).                                                           | Names the series the charts read.                                                             |
| `slotContextTokens()` | Sums the context the slots use (`kvUsage()` in `llamacpp-js/metrics`).                                                                 | The Dashboard context card.                                                                   |
| `profileModelPath()`  | The model path written into a profile created from a benchmark run (`app/server/bench/toProfile.ts`).                                  | The same path in the profile form and the Tuning page's actions.                              |
| `defer()`             | Not used: the server's resources are scoped by Effect.                                                                                 | `using` blocks in the stores (`app/src/lib/server.ts`, `monitor.ts`, `chat.ts`…).             |

Some functions run on one side only and still live here, next to the types they work on. `parseHelp()` turns the
server's `llama-server --help` into a `FlagCatalog`; `GET /api/flags` sends its flag list as JSON, and `catalogFrom()`
rebuilds the catalogue's lookup map in the browser. `phaseOf()` derives the inference phase the Topology page shows
from a `ServerState` and a `Snapshot`, both shared types.

Text that earlier versions stored in the database is recognized here, once: `isOomError()` accepts the
`OOM_ERROR = 'Out of memory'` prefix and the earlier French wording, `isDefaultTitle()` accepts
`DEFAULT_TITLE = 'New conversation'` and its earlier French form. The web app calls these helpers instead of comparing
the text itself.

## What shared may import

The package imports nothing from `app/`: its modules import `effect`, the browser-safe modules of `llamacpp-js` (never
`llamacpp-js/node`) and each other, and only the tests use `vitest` and `node:path`. Keep it that way: `pnpm lint`
refuses an import of `app/` and, outside the tests, of `node:*` and `llamacpp-js/node`
([Import bans](/developers/contributing/conventions/#import-bans)). The same module runs on the server (Node) and in the
browser bundle, so a module that reached into the server would drag server code into the UI, and one that needed the DOM would break on the server.
Inputs that depend on the environment are passed in instead of read: `profileModelPath()` takes the home directory as
an argument and expands `~` itself, without `node:os` or `node:path`.

Its project (`packages/webui-shared/tsconfig.json`) compiles it with `lib: ["ESNext"]`, the
Node types (for its tests) and no DOM types, so a DOM API in a shared module fails there.
