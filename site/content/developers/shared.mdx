`@llama-webui/shared` (`packages/webui-shared/src/`) holds what the server and the web app must agree on: the types of every API
response and WebSocket message, the zod schemas of request bodies and settings, and pure functions that both sides
run. It has no build step and two dependencies: zod, and [llamacpp-js](/developers/llamacpp-js/) for llama.cpp's own
formats.

## The package

`packages/webui-shared/package.json` exports its TypeScript sources directly (`"exports": { ".": "./src/index.ts" }`). `server` and
`web` depend on it as `workspace:*` and resolve it through their `node_modules`; their `tsconfig.json` references
`packages/webui-shared/tsconfig.json`. `index.ts` re-exports every module, so both sides import from the package root and never from a
file path:

```ts title="web/src/lib/logs.ts"
import { EMPTY_LOG_VIEW, type LogLine, type LogView, mergeLogs, onBoot } from '@llama-webui/shared';
```

Tests sit next to their module (`packages/webui-shared/src/<module>.test.ts`) and run with Vitest on Node, then
again under Bun while the app runs on it ([Tests under Bun](/developers/contributing/testing/#tests-under-bun)).

### Re-exported from llamacpp-js

Part of the API both sides share is llama.cpp's own format, so it lives in `llamacpp-js` and `index.ts` re-exports it:
the whole flag catalogue (`llamacpp-js/flags`: `Flag`, `FlagCatalog`, `parseHelp()`, `catalogFrom()`, `flagOf()`,
`complete()`, `flagSuggestions()`, `unknownFlags()`, `describeFlag()`), `SseParser` and `SseEvent` (`llamacpp-js/sse`),
and through `monitor.ts` the `SlotView`, `Health`, `RequestStats`, `SpecStats` and `RequestRecord` types. The web app
keeps importing them from `@llama-webui/shared`. `bench.ts` builds on `BenchMeasure` and `BenchDevice` of
`llamacpp-js/bench` (`Measure` is the same type; `BenchDevice` adds `otherUsedMib`), `chat.ts` on `LlamaTimings` of
`llamacpp-js/client`.

## Why the zod schemas live here

A schema is written once and gives two things: the server validates with it, and both sides get its TypeScript type
with `z.infer`.

```ts title="packages/webui-shared/src/settings.ts"
export const SettingsSchema = z.object({
  binary: z.string().min(1, 'Required').default('llama-server'),
  // …
  pollIntervalMs: z.number().int().min(250, 'At least 250 ms').default(1000),
  historySeconds: z.number().int().min(30, 'Between 30 and 1800 s').max(1800, 'Between 30 and 1800 s').default(300),
  // …
});

export type Settings = z.infer<typeof SettingsSchema>;

export const DEFAULT_SETTINGS: Settings = SettingsSchema.parse({});
```

- **The server validates.** Routes and repositories call `parse()`: `BenchSpecSchema` in `server/routes/bench.ts`,
  `SweepSpecSchema` in `server/routes/sweeps.ts` and `server/routes/tuning.ts`, `DownloadRequestSchema` in
  `server/routes/hf.ts`, `SettingsSchema` in `server/db/settings.ts`, `ProfileInputSchema` in `server/db/profiles.ts`,
  `ConversationPatchSchema` in `server/db/conversations.ts`. A failure throws a `ZodError`, which the API's `onError`
  turns into a `400` with the zod `issues`.
- **Both sides share the types.** The web app imports `Settings`, `BenchParams`, `Profile` and the others as types
  and does not parse with zod itself. It shows the server's `issues` next to the matching field.
- **Defaults and messages live in one place.** The defaults come from the schema (`DEFAULT_SETTINGS` is
  `SettingsSchema.parse({})`), and the validation messages the user reads ("Port between 1 and 65535",
  "expected an absolute path") are written in the schema.

Shared rules are shared through the schema too. `serverArgsField` (`packages/webui-shared/src/bench.ts`), used by both
`BenchSpecSchema` and `SweepSpecSchema`, rejects the flags llama-webui sets itself (`RESERVED_FLAGS`: `--host`,
`--port`, `--metrics`, `--slots`, `--props`, `-m`, `--model`, `-mm`, `--mmproj`) at the index of the offending argument,
the same rule `ProfileInputSchema` applies to a profile's `args`.

## Pure logic used on both sides

Functions that both sides need to compute the same way live here rather than being written twice:

| Function | On the server | In the web app |
| --- | --- | --- |
| `SseParser` | Reads `llama-server`'s OpenAI-compatible stream (`server/chat/runs.ts`). | Reads llama-webui's chat SSE (`web/src/lib/chat.ts`). |
| `rankRuns()` | Picks a sweep's best run (`server/bench/runner.ts`) and the runs to validate with a real server (`server/routes/sweeps.ts`). | Ranks the same runs on the Tuning page (`features/tuning/RankingTable.tsx`). |
| `benchArgs()` | Builds the `llama-bench` arguments (`server/bench/execute.ts`). | Shows a run's arguments in the benchmark history and comparison (`features/bench/`). |
| `shellQuote()` | Builds the displayed command line of a launch (`server/supervisor/args.ts`) and of a benchmark (`server/bench/execute.ts`). | Formats arguments in the profile editor, the benchmark form and history, and the Tuning page. |
| `SERIES` | Names the history series the monitor records (`server/monitor/monitor.ts`). | Names the series the charts read. |
| `slotContextTokens()` | Sums the context the slots use (`kvUsage()` in `llamacpp-js/metrics`). | The Dashboard context card. |
| `profileModelPath()` | The model path written into a profile created from a benchmark run (`server/routes/bench.ts`). | The same path in the profile form and the Tuning page's actions. |
| `defer()` | `using` blocks in the bench gate, runner and executor, the monitor and the external server watcher. | `using` blocks in the stores (`web/src/lib/server.ts`, `monitor.ts`, `chat.ts`…). |

Some functions run on one side only and still live here, next to the types they work on. `parseHelp()` turns the
server's `llama-server --help` into a `FlagCatalog`; `GET /api/flags` sends its flag list as JSON, and `catalogFrom()`
rebuilds the catalogue's lookup map in the browser. `phaseOf()` derives the inference phase the Topology page shows
from a `ServerState` and a `Snapshot`, both shared types.

Text that earlier versions stored in the database is recognized here, once: `isOomError()` accepts the
`OOM_ERROR = 'Out of memory'` prefix and the earlier French wording, `isDefaultTitle()` accepts
`DEFAULT_TITLE = 'New conversation'` and its earlier French form. The web app calls these helpers instead of comparing
the text itself.

## What shared may import

The package imports nothing from `server/` or `web/`: its modules import zod, the browser-safe modules of
`llamacpp-js` (never `llamacpp-js/node`) and each other, and only the tests use
`vitest` and `node:path`. Keep it that way. The same module runs in Bun and in the browser bundle, so a module that
reached into the server would drag server code into the UI, and one that needed the DOM would break on the server.
Inputs that depend on the environment are passed in instead of read: `profileModelPath()` takes the home directory as
an argument and expands `~` itself, without `node:os` or `node:path`.

Its project (`packages/webui-shared/tsconfig.json`, checked by `tsc -b`) compiles it with `lib: ["ESNext"]`, the
Bun types and no DOM types, so a DOM API in a shared module fails there.
