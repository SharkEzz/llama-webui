description: The single Node.js process behind llama-webui, its startup and shutdown, the REST, WebSocket and SSE channels, UI serving, and the development reload pitfall.
---

llama-webui is one Node.js process (Node 26.13 or later). `server/index.ts` builds every service and `mount()`
(`server/host.ts`) puts them on one `node:http` server, which serves the web UI, the REST API under `/api/*` and the
`/ws` WebSocket on one port (7860 by default). The same process supervises one `llama-server`, samples the hardware,
runs benchmarks and relays chat generations.

## Startup sequence

`server/index.ts` is the composition root of both `pnpm dev` and `pnpm start`. In development, `server/dev.ts`
evaluates it again on every server-side save, inside the same process, so it is written to run more than once. In
production, `server/main.ts` (bundled to `dist/server/main.js`) sets `NODE_ENV` to `production` if it is unset and
imports it. Both entry points first load `.env` from the working directory (`loadDotEnv()`, `server/env.ts`): its
variables fill what the environment lacks, and replace it too with `--env-override`
(read from the arguments before they are parsed) or `LLAMA_WEBUI_ENV_OVERRIDE=1`. In order, `server/index.ts`:

1. Reads the launch options with `cliOptionsOrExit()` (see [Launch options](#launch-options)).
2. Opens the database with `openDb(dbPath(cli.dataDir))`: creates the data directory, opens
   `llama-webui.sqlite` with `node:sqlite`, sets `journal_mode = WAL` and `foreign_keys = ON`, and runs the migrations.
3. Gets the runtime with `getRuntime()` (`server/runtime.ts`): the supervisor, the log ring, the boot id and the bench
   gate, created on the first call and kept on `globalThis` afterwards.
4. Prepares the web handler: Vite's middlewares in development, the files of `pnpm build` in production (see
   [Serving the UI](#serving-the-ui)).
5. Starts the monitor with `startMonitor()`, once per process: later calls return the running one.
6. Calls `createDeps()` (`server/deps.ts`), which only constructs and wires the services, without starting any work:
   the `WsHub` with the runtime's `bootId`; the settings, profiles, conversations, bench run, sweep and download
   repositories; `ChatRuns`, whose `target()` sends generations to the managed server when it is `ready`, or to an
   external server; the `RunExecutor` and the `BenchRunner`; the Hugging Face client and the `DownloadQueue`; and the
   `PlacementTracker`, which replays the log ring to find the loaded model's placement.
7. Calls `mount()` with the API (`createApi(deps).fetch`), the hub and the web handler, on the development host's
   HTTP server or on a new one (see [Routes](#routes)). The first mount listens on the port; a later one swaps the
   listeners of the previous evaluation.
8. Calls `globalThis.__llamaWebuiDispose()` if a previous evaluation left one, to release that instance (see
   [What a reload recreates](#what-a-reload-recreates)). It comes after the new instance is built and mounted, so a
   reload that fails before this point leaves the old one serving.
9. Marks the chat replies left `streaming` by a killed process as `stopped` (`conversations.stopOrphans()`).
10. Marks the runs and sweeps left `running` as `interrupted` on a cold start (bench gate not held), and calls
   `benchRunner.resume()` in every case.
11. Gives the monitor the profile → model path resolver it uses for the model's disk.
12. Calls `downloads.resume()` to pick up the items left queued or downloading.
13. Subscribes the WebSocket hub to the services (table below), installs its shutdown handler, starts the external
    server watcher, and stores its own dispose function in `globalThis.__llamaWebuiDispose`.

It finally prints `llama-webui on http://<host>:<port>`, followed by `(dev, HMR)` in development or by the version
in production.

The services do not know about the WebSocket: `index.ts` passes them callbacks or subscribes to them, and broadcasts
each event as a `WsMessage` to every client. The benchmark and sweep routes also broadcast directly when they delete
runs.

| Source | Messages |
| --- | --- |
| `supervisor.subscribe()` | `server-state` |
| `logs.onLines()` | `log` |
| `monitor.onSnapshot()` | `snapshot` |
| `placement.onChange()` | `placement` |
| `BenchRunner` callbacks | `bench-progress`, `bench-run`, `sweep`, `sweep-progress` |
| `DownloadQueue` callbacks | `download`, `download-progress`, `download-deleted` |
| `server/routes/bench.ts`, `server/routes/sweeps.ts` | `bench-deleted`, `sweep-deleted` |

The external server watcher (`externalWatcher()` in `server/supervisor/external.ts`) runs at startup, then every
`EXTERNAL_CHECK_MS = 2000` ms. It is paused while the bench gate is held or the bench runner is busy, because the
`llama-server` a benchmark starts on the settings port is not an external server.

## Routes

`mount()` in `server/host.ts` routes the requests of the `node:http` server by path:

- `/api/*`, handed to the [Hono](https://hono.dev) app built by `createApi()` (`server/api.ts`), through the
  `getRequestListener()` adapter of `@hono/node-server`;
- `/ws`: an upgrade runs `guard()`, then goes to a `WebSocketServer({ noServer: true })` of the `ws` library, which
  hands the socket to the `WsHub` (`attachSocket()`, `server/ws/attach.ts`); a request without an upgrade runs
  `guard()`, then gets `426`;
- anything else, to the web handler: the UI files and the SPA fallback, so reloading `/chat/12` serves the app.

Only a WebSocket upgrade takes that route: `mount()` sets the server's `shouldUpgradeCallback`, so a request with
another `Upgrade` header (`h2c`, which `curl --http2` sends) is a plain request. An upgrade on another path is closed in
production, and left to Vite's HMR WebSocket in development. A `Host` header
that is not an authority gets `403` with `Invalid host`, as from the guard. A second `mount()` on the same server (a
development reload) removes the listeners of the previous one before adding its own, and only the first one listens.

`createApi()` mounts the request guard, the `405` table and the JSON charset middleware, defines `/api/health`, then
mounts the routes of each domain from `server/routes/<domain>.ts` with `.route('/', …)`: `settingsRoutes`,
`profileRoutes`, `serverRoutes`, `monitorRoutes`, `topologyRoutes`, `setupRoutes`, `modelRoutes`, `hfRoutes`,
`tuningRoutes`, `chatRoutes`, `benchRoutes` and `sweepRoutes`. An unknown API path gets `404` with
`{ "error": "Unknown route" }` (Hono's `notFound`), so it never receives the app's HTML, and whatever a route throws
goes through `onError`.

Each route module exports a function that takes only the dependencies it needs and returns a chained `Hono` app:

```ts title="server/routes/topology.ts"
export const topologyRoutes = ({ placement }: TopologyRouteDeps) =>
  new Hono<Env>().get('/api/topology', async (c) =>
    c.json({ graph: await readPciTopology(), placement: placement.current }),
  );
```

`errorResponse()` (`server/http.ts`) turns an exception into a JSON response: an `HttpError` keeps its status and
returns `{ error, code? }`, a `ZodError` becomes a `400` with the zod `issues`, invalid JSON a `400`, and anything
else a `500` with `Internal error`. The `id()`, `body()` and `json()` validators and `notFound()` are the helpers
routes use for path ids and bodies. The [API overview](/developers/api/overview/) documents the error shape and the
order of the middlewares, the [Security](/developers/server/security/) page the guard.

## Channels to the browser

The browser talks to llama-webui over three channels, all on the same port.

| Channel | Direction | Used for |
| --- | --- | --- |
| REST, `/api/*` | request, response | Every read and every command: settings, profiles, starting the server, launching a benchmark, the history dump, the log replay. JSON in both directions. |
| WebSocket, `/ws` | server to browser | Live state pushed to every open tab: snapshots on every monitor tick, log lines, server state changes, benchmark, sweep and download progress, model placement. |
| SSE, `text/event-stream` | server to browser, per request | Chat generations only: the response of `POST /api/chat/:id/messages`, `POST /api/chat/:id/regenerate` and `GET /api/chat/:id/stream`. |

### WebSocket

There is one hub (`server/ws/hub.ts`) and one connection per tab. The hub sends `hello` with the `bootId` and the
server time when a client connects, then broadcasts every message to every client: there are no subscriptions, the
client dispatches by `type`. Every `PING_INTERVAL_MS = 15_000` ms the hub sends `ping`; a client that leaves
`MAX_MISSED_PINGS = 2` pings unanswered is closed with code `4000`. The messages are the `WsMessage` union of
`packages/webui-shared/src/ws.ts`, listed on the [WebSocket](/developers/api/websocket/) page.

The WebSocket only carries changes. After every (re)connection, the web app reads the current state again over REST,
and the `bootId` tells it whether the process restarted in between ([Web app](/developers/frontend/) describes the
client).

### SSE for chat

A chat generation belongs to the server, not to the HTTP request (see [Chat runs](/developers/server/chat/)). The SSE
response only subscribes to the run: events `start`, `delta` and `done` (`ChatEvent` in `packages/webui-shared/src/chat.ts`,
formatted by `formatSse()`), plus a `: ping` comment every `PING_MS = 15_000` ms: a long prompt can be processed
without sending anything, and a proxy may drop a silent connection (Node's own server has no idle timeout). A client
that leaves only unsubscribes; the generation goes on, and `GET /api/chat/:id/stream` attaches to it again.

## Serving the UI

One `vite.config.ts` at the root of the repository describes both halves of the app: the web client (`web/`, with
`@vitejs/plugin-react` and `@tailwindcss/vite`) and the server (`server/main.ts`). `server/index.ts` picks the web
handler `mount()` sends every other path to.

### Development

`pnpm dev` runs `node server/dev.ts`. `startDev()` creates the `node:http` server and a Vite server in middleware mode
(`appType: 'spa'`), whose HMR WebSocket shares that HTTP server, then publishes both on
`globalThis.__llamaWebuiDevHost = { http, web }`. The web handler is Vite's middlewares: the UI is transformed on
request, with hot module replacement. The server entry, `server/index.ts`, is evaluated by the module runner of
Vite's `ssr` environment (see [The development reload pitfall](#the-development-reload-pitfall)).

### Production

`pnpm start` runs `pnpm build`, then `node dist/server/main.js`. `vite build` writes three outputs:

- the client, `web/` → `dist/web`, split per page: each page loads only its own chunks, so the Topology page's
  three.js (about 1 MB) stays out of the others;
- the server, `server/main.ts` → `dist/server/main.js`, one file with its dependencies bundled, except `hono`,
  `@hono/node-server` and `ws`, the network-facing ones, which stay `dependencies` installed with the app. The
  licenses of the bundled code are written next to it, in `THIRD-PARTY-LICENSES.md`;
- the NVML worker, `server/collectors/nvml/worker.ts` → `dist/server/nvml-worker.js`, next to `main.js`, which starts
  it. It has its own environment (`nvml`, build only): Rolldown takes a single input when code splitting is off, and
  development runs the worker's sources as is.

The build also replaces `LLAMA_WEBUI_VERSION` (a `define`) with `git describe --tags --always --dirty`, or the version
of `package.json` without git. It becomes `APP_VERSION` (`server/version.ts`), which `/api/health` reports and the
status bar shows: the tag, else the short commit hash. In development, it is `dev`.

At startup, `staticWeb()` in `server/routes/web.ts` reads `dist/web` (next to the bundle: `dist/server/main.js` →
`dist/web`) into memory once. A file's exact path is served with `Cache-Control: public, max-age=31536000, immutable`
(the names are content-hashed). Any other path gets `index.html` with `Cache-Control: no-cache`, since it points to
the current chunks.

If `dist/web` is missing or unreadable, `unavailableWeb()` serves a `503` with the error for every page until the next
startup. The API, the WebSocket and `llama-server` control keep working.

## Launch options

`server/cli.ts` reads three options, each from a flag, else its environment variable, else a default. An empty
variable counts as unset.

| Flag | Variable | Default |
| --- | --- | --- |
| `--host <address>` | `LLAMA_WEBUI_HOST` | `DEFAULT_HOST = '127.0.0.1'` |
| `--port <port>` | `LLAMA_WEBUI_PORT` | `DEFAULT_PORT = 7860` (an integer from 1 to 65535) |
| `--data-dir <path>` | `LLAMA_WEBUI_DATA_DIR` | `$XDG_DATA_HOME/llama-webui`, else `~/.local/share/llama-webui` (`dataDir()` in `server/paths.ts`) |

`parseCli()` is pure: it takes the arguments and the environment and returns `run`, `help` or `error`, which keeps it
testable. `cliOptionsOrExit()` prints `HELP_TEXT` and exits with code 0 for `-h`/`--help`, or prints the error and the
help and exits with code 2. The options are read again on every development reload, with the same arguments. User-facing
details are on [Launch options](/docs/configuration/).

## Shutdown

Two handlers run on `SIGINT` and `SIGTERM`:

1. The one `server/index.ts` installs with `process.prependListener`, so it runs first: `chatRuns.dispose()` saves each
   running reply as `stopped` and closes its SSE streams, `benchRunner.dispose({ restart: false })` kills the running
   benchmark and marks it (and its sweep) `interrupted`, and `downloads.dispose()` stops the running download, keeping
   its `.part` file. It runs before the runtime's handler stops `llama-server`, otherwise the replies would see the
   disconnection and end as errors.
2. The runtime's handler, installed once by `getRuntime()`: it stops the monitor, stops the managed `llama-server`
   (`SIGTERM`, then `SIGKILL` after 5 seconds), and exits with code 0. A second signal during this stop is ignored.

A `process.on('exit')` handler also kills the managed server with `SIGKILL` as a last resort. If the process dies without
running any handler, `setpriv --pdeathsig KILL` makes the kernel kill `llama-server` and `llama-bench` with it. On the
next start, the orphan cleanup of the [startup sequence](#startup-sequence) settles whatever was left `streaming` or
`running`.

## The development reload pitfall

`pnpm dev` watches `server/` and `packages/`. On every save there, the module runner of `server/dev.ts` evaluates
`server/index.ts` and the modules it imports again, inside the same process: `globalThis` survives, module-level
state does not. Without care, each save would create a new supervisor that has lost track of the running
`llama-server`, and kill or orphan the loaded model.

A reload that fails (a syntax error, an import of a missing file) leaves the previous instance serving, and the next
save that fixes it reloads again. A first evaluation that fails (`pnpm dev` started while a file is broken) waits the
same way, with nothing listening yet; only a listen error (port taken) ends `pnpm dev`. `server/dev.ts` also replays a change its file watcher drops, a second write less
than 50 ms after the first (a format on save), so the reload always runs the last content.

### What survives a reload

`getRuntime()` keeps one `Runtime` object on `globalThis.__llamaWebuiRuntime`:

```ts title="server/runtime.ts"
export interface Runtime {
  supervisor: Supervisor;
  logs: LogBuffer;
  /** ID of this llama-webui boot (stable across development reloads): the client ties log numbering to it. */
  bootId: string;
  /** Always-on monitoring, started once by startMonitor() (also survives development reloads). */
  monitor: Promise<Monitor> | null;
  /** Server gate during benchmarks: held across a reload, so a sweep resumes without a restart. */
  benchGate: BenchGate;
}
```

- `supervisor`: the managed `llama-server`, its state and its child process.
- `logs`: the `LogBuffer` ring of 10,000 lines.
- `bootId`: `crypto.randomUUID()`, generated once per process. The client compares it to detect a real restart.
- `monitor`: the `Monitor`, with its collectors and the NVML worker thread, started once by `startMonitor()`.
- `benchGate` (`server/bench/gate.ts`): the gate that stops the managed server for a benchmark and restarts it
  afterwards. It is held across a reload so that a sweep continues in the new module without restarting the server in
  between.

The shutdown signal handlers are installed once, with the runtime. The development host
(`globalThis.__llamaWebuiDevHost`: the HTTP server and Vite's middlewares) belongs to `server/dev.ts` and is never
re-evaluated: every evaluation of `server/index.ts` mounts on it again.

### Files that need a full restart

These objects were built from the first evaluation of their modules. After a reload the new code is loaded, but the
live objects keep running the old one, along with the modules they imported at startup. A change to these files
therefore has no effect until the process restarts:

- `server/supervisor/supervisor.ts`, and what it imports: `llamacpp-js/client` (`probeHealth()`), `llamacpp-js/node`
  (`findLlamaServerPid()`) and `server/logs/lines.ts` (`LineSplitter`)
- `server/logs/buffer.ts`
- `server/bench/gate.ts`
- `server/monitor/**`, except `server/monitor/placement.ts` (the `PlacementTracker` is recreated on every reload)
- `server/collectors/**`
- `packages/llamacpp-js/src/**`, imported by the supervisor and the monitor (`fetchLlama()`, the `/metrics` math)
- `server/proc.ts`, imported by the supervisor and the collectors (`spawnProc()`, `readText()`)
- `server/runtime.ts`

After changing any of them, stop `pnpm dev` with <Kbd>Ctrl</Kbd> + <Kbd>C</Kbd> and run it again.

### What a reload recreates

Everything else `server/index.ts` and `createDeps()` build is created again: the database connection, the WebSocket hub, the repositories,
`ChatRuns`, `RunExecutor`, `BenchRunner`, the Hugging Face client, the `DownloadQueue`, the `PlacementTracker` and the
listeners `mount()` puts on the HTTP server. Once it has mounted them, the new evaluation calls the dispose function
the previous one left on `globalThis`.
It clears the external server timer, unsubscribes from the supervisor, the logs, the monitor and the placement,
removes its signal handlers, disposes the hub (every socket is closed with code `1001`), `ChatRuns`, the bench runner
and the download queue, and closes the database.

Work in progress at that moment ends differently depending on its kind:

| In progress | During a reload |
| --- | --- |
| A chat generation | Interrupted. The partial reply is saved as `stopped` and its SSE streams receive `done`. `llama-server` keeps running. |
| A one-off benchmark run | Interrupted. Its child process is killed and the run is saved as `interrupted`. If the gate had stopped `llama-server` for it, the gate restarts it once the child has exited and a grace period of 3 seconds (`adoptGraceMs`) has passed without a new module taking the gate over. |
| A sweep | Continues. The running item goes back to the queue and the sweep stays `running`. The new runner takes the gate over (`benchGate.adopt()`), waits for the killed child to exit so the replayed item does not share the GPUs with it, and replays the item. The server is only restarted at the end of the sweep. If the reload took longer than the grace period, the sweep is marked `interrupted` and can be resumed from the UI. |
| A download | Stops. Its `.part` file and its database row stay, and the new queue resumes it. |
| Open tabs | Their WebSocket is closed. They reconnect to the new hub, receive `hello` with the same `bootId`, and read the state again over REST. |

### Errors are compared by name

A class defined in a module is a different class after a reload. The supervisor is created once, so it throws the
`SupervisorError` of the first evaluation, while the reloaded `server/routes/server.ts` imports the new class:
`instanceof` would be `false`. The route compares the error's `name` instead:

```ts title="server/routes/server.ts"
if (e instanceof Error && e.name === 'SupervisorError') throw new HttpError(409, e.message);
```

`SupervisorError` sets `override name = 'SupervisorError'` for this. Apply the same rule to any error thrown by an
object that lives in the runtime.

`HttpError` does the same (`override name = 'HttpError'`): the bench gate lives in the runtime and throws the class
of the first evaluation of `server/http.ts`, so `errorResponse()` recognizes it with `isHttpError()` (its `name` and a
numeric `status`) rather than `instanceof`. Its refusals keep their `409` and `code: "server-running"` after a reload.
