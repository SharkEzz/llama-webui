llama-webui is one Bun process. `server/index.ts` builds every service and `server/app.ts` hands them to `Bun.serve`,
which serves the web UI, the REST API under `/api/*` and the `/ws` WebSocket on one port (7860 by default). The same
process supervises one `llama-server`, samples the hardware, runs benchmarks and relays chat generations.

## Startup sequence

`server/index.ts` is the entry point of both `bun run dev` and `bun run start`. Under `bun --hot` it is evaluated again
on every reload, so it is written to run more than once. In order, it:

1. Reads the launch options with `cliOptionsOrExit()` (see [Launch options](#launch-options)).
2. Calls `globalThis.__llamaWebuiDispose()` if a previous evaluation left one, to release that instance (see
   [What a reload recreates](#what-a-reload-recreates)).
3. Opens the database with `openDb(dbPath(cli.dataDir))`: creates the data directory, opens
   `llama-webui.sqlite` with `bun:sqlite`, sets `journal_mode = WAL` and `foreign_keys = ON`, and runs the migrations.
4. Gets the runtime with `getRuntime()` (`server/runtime.ts`): the supervisor, the log ring, the boot id and the bench
   gate, created on the first call and kept on `globalThis` afterwards.
5. Creates the `WsHub` with the runtime's `bootId`, and the settings, profiles and conversations repositories. Chat
   replies left `streaming` by a killed process are marked `stopped` (`conversations.stopOrphans()`).
6. Creates `ChatRuns`. Its `target()` sends generations to the managed server when it is `ready`, or to an external
   server.
7. Prepares the web routes: the HTML import in development and in the standalone executable, `Bun.build` in
   production from source (see [Serving the UI](#serving-the-ui)).
8. Starts the monitor with `startMonitor()`, once per process: later calls return the running one.
9. Creates the bench repositories, the `RunExecutor` and the `BenchRunner`, and calls `benchRunner.resume()`. On a cold
   start (bench gate not held), runs and sweeps left `running` are first marked `interrupted`.
10. Creates the Hugging Face client and the `DownloadQueue`, and calls `downloads.resume()` to pick up the items left
    queued or downloading.
11. Creates the `PlacementTracker`, which replays the log ring to find the loaded model's placement.
12. Calls `createApp()`, which starts `Bun.serve`.
13. Subscribes the WebSocket hub to the services (table below), installs its shutdown handler, starts the external
    server watcher, and stores its own dispose function in `globalThis.__llamaWebuiDispose`.

It finally prints `llama-webui on http://<host>:<port>`, followed by `(dev, HMR)` in development.

The services do not know about the WebSocket: `index.ts` passes them callbacks or subscribes to them, and broadcasts
each event as a `WsMessage` to every client. The benchmark and sweep routes also broadcast directly when they delete
runs.

| Source | Messages |
| --- | --- |
| `supervisor.subscribe()` | `server-state` |
| `logs.onLines()` | `log` |
| `monitor.onSnapshot()` | `snapshot` |
| `placement.onChange()` | `placement` |
| `BenchRunner` callbacks | `bench-progress`, `bench-run`, `sweep`, `sweep-progress` |
| `DownloadQueue` callbacks | `download`, `download-progress`, `download-deleted` |
| `server/routes/bench.ts`, `server/routes/sweeps.ts` | `bench-deleted`, `sweep-deleted` |

The external server watcher (`externalWatcher()` in `server/supervisor/external.ts`) runs at startup, then every
`EXTERNAL_CHECK_MS = 2000` ms. It is paused while the bench gate is held or the bench runner is busy, because the
`llama-server` a benchmark starts on the settings port is not an external server.

## Routes

`createApp()` in `server/app.ts` passes a single `routes` object to `Bun.serve`:

- `/api/health` and `/api/settings`, defined in `app.ts` itself;
- the routes of each domain, spread from `server/routes/<domain>.ts`: `profileRoutes`, `serverRoutes`,
  `monitorRoutes`, `modelRoutes`, `hfRoutes`, `chatRoutes`, `benchRoutes`, `sweepRoutes`, `tuningRoutes`,
  `topologyRoutes` and `setupRoutes`;
- `/api/*`, a catch-all that answers `404` with `{ "error": "Unknown route" }`, so an unknown API path never receives
  the app's HTML;
- `/ws`, which upgrades the request to a WebSocket or answers `426`;
- the web routes, last: the UI files and the SPA fallback `/*`, so reloading `/chat/12` serves the app.

Each route module exports a function that takes only the dependencies it needs and returns paths mapped to handlers
by method. Every handler, `/ws` included, is wrapped in `guarded()`:

```ts title="server/routes/topology.ts"
export function topologyRoutes({ placement }: TopologyRouteDeps) {
  return {
    '/api/topology': {
      GET: guarded(async () => Response.json({ graph: await readPciTopology(), placement: placement.current })),
    },
  };
}
```

`guarded()` (`server/http.ts`) runs `guard()` from `server/security.ts` first (Host header, Origin, JSON-only writes),
then the handler, and turns any exception into a JSON response: an `HttpError` keeps its status and returns
`{ error, code? }`, a `ZodError` becomes a `400` with the zod `issues`, a JSON `SyntaxError` a `400`, and anything else
a `500` with `Internal error`. `idParam()`, `jsonObject()` and `notFound()` are the helpers routes use for path ids
and bodies. The [API overview](/developers/api/overview/) documents the error shape and the
[Security](/developers/server/security/) page the guard.

## Channels to the browser

The browser talks to llama-webui over three channels, all on the same port.

| Channel | Direction | Used for |
| --- | --- | --- |
| REST, `/api/*` | request, response | Every read and every command: settings, profiles, starting the server, launching a benchmark, the history dump, the log replay. JSON in both directions. |
| WebSocket, `/ws` | server to browser | Live state pushed to every open tab: snapshots on every monitor tick, log lines, server state changes, benchmark, sweep and download progress, model placement. |
| SSE, `text/event-stream` | server to browser, per request | Chat generations only: the response of `POST /api/chat/:id/messages`, `POST /api/chat/:id/regenerate` and `GET /api/chat/:id/stream`. |

### WebSocket

There is one hub (`server/ws/hub.ts`) and one connection per tab. The hub sends `hello` with the `bootId` and the
server time when a client connects, then broadcasts every message to every client: there are no subscriptions, the
client dispatches by `type`. Every `PING_INTERVAL_MS = 15_000` ms the hub sends `ping`; a client that leaves
`MAX_MISSED_PINGS = 2` pings unanswered is closed with code `4000`. The messages are the `WsMessage` union of
`packages/webui-shared/src/ws.ts`, listed on the [WebSocket](/developers/api/websocket/) page.

The WebSocket only carries changes. After every (re)connection, the web app reads the current state again over REST,
and the `bootId` tells it whether the process restarted in between ([Web app](/developers/frontend/) describes the
client).

### SSE for chat

A chat generation belongs to the server, not to the HTTP request (see [Chat runs](/developers/server/chat/)). The SSE
response only subscribes to the run: events `start`, `delta` and `done` (`ChatEvent` in `packages/webui-shared/src/chat.ts`,
formatted by `formatSse()`), plus a `: ping` comment every `PING_MS = 15_000` ms. Bun closes a connection that stays
silent for 10 seconds, so the route also disables the idle timeout for this request (`server.timeout(req, 0)`): a long
prompt can be processed without sending anything. A client that leaves only unsubscribes; the generation goes on, and
`GET /api/chat/:id/stream` attaches to it again.

## Serving the UI

From source, the UI is never built ahead of time. `server/index.ts` picks one of three route sets: the HTML import
in development, a build at startup in production, and the HTML import again, bundled at compile time, in the
standalone executable (`Bun.isStandaloneExecutable`).

### Development

`server/index.ts` imports `web/index.html` and serves it as `{ '/*': index }`. `Bun.serve` bundles the page on the fly,
with hot module replacement and the browser console streamed to the terminal
(`development: { hmr: true, console: true }`). Tailwind comes from `bun-plugin-tailwind`, declared in `bunfig.toml`
under `[serve.static]`.

### Production

With `NODE_ENV=production`, `buildWebRoutes()` in `server/routes/web.ts` builds the front end once, at startup, in
memory:

```ts title="server/routes/web.ts"
export const WEB_BUILD_OPTIONS = {
  splitting: true,
  minify: true,
  // Absolute paths: a deep URL (/chat/12) must not look for its chunks under /chat/.
  publicPath: '/',
  define: { 'process.env.NODE_ENV': '"production"' },
} as const satisfies Partial<Bun.BuildConfig>;

const result = await Bun.build({
  ...WEB_BUILD_OPTIONS,
  entrypoints: [entry],
  target: 'browser',
  plugins: await webPlugins(), // [tailwind], imported lazily
});
```

Each output file becomes a route at `/<name>` with `Cache-Control: public, max-age=31536000, immutable` (the names are
content-hashed). The HTML becomes the `/*` fallback with `Cache-Control: no-cache`, since it points to the current
chunks. Nothing is written to disk.

`Bun.serve`'s HTML import would also bundle the page in production, but into a single file: it ignores code splitting
and inlines the router's `import()` calls, so every page would load everything, including the Topology page's
three.js (about 1 MB). `Bun.build` splits, so each page loads only its own chunks. The `[serve.static]` plugins of
`bunfig.toml` only apply to the HTML import, so a Bun plugin added there must also be added to `webPlugins()`, which
both this build and the executable's use.

If the build fails (a broken import, a failing plugin), `unavailableWebRoutes()` serves a `503` with the error for
every page until the next startup. The API, the WebSocket and `llama-server` control keep working.

### Standalone executable

`bun run compile` (`scripts/compile.ts`) runs `Bun.build` with `compile` on `server/index.ts`, with the same
`WEB_BUILD_OPTIONS` and `webPlugins()`. The `web/index.html` import is then bundled at compile time, split per page
(unlike the on-the-fly bundling of `Bun.serve`) and embedded under `/$bunfs/root/`; `Bun.serve` serves that manifest
from `{ '/*': index }`, with an ETag per file. The `define` also replaces `process.env.NODE_ENV` in the server code,
so the executable always runs in production, without HMR. A second constant, `LLAMA_WEBUI_VERSION`, carries
`git describe --tags --always --dirty` (or `--version <name>`) into `APP_VERSION` (`server/version.ts`), which
`/api/health` reports and the status bar shows: the tag, else the short commit hash. From source, it is `dev`.

Inside the executable, `import.meta.dirname` is `/$bunfs/root`, so nothing may read the source tree at runtime:

- the startup build is skipped, and `bun-plugin-tailwind` (with its native binding) is imported lazily by
  `webPlugins()` and marked `external`, so it stays out of the binary;
- the NVML worker (`server/collectors/nvml/worker.ts`) is a second compile entrypoint. Bundled, `monitor.ts` lives in
  the entrypoint, so `workerUrl()` resolves the worker against `Bun.main` (`collectors/nvml/worker.ts`, relative to
  `server/`, the entrypoints' root) instead of `import.meta.url`. Without it, NVML would silently fall back to
  `nvidia-smi`;
- `bunfig.toml` autoloading is off (`autoloadBunfig: false`); `.env` in the working directory is still loaded, as
  with `bun run start`.

`.github/workflows/release.yml` builds `llama-webui-linux-x64` and `llama-webui-linux-arm64` for every `v*` tag,
smoke-tests the x64 one and attaches both, with `SHA256SUMS`, to the GitHub Release.

## Launch options

`server/cli.ts` reads three options, each from a flag, else its environment variable, else a default. An empty
variable counts as unset.

| Flag | Variable | Default |
| --- | --- | --- |
| `--host <address>` | `LLAMA_WEBUI_HOST` | `DEFAULT_HOST = '127.0.0.1'` |
| `--port <port>` | `LLAMA_WEBUI_PORT` | `DEFAULT_PORT = 7860` (an integer from 1 to 65535) |
| `--data-dir <path>` | `LLAMA_WEBUI_DATA_DIR` | `$XDG_DATA_HOME/llama-webui`, else `~/.local/share/llama-webui` (`dataDir()` in `server/paths.ts`) |

`parseCli()` is pure: it takes the arguments and the environment and returns `run`, `help` or `error`, which keeps it
testable. `cliOptionsOrExit()` prints `HELP_TEXT` and exits with code 0 for `-h`/`--help`, or prints the error and the
help and exits with code 2. The options are read again on every `bun --hot` reload, with the same arguments. User-facing
details are on [Launch options](/docs/configuration/).

## Shutdown

Two handlers run on `SIGINT` and `SIGTERM`:

1. The one `server/index.ts` installs with `process.prependListener`, so it runs first: `chatRuns.dispose()` saves each
   running reply as `stopped` and closes its SSE streams, `benchRunner.dispose({ restart: false })` kills the running
   benchmark and marks it (and its sweep) `interrupted`, and `downloads.dispose()` stops the running download, keeping
   its `.part` file. It runs before the runtime's handler stops `llama-server`, otherwise the replies would see the
   disconnection and end as errors.
2. The runtime's handler, installed once by `getRuntime()`: it stops the monitor, stops the managed `llama-server`
   (`SIGTERM`, then `SIGKILL` after 5 seconds), and exits with code 0. A second signal during this stop is ignored.

A `process.on('exit')` handler also kills the managed server with `SIGKILL` as a last resort. If Bun dies without
running any handler, `setpriv --pdeathsig KILL` makes the kernel kill `llama-server` and `llama-bench` with it. On the
next start, the orphan cleanup of the [startup sequence](#startup-sequence) settles whatever was left `streaming` or
`running`.

## The `bun --hot` pitfall

`bun run dev` runs under `bun --hot`. On every save, Bun resets its module registry and evaluates every module again,
inside the same process: `globalThis` survives, module-level state does not. Without care, each save would create a
new supervisor that has lost track of the running `llama-server`, and kill or orphan the loaded model.

### What survives a reload

`getRuntime()` keeps one `Runtime` object on `globalThis.__llamaWebuiRuntime`:

```ts title="server/runtime.ts"
export interface Runtime {
  supervisor: Supervisor;
  logs: LogBuffer;
  /** ID of this llama-webui boot (stable across bun --hot): the client ties log numbering to it. */
  bootId: string;
  /** Always-on monitoring, started once by startMonitor() (also survives bun --hot). */
  monitor: Promise<Monitor> | null;
  /** Server gate during benchmarks: held across a reload, so a sweep resumes without a restart. */
  benchGate: BenchGate;
}
```

- `supervisor`: the managed `llama-server`, its state and its child process.
- `logs`: the `LogBuffer` ring of 10,000 lines.
- `bootId`: `crypto.randomUUID()`, generated once per process. The client compares it to detect a real restart.
- `monitor`: the `Monitor`, with its collectors and the NVML worker, started once by `startMonitor()`.
- `benchGate` (`server/bench/gate.ts`): the gate that stops the managed server for a benchmark and restarts it
  afterwards. It is held across a reload so that a sweep continues in the new module without restarting the server in
  between.

The shutdown signal handlers are installed once, with the runtime.

### Files that need a full restart

These objects were built from the first evaluation of their modules. After a reload the new code is loaded, but the
live objects keep running the old one, along with the modules they imported at startup. A change to these files
therefore has no effect until Bun restarts:

- `server/supervisor/supervisor.ts`, and what it imports: `llamacpp-js/client` (`probeHealth()`), `llamacpp-js/node`
  (`findLlamaServerPid()`) and `server/logs/lines.ts` (`LineSplitter`)
- `server/logs/buffer.ts`
- `server/bench/gate.ts`
- `server/monitor/**`, except `server/monitor/placement.ts` (the `PlacementTracker` is recreated on every reload)
- `server/collectors/**`
- `packages/llamacpp-js/src/**`, imported by the supervisor and the monitor (`fetchLlama()`, the `/metrics` math)
- `server/runtime.ts`

After changing any of them, stop Bun with <Kbd>Ctrl</Kbd> + <Kbd>C</Kbd> and run `bun run dev` again.

### What a reload recreates

Everything else in `server/index.ts` is created again: the database connection, the WebSocket hub, the repositories,
`ChatRuns`, `RunExecutor`, `BenchRunner`, the Hugging Face client, the `DownloadQueue`, the `PlacementTracker` and the
`Bun.serve` routes. Before that, the new evaluation calls the dispose function the previous one left on `globalThis`.
It clears the external server timer, unsubscribes from the supervisor, the logs, the monitor and the placement,
removes its signal handlers, disposes the hub (every socket is closed with code `1001`), `ChatRuns`, the bench runner
and the download queue, and closes the database.

Work in progress at that moment ends differently depending on its kind:

| In progress | During a reload |
| --- | --- |
| A chat generation | Interrupted. The partial reply is saved as `stopped` and its SSE streams receive `done`. `llama-server` keeps running. |
| A one-off benchmark run | Interrupted. Its child process is killed and the run is saved as `interrupted`. If the gate had stopped `llama-server` for it, the gate restarts it once the child has exited and a grace period of 3 seconds (`adoptGraceMs`) has passed without a new module taking the gate over. |
| A sweep | Continues. The running item goes back to the queue and the sweep stays `running`. The new runner takes the gate over (`benchGate.adopt()`), waits for the killed child to exit so the replayed item does not share the GPUs with it, and replays the item. The server is only restarted at the end of the sweep. If the reload took longer than the grace period, the sweep is marked `interrupted` and can be resumed from the UI. |
| A download | Stops. Its `.part` file and its database row stay, and the new queue resumes it. |
| Open tabs | Their WebSocket is closed. They reconnect to the new hub, receive `hello` with the same `bootId`, and read the state again over REST. |

### Errors are compared by name

A class defined in a module is a different class after a reload. The supervisor is created once, so it throws the
`SupervisorError` of the first evaluation, while the reloaded `server/routes/server.ts` imports the new class:
`instanceof` would be `false`. The route compares the error's `name` instead:

```ts title="server/routes/server.ts"
if (e instanceof Error && e.name === 'SupervisorError') throw new HttpError(409, e.message);
```

`SupervisorError` sets `override name = 'SupervisorError'` for this. Apply the same rule to any error thrown by an
object that lives in the runtime.

`HttpError` does the same (`override name = 'HttpError'`): the bench gate lives in the runtime and throws the class
of the first evaluation of `server/http.ts`, so `errorResponse()` recognizes it with `isHttpError()` (its `name` and a
numeric `status`) rather than `instanceof`. Its refusals keep their `409` and `code: "server-running"` after a reload.

### New files in web/src

The development bundler may not see a file created under `web/src/` after `bun run dev` started: the import fails with
"Could not resolve" while `bun check` passes. Restart `bun run dev`.
