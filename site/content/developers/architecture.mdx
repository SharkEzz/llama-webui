description: The single Node.js process behind llama-webui, its startup and shutdown, the REST, WebSocket and SSE channels, UI serving, and how development restarts it.
---

llama-webui is one Node.js process (Node 26.13 or later). `server/index.ts` builds every service and `mount()`
(`server/host.ts`) puts them on one `node:http` server, which serves the web UI, the REST API under `/api/*` and the
`/ws` WebSocket on one port (7860 by default). The same process supervises one `llama-server`, samples the hardware,
runs benchmarks and relays chat generations.

## Startup sequence

`server/index.ts` is the composition root of both `pnpm dev` and `pnpm start`: it exports `start()`, which runs once
per process. In development, `server/dev.ts` evaluates it and calls `start()` with its HTTP server and Vite's
middlewares. In production, `server/main.ts` (bundled to `dist/server/main.js`) sets `NODE_ENV` to `production` if it
is unset, imports it and calls `start()`. Both entry points first load `.env` from the working directory
(`loadDotEnv()`, `server/env.ts`): its variables fill what the environment lacks, and replace it too with
`--env-override` (read from the arguments before they are parsed) or `LLAMA_WEBUI_ENV_OVERRIDE=1`. Only that file is
read (no `.env.local`, no per-mode file), and `parseEnv()` does not expand `$VAR` references. They then call
`useEnvProxy()` (same file): with `HTTP_PROXY` or `HTTPS_PROXY` set, `fetch` goes through that proxy, loopback excepted
(see [Hugging Face](/developers/server/hugging-face/)). In order, `start()`:

1. Opens an `AsyncDisposableStack` with `await using`. Each step below registers what undoes it on that stack as soon
   as it has built it (see [Shutdown](#shutdown)).
2. Reads the launch options with `cliOptionsOrExit()` (see [Launch options](#launch-options)).
3. Opens the database with `openDb(dbPath(cli.dataDir))`: creates the data directory, opens
   `llama-webui.sqlite` with `node:sqlite`, sets `journal_mode = WAL` and `foreign_keys = ON`, and runs the migrations.
4. Creates the runtime with `createRuntime()` (`server/runtime.ts`): the supervisor, the log ring of 10,000 lines, the
   boot id (`crypto.randomUUID()`) and the bench gate. It only builds them; `start()` also installs the
   `process.on('exit')` last resort that kills the managed server.
5. Prepares the web handler: Vite's middlewares in development, the files of `pnpm build` in production (see
   [Serving the UI](#serving-the-ui)).
6. Starts the monitor with `startMonitor()`.
7. Calls `createDeps()` (`server/deps.ts`), which only constructs and wires the services, without starting any work:
   the `WsHub` with the runtime's `bootId`; the settings, profiles, conversations, bench run, sweep and download
   repositories; `ChatRuns`, whose `target()` sends generations to the managed server when it is `ready`, or to an
   external server; the `RunExecutor` and the `BenchRunner`; the Hugging Face client and the `DownloadQueue`; and the
   `PlacementTracker`, which replays the log ring to find the loaded model's placement.
8. Calls `mount()` with the API (`createApi(deps).fetch`), the hub and the web handler, on the development host's
   HTTP server or on a new one, and listens on the port (see [Routes](#routes)).
9. Marks the chat replies left `streaming` by the previous process as `stopped` (`conversations.stopOrphans()`), and
   the runs and sweeps it left `running` as `interrupted`.
10. Gives the monitor the profile → model path resolver it uses for the model's disk.
11. Calls `downloads.resume()` to pick up the items left queued or downloading.
12. Subscribes the WebSocket hub to the services (table below) and starts the external server watcher.
13. Takes the stack out of the `await using` (`stack.move()`) and installs the shutdown handler on `SIGINT` and
    `SIGTERM`.

If a step throws before the last one (the port is taken, for instance), the `await using` undoes what was already
built and the error ends the process.

It finally prints `llama-webui on http://<host>:<port>`, followed by `(dev)` in development or by the version
in production.

The services do not know about the WebSocket: `index.ts` passes them callbacks or subscribes to them, and broadcasts
each event as a `WsMessage` to every client. The benchmark and sweep routes also broadcast directly when they delete
runs.

| Source | Messages |
| --- | --- |
| `supervisor.subscribe()` | `server-state` |
| `logs.onLines()` | `log` |
| `monitor.onSnapshot()` | `snapshot` |
| `placement.onChange()` | `placement` |
| `BenchRunner` callbacks | `bench-progress`, `bench-run`, `sweep`, `sweep-progress` |
| `DownloadQueue` callbacks | `download`, `download-progress`, `download-deleted` |
| `server/routes/bench.ts`, `server/routes/sweeps.ts` | `bench-deleted`, `sweep-deleted` |

The external server watcher (`externalWatcher()` in `server/supervisor/external.ts`) runs at startup, then every
`EXTERNAL_CHECK_MS = 2000` ms. It is paused while the bench gate is held or the bench runner is busy, because the
`llama-server` a benchmark starts on the settings port is not an external server.

## Routes

The HTTP server comes from `createHostServer()` (`server/hostServer.ts`): `createAdaptorServer()` of
`@hono/node-server`, the Hono adapter for Node, with the `WebSocketServer({ noServer: true })` of the `ws` library
for its WebSocket upgrades. Requests and upgrades alike go to the Hono app `mount()` (`server/host.ts`) put on the
server, which routes them by path:

- `/api/*`, handed to the [Hono](https://hono.dev) app built by `createApi()` (`server/api.ts`). `/api` alone is not an
  API path;
- `/ws`: `guard()` first, then `upgradeWebSocket()` of `@hono/node-server`, which hands the socket to the `WsHub`
  (`hubEvents()`, `server/ws/attach.ts`); a request without an upgrade gets `426`. An upgrade the guard refuses is never
  handed over as one (`shouldUpgradeCallback`): it stays a plain request, answered by the guard on a connection the
  server closes. A client message over 4,096 bytes (`maxPayload`: the protocol only has `ping` and `pong`) closes the
  socket with code `1009`;
- anything else, to the web handler: the UI files and the SPA fallback, so reloading `/chat/12` serves the app.

Only a WebSocket upgrade takes the upgrade route: `mount()` sets the server's `shouldUpgradeCallback`, so a request with
another `Upgrade` header (`h2c`, which `curl --http2` sends) is a plain request. An upgrade on another path is refused
with a `404`, unless another `upgrade` listener is there: in development, Vite's HMR WebSocket takes its own. A `Host`
header that is not an authority never reaches the app: the HTTP adapter cannot build the request and answers `400`
without a body.

`createApi()` mounts the request guard and the `405` table, defines `/api/health`, then
mounts the routes of each domain from `server/routes/<domain>.ts` with `.route('/', …)`: `settingsRoutes`,
`profileRoutes`, `serverRoutes`, `monitorRoutes`, `topologyRoutes`, `setupRoutes`, `modelRoutes`, `hfRoutes`,
`tuningRoutes`, `chatRoutes`, `benchRoutes` and `sweepRoutes`. An unknown API path gets `404` with
`{ "error": "Unknown route" }` (Hono's `notFound`), so it never receives the app's HTML, and whatever a route throws
goes through `onError`.

Each route module exports a function that takes only the dependencies it needs and returns a chained `Hono` app:

```ts title="server/routes/topology.ts"
export const topologyRoutes = ({ placement }: TopologyRouteDeps) =>
  new Hono<Env>().get('/api/topology', async (c) =>
    c.json({ graph: await readPciTopology(), placement: placement.current }),
  );
```

`errorResponse()` (`server/http.ts`) turns an exception into a JSON response: an `HttpError` keeps its status and
returns `{ error, code? }`, a `ZodError` becomes a `400` with the zod `issues`, invalid JSON a `400`, and anything
else a `500` with `Internal error`. The `id()`, `body()` and `json()` validators and `notFound()` are the helpers
routes use for path ids and bodies. The [API overview](/developers/api/overview/) documents the error shape and the
order of the middlewares, the [Security](/developers/server/security/) page the guard.

## Channels to the browser

The browser talks to llama-webui over three channels, all on the same port.

| Channel | Direction | Used for |
| --- | --- | --- |
| REST, `/api/*` | request, response | Every read and every command: settings, profiles, starting the server, launching a benchmark, the history dump, the log replay. JSON in both directions. |
| WebSocket, `/ws` | server to browser | Live state pushed to every open tab: snapshots on every monitor tick, log lines, server state changes, benchmark, sweep and download progress, model placement. |
| SSE, `text/event-stream` | server to browser, per request | Chat generations only: the response of `POST /api/chat/:id/messages`, `POST /api/chat/:id/regenerate` and `GET /api/chat/:id/stream`. |

### WebSocket

There is one hub (`server/ws/hub.ts`) and one connection per tab. The hub sends `hello` with the `bootId` and the
server time when a client connects, then broadcasts every message to every client: there are no subscriptions, the
client dispatches by `type`. Every `PING_INTERVAL_MS = 15_000` ms the hub sends `ping`; a client that leaves
`MAX_MISSED_PINGS = 2` pings unanswered is closed with code `4000`. The messages are the `WsMessage` union of
`packages/webui-shared/src/ws.ts`, listed on the [WebSocket](/developers/api/websocket/) page.

The WebSocket only carries changes. After every (re)connection, the web app reads the current state again over REST,
and the `bootId` tells it whether the process restarted in between ([Web app](/developers/frontend/) describes the
client).

### SSE for chat

A chat generation belongs to the server, not to the HTTP request (see [Chat runs](/developers/server/chat/)). The SSE
response only subscribes to the run: events `start`, `delta` and `done` (`ChatEvent` in `packages/webui-shared/src/chat.ts`,
written by `streamSSE()` of `hono/streaming`), plus a `: ping` comment every `PING_MS = 15_000` ms: a long prompt can be processed
without sending anything, and a proxy may drop a silent connection (Node's own server has no idle timeout). A client
that leaves only unsubscribes; the generation goes on, and `GET /api/chat/:id/stream` attaches to it again.

## Serving the UI

One `vite.config.ts` at the root of the repository describes both halves of the app: the web client (`web/`, with
`@vitejs/plugin-react` and `@tailwindcss/vite`) and the server (`server/main.ts`). `server/index.ts` picks the web
handler `mount()` sends every other path to.

### Development

`pnpm dev` runs `node --watch-path=server --watch-path=packages --watch-preserve-output server/dev.ts`. `startDev()`
creates the HTTP server (`createHostServer()`) and a Vite server in middleware mode (`appType: 'spa'`), whose HMR
WebSocket shares that HTTP server. The web handler is Vite's middlewares, which answer on Node's own response
(`nodeWeb()`, `server/routes/web.ts`, then `RESPONSE_ALREADY_SENT`): the UI is transformed on request, with hot module
replacement. The server entry, `server/index.ts`, is evaluated once by a module runner of Vite's `ssr` environment
(`createServerModuleRunner(ssr, { hmr: false })`), and `startDev()` calls its `start({ http, web })`. A change to the
server restarts the whole process (see [Development restarts](#development-restarts)).

### Production

`pnpm start` runs `pnpm build`, then `node dist/server/main.js`. `vite build` writes three outputs:

- the client, `web/` → `dist/web`, split per page: each page loads only its own chunks, so the Topology page's
  three.js (about 1 MB) stays out of the others;
- the server, `server/main.ts` → `dist/server/main.js`, one file with its dependencies bundled, except `hono`,
  `@hono/node-server` and `ws`, the network-facing ones, which stay `dependencies` installed with the app. The
  licenses of the bundled code are written next to it, in `THIRD-PARTY-LICENSES.md`;
- the NVML sampler, `server/collectors/nvml/worker.ts` → `dist/server/nvml-worker.js`, next to `main.js`, which starts
  it as a child process. It has its own environment (`nvml`, build only): Rolldown takes a single input when code splitting is off, and
  development runs the worker's sources as is.

The build also replaces `LLAMA_WEBUI_VERSION` (a `define`) with `git describe --tags --always --dirty`, or the version
of `package.json` without git. It becomes `APP_VERSION` (`server/version.ts`), which `/api/health` reports and the
status bar shows: the tag, else the short commit hash. In development, it is `dev`.

At startup, `staticWeb()` in `server/routes/web.ts` reads `dist/web` (next to the bundle: `dist/server/main.js` →
`dist/web`) into memory once. A file's exact path is served with `Cache-Control: public, max-age=31536000, immutable`
(the names are content-hashed). Any other path gets `index.html` with `Cache-Control: no-cache`, since it points to
the current chunks.

If `dist/web` is missing or unreadable, `unavailableWeb()` serves a `503` with the error for every page until the next
startup. The API, the WebSocket and `llama-server` control keep working.

### Distribution

A release is the npm package of the repository's root: `pnpm pack` after `pnpm build` writes
`llama-webui-<version>.tgz` (about 1.5 MB), which `npm install -g ./llama-webui-<version>.tgz` turns into a
`llama-webui` command. The root `package.json` is the packed one:

- `bin` maps `llama-webui` to `dist/server/main.js`, which starts with `#!/usr/bin/env node`. Node runs it from its
  real path, so `dist/web` and `nvml-worker.js` are found next to it even through the link npm creates.
- `files` ships `dist/server` (the bundle, the NVML sampler and `THIRD-PARTY-LICENSES.md`) and `dist/web`, plus the
  `README.md`, `LICENSE` and `package.json` npm always adds; `os` is `linux` and `engines` asks for Node.js 26.13.
- `dependencies` are the three libraries left out of the bundle, `hono`, `@hono/node-server` and `ws`, at exact
  versions (the pnpm catalog): an install from the tarball has no lockfile, and none of the three has dependencies of
  its own, so the installed tree is exactly the one tested. The workspace packages and every other library are
  bundled.

`node scripts/smoke.ts --tarball [file.tgz]` checks the package the way a user gets it: it packs the root (or takes
the given tarball), installs it with npm into an empty prefix, checks that npm installed nothing but the package and
those three versions, then runs the build's smoke checks through `node_modules/.bin/llama-webui`. Packing never
builds: `pnpm pack` runs `scripts/prepack.ts` first, which refuses without `dist/server/main.js`,
`dist/server/nvml-worker.js` and `dist/web/index.html`, so a package without its command cannot be written; run
`pnpm build` before it. CI runs it on every
pull request, and `release.yml` runs it on the tarball it publishes.

Up to v0.2.1, llama-webui ran on Bun and shipped as a standalone executable. The port to Node.js kept the API's answers
but one: the contract suite replays each route against a golden record taken before the move to Hono and to
Node.js, and changed once on purpose (an invalid `Host` gets `403` instead of `500`)
([Testing](/developers/contributing/testing/)).

## Launch options

`server/cli.ts` reads three options, each from a flag, else its environment variable, else a default. An empty
variable counts as unset.

| Flag | Variable | Default |
| --- | --- | --- |
| `--host <address>` | `LLAMA_WEBUI_HOST` | `DEFAULT_HOST = '127.0.0.1'` |
| `--port <port>` | `LLAMA_WEBUI_PORT` | `DEFAULT_PORT = 7860` (an integer from 1 to 65535) |
| `--data-dir <path>` | `LLAMA_WEBUI_DATA_DIR` | `$XDG_DATA_HOME/llama-webui`, else `~/.local/share/llama-webui` (`dataDir()` in `server/paths.ts`) |

`parseCli()` is pure: it takes the arguments and the environment and returns `run`, `help` or `error`, which keeps it
testable. `cliOptionsOrExit()` prints `HELP_TEXT` and exits with code 0 for `-h`/`--help`, or prints the error and the
help and exits with code 2. User-facing
details are on [Launch options](/docs/configuration/).

## Shutdown

`start()` builds everything on one `AsyncDisposableStack`: each part registers what undoes it (`stack.use(db)`,
`stack.defer(…)`) right after it is created, and the stack undoes them in reverse order. The order of construction
therefore sets the order of the shutdown:

1. `chatRuns.dispose()` saves each running reply as `stopped` and closes its SSE streams.
2. `benchRunner.dispose()` kills the running benchmark and marks it (and its sweep) `interrupted`, with the error
   `interrupted (llama-webui stopped)`. The gate is not released: `llama-server` stops with the process.
3. `downloads.dispose()` stops the running download, keeping its `.part` file and its row for the next start.
4. `hub.dispose()` closes every WebSocket with code `1001`, and `placement.dispose()` unsubscribes the tracker.
5. `monitor.stop()` stops the sampling and its collectors.
6. `supervisor.stop()` stops the managed `llama-server` (`SIGTERM`, then `SIGKILL` after 5 seconds).
7. The database is closed.

The replies, the benchmark and the download come first, while `llama-server` still runs: a reply would otherwise see
the disconnection and end as an error.

Once everything is started, `start()` moves the stack out of its `await using` (`stack.move()`) and installs one
handler on `SIGINT` and `SIGTERM`. It prints `[llama-webui] SIGINT: stopping llama-server…` when a managed server
runs, awaits `disposeAsync()` (an error, a `SuppressedError` included, is logged without stopping the exit), and exits
with code 0. A second signal during this stop is ignored.

A `process.on('exit')` handler also kills the managed server with `SIGKILL` as a last resort. If the process dies without
running any handler, `setpriv --pdeathsig KILL` makes the kernel kill `llama-server` and `llama-bench` with it. On the
next start, the orphan cleanup of the [startup sequence](#startup-sequence) settles whatever was left `streaming` or
`running`.

## Development restarts

`pnpm dev` evaluates the server once. Node's watch mode (`--watch-path=server --watch-path=packages`) restarts the
whole process on every save under `server/` or `packages/`: it sends `SIGTERM`, so the [shutdown](#shutdown) runs as
at any stop, then starts `server/dev.ts` again. `llama-server` is stopped with it, a running sweep becomes
`interrupted` (the Resume button continues it), a chat reply is saved as `stopped`, and a download resumes from its
`.part` file. The new process has a new `bootId`: open tabs reconnect, see it in `hello`, and read the state again.
A save under `web/` is a hot module replacement and keeps the process.

A start that fails (a syntax error, an import of a missing file, the port taken) prints the error and exits with code
1; Node then waits for the next save to start again.
