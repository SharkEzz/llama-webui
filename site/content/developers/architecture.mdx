llama-webui is one Node.js process (Node 26.13 or later): a server written with [Effect](https://effect.website),
built from the `app/` package. Its HTTP server serves the web UI, the REST API under `/api/*` and the `/ws` WebSocket
on one port (7860 by default). The API is declared once, in `packages/webui-shared/src/api/` (`Api`, one group per
domain), and both the server and the web client are built on that declaration. The same process supervises one
`llama-server`, samples the hardware, runs benchmarks and relays chat generations.

## Startup sequence

The server's entry point is `app/server/main.ts`, run from source in development and bundled to
`app/.output/server/index.mjs` in production. In order, it:

1. Applies `.env` from the working directory (`loadDotEnv()`, `app/server/config/DotEnv.ts`): its variables fill
   what the environment lacks, and replace it too with `--env-override` or `LLAMA_WEBUI_ENV_OVERRIDE=1` (or `true`,
   in the environment or in the file). Only that file is read, and `parseEnv()` of `node:util` does not expand `$VAR`
   references. This comes first: Effect's configuration takes its snapshot of the environment the first time it is
   read.
2. Parses the command line (`cli()`, `app/server/config/Cli.ts`, see [Launch options](#launch-options)).
3. Checks the address (`assertFree`, `app/server/http/Address.ts`): it listens on the configured host and port for a
   moment, exclusively, then lets go. A port already taken ends the process with code 1 and
   `llama-webui: cannot listen on 127.0.0.1:7860: the port is already in use`, before anything touches the data
   directory: a second instance on the same folder would otherwise mark the first one's streaming reply `stopped` or
   take over its download.
4. Builds the app (`Layer.launch(App)`, `app/server/App.ts`): the services, then the HTTP server on them.

The services are layers, built in tiers (`Services` in `app/server/App.ts`), each tier after the ones below it:

| Tier | Layers                                                              | What their build does                                                                                                                                                                                                                                                                                                                 |
| ---- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `Db.layer`                                                          | Creates the data directory, opens `llama-webui.sqlite` (`@effect/sql-sqlite-node`, on `node:sqlite`) in WAL mode with foreign keys on, and runs the migrations (`app/server/db/migrations.ts`).                                                                                                                                       |
| 2    | `AppInfo`                                                           | The version and the boot id (a random UUID), the start time `/api/health` counts from.                                                                                                                                                                                                                                                |
| 3    | `WsHub`, the repositories, `GgufReader`, `ActiveWrites`             | The WebSocket hub; the settings, profiles, conversations, model cache, downloads, bench run and sweep repositories.                                                                                                                                                                                                                   |
| 4    | `LogRing`, `LlamaHttp`, `CpuInfo`, `PciIds`, `HfClient` on `HfHttp` | The ring of the last 10,000 log lines; the HTTP clients of llama-server and of Hugging Face; the CPU details and the PCI ID database, both read on first use and cached.                                                                                                                                                              |
| 5    | `Flags`, `BenchHardware`                                            | The flag catalogue of `llama-server --help` and the bench's device listing, both read on demand and cached.                                                                                                                                                                                                                           |
| 6    | `Supervisor`                                                        | The supervisor of `llama-server`; nothing runs until a start.                                                                                                                                                                                                                                                                         |
| 7    | `Monitor`, `Placement`, `ChatRuns`, `Downloads`                     | The monitor starts its collectors in a fiber (`LLAMA_WEBUI_TEST_MONITOR=stub`, a setting of the contract suite, gives a monitor without them); the placement follows the log ring; `ChatRuns` marks the replies left `streaming` by the previous process `stopped`; the download queue picks up the items left queued or downloading. |
| 8    | `BenchRunner`, `TuningHardware`, `TuningMemo`                       | The runner marks the runs and sweeps left `running` `interrupted`.                                                                                                                                                                                                                                                                    |
| 9    | `ExternalWatch`                                                     | Looks for a `llama-server` started by hand at once, then every 2 seconds, one look at a time; it skips its looks while the bench runner is busy, since the `llama-server` a benchmark starts on the settings port is not an external server.                                                                                          |

Only then is the port bound (`HttpLive`, `app/server/http/HttpLive.ts`), and the server prints
`ready (<version>) on http://127.0.0.1:7860`: `dev` from source, the build's version in production. There is no
"starting" window: a request always finds every service built. A layer that fails ends the process with code 1 and
`llama-webui: <message>` (`runApp`, `app/server/runtime/runApp.ts`).

A service that others follow exposes its changes as a stream (`changes` of the supervisor, `batches` of the log ring),
and a service publishes its own `/ws` messages with `WsHub.publish`, in the step that changes its state, so the
messages leave in the order of the changes:

| Publisher     | Messages                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------ |
| `Supervisor`  | `server-state`                                                                             |
| `LogRing`     | `log` (one batch per turn of its fiber)                                                    |
| `Monitor`     | `snapshot`                                                                                 |
| `Placement`   | `placement`                                                                                |
| `BenchRunner` | `bench-progress`, `bench-run`, `bench-deleted`, `sweep`, `sweep-progress`, `sweep-deleted` |
| `Downloads`   | `download`, `download-progress`, `download-deleted`                                        |

## Requests

`HttpLive` serves, on `NodeHttpServer` (the server of `node:http`):

- the API: `HttpApiBuilder.layer(Api)`, with each group's handlers (`app/server/<domain>/http.ts`, merged in
  `ApiRoutes`): 67 endpoints in all. Any other path under `/api`, whatever its method, is a `404`
  `{ "_tag": "RouteNotFound", "message": "Unknown route" }`, a method a path lacks too (there is no `405`);
- `/ws`: the WebSocket (see [WebSocket](#websocket)); a request without an upgrade gets `426`
  `WebSocket upgrade expected`;
- the UI: the built files of `app/.output/public/`, and `index.html` for every other `GET`, so reloading `/chat/12`
  serves the app (see [Serving the UI](#serving-the-ui)).

A request to a route of the API or of `/ws` goes through that route's middlewares (`Guarded`,
`app/server/http/Guard.ts`), in this order, whatever the spelling of the path the router matched:

1. The guard: the `Host`, the `Origin` and the content type of a write (see
   [Security](/developers/server/security/)). A refusal is JSON, `RequestRefused`.
2. A path that ends with a slash is a `308` to the path without it (`app/server/http/TrailingSlash.ts`).

Around every route, the UI's included, a defect of a handler (an exception, not an error the endpoint declares) is
logged with its cause, and the client gets a `500` without its message.

An endpoint declares what it reads as schemas, `params`, `payload` and `query`, and what it answers: its `success`
schema and its errors, each a `Schema.TaggedError` with its `httpApiStatus`. The handler never parses anything
itself:

```ts title="app/server/profiles/http.ts"
export const ProfilesHandlers = HttpApiBuilder.group(
  Api,
  'profiles',
  Effect.fn(function* (handlers) {
    const repo = yield* ProfilesRepo;
    return handlers
      .handle('list', () => repo.list)
      .handle('get', ({ params }) => repo.get(params.id))
      .handle('update', ({ params, payload }) => repo.update(params.id, payload))
      // …
  }),
);
```

A body that does not decode (malformed JSON, a missing or unknown key, a value a check refuses) never reaches the
handler: `RequestErrorsLive` (`app/server/http/RequestErrors.ts`) answers it with a `400`
`{ "_tag": "RequestInvalid", "message": "Invalid data: <first issue> (<path>)", "issues": [...] }`, and a path
parameter that does not decode (`/api/profiles/abc`) with the `404` `RouteNotFound`. An error the handler fails with
is answered with its own status and `{ _tag, message }`, plus its other fields. The
[API overview](/developers/api/overview/) documents the shapes and the order of the checks.

## Channels to the browser

The browser talks to llama-webui over three channels, all on the same port.

| Channel                  | Direction                      | Used for                                                                                                                                                        |
| ------------------------ | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REST, `/api/*`           | request, response              | Every read and every command: settings, profiles, starting the server, launching a benchmark, the history dump, the log replay. JSON in both directions.        |
| WebSocket, `/ws`         | server to browser              | Live state pushed to every open tab: snapshots on every monitor tick, log lines, server state changes, benchmark, sweep and download progress, model placement. |
| SSE, `text/event-stream` | server to browser, per request | Chat generations only: the response of `POST /api/chat/:id/messages`, `POST /api/chat/:id/regenerate` and `GET /api/chat/:id/stream`.                           |

### WebSocket

`GET /ws` is a route of `WsHub` (`app/server/ws/WsHub.ts`). The guard has judged the upgrade before it; the hub then
runs one fiber per client. A client message over 4,096 bytes closes the socket with code `1009`.

There is one hub and one connection per tab. The hub sends `hello` with the `bootId` and the server time when a
client connects, then the last monitor `snapshot` it kept (none before the first tick), then broadcasts every message to
every client: there are no subscriptions, the client dispatches by
`type`. Every 15 seconds the hub sends `ping`; a client that leaves two pings unanswered is closed with code `4000`
`heartbeat`. A client's `ping` is answered with `pong`. Every message is encoded with the `WsMessage` union of
`packages/webui-shared/src/ws.ts`, listed on the [WebSocket](/developers/api/websocket/) page.

The WebSocket only carries changes. After every (re)connection, the web app reads the current state again over REST,
and the `bootId` tells it whether the server restarted in between ([Web app](/developers/frontend/) describes the
client).

### SSE for chat

A chat generation belongs to the server, not to the HTTP request (see [Chat runs](/developers/server/chat/)). The SSE
response only subscribes to the run: events `start`, `delta` and `done` (`ChatEvent` in
`packages/webui-shared/src/chat.ts`). The endpoint's success is `HttpApiSchema.StreamSse`, and its handler answers
`sseResponse` (`app/server/http/Sse.ts`), which adds a `: ping` comment after 15 seconds of silence: a long prompt can
be processed without sending anything, and a proxy may drop a silent connection. The response sends
`Connection: close`, so the browser does not keep the connection open once the stream ends (it would hold the
shutdown). A client that leaves only unsubscribes; the generation goes on, and `GET /api/chat/:id/stream` attaches to
it again.

## Serving the UI

`app/vite.config.ts` builds the web client (`app/index.html` and `app/src/`, with `@vitejs/plugin-react`,
`@tailwindcss/vite` and the `@` → `src` alias). The server is not a Vite plugin: `app/build/server.ts` bundles it with
Rolldown, and in development Vite only starts it and forwards `/api` and `/ws` to it.

### Development

`pnpm dev` runs `vite dev` in `app/`. Vite serves the UI with hot module replacement on `LLAMA_WEBUI_PORT` (7860 by
default, `strictPort`) of `LLAMA_WEBUI_HOST` (`127.0.0.1` by default). Its plugin `app/build/devServer.ts` starts the
server from source, `node --watch server/main.ts`, on a free loopback port and in its own process group, with
`LLAMA_WEBUI_DEV=1`, and proxies `/api` and `/ws` to it without changing the `Host` (the guard reads what the browser
sent). While the server starts or restarts, an API request waits for it rather than failing in the proxy: the plugin
keeps one idle connection open to the server (`serverLink()`), which says it is up without a probe per request and
closes when the server stops (Node also closes it after a minute without a request; the next API request takes a new
one). A server that still accepts nothing after 10 seconds is logged
(`API not reachable on "<url>"…`) and the proxy answers for it.

`app/vite.config.ts` applies `.env` the way `main.ts` does, before it reads the address, and the server inherits the
result. No other environment file is read.

In development, the server sends its spans and its metrics to the
[Effect DevTools](https://effect.website/docs/getting-started/devtools/) when they listen, at `LLAMA_WEBUI_DEVTOOLS_URL`
(`ws://localhost:34437` by default); it says in the terminal whether it connected. A build never connects to them
([Metrics](#metrics)).

### Production

`pnpm start` runs `pnpm build`, then `node app/.output/llama-webui.mjs`. `pnpm build` runs `vite build`, then
`node build/server.ts`, in `app/`, and writes `app/.output/`:

- `public/`: the client, split per page: each page loads only its own chunks. The files of `public/assets/` are
  content-hashed, and each text one (script, style, SVG…) of more than 1 KiB has its Brotli (`<file>.br`, quality 11)
  and gzip (`<file>.gz`, level 9) copies next to it, each kept only when it is smaller (`app/build/precompress.ts`,
  run at the end of `build/server.ts`): about 3.7 MiB of assets become 0.65 MiB in Brotli;
- `server/index.mjs`: the server, one file with every dependency bundled (it imports only `node:*`);
- `server/nvml-worker.mjs`: the NVML sampler, built from `app/server/collectors/nvml/worker.ts`, and started as a
  child process. Development runs its sources as they are;
- `llama-webui.mjs`: the launcher, built from `app/bin/llama-webui.ts`, which starts with `#!/usr/bin/env node` and
  imports `./server/index.mjs`;
- `server/THIRD-PARTY-LICENSES.md`: the licenses of the npm code bundled into the server and the sampler
  (`app/build/licenses.ts`).

The build also replaces `LLAMA_WEBUI_VERSION` with `git describe --tags --always --dirty`, or the version of
`package.json` without git. `AppInfo` (`app/server/config/AppInfo.ts`) reports it in `/api/health`, `--version`
prints it, and the status bar shows it: the tag, else the short commit hash. From source, it is `dev`.

`app/server/http/Static.ts` serves the UI next to the bundle (`<bundle folder>/../public`): `/assets/*` with
`Cache-Control: public, max-age=31536000, immutable`, and a missing asset is a `404` (a stale tab after an upgrade
asks for the old names). An asset the build compresses goes out as its `.br` or `.gz` copy when the request's
`Accept-Encoding` accepts it (the highest `q` first, Brotli before gzip on a tie, `q=0` refused), with the file's
`Content-Type`, `Content-Encoding` and `Vary: Accept-Encoding`; without an accepted copy, or for a `Range` request
(a range counts the bytes of the file), the file itself. Every other `GET` is a file of `public/` when there is one,
`index.html` otherwise, both with `Cache-Control: no-cache`, since `index.html` points to the current chunks. The API
sets no cache header.

The server compresses only one thing at each request: a JSON response of 1 KiB or more, in gzip, for a client that
accepts it (`compressJson` of `app/server/http/HttpLive.ts`, Effect's `HttpMiddleware.compression`): the lists of the
API shrink about fourfold (`/api/flags`: 56 KB, 13 KB in gzip). A stream of events (`text/event-stream`) goes out as
written, each event at once.

### Distribution

A release is the npm package of the repository's root: `pnpm pack` after `pnpm build` writes
`llama-webui-<version>.tgz`, which `npm install -g ./llama-webui-<version>.tgz` turns into a `llama-webui` command.
The root `package.json` is the packed one:

- `bin` maps `llama-webui` to `app/.output/llama-webui.mjs`. Node runs it from its real path, so `server/index.mjs`
  and `server/nvml-worker.mjs` are found next to it even through the link npm creates.
- `files` ships `app/.output`, plus the `README.md`, `LICENSE` and `package.json` npm always adds; `os` is `linux`
  and `engines` asks for Node.js 26.13. `.output` is ignored by the root `.gitignore`, not by one in `app/`, which
  npm would have applied to the package too.
- There are no `dependencies`: the build bundles every library and workspace package, so an install from the
  tarball fetches nothing else.

`node scripts/smoke.ts` checks the build: `--help`, then a run on a free port with an empty data directory (the API,
the UI from a deep URL with every file it references, the WebSocket's `hello`), with a decoy `PORT` in the environment
that must not win over `--port`. `node scripts/smoke.ts --tarball [file.tgz]` checks the package the way a user gets
it: it packs the root (or takes the given tarball), installs it with npm into an empty prefix, checks that npm
installed nothing but the package, then runs the same checks through `node_modules/.bin/llama-webui`. Packing never
builds: `pnpm pack` runs `scripts/prepack.ts` first, which refuses without `app/.output/llama-webui.mjs`,
`app/.output/server/index.mjs` and `app/.output/server/nvml-worker.mjs`, so a package without its command cannot be
written; run `pnpm build` before it. CI runs both on every pull request, and `release.yml` runs the tarball check on
the tarball it publishes, with `--expect-version <tag>`: the build must report the tag itself as its version, so a
`-dirty` build is not published. Stopped by SIGINT or SIGTERM, the smoke test stops the server and removes its
temporary directories before it exits.

Up to v0.2.1, llama-webui ran on Bun and shipped as a standalone executable. It then moved to Node.js and Nitro, and
from Nitro to Effect. Each move kept the API's answers or recorded each change: the contract suite replays every
endpoint against a golden record ([Testing](/developers/contributing/testing/)). The move to Effect changed, on
purpose, the error bodies (`{ _tag, message }` instead of `{ error, code }`), the answer to a method a path lacks (a
`404` instead of a `405` with `Allow`), the validation messages, and a few refusals that are now stricter (an id
written `"1"`, an unknown key in a body); the [API overview](/developers/api/overview/) lists them.

## Launch options

`app/server/config/Cli.ts` declares the command line (`effect/cli`). Each option comes from its flag, else its
environment variable, else a default (`AppConfig`, `app/server/config/AppConfig.ts`). An empty variable counts as
unset.

| Flag                | Variable                     | Default                                                         |
| ------------------- | ---------------------------- | --------------------------------------------------------------- |
| `--host <address>`  | `LLAMA_WEBUI_HOST`           | `127.0.0.1`                                                     |
| `--port <port>`     | `LLAMA_WEBUI_PORT`           | `7860` (an integer from 1 to 65535)                             |
| `--data-dir <path>` | `LLAMA_WEBUI_DATA_DIR`       | `$XDG_DATA_HOME/llama-webui`, else `~/.local/share/llama-webui` |
| `--env-override`    | `LLAMA_WEBUI_ENV_OVERRIDE=1` | off: `.env` only fills what the environment lacks               |

`-h`/`--help` prints the help and exits with code 0, `-v`/`--version` prints `llama-webui v<version>`. An unknown flag
or an invalid value prints the help, then the error, and exits with code 1. In development, `vite dev` starts the
server with `--host 127.0.0.1` and a port of its own; the public address comes from the variables, in the environment
or in `.env`. User-facing details are on [Launch options](/docs/configuration/).

## Shutdown

`SIGINT` or `SIGTERM` interrupts the app (`runApp`, `app/server/runtime/runApp.ts`), which undoes in this order:

1. **The shutdown steps** (`Shutdown`, `app/server/runtime/Shutdown.ts`), while the clients are still connected, last
   registered first: `ChatRuns` saves each running reply as `stopped` and ends its SSE streams with `done`; the bench
   runner interrupts its work and saves the current run and the running sweep `interrupted`, with the error
   `interrupted (llama-webui stopped)` (the gate is not released: `llama-server` is about to stop); the download queue
   stops its loop, the running item keeping its row and its `.part` file for the next start; then the hub flushes the
   last messages to its clients, 500 ms at most.
2. **The HTTP server** stops serving: every WebSocket is closed with code `1001`, and open connections get 500 ms
   before they are cut.
3. **The services**, in the reverse order of their tiers: the external watch first (no look while the rest stops),
   then the bench runner (its programs killed), the monitor (its collectors' programs), the chat runs and the
   downloads, then the supervisor stops the managed `llama-server` (`SIGTERM`, then `SIGKILL` after 5 seconds) while
   the log ring and the hub it writes to are still up, and the database closes last.

The process then exits with code 0, in well under 2 seconds with a page open and a reply streaming
(`app/server/lifecycle.test.ts`). A second signal while it stops exits at once.

If the process dies without running any of this (`SIGKILL`), `setpriv --pdeathsig KILL` makes the kernel kill
`llama-server` and `llama-bench` with it. On the next start, the layers of the [startup sequence](#startup-sequence)
settle whatever was left `streaming` or `running`.

## Development restarts

Under `pnpm dev`, the server is a child of Vite run by `node --watch`, which restarts it whenever a file it imports
changes (under `app/server/` or `packages/`). A restart is a [shutdown](#shutdown) then a [startup](#startup-sequence):
`llama-server` is stopped, a running sweep becomes `interrupted` (the Resume button continues it), a chat reply is
saved as `stopped`, and a download resumes from its `.part` file. The new process has a new `bootId`: open tabs see
it in `hello` when they reconnect, and read the state again. A server that fails to start prints its error and
`node --watch` waits for the next save.

A save under `app/src/` is a hot module replacement of the UI and leaves the server, and `llama-server`, alone.

Stopping Vite (Ctrl+C, `SIGTERM`, or the terminal closed) sends the server `SIGTERM` and waits for it, so an open
page gets its `1001` and `llama-server` stops; a second Ctrl+C kills the server and exits at once.

## Metrics

The metrics of the server are declared in `app/server/runtime/Metrics.ts`, each named `llama_webui_<domain>_<what>`
with its description; the DevTools show them in their Metrics panel, refreshed while they are connected. They are
recorded in production too (an update is a write to a map in memory), where nothing reads them. With the DevTools, the
server also adds the fibers' own metrics (`child_fibers_*`).

The DevTools of the VS Code extension (0.10.0) still decode the metrics in the shape of Effect 3: the server's client
(`app/server/runtime/DevToolsWire.ts`) rewrites its snapshots, and its span events without attributes, into that shape
before they leave, as the extension's own debugger instrumentation does.

| Group              | What it measures                                                                                                                                                                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HttpMetrics`      | every response by method and class of status (`2xx`…, `aborted`), its duration, the defects (500), the requests the guard refused, the ones that did not decode (by part)                                                                                              |
| `WsMetrics`        | the `/ws` clients connected, the messages published by type, the messages and bytes written, the clients closed by the heartbeat                                                                                                                                       |
| `ChatMetrics`      | the replies being written, the replies saved by status, the failures by cause, the refusals by tag, the time to the first token, the speeds (tg and pp) and the tokens of each reply                                                                                   |
| `LlamaMetrics`     | the states the supervised `llama-server` entered, whether it is ready, the time to ready, the time a stop took, the stops that needed SIGKILL                                                                                                                          |
| `DownloadMetrics`  | the bytes received, the current speed, the files resumed, the retries, the items ended by status, the errors by code, the time an item ran                                                                                                                             |
| `MonitorMetrics`   | the time a tick took, the ticks longer than the interval, the ticks that failed, the readers that died, the source of the NVIDIA cards, the NVML sampler's stops and restarts                                                                                          |
| `BenchMetrics`     | the runs ended by kind and status and their duration, the sweeps ended by status, the works that died, the refusals of the gate, the failed restarts of `llama-server`, the time a trial server took to load                                                           |
| `HfMetrics`        | the requests to the Hub API by result (`ok` or the error's tag), their duration                                                                                                                                                                                        |
| `LlamaHttpMetrics` | the requests to a `llama-server` (the monitor's polls, the chat, the trials) by class of status, `failed` or `aborted`, and the time to their headers                                                                                                                  |
| `CacheMetrics`     | the lookups and the loads of each cache (`gguf`, `flags`, `bench_build`, `bench_devices`, `model_cache`, `whoami`: a hit is a lookup that loaded nothing), the time a GGUF header and a `--help` took to read, the device listings that fell back to the last good one |
| `ModelMetrics`     | the time a scan of the models folder took, the models it found and could not read, the `model_cache` rows pruned                                                                                                                                                       |
| `ShutdownMetrics`  | the time the shutdown steps took, the steps that failed                                                                                                                                                                                                                |

An attribute is always a value from a closed set (a status, a kind, a tag): never an id, a path or a model, which would
make one series per value.
