llama-webui has no authentication: whoever can send it a request can do anything the interface can, including run a
program of their choice (the **Binary** setting). Its protection is where it listens, plus one request guard that keeps
other websites in the browser away from the API. The guard is `guard()` in `server/security.ts`, applied by
the `guardMw` middleware of the Hono API (`server/http.ts`, mounted in `server/api.ts`).

| File                       | Role                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------ |
| `server/security.ts`       | `guard(req)`: the `Host`, `Origin` and content-type checks.                          |
| `server/http.ts`           | `guardMw`, `HttpError`, `errorResponse()`, `notFound()`, the `id()`, `body()` and `json()` validators. |
| `server/security.test.ts`  | Tests of each rule of the guard.                                                     |
| `server/cli.ts`            | `--host` (default `127.0.0.1`) and `--port` (default `7860`).                          |
| `server/hf/paths.ts`       | `repoDir()` and `fileDest()`: download paths kept inside the models folder.           |

The user-facing version of this page is [Security](/docs/security/).

## Threat model

| Who                                               | What they can do                                       | What stops them                                     |
| ------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| Programs and users on the same machine            | Everything                                             | Nothing: same trust as the user running llama-webui |
| Devices on the network, once `--host` opens it    | Everything                                             | Nothing in llama-webui: the network and a firewall  |
| Another website open in the browser               | Make the browser send requests to `127.0.0.1:7860`      | `guard()`                                           |

The guard handles three ways a web page can reach a local API:

- **DNS rebinding**: a page served from `attacker.example` makes that name resolve to `127.0.0.1`. Its requests are
  then same-origin for the browser, but they carry `Host: attacker.example:7860`.
- **Cross-site requests**: a page on another origin calls `fetch()` on the API or opens a WebSocket to it. The browser
  sends that page's `Origin`.
- **Simple-request CSRF**: an HTML form, or a `fetch()` with a `text/plain`, `application/x-www-form-urlencoded` or
  `multipart/form-data` body, is sent cross-site without a CORS preflight.

llama-webui sends no CORS headers (`Access-Control-*`), so the browser never lets another origin read a response.

## The guard

```ts title="server/security.ts"
/** Safe hostname: localhost or a literal IP address. A domain name can be rebound to 127.0.0.1. */
function trustedHostname(hostname: string): boolean {
  const h = hostname.replace(/^\[|\]$/g, '').toLowerCase();
  return h === 'localhost' || h.endsWith('.localhost') || isIP(h) !== 0;
}
```

`guard(req)` returns a `Response` that refuses the request, or `undefined` to let it through. The rules run in this
order, and the first that fails answers:

| Rule                                                                                                                | Response                                                                     |
| ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| The request URL and the `Host` header (or the URL's host when there is none) parse as `http://<host>`; over HTTP the adapter refuses such a request first (`400`, no body, which `server/host.ts` does not rewrite), so this rule only answers a caller of `guard()` itself | `400` `{"error":"Invalid host"}` |
| Its hostname is `localhost`, ends with `.localhost`, or is an IPv4 or IPv6 literal (brackets removed, any case)     | `403` `{"error":"Host not allowed"}`                                         |
| When an `Origin` header is present, it equals `` `${url.protocol}//${host}` `` exactly                              | `403` `{"error":"Origin not allowed"}`                                       |
| For `POST`, `PUT`, `PATCH` and `DELETE`: a `Content-Type`, when present, matches `/^application\/json\b/i`, and a request with a body has one | `415` `{"error":"JSON body expected (content-type: application/json)"}` |

What follows from these rules:

- Any IP address passes the `Host` check, so `http://192.168.1.20:7860` works from the network when llama-webui
  listens there, while `http://myserver.lan:7860` is refused. The rule does not depend on `--host`.
- The `Origin` comparison is a plain string comparison with the `Host` the request carries: a page on
  `http://localhost:7860` calling `http://127.0.0.1:7860` is refused, even though both reach the same server.
- A request without `Origin` passes the `Origin` rule: `curl` sends none, and browsers omit it on many same-origin
  requests.
- Behind a reverse proxy that terminates TLS, `url.protocol` is `http:` while the browser's `Origin` is `https://…`:
  every write and the WebSocket get `403`. The guard does not read `X-Forwarded-Proto`, which any client can set, so
  this setup is not supported; trusting it would need an explicit setting naming the proxy.
- `application/json; charset=utf-8` passes the content-type rule. A write without a body and without a
  `Content-Type` (for example `POST /api/server/stop`) passes too; with a body, it must be JSON. The guard detects a
  body from the headers, a `Content-Length` above 0 or a `Transfer-Encoding`, not from the body stream: Node's
  adapter (`@hono/node-server`) gives every write a body stream, even an empty one. A cross-site
  `fetch()` that sends `application/json` triggers a CORS preflight, which gets no CORS headers back.

## Where it applies

The Hono API (`createApi()`, `server/api.ts`) runs `guardMw` on every request, before the 405 table and the routes:

```ts title="server/http.ts"
export const guardMw: MiddlewareHandler = async (c, next) => {
  const refused = guard(c.req.raw);
  if (refused) return refused;
  await next();
};
```

Whatever a validator or a handler throws afterwards reaches the API's `onError`, which answers with
`errorResponse()`.

- Every `/api/*` request goes through it, routes and the `404` `{"error":"Unknown route"}` alike: it is mounted with
  `.use()` ahead of every domain file, so a new route is guarded without doing anything.
- The WebSocket endpoint is guarded too: `mount()` (`server/host.ts`) runs `guard()` on a `/ws` upgrade request
  before handing it to `upgradeWebSocket()`, so another site cannot open the socket (browsers always send `Origin` on a WebSocket
  handshake). A request to `/ws` that is not an upgrade gets `426` `WebSocket upgrade expected`. An upgrade the
  guard refuses is not treated as one: the server's `shouldUpgradeCallback` runs the guard first, so the refusal is
  an ordinary response (Node writes it and handles a client that resets the connection), sent with
  `Connection: close` so the server closes the socket even when the client keeps its side open. An accepted client
  can send messages of 4,096 bytes at most.
- The web interface itself (the HTML page, its bundles and the SPA fallback, `server/routes/web.ts`) is not guarded:
  it is static and holds no data. That is why a page opened through a host name loads, then has all its API calls
  refused with `Host not allowed`.

## Errors and `HttpError`

Every error an `/api` route returns is a JSON object with an `error` string, and sometimes more:

| Thrown                                 | Status          | Body                                                             |
| -------------------------------------- | --------------- | ---------------------------------------------------------------- |
| `new HttpError(status, message)`       | `status`        | `{ "error": message }`                                           |
| `new HttpError(status, message, code)` | `status`        | `{ "error": message, "code": code }`                             |
| A `ZodError`                           | `400`           | `{ "error": "Invalid data: <first issue> (<path>)", "issues": [...] }`, the path only when the issue has one |
| A `SyntaxError`, or Hono's `Malformed JSON in request body` (body is not JSON) | `400` | `{ "error": "Invalid JSON" }` |
| Anything else                          | `500`           | `{ "error": "Internal error" }`, and the error is logged         |

The helpers in `server/http.ts` build the common cases: `notFound(what)` is a `404` `<what> not found`, the `id()`
validator a `404` for an `:id` that is not a positive integer, and `object(body)` (used by `body(Schema, { object:
true })` and `json(object)`) a `400` `JSON object expected` for a body that is not a JSON object. `code` is the machine-readable reason (`server-running`, `name-taken`, `hf-gated`…): the
web app reads it instead of the message text. [API overview](/developers/api/overview/) lists the conventions for
clients.

## What `--host` changes

`server/index.ts` passes `--host` (or `LLAMA_WEBUI_HOST`, default `DEFAULT_HOST = '127.0.0.1'`) as the `hostname` the HTTP server listens on.
That decides who can connect, and nothing else: the guard applies the same rules on every address, and no
authentication appears. With a non-loopback address, `GET /api/setup` reports `listen.exposed: true` (from
`isLoopback()`, `packages/webui-shared/src/setup.ts`), and the setup checklist shows a network access reminder.

## llama-server's own exposure

`llama-server` is a separate HTTP server with its own address. `buildCommand()` passes `--host` and `--port` from the
profile, else from the `host` and `port` settings, whose defaults are `127.0.0.1` and `8080`
(`packages/webui-shared/src/settings.ts`): `llama-server` stays local, like llama-webui, unless a user opens it. `GET /api/setup`
reports `llamaListen: { host, exposed }` for the `host` setting, and the setup checklist, the Settings field and the
Server page's command card warn when it is not loopback. The benchmark's temporary `llama-server` always gets
`host: '127.0.0.1'` (`server/bench/execute.ts`). llama-webui talks to `llama-server` on the address it listens on
(`probeUrl()`: loopback for a wildcard address).

[How llama-server is exposed](/docs/security/#how-llama-server-is-exposed) gives users the settings to change.

## Processes and arguments

Every process llama-webui starts (`llama-server`, `llama-bench`, `nvidia-smi`, `perf`…) goes through `spawnProc`
(`server/proc.ts`, `node:child_process` without `shell`) with an argument array, never through a shell. A profile
argument such as `$(whoami)` reaches `llama-server` as a literal string. `shellQuote()` only builds the displayed command.

That does not make the API safe to expose: the `binary` setting can name any program, and profiles set its arguments
(except the reserved flags in `RESERVED_FLAGS`, see [Supervisor](/developers/server/supervisor/#building-the-command))
and environment variables.

## Paths the API reads and writes

The API reads files where the user points it, by design: there is no allowlist of folders.

- **Models folder**: the `modelsDir` setting, `~`-expanded, can be any directory. `GET /api/models` walks it for
  `*.gguf` files, skipping names that start with `.` and not following directory symlinks (a symlinked `.gguf` file is
  followed).
- **GGUF info**: `GET /api/models/info?path=` reads the header of any absolute path that ends in `.gguf` and is a
  regular file: `400` `Absolute path to a .gguf file expected` otherwise, `404` `File not found` when it does not
  exist, `422` when the file does not parse. It is not limited to the models folder.
- **Profile paths**: a profile's model, projector and working directory can be anywhere. `profilePaths()` resolves
  them the way `llama-server` will (`~` expanded, relative to the profile's `cwd`) wherever llama-webui reads the
  model itself, for example for the launch pad and benchmarks.
- **llama-tui import**: reads only `$XDG_CONFIG_HOME/llama-tui/config.json` (else `~/.config/llama-tui/config.json`);
  the request cannot choose the path.
- **Hugging Face downloads** are the only writes into a user-chosen folder, and they are confined. `repoDir()` accepts
  only an `org/name` repository ID matching `HF_REPO_RE` (`400` `Invalid repository id: …`) and maps it to
  `<modelsDir>/<org>/<name>`. `fileDest()` refuses a file path that is absolute or resolves outside that folder
  (`400` `Invalid file path in the repository: …`).

## Tests

`server/security.test.ts` calls `guard()` on plain `Request` objects:

- `127.0.0.1`, `localhost`, a LAN IP and `[::1]` are accepted as `Host`, and `evil.example` gets `403`;
- an `Origin` from another site gets `403`, the same origin passes, and `http://localhost:7860` is refused for a
  request to `127.0.0.1:7860`;
- a `PATCH` with `text/plain` and a `POST` with a body and no `Content-Type` get `415`;
  `application/json; charset=utf-8` passes, and so does a `POST` without a body.

`server/hf/hf.test.ts` checks that `repoDir()` and `fileDest()` refuse `..`, absolute and empty paths, and
`packages/webui-shared/src/profile.test.ts` that an import with a reserved flag is rejected.
