llama-webui has no authentication: whoever can send it a request can do anything the interface can, including run a
program of their choice (the **Binary** setting). Its protection is where it listens, plus one request guard that keeps
other websites in the browser away from the API. The guard is `refusal()` in `app/server/http/Guard.ts`, run around every
route of the API and of `/ws` (`Guarded`), before the route's handler.

| File | Role |
| --- | --- |
| `app/server/http/Guard.ts` | `refusal(request)`: the `Host`, `Origin` and content-type checks; `Guarded`: the route middleware that answers a refusal, then the trailing slash. |
| `app/server/http/HttpLive.ts` | `ApiRoutes`: the API's routes, provided `Guarded`; `serve()`: the defect log around every route; `SERVER_OPTIONS`. |
| `app/server/http/TrailingSlash.ts` | `noTrailingSlash`: the `308` of a trailing slash on a route of the API or of `/ws`. |
| `app/server/http/RequestErrors.ts` | `RequestErrorsLive`: a request that does not decode becomes `RequestInvalid` (or `RouteNotFound` for a path parameter). |
| `packages/webui-shared/src/api/errors.ts` | `RequestRefused`, `RouteNotFound`, `RequestInvalid`. |
| `app/server/http/Guard.test.ts` | Tests of each rule of the guard. |
| `app/server/config/Cli.ts`, `AppConfig.ts` | `--host` (default `127.0.0.1`) and `--port` (default `7860`). |
| `app/server/hf/paths.ts` | `repoDir()` and `fileDest()`: download paths kept inside the models folder. |

The user-facing version of this page is [Security](/docs/security/).

## Threat model

| Who                                               | What they can do                                       | What stops them                                     |
| ------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| Programs and users on the same machine            | Everything                                             | Nothing: same trust as the user running llama-webui |
| Devices on the network, once `--host` opens it    | Everything                                             | Nothing in llama-webui: the network and a firewall  |
| Another website open in the browser               | Make the browser send requests to `127.0.0.1:7860`      | The guard                                           |

The guard handles three ways a web page can reach a local API:

- **DNS rebinding**: a page served from `attacker.example` makes that name resolve to `127.0.0.1`. Its requests are
  then same-origin for the browser, but they carry `Host: attacker.example:7860`.
- **Cross-site requests**: a page on another origin calls `fetch()` on the API or opens a WebSocket to it. The browser
  sends that page's `Origin`.
- **Simple-request CSRF**: an HTML form, or a `fetch()` with a `text/plain`, `application/x-www-form-urlencoded` or
  `multipart/form-data` body, is sent cross-site without a CORS preflight.

llama-webui sends no CORS headers (`Access-Control-*`), so the browser never lets another origin read a response.

## The guard

```ts title="app/server/http/Guard.ts"
/**
 * Safe hostname: localhost or a literal IP address. A domain name can be rebound to 127.0.0.1. `hostname` comes from
 * `URL`: lower case, IPv4 dotted, IPv6 in brackets (and valid, or `URL` would have refused it).
 */
const trustedHostname = (hostname: string): boolean =>
  hostname === 'localhost' ||
  Str.endsWith('.localhost')(hostname) ||
  IPV4.test(hostname) ||
  Str.startsWith('[')(hostname);
```

`refusal(request)` returns the status and message of a refusal, or `undefined` to let the request through. The rules
run in this order, and the first that fails answers with a `RequestRefused` body, `{ "_tag": "RequestRefused",
"message": … }`:

| Rule                                                                                                                | Response                                                                     |
| ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| A `Host` header is present and parses as `http://<host>` (`Host: a b` does not) | `400` `Invalid host` |
| Its hostname (as `URL` gives it: lower case, IPv4 dotted) is `localhost`, ends with `.localhost`, or is an IPv4 or IPv6 literal | `403` `Host not allowed` |
| When an `Origin` header is present, it equals `` `http://${host}` `` exactly | `403` `Origin not allowed` |
| For `POST`, `PUT`, `PATCH` and `DELETE`: a `Content-Type`, when present, matches `/^application\/json\b/i`, and a request with a body has one | `415` `JSON body expected (content-type: application/json)` |

What follows from these rules:

- Any IP address passes the `Host` check, so `http://192.168.1.20:7860` works from the network when llama-webui
  listens there, while `http://myserver.lan:7860` is refused. The rule does not depend on `--host`.
- The `Origin` comparison is a plain string comparison with the `Host` the request carries: a page on
  `http://localhost:7860` calling `http://127.0.0.1:7860` is refused, even though both reach the same server.
- A request without `Origin` passes the `Origin` rule: `curl` sends none, and browsers omit it on many same-origin
  requests.
- The server speaks plain HTTP, so the page's own origin is `http://<Host>`. Behind a reverse proxy that terminates
  TLS, the browser's `Origin` is `https://…`:
  every write and the WebSocket get `403`. The guard does not read `X-Forwarded-Proto`, which any client can set, so
  this setup is not supported; trusting it would need an explicit setting naming the proxy.
- `application/json; charset=utf-8` passes the content-type rule. A write without a body and without a
  `Content-Type` (for example `POST /api/server/stop`) passes too; with a body, it must be JSON. The guard detects a
  body from the headers, a `Content-Length` above 0 or a `Transfer-Encoding`, not from the body stream, which it
  never reads. A cross-site `fetch()` that sends `application/json` triggers a CORS preflight, which gets no CORS
  headers back.

## Where it applies

The guard is a middleware of the routes it protects, not of the server: `Guarded` (`app/server/http/Guard.ts`) is
provided to the layers that register them, `ApiRoutes` (`app/server/http/HttpLive.ts`) and `WsHub.route`.

```ts title="app/server/http/Guard.ts"
export const Guarded = HttpRouter.middleware((route) => route.pipe(noTrailingSlash, guard)).layer;
```

It runs once the router has chosen the route, so it never reads the path itself. The router of `effect/http` ignores
the case, folds repeated slashes, decodes percent escapes and cuts the path at a `;`: `/API/settings`, `//api/settings`,
`/%61pi/settings` and `/ws;x` all reach a route, and each is judged as that route is. A guard in front of the router
that compared the raw path with `/api/` let them through.

- Every request to a route of `ApiRoutes` goes through it, the endpoints of `Api` and the `404` `RouteNotFound`
  `Unknown route` of any other path under `/api` alike: a new endpoint of `Api` is guarded without doing anything. A
  route added outside `Api` (`HttpRouter.add`) is guarded only when its layer is provided `Guarded`. A refused request
  with a trailing slash gets the refusal, not the `308`.
- The WebSocket endpoint is guarded too: another site cannot open the socket (browsers always send `Origin` on a
  WebSocket handshake). A refused upgrade gets `Connection: close`, so the server closes the socket even when the
  client keeps its side open. A request to `/ws` that is not an upgrade passes the guard, then gets `426`
  `WebSocket upgrade expected`. An accepted client can send messages of 4,096 bytes at most (`SERVER_OPTIONS`): a
  larger one closes the connection with code `1009`.
- The web interface itself (`index.html`, its hashed assets, served by `app/server/http/Static.ts`) is not guarded: it
  is static and holds no data. That is why a page opened through a host name loads, then has all its API calls
  refused with `Host not allowed`.

## Errors

Every error an `/api` route returns is a tagged error of the API definition, encoded as a JSON object with its `_tag`
and its `message`, and its own fields (`issues` for a validation): the guard's `RequestRefused`, the `RequestInvalid`
of a body, query or header that does not decode, the `RouteNotFound` of an unknown path or of a path parameter that
does not decode, and the errors each endpoint declares (`ServerRunning`, `ProfileNameTaken`, `HfGated`…). The web app
reads the `_tag`, never the message text. A defect of a handler is logged with its cause (`logDefects`), and the
client gets a `500` without its message. [API overview](/developers/api/overview/#errors) lists the tags and the
status codes.

## What `--host` changes

`--host` (or `LLAMA_WEBUI_HOST`, default `127.0.0.1`) is read by `config/Cli.ts` and `config/AppConfig.ts`, and the
Node server listens on it (`HttpLive.ts`); `pnpm dev` gives `LLAMA_WEBUI_HOST` to Vite's `server.host`
(`app/vite.config.ts`), and the server started by Vite listens on loopback behind it.
That decides who can connect, and nothing else: the guard applies the same rules on every address, and no
authentication appears. With a non-loopback address, `GET /api/setup` reports `listen.exposed: true` (from
`isLoopback()`, `packages/webui-shared/src/setup.ts`), and the setup checklist shows a network access reminder.

## llama-server's own exposure

`llama-server` is a separate HTTP server with its own address. `buildCommand()` passes `--host` and `--port` from the
profile, else from the `host` and `port` settings, whose defaults are `127.0.0.1` and `8080`
(`packages/webui-shared/src/settings.ts`): `llama-server` stays local, like llama-webui, unless a user opens it. `GET /api/setup`
reports `llamaListen: { host, exposed }` for the `host` setting, and the setup checklist, the Settings field and the
Server page's command card warn when it is not loopback. The benchmark's temporary `llama-server` always gets
`host: '127.0.0.1'` (`app/server/bench/execute.ts`). llama-webui talks to `llama-server` on the address it listens on
(`probeUrl()` of `llamacpp-js/client`: loopback for a wildcard address).

[How llama-server is exposed](/docs/security/#how-llama-server-is-exposed) gives users the settings to change.

## Processes and arguments

Every program llama-webui starts (`llama-server`, `llama-bench`, `nvidia-smi`, `perf`, the NVML sampler…) goes through
Effect's `ChildProcess` (`effect/process`, the long-running ones through `followProgram()` in
`app/server/process/followed.ts`) with an argument array, never through a shell. A profile argument such as
`$(whoami)` reaches `llama-server` as a literal string. `shellQuote()` (`packages/webui-shared/src/shell.ts`) only
builds the displayed command.

That does not make the API safe to expose: the `binary` setting can name any program, and profiles set its arguments
(except the reserved flags in `RESERVED_FLAGS`, see [Supervisor](/developers/server/supervisor/#building-the-command))
and environment variables.

## Paths the API reads and writes

A request that names a model or a projector may only name one under the models folder, or the model or projector of
a profile: `checkModelPath()` (`app/server/models/allowedPath.ts`) answers `403` `ModelPathRefused` `Outside the
models folder and not used by a profile` otherwise. It applies to `GET /api/models/info`, the tuning endpoints that
take a `modelPath` or an `mmprojPath` (`estimate`, `plan`, `inputs`, `disk-speed`, `checks?model=`), `POST
/api/bench/run` and `POST /api/sweeps`.

- **Under the folder**: the path as written (`..` resolved) or once its links are followed, against the folder as
  written or followed. A link the user put under the models folder counts as under it, wherever it leads: the scan
  lists it.
- **A profile's file**: equal to the model or projector of a profile, resolved by `profilePaths()`, as written or once
  both are followed. A profile opens its paths to every request, as it opens them to `llama-server`: creating or
  editing a profile is not limited, and that is where a file outside the folder is chosen.
- **A missing file** is judged as written, before the endpoint's own `404`: the answer tells nothing of a file outside.
- Not checked: a resume or a validate of a sweep replays a spec stored when it was created, and the server's own
  reads (a profile's start) open what a profile names.

- **Models folder**: the `modelsDir` setting, `~`-expanded, can be any directory. `GET /api/models` walks it for
  `*.gguf` files, skipping names that start with `.` and not following directory symlinks (a symlinked `.gguf` file is
  followed).
- **GGUF info**: `GET /api/models/info?path=` reads the header of any absolute path that ends in `.gguf` and is a
  file allowed by the rule above: `400` `RequestInvalid` `Invalid data: Absolute path to a .gguf file expected (path)`
  for another path, `403` `ModelPathRefused` outside the rule, `404` `ModelFileNotFound` `File not found` when it does
  not exist, `422` `ModelUnreadable` when the file does not parse.
- **Profile paths**: a profile's model, projector and working directory can be anywhere (they open the rule above). `profilePaths()` resolves
  them the way `llama-server` will (`~` expanded, relative to the profile's `cwd`) wherever llama-webui reads the
  model itself, for example for benchmarks.
- **Hugging Face downloads** are the only writes into a user-chosen folder, and they are confined. `repoDir()` accepts
  only an `org/name` repository ID matching `HF_REPO_RE` (checked by the request's schema: `400` `RequestInvalid`
`Invalid data: Invalid repository id: …`) and maps it to
  `<modelsDir>/<org>/<name>`. `fileDest()` refuses a file path that is absolute or resolves outside that folder
  (`400` `HfInvalidPath` `Invalid file path in the repository: …`).

## Tests

`app/server/http/Guard.test.ts` calls `refusal()` on plain requests:

- `127.0.0.1`, `localhost`, a LAN IP and `[::1]` are accepted as `Host`, and `evil.example` gets `403`;
- an `Origin` from another site gets `403`, the same origin passes, and `http://localhost:7860` is refused for a
  request to `127.0.0.1:7860`;
- a `PATCH` with `text/plain` and a `POST` with a body and no `Content-Type` get `415`;
  `application/json; charset=utf-8` passes, and so does a `POST` without a body;
- the body is judged from `content-length` and `transfer-encoding`, and a `Host` that is not an authority is a `400`.

The contract suite (`app/server/contract/cases.ts`) replays the guard against the production build: a domain as
`Host`, a `Host` that is not an authority, a foreign `Origin`, and the broken bodies of each payload. `app/server/hf/paths.test.ts` checks that
`repoDir()` and `fileDest()` refuse `..`, absolute and empty paths, and `packages/webui-shared/src/profile.test.ts`
that an import with a reserved flag is rejected.
