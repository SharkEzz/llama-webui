The benchmark module measures one configuration at a time with `llama-bench` or with a temporary `llama-server`, and
runs sweeps: lists of `llama-bench` runs planned by the estimator, optionally validated on the server. It lives in
`app/server/bench/`, with its schemas in `packages/webui-shared/src/bench.ts` and `packages/webui-shared/src/sweep.ts`
and its API groups in `packages/webui-shared/src/api/BenchApi.ts` and `SweepsApi.ts`. For what users see, read [Benchmark](/docs/benchmark/) and
[Sweeps](/docs/sweeps/).

## How the pieces fit

A request goes through three parts, each with one job:

- **`BenchRunner`** decides what runs. It accepts one one-off run or one sweep at a time, creates and updates the rows,
  and publishes the progress on the WebSocket hub.
- **The gate** owns the managed `llama-server` for the duration: it stops it before the first measurement and
  restarts it after the last one, once per one-off run or per sweep.
- **`execute()`** runs a single measurement. It never touches the managed server and never writes to the database:
  it gives back a result that the runner saves.

The runner is a service of the app (`BenchRunner.layer`); it makes its gate on the supervisor when it is built, runs
its work in fibers of its own scope, and registers a shutdown step (see
[Shutdown and restarts](#shutdown-and-restarts)).

## Specs and parameters

A run is described by a `BenchSpec` (`packages/webui-shared/src/bench.ts`):

| Field        | Type                    | Default | Notes                                                                                |
| ------------ | ----------------------- | ------- | ------------------------------------------------------------------------------------ |
| `kind`       | `"bench"` or `"server"` |         | The tool: `llama-bench` or a temporary `llama-server`                                |
| `modelPath`  | string                  |         | Absolute path ending in `.gguf`                                                      |
| `mmprojPath` | string or null          | `null`  | Projector, loaded by server runs only                                                |
| `profileId`  | integer or null         | `null`  | Source profile: its directory and environment variables are reused                   |
| `p`          | integer, 1 to 32,768    | `512`   | Prompt tokens                                                                        |
| `n`          | integer, 1 to 4,096     | `128`   | Generated tokens                                                                     |
| `r`          | integer, 1 to 20        | `3`     | Repetitions                                                                          |
| `params`     | `BenchParams`           | `{}`    | The flags both tools understand                                                      |
| `serverArgs` | string[]                | `[]`    | Other `llama-server` flags; reserved flags and flags covered by a field are rejected |

`BenchParams` holds the flags that both tools accept, in a fixed order (`FIELD_ORDER`): `ngl`, `ot`, `ncmoe`, `dev`,
`ts`, `sm`, `fa`, `ctk`, `ctv`, `t`, `b`, `ub`. A missing key means the tool's default. Two functions write them out,
because the tools disagree on list syntax:

- `serverArgs(params)` separates values with `,` and writes `-ngl all` as is.
- `benchArgs(params)` separates `-dev` and `-ts` values with `/` and `-ot` rules with `;`, and writes `-ngl all` as
  `-ngl 999`.

Neither writes `-ngl auto`: the tool's default applies. In the other direction, `paramsFromServerArgs(args)` splits a
profile's arguments into fields and the rest, in their original order (`GET /api/bench/from-profile/:id` uses it), and
`ignoredByBench(rest)` lists the profile flags `llama-bench` does not reproduce: `-c`, the speculative decoding flags,
`-cmoe` and `-np`.

## The server gate

The gate (`app/server/bench/gate.ts`) has a single holder, a one-off run or a sweep. It remembers the command of the
server it stopped (`stoppedCommand`), the stop in progress, and the release in progress.

### Acquire

`acquire({ stopServer })` takes the gate, or refuses with a `409` (the runner has already refused a second benchmark
with `BenchRunning` `A benchmark is running`):

1. If the managed server is stopping, it waits for the stop, polling every 100 ms for up to 60 seconds
   (`stoppingTimeout`), then fails with `ServerStopTooSlow` `llama-server is taking too long to stop: try again`. A
   stop that someone else started leaves nothing to restart.
2. If an external server runs: `ExternalServerRunning` `An external llama-server is running on port N: stop it
first`.
3. If the managed server is starting, ready or sleeping and `stopServer` is false: `ServerRunning`. The web app tells it by its
   `_tag`, shows its confirmation dialog, then sends the same request again with `stopServer: true`.
4. Otherwise it records the supervisor's `lastCommand`, logs `[bench] stopping llama-server for the benchmark`, and
   forks the stop in the runner's scope **without awaiting it**.

The request therefore answers as soon as the gate is taken. The first run starts in the `stopping-server` phase, and
the runner runs `ready`, which awaits the stop, before it launches anything. If the stop fails, nothing is restarted
and the run fails with `could not stop llama-server: …`.

### Release

`release(rebuild)` waits for the stop to finish, restarts the stopped server (logged as
`[bench] restarting llama-server (<profile>)`), and frees the gate even when the restart fails. The command comes from
`rebuild(stopped)`, given by the runner: `buildCommand()` on the profile as it is now, so edits saved during the
benchmark apply. The recorded command is the fallback, when the profile was deleted. Two releases at once are one (a
`Deferred`). A failed restart fails with `could not restart llama-server: …` (also pushed to the log ring); the runner
appends that message to the error of the run (the last item for a sweep), so it shows on the **Last run** card and in
the history.

### While the gate is held

`BenchRunner.busy` is true while a run is being accepted, while one runs, while a sweep runs, and while the gate is
held. Other modules read it:

- the server endpoints (`app/server/supervisor/http.ts`) refuse start, switch, restart and stop with `409`
  `BenchRunning` `A benchmark is running`;
- `POST /api/tuning/disk-speed` refuses with `A benchmark is running: the measurement would be skewed`;
- the external watch (`ExternalWatch`) does nothing: the temporary `llama-server` listens on the settings port and
  would otherwise be seen as an external server;
- `files` gives the model and projector in use, which the model deletion refuses to delete.

## The runner

`BenchRunner` (`app/server/bench/BenchRunner.ts`) holds, in one `SynchronizedRef`, the current run, the running
sweep and the fiber of the work.

### One-off runs

`start(spec, { stopServer })` claims the runner (`409` `BenchRunning` `A benchmark is running` when it is busy),
checks that the model and the projector exist (`404` `BenchFileMissing` `Model not found: …`, `Projector not found:
…`), then takes the gate: a missing file is refused before anything is stopped. It reads the hardware, creates the row
with status `running`, the command and the hardware frozen (`BenchRunsRepo.create`), publishes it, and returns it while
the run continues in a fiber of the runner: the endpoint answers `202`.

The background part executes the run, saves its result with `BenchRunsRepo.finish`, then releases the gate. While the
server restarts, the live state shows the `restarting-server` phase; when everything is over, the live state becomes
`null`.

That fiber is not awaited by anyone, so a defect in it (the database failing while a result is saved…) is caught where
it is forked (`crashed()`): it is logged (`a benchmark stopped on a defect`), the current run is saved `failed` with
`internal error: <message>`, a running sweep is left `interrupted` (it can be resumed), the gate is released, so
`llama-server` is restarted, and the runner is free again. Each of these steps is tried even when the one before it
fails.

`cancel(id)` only acts on the current run (`404` `RunNotFound`, `409` `RunNotRunning` otherwise). It completes the
run's cancel signal, and `execute()` sends `SIGTERM`, then `SIGKILL` after 5 seconds (`killTimeout`); the saved
status is `cancelled`. In a sweep, cancelling the current item
moves on to the next one.

A run's status (`BenchStatus`) is one of `queued` (a sweep item waiting its turn), `running`, `ok`, `failed`,
`cancelled` and `interrupted`.

## The executor

`execute()` (`app/server/bench/execute.ts`) runs one measurement in the runner's scope and gives back its result,
without saving it.

### The command

`commandOf(spec)` gives the `argv`, the `display` string stored with the run, and for server runs the
`BuiltCommand`.

<Tabs>
  <Tab title="llama-bench">

`llama-bench` is looked for next to the `llama-server` binary from the settings, `~` expanded (`benchBinary()`: the
same folder, with `llama-server` replaced by `llama-bench` in the file name; a bare name stays bare and is looked up
in the `PATH`). The child runs under `setpriv --pdeathsig KILL`, so it dies with llama-webui, and gets llama-webui's
environment, then the `env` setting, then the source profile's environment (the same `CUDA_VISIBLE_DEVICES`, for
example).

```ts title="app/server/bench/execute.ts"
const bench = [
  binary,
  '-m',
  spec.modelPath,
  '-o',
  'json',
  '--progress',
  '-r',
  `${spec.r}`,
  '-p',
  `${spec.p}`,
  '-n',
  `${spec.n}`,
  ...benchArgs(spec.params),
];
const command: RunCommand = {
  argv: ['setpriv', '--pdeathsig', 'KILL', '--', ...bench],
  display: shellQuote(bench),
  server: Option.none(),
};
```

The displayed command leaves out the `setpriv` prefix.

  </Tab>
  <Tab title="Server">

A server run builds a throwaway profile named `bench` and passes it to `buildCommand()`: the model and
projector, `serverArgs(params)` followed by `serverArgs`, host `127.0.0.1` and the port from the settings, plus the
flags the supervisor always adds (`--metrics`, `--slots`, `--props`). The working directory and environment variables
come from the source profile, because its flags may use relative paths; without one, the folder is the model's.
`buildCommand()` adds the `env` setting under the profile's variables, as for any launch.

  </Tab>
</Tabs>

### Running and reporting

`execute({ run, spec, onLive, cancel, … })` runs the tool through `followProgram()` and gives back an `ExecResult`
with:

- `status`, `pp`, `tg` (each a `Measure`: `tps`, `stddev`, `tokens`) and, for server runs, `draftAcceptPct`;
- `vramPeak`: one entry per card, in MiB, cards at 0 left out (see [Peak VRAM and disk](#peak-vram-and-disk));
- `logExcerpt`: the tool's last `TAIL = 50` lines, stored in the run's `log_excerpt` column (cleared by a requeue) and
  never read back: no reply carries it, and the repository does not select it;
- `durationMs` and `diskReadPeakBps`.

Every line of the tool also goes to the log ring with a `[bench]` prefix. The live state (`BenchLive`) carries the
phase, the step (`index` of `total`), the start time and the last `LIVE_LINES = 20` lines. A phase change is reported
at once; new lines at most every `liveThrottle` (250 ms, throttled by the runner), because `llama-server` writes hundreds of them while it
loads.

### llama-bench runs

`llama-bench` writes its progress on stderr (`--progress`) and its results as JSON on stdout (`-o json`).

- `parseBenchProgress(line)` reads lines such as `llama-bench: benchmark 1/2: prompt run 2/3`. The phase becomes
  `warmup`, `prompt` or `generation`, and the step counts runs across both tests: `(test − 1) × runs + run` out of
  `tests × runs`.
- `parseBenchJson(stdout)` is only called when the exit code is 0. An entry with `n_prompt > 0` and `n_gen = 0` is the
  prompt test, the reverse is the generation test; `avg_ts`, `stddev_ts` and the token count make the `Measure`. It
  returns `null` for missing or truncated JSON (a failed load). It never reads `model_filename`, which `llama-bench`
  encodes badly.

The run is `ok` when the JSON gives at least one of the two measures, `failed` otherwise.

### Server runs

`runTrial()` (`app/server/bench/trial.ts`) measures a real `llama-server`:

<Steps>
  <Step title="Check the port">

If something already answers `/health` on the port, the run fails with `port N is used by another server`.

  </Step>
  <Step title="Load">

It spawns the server, follows `GET /models/sse` for live `loadProgress` (`status_change` events), and independently
polls `/health` every 500 ms. Stage-only SSE announcements reuse the current load's last stage order.
Warmup starts when SSE reports `loaded` or `/health` returns `200`. It fails with
`loading > 10 min` after 10 minutes (`loadTimeout`), or with the failure read from its output (see
[Failure messages](#failure-messages)) if the process exits first.

  </Step>
  <Step title="Warm up">

One `POST /completion` with `WARMUP_PROMPT` (`Write one short sentence about the sea.`) and `n_predict: 16`. The
prompt is a sentence on purpose: llama.cpp segfaults on a 2-token prompt with `-sm tensor` and an MTP draft
(`--spec-type draft-mtp`), and the earlier `Hello.` crashed every such run.

  </Step>
  <Step title="Measure">

`r` identical `POST /v1/chat/completions` requests. The user message is `promptOf(p)` (a fixed text of about `p`
tokens, at 4 characters per token, the same on every run) followed by an instruction to write a new story. Each request
asks for exactly `n` tokens (`max_tokens: n`, `ignore_eos: true`) with thinking disabled
(`chat_template_kwargs: { enable_thinking: false }`). Every request also sends `cache_prompt: false`,
`temperature: 0`, `seed: 42` and `stream: false`, and times out after 10 minutes (`requestTimeout`). The requests
go through `LlamaHttp` (`app/server/llama/LlamaHttp.ts`), `node:http` without a time limit on the headers or the body:
Node's own `fetch` gives up after 300 s without response headers, well before that timeout, and nothing in Node
changes it.

  </Step>
  <Step title="Stop">

The server is always stopped, whatever happened (`stopGently()`, in a finalizer of the trial's scope): `SIGTERM`,
then `SIGKILL` after 5 seconds. An interruption (llama-webui stopping) kills it at once (`killSignal: 'SIGKILL'`).

  </Step>
</Steps>

`pp` and `tg` are the mean and the population standard deviation of `prompt_per_second` and `predicted_per_second`
from the responses' `timings`, with the token counts of the last response. `draftAcceptPct` is the sum of
`draft_n_accepted` over the sum of `draft_n`, as a percentage with one decimal, or `null` without speculative decoding.

The measurement goes through chat on purpose. The code's comment explains why: a repeated raw prompt makes the model
copy it, and speculative decoding (MTP) then accepts almost all its drafts, 95% measured against about 50% in a real
conversation.

When the server dies during a request (a CUDA out of memory, for example), the socket closes before its output is read.
The trial then waits up to `EXIT_GRACE` (2 seconds) for the process to exit, so that the error is the server's own
line rather than the closed connection.

A server trial keeps the last 10 lines that match `ERROR_LINE` apart from its 50-line tail, and passes both to
`benchFailure()`. A crash can bury the error under more lines than the tail keeps: on a `GGML_ASSERT` llama.cpp prints a
gdb backtrace after the `cudaMalloc failed: out of memory` line, and the run would otherwise read as a bare
`llama-server exited (code SIGABRT)`.

### Failure messages

`benchFailure({ … })` turns the last lines of a tool into the run's error:

- If any line matches `out of memory`, `failed to allocate` or `unable to allocate`, the run is an out of memory: the
  error is `OOM_ERROR` (`"Out of memory"`) followed by the last such line, for example
  `Out of memory: … unable to allocate CUDA1 buffer`.
- Otherwise the last line matching `ERROR_LINE` (CUDA errors, `error loading …:`, `what():`…) is the error.
- Without such a line: `llama-bench exited (code N)` (or `llama-server exited …`).

The web app recognizes an out of memory with `isOomError(error)` from `@llama-webui/shared` rather than by comparing
the text itself. `isOomError` also accepts the prefix written by earlier versions (`Mémoire insuffisante`), still present in
existing databases.

## Peak VRAM and disk

During each run, `execute()` measures what the run itself adds on each card:

- **Starting point.** The VRAM used per card in the Monitor's latest snapshot when the run starts (`allGpus`: hidden
  cards included).
- **Monitor samples.** Every 500 ms (`SAMPLE`) it reads the latest snapshot again. The Monitor itself samples every
  second by default, so a short peak can slip between two snapshots.
- **Fast probe.** `startVramProbe()` (`app/server/bench/vram.ts`) samples every 100 ms, in the run's scope: one
  `nvidia-smi --query-gpu=uuid,memory.used --format=csv,noheader,nounits -lms 100` process for NVIDIA cards
  (`parseSmiLine()` maps each UUID to the Monitor's `nvidia:<uuid>` key), and the sysfs file
  `/sys/bus/pci/devices/<busId>/mem_info_vram_used` for AMD cards. A source that fails is ignored.

The peak of a card is the largest of the two measures, each taken as the maximum minus the starting value. When the run
exits, the executor takes a last sample, stops the probe (`stop`: its `nvidia-smi` and its sysfs fiber end with its
scope) and merges the probe's peaks (`readings`).

The same sampler keeps the highest read bandwidth of the model's disk reported by the Monitor (`disk.model.readBps`),
saved as `diskReadPeakBps`.

## Hardware and the device list

`BenchHardware` (`app/server/bench/BenchHardware.ts`) reads what a run records about the machine, and the devices
llama.cpp sees.

- `hardware(gpus)` gives the hardware of a run: the CPU model (from `CpuInfo`, read once), each GPU's name, bus id and total VRAM, and
  the build. It is frozen in `hardware_json` when a one-off run is created or a sweep item starts.
- `build(binary)` runs `<binary> --version` (5-second timeout) and turns `build 12119, commit 6f1e65437` into
  `b12119 (6f1e65437)`. The result is cached per binary path and modification time, so a rebuild is read again;
  `null` when unreadable.
- `devices(benchBinary)` runs `llama-bench --list-devices` (15-second timeout) and parses it with
  `parseDeviceList()` into `BenchDevice`s: `id` (`CUDA0`), `name`, `totalMib`, `freeMib`, and `backend` (the letters
  of the id: `CUDA`, `Vulkan`, `BLAS`…). It gives `{ devices, error }`; `listDevices()` is its `devices`.

The list is cached per binary path and modification time, so a rebuild is read again. A listing is not trusted, and
not cached, when:

- the tool is missing, exits with a non-zero code or is killed by a signal (recent builds crash in `--list-devices`
  while llama-server holds the GPUs, after printing part of the list);
- it prints more than 1 MiB: it is killed at once (`printed more than 1 MiB`); `--version` gives `null` the same way;
- a GPU backend's device (CUDA, ROCm, Vulkan…) is listed with 0 MiB.

`error` then says why, and `devices` is the last good list of that binary (`[]` if there was none). The free memory in
the cached list is that of its first read: the estimator takes the live one from the Monitor (see
[Live memory](/developers/server/tuning/#live-memory)).

The list feeds `GET /api/bench/devices` (the device picker of the form), and through `TuningHardware` the
[Tuning](/developers/server/tuning/) estimator and sweep planning.

## Sweeps

A sweep explores a space of flags with `llama-bench`, ranks the results with a preset's score, and can validate the
best ones on the server. It runs through the same runner, gate and executor as a one-off run: the gate is taken once
for the whole sweep.

### The spec and the plan

A `SweepSpec` (`packages/webui-shared/src/sweep.ts`) has the run fields of a `BenchSpec` (`modelPath`,
`mmprojPath`, `profileId`, `p`, `n`, `r`, `serverArgs`) plus:

| Field          | Type            | Default | Notes                                             |
| -------------- | --------------- | ------- | ------------------------------------------------- |
| `name`         | string, 1 to 80 |         | Trimmed                                           |
| `preset`       | a `PresetId`    |         | Gives the score and the default context           |
| `base`         | `BenchParams`   | `{}`    | The values every item shares                      |
| `space`        | `SweepSpace`    | `{}`    | For each field, a non-empty list of values to try |
| `includeUnfit` | boolean         | `false` | Keep the items the estimator says do not fit      |

`planSweep()` (`app/server/tuning/space.ts`) turns the spec into items:

1. `expandSpace(base, space)` makes the cartesian product of the space over the base, in `FIELD_ORDER`. A `-ts` is kept
   only on items whose `-dev` lists the same number of devices, and more than one; `droppedTs` counts the ones dropped.
   Duplicates are removed, and an empty space gives the base alone.
2. Each item gets `fitOf()` from the [estimator](/developers/server/tuning/), at the sweep's context `sweepCtx(spec)`
   (the last `-c` among `serverArgs`, read by `ctxFromArgs()`, otherwise the preset's `ctxMin`; the web app appends
   the recommendation's `-c` when the source profile has none), with the item's cache types (`f16` by default) and
   `-ub` (512 by default).
3. Items with a `no` verdict are left out unless `includeUnfit`; `excluded` counts them.
4. Each item is labelled with `itemLabel()`: only the dimensions of the space, as `llama-server` flags
   (`-ncmoe 8 · -dev CUDA0,CUDA1`), or `base` when the space is empty.
5. `estimatedSweepSeconds()` adds, per item, one model load at 1.5 GiB/s and 10 seconds per repetition.

The same function answers `POST /api/tuning/plan` (the preview) and runs again in `POST /api/sweeps`, which refuses an
empty plan with `409` `NothingToRun` `No configuration to run: N excluded by the estimator`.

### Exploration

`POST /api/sweeps` calls `startSweep({ files, stopServer, check, prepare })`. `prepare` writes the `sweeps` row and
enqueues one `bench_runs` row per item (`kind: "bench"`, status `queued`, its label and verdict). The runner runs it
only once the gate is taken, so a `409` refusal writes nothing; a failure of `prepare` releases the gate.

The sweep loop then repeats until the queue is empty or the sweep is cancelled:

1. Take the next queued item of the sweep (`nextQueued`: lowest id first).
2. Publish a `SweepLive`: `sweepId`, `runId`, `index` (1-based), `total`, and `stage`, which is `validate` for a server
   item and `explore` otherwise.
3. Read the hardware, freeze the command and hardware on the row and set its date to now (`BenchRunsRepo.begin`), run
   it, save the result. A failure, out of memory included, does not stop the sweep.
4. Publish the updated `Sweep` (its counters changed), then wait `pause` (1 second) before the next item while the VRAM
   is freed.

At the end, the sweep becomes `done` (or `cancelled`) with its best run and `finishedAt`, and the gate is released:
the server is restarted once, and a failed restart is appended to the error of the last item.

### Ranking

`rankRuns(runs, preset, ctx)` sorts the successful runs by the preset's score (`scoreOf()`, which uses the preset's
`score` function from `packages/webui-shared/src/tuning.ts`) and gives them a rank; the other runs follow, unranked, in their original
order. A run is a `tie` with the best when its score is within the noise band: the difference between the best score
and the score the best run would get with its prompt speed lowered by `NOISE.pp = 0.1` and its generation speed by
`NOISE.tg = 0.02`. The best run is marked as a tie too when another run ties with it.

The sweep's best run (`bestRunId`) comes from the validation runs if at least one succeeded, otherwise from the
exploration runs. The two kinds are never ranked together: `llama-bench` and `llama-server` speeds are not comparable.

### Validation

`POST /api/sweeps/:id/validate` takes the `n` best ranked exploration runs (1 to 5, 3 by default) and enqueues one
server run for each: `kind: "server"`, the run's `params`, the sweep's `serverArgs`, `p`, `n` and `r`, the label
`validation · <label>`, and the exploration run's verdict. It also puts the sweep's interrupted items back in the
queue, since nothing else could finish them, then starts the sweep again. It is refused when no
exploration run succeeded (`409` `NothingToValidate` `No successful run to validate`). See
[Validate on the server](/docs/sweeps/#validate-on-the-server) for what the user sees.

### Persistence

A sweep is one row of `sweeps` (status, `spec_json` holding the `SweepSpec`, `best_run_id`, `created_at`,
`finished_at`); its items are rows of `bench_runs` with a `sweep_id`, a `sweep_label` and the estimator's `fit`.
Deleting a sweep deletes its runs (`ON DELETE CASCADE`). `bench_runs` ids use `AUTOINCREMENT`, so a deleted id is
never handed out again: `best_run_id` relies on it.

`SweepsRepo` computes `counts` (total and per status) from `bench_runs` on every read, and `best` (label, kind, prompt
and generation speed) from the best run. `BenchRunsRepo.list` only returns one-off runs by default (`sweepId:
"none"`). The schema itself is on the [Database](/developers/server/database/) page.

A sweep's status (`SweepStatus`) is `running`, `done`, `cancelled` or `interrupted`.

### Cancel and resume

- `cancelSweep(id)` sets the queued items to `cancelled`, cancels the current item, and publishes the sweep. The loop then
  ends with the status `cancelled` and releases the gate.
- `POST /api/sweeps/:id/resume` (`resume(id, { stopServer })`) checks first that the sweep has an interrupted or queued
  item (`409` `NothingToResume` `Nothing to resume: no interrupted or queued item`: a cancelled sweep has none), then
  takes the gate, puts the interrupted items back in the queue (`requeueInterrupted`) and starts the sweep.
- Resume, validate and delete refuse a running sweep with `409` `SweepStillRunning` `This sweep is still running:
cancel it first`.

## Shutdown and restarts

| Event                              | One-off run in progress | Sweep item in progress | Sweep         | Server stopped by the gate       |
| ---------------------------------- | ----------------------- | ---------------------- | ------------- | -------------------------------- |
| Shutdown (`SIGINT`, `SIGTERM`)     | `interrupted`           | `interrupted`          | `interrupted` | Not restarted: llama-webui exits |
| Start after llama-webui was killed | `interrupted`           | `interrupted`          | `interrupted` | Not restarted                    |

In development, a save of a file the server imports (`app/server/`, `packages/`) restarts it (`node --watch`): it is
a shutdown like any other, and an interrupted sweep is resumed from the UI. A save under `app/src/` is HMR, and a
running benchmark goes on.

### Shutdown and cold start

On `SIGINT` or `SIGTERM`, the shutdown step of the runner (`shutdown.before`) runs before the HTTP server closes and
while `llama-server` still runs ([Architecture](/developers/architecture/#shutdown)). It sets `closing` (the work
publishes nothing after it), interrupts the work, which kills the child at once through its scope
(`killSignal: 'SIGKILL'`), saves the current run (sweep item included) as `interrupted` with the error
`interrupted (llama-webui stopped)`, and the sweep as `interrupted`. It publishes them itself, straight to the hub
(`bench-run`, then `sweep`), then `bench-progress` and `sweep-progress` `null`: the hub is still open, so a page that
is open sees the end before its `1001`. The gate is not released: llama-webui is exiting, and the supervisor stops with it.

When llama-webui was killed without that chance, rows stay `running`. When the runner's layer is built at the next
start, it runs `BenchRunsRepo.stopOrphans` (running runs become `interrupted`, with the error
`interrupted (llama-webui stopped)` when they had none) and `SweepsRepo.stopOrphans` (running sweeps become
`interrupted`). The command of the stopped server was only in memory: llama-webui does not start the profile again.

## WebSocket messages

The runner publishes these on the hub; the delete endpoints publish the deletions. The payload schemas are in
`packages/webui-shared/src/ws.ts`; see [WebSocket](/developers/api/websocket/).

| Message          | Payload             | When                                                                                                    |
| ---------------- | ------------------- | ------------------------------------------------------------------------------------------------------- |
| `bench-progress` | `BenchLive \| null` | Phase or step changes, new lines (at most every 250 ms); `null` when a one-off run or a sweep item ends |
| `bench-run`      | `BenchRun`          | A one-off run is created, a sweep item starts, a run ends, a failed restart is added to a run's error   |
| `bench-deleted`  | `{ ids }`           | A run is deleted, failed runs are cleared, or a sweep is deleted (its runs)                             |
| `sweep-progress` | `SweepLive \| null` | Before each item; `null` when the sweep ends                                                            |
| `sweep`          | `Sweep`             | The sweep starts or resumes, after each item, on cancel, at the end                                     |
| `sweep-deleted`  | `{ id }`            | A sweep is deleted                                                                                      |

A client that connects late reads the current state over HTTP: `GET /api/bench/runs` returns `live`, and
`GET /api/sweeps` returns the sweep's `live`.
