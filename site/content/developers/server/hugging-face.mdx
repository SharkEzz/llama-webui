description: The Hub client, how repository files become variants, and the persistent download queue with .part resume, retries, sha256 checks and path safety.

The Hugging Face module searches the Hub, lists a repository's GGUF files as downloadable variants, and downloads them
into the models folder through a persistent queue that survives restarts. The Hub client lives in `app/server/hf/`,
the queue in `app/server/downloads/`, their schemas in `packages/webui-shared/src/hf.ts` and their API groups in
`packages/webui-shared/src/api/HfApi.ts` and `DownloadsApi.ts`. For what users see, read
[Hugging Face downloads](/docs/hugging-face/).

## From a search to a file

1. The web app reads what the user typed with `parseHfInput()` (`packages/webui-shared/src/hf.ts`): a repository id (`org/name`), the
   llama.cpp `-hf` syntax (`org/name:Q4_K_M`), a `huggingface.co` or `hf.co` URL (a `blob` or `resolve` URL also gives
   the file), or free text.
2. Free text goes to `GET /api/hf/search`, which calls `HfClient.search()`.
3. A repository goes to `GET /api/hf/repo`, which calls `describeRepo()`: the repository's files at a revision
   (`main` by default), grouped into variants, with what is already on disk and the commit they were listed at
   (`sha`).
4. `POST /api/downloads` sends `{ repo, revision, keys }` (`DownloadRequest`: `revision` must be a 40-character
   commit sha, 1 to 16 keys). `downloadInputs()` reads the repository again **at that commit**, so sizes and checksums
   come from the Hub and not from the client, then `Downloads.enqueue()` queues them.
5. The queue downloads each file to `<file>.part`, checks its sha256 and renames it into place. The web app follows it
   over the WebSocket and rescans the models when an item is done.

Pinning the commit guarantees that all the shards of a split model come from the same version, even if the
repository changes while they download.

## The Hub client

`HfClient` (`app/server/hf/HfClient.ts`) calls the Hub's JSON API at the [endpoint](#token-and-endpoint) through
`HfHttp`, with the header `user-agent: llama-webui` and, when there is a token, `authorization: Bearer <token>`. Every
call runs in a scope of its own and must end within 10 seconds, its redirects followed (5 at most, only on the
endpoint's origin, so the token never leaves it) and its body read; a `200` is decoded with a schema. A call is also
dropped when the browser's request is (a closed sheet, a new keystroke): the handler is interrupted, which aborts the
request.

| Method                    | Hub request                                                                                                                               | Returns                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `search(q)`               | `/api/models?search=<q>&filter=gguf&sort=downloads&direction=-1&limit=30`, with `downloads`, `likes`, `gated` and `lastModified` expanded | `HfSearchHit[]`, most downloaded first                                           |
| `repoFiles(id, revision)` | `/api/models/<id>/revision/<revision>?blobs=true`                                                                                         | The resolved commit (`sha`), `gated`, and each file's path, size and sha256      |
| `status`                  | `/api/whoami-v2`, only with a token                                                                                                       | `HfStatus`: token source, account name, whether the token was rejected, endpoint |

For a file stored with Git LFS, the size and the sha256 come from its `lfs` entry. Other files have no sha256: they
are not verified. `status` asks for the account once per token; a network failure is not cached (it is tried again next
time), a rejected token is.

### Errors

`hubError()` turns a Hub answer that is not a success into one of the tagged errors of `HfApi`, which the endpoint
answers as they are. It reads the `X-Error-Code` header first, because a missing or private repository answers
`401 RepoNotFound` to an anonymous request.

| `_tag`           | Status | When                                                                                                                                                                 |
| ---------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HfGated`        | 403    | `X-Error-Code: GatedRepo`, or a `403`                                                                                                                                |
| `HfNotFound`     | 404    | `RepoNotFound`, `RevisionNotFound`, `EntryNotFound`, or a `404`                                                                                                      |
| `HfUnauthorized` | 401    | Any other `401`: the token was rejected                                                                                                                              |
| `HfRateLimited`  | 429    | `429`                                                                                                                                                                |
| `HfUnreachable`  | 502    | Any other status, a request without an answer (`Hugging Face unreachable: <reason>`), no answer in 10 s, or a `200` that does not decode (a proxy or captive portal) |

Without a token, the gated and not-found messages end with ``(set HF_TOKEN or run `hf auth login`)``.

## Variants

`groupRepoFiles(files)` (`app/server/hf/variants.ts`) turns the repository's file list into what the download sheet
offers:

- Only `.gguf` files are kept; README, safetensors and the rest are ignored, and so are the GGUF files whose name
  starts with `imatrix` (`imatrix.gguf`, `imatrix_unsloth.gguf`): calibration data, not a model.
- Shards (`…-00001-of-00003.gguf`, possibly in a subfolder) are grouped by prefix and total into one variant; any
  other file is a variant of its own.
- A variant's `key` is the path of its first file (files sorted by path): it identifies the variant in requests and
  in the queue. Its `name` is the file name without folder, shard suffix or extension, and its `quant` is read from
  the name by `parseGGUFQuantLabel()` (`Q4_K_M`, `UD-Q4_K_XL`, `BF16`…), or `null`.
- A variant whose first file name contains `mmproj` is a projector, listed apart.
- Both lists are sorted by total size, smallest first.

Only the extension is checked: a `.gguf` that is not a model, such as an importance matrix shipped as GGUF, is listed
as a variant too.

`describeRepo()` adds the local state of each variant (`HfPresence`): `complete` when every file is at its destination
with the expected size, `partial` when some are, or when a `.part` or a file of another size exists, `none` otherwise. Whether a variant is queued is
left to the web app, which has the queue. The fit badge comes from `vramFit(bytes, vramBytes)` in the web app: up to
85% of the VRAM `fits`, up to 100% `tight`, beyond `offload`, and no badge without a GPU.

## Destination paths

Downloads land in `<models folder>/<org>/<name>/`, keeping the repository's subfolders.

- `repoDir(modelsDir, repo)` returns `<resolved modelsDir>/<org>/<name>`. The id was checked against `HF_REPO_RE`
  (two segments that start and end with a word character, which rules out `..`): the request's by its schema, the
  one the Hub answers by `HfClient`'s. The models folder comes from [Settings](/docs/settings/), with `~` expanded.
- `fileDest(dir, path)` refuses an absolute path, and any path that resolves outside the repository's folder, with
  `400` `HfInvalidPath` `Invalid file path in the repository: …`. `downloadInputs()` calls it for every file before anything is queued,
  and the queue calls it again before every file operation.
- `partPath(dest)` is `<dest>.part`. The models scan only keeps `*.gguf` files, so a download in progress never shows
  up as a model.

A `DownloadItem` stores its absolute folder (`dir`) when it is queued: changing the models folder later does not move
it.

## The download queue

`Downloads` (`app/server/downloads/Downloads.ts`) downloads one item at a time, one file after another, in a fiber of
the layer's scope that the build starts (for the items left by the last run), and `enqueue` and `retry` too.

### Enqueue

`enqueue(inputs)`, `retry(id)` and the removals run one after the other (a semaphore), so that the duplicate and
disk space checks of two concurrent requests see each other's rows. Before it, `downloadInputs()` refuses a variant
listed twice in the request (`400` `ListedTwice` `… is listed twice`) and a key the repository does not have
(`404` `HfNotFound` `No GGUF “<key>” in <repo>`). `enqueue()`:

1. Refuses a variant already queued or downloading, matched by repository and key (`409` `AlreadyQueued`
   `… is already in the download queue`).
2. Leaves out the files already at their destination with the expected size. A variant with nothing left is skipped;
   when every variant is skipped, the response has no item and the web app says the model is already downloaded.
3. Checks the disk space: the bytes still needed (a `.part` counts as written), plus what the active items still have
   to write, plus the margin (1 GiB), against the free space of the folder's file system (`freeBytesOf()`: the folder
   or its nearest existing parent). It refuses with `507` `DiskFull`
   `Not enough disk space: 1.5 GiB to download (plus 1.0 GiB margin), 2.0 GiB free`. When the free space is unknown,
   there is no check.
4. Creates one row per variant (status `queued`) in one transaction, publishes each one, and starts the loop.

### Processing a file

The loop takes `DownloadsRepo.next`: an item left `downloading` first (interrupted by a restart), then
the oldest queued one. For each file not yet done, an attempt:

<Steps>
  <Step title="Look at the disk">

A destination file with the expected size counts as done (renamed into place just before a stop, before the row
recorded it). Otherwise the offset is the size of the `.part`; a `.part`
larger than the file cannot be this file and is deleted. An empty file has nothing to ask the Hub for: its empty
`.part` is created on the spot, then checked and renamed like any other.

  </Step>
  <Step title="Prepare the checksum">

The sha256 of the bytes already in the `.part` is needed to finish the computation. It is kept in memory between the
attempts of an item; after a restart, or a write that failed half-way, the `.part` is read back from disk
(the `verifying` phase).

  </Step>
  <Step title="Transfer">

A `GET` of the file from the offset, appended to the `.part` (see [Range resume](#range-resume)). Each chunk is written
first, then added to the hash: a chunk that failed to reach the disk is never hashed.

  </Step>
  <Step title="Verify and rename">

A `.part` shorter than the file is kept, a longer one is deleted, and the attempt is retried. On a sha256 mismatch the
`.part` is deleted and the item fails with `code: "checksum-mismatch"`
(`Checksum mismatch for <file>: the file was deleted`). Otherwise the `.part` is renamed to its final name and the file
is marked done.

  </Step>
</Steps>

When every file is done, the item becomes `done`. The `.part` is written through Effect's `FileSystem`, and the
checksum is a streamed sha256 (`downloads/hash.ts`, on `node:crypto`: Effect's digest is one-shot over one buffer).

The transfer goes through `HfHttp` (`app/server/hf/HfHttp.ts`), `node:https` on agents of its own that speak
HTTP/1.1, not through `fetch`: Node's `fetch` speaks HTTP/2 with the Hub and its CDN, and its flow-control window
caps one stream at about 22 MiB/s, where an HTTP/1.1 request goes at the speed of the link.

### Range resume

An attempt asks for `<endpoint>/<repo>/resolve/<revision>/<path>`, with `range: bytes=<offset>-` when the offset is
above 0. `HfHttp` follows no redirect: the transfer follows them itself, so that the token is only sent to the Hub's
origin, never to the CDN that serves the file; the signed CDN URL is requested again on every attempt, since it
expires. After six redirects, the item fails with `Too many redirects from Hugging Face` (`code: "hf-unreachable"`).

| Response                                     | What the queue does                                                                |
| -------------------------------------------- | ---------------------------------------------------------------------------------- |
| `206` with `content-range: bytes <offset>-…` | Appends to the `.part`                                                             |
| `206` starting elsewhere                     | Deletes the `.part`, retries                                                       |
| `200` while the offset is above 0            | The server ignored the range: rewrites the `.part` from zero and restarts the hash |
| `416`                                        | The `.part` no longer matches the file: deletes it, retries from zero              |
| `408`, `429`, `5xx`                          | Retries                                                                            |
| Any other error                              | Fails the item with the [Hub error](#errors) and its code (`hf-gated`…)            |

### Retries

An attempt is retried after a network error, a `408`, `429` or `5xx`, a body that ends early, a range mismatch, or a
stall: no data for 60 seconds (`STALL`), measured from the start of the request. The pauses are `RETRY_DELAYS`
(2, 4, 8, 16 and 30 seconds, options of `Downloads.layerWith`); each retry is logged, and during a pause the live phase is `retrying`, with `retryAt`. An attempt that received
data resets the count. When the pauses run out, the item fails with `code: "hf-unreachable"` and the last
message.

These failures end the item at once (`TransferFailed`): a [Hub error](#errors) (`code: "hf-gated"`, `hf-not-found`,
`hf-unauthorized`), a checksum mismatch, a full disk while writing (`Disk full`, `code: "disk-full"`), and a file
operation that failed outside the writes, such as a failed rename (`code: "download-failed"`). A defect of the loop
also saves the item `error` with `download-failed`, its cause logged. The item keeps the message and the code in
`error` and `code`.

### Remove, retry, clear

- `remove(id)` (`DELETE /api/downloads/:id`, `404` `DownloadNotFound` for an unknown id): a running item is canceled
  (its transfer interrupted, then what it wrote deleted), a queued one is canceled at once (marked `canceled` first,
  so the loop cannot pick it up while its files are deleted), and a finished one is taken out of the list with its
  files kept. Deleting removes the `.part` files, the files it put in place itself (renamed from their `.part`: not
  one it found in place, which another download placed, even one cleared from the list since), then the folders left
  empty, deepest first, up to the organization's folder. A file another item of the list names too (queued, running, done or
  failed, not a canceled one) is left as it is, its `.part` included: two variants of a repository share their
  projector, and the copy one of them placed, or the `.part` the next one will resume, is not the canceled item's to
  delete.
- `retry(id)` puts a failed or canceled item back in the queue (`409` `NotFinished` `Only a failed or canceled
download can be retried` otherwise), with the same duplicate and disk space checks as a new download. No file is
  trusted as done any more: each one is checked on disk again, and those still in place are kept. A canceled item
  retried owns none of the files it placed before (they are gone, or kept for another item).
- `clear` takes the `done`, `error` and `canceled` items out of the list, their files kept.

## Persistence

The queue is the `downloads` table (`DownloadsRepo`, `app/server/downloads/DownloadsRepo.ts`). A row holds the repository, the pinned
revision, the variant's key, name, quant and kind, the absolute folder, the files (`files_json`: path, size, sha256,
`done`, and `placed` when the item renamed the file into place itself, written with the rename and never sent to the
web), the status, `bytes_done`, `total_bytes`, `error`, `code`, `created_at` and `finished_at`. The full schema is
on the [Database](/developers/server/database/) page.

A status (`DownloadStatus`) is `queued`, `downloading`, `done`, `error` or `canceled`; `isDownloadActive()` is true for
the first two. `bytes_done` only counts the files already renamed into place: the bytes of the file in progress are in
the live state.

## Shutdown and restarts

| Event                          | What happens                                                                                                                                                                                        |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shutdown (`SIGINT`, `SIGTERM`) | The shutdown step of `Downloads` (`shutdown.before`) interrupts the transfer under the queue's lock: nothing is written or started after it, the `.part` and the row, still `downloading`, are kept |
| llama-webui killed             | Same state on disk: the `.part` and a `downloading` row                                                                                                                                             |
| Next start                     | Building `Downloads` starts the loop, which takes the `downloading` item first and resumes it from its `.part`                                                                                      |

There is no orphan cleanup for downloads: an interrupted item carries on where it stopped. In development, a save of a
file the server imports restarts it: a shutdown, then a next start. One queue runs one attempt at a time, so a
`.part` has a single writer.

## Token and endpoint

`hfToken` (`app/server/hf/token.ts`) follows the rules of the `hf` command-line tool:

1. `HF_TOKEN`, or the older `HUGGING_FACE_HUB_TOKEN`, from the environment;
2. otherwise the file written by `hf auth login`, at `hfTokenPath`: `HF_TOKEN_PATH` when set, else
   `$HF_HOME/token`, with `HF_HOME` defaulting to `$XDG_CACHE_HOME/huggingface`, then `~/.cache/huggingface`.

It runs on every call (each API request and each download attempt), so an `hf auth login` done while llama-webui runs
is picked up without a restart. The environment variables are read through Effect's `Config`, from the process
environment set at launch (and the `.env` file). The token is
never stored by llama-webui; `HfStatus.token` only says where it came from (`env`, `file` or `null`).

`hfEndpoint` gives `HF_ENDPOINT` (a mirror, for example), trimmed and without trailing slashes, or
`https://huggingface.co`. It is the base of the API calls and of the `resolve` URLs, the origin the token is sent to,
and the start of the repository page link (`HfRepo.url`). See
[Launch options](/docs/configuration/#hugging-face) for how users set these variables.

Every request to Hugging Face goes through `HfHttp`, whose agents carry the proxy of the environment: the proxy
variables that are set (`HTTP_PROXY`, `HTTPS_PROXY`, an empty one counting as unset), and `NO_PROXY` with
`localhost`, `127.0.0.1` and `::1` always added. The requests to `llama-server` go through `LlamaHttp`, which uses
no proxy. With `LLAMA_WEBUI_TEST_OFFLINE=1` (the exact value), nothing leaves the machine: every request fails with
`fetch failed`, which the contract suite relies on.

## WebSocket messages

`Downloads` publishes these on the hub; see [WebSocket](/developers/api/websocket/).

| Message             | Payload                | When                                                                                                                           |
| ------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `download`          | `DownloadItem`         | An item is queued, starts downloading, is done, fails, is canceled, or is retried                                              |
| `download-progress` | `DownloadLive \| null` | A phase change (`downloading`, `verifying`, `retrying`), progress at most every `liveEvery` (250 ms); `null` when an item ends |
| `download-deleted`  | `{ ids }`              | Finished items are removed or cleared                                                                                          |

`DownloadLive` gives the item, the phase, the file in progress, the bytes done over the total, and `bps`, an
exponential average of the throughput (70% of the previous value, 30% of the latest measure). A client that connects
late reads `GET /api/downloads`, which returns the items and `live`.
