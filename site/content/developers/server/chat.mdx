A chat reply is generated by the llama-webui server, not by the browser. `ChatRuns` (`server/chat/runs.ts`) sends the
request to `llama-server`, accumulates the streamed reply, saves it to the database as it goes, and lets any number of
HTTP clients follow it over Server-Sent Events (SSE).

| File                       | Role                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `server/chat/runs.ts`      | `ChatRuns` (the running generations, one per conversation at most) and `Run` (one generation). |
| `server/chat/request.ts`   | `buildChatRequest()`, the body sent to `llama-server`, and `llamaErrorMessage()`.               |
| `server/routes/chat.ts`    | The `/api/chat` routes and the `sse()` helper that turns a run into a `text/event-stream`.     |
| `server/db/conversations.ts` | `ConversationsRepo`: the `conversations` and `messages` tables.                              |
| `shared/src/chat.ts`       | `Conversation`, `ChatMessage`, `ChatEvent`, `MessageStats`, `statsFromTimings()`, the zod schemas. |
| `shared/src/sse.ts`        | `SseParser` (incremental reader, used on both sides) and `formatSse()`.                         |

The routes are documented in [Chat](/developers/api/chat/), the user-facing behavior in [Chat](/docs/chat/).

## Why the server owns generations

`ChatRuns` keeps the running generations in a `Map` keyed by conversation ID. A run does not belong to the request
that started it:

- It goes on when its client disconnects. Closing the SSE stream only unsubscribes that client.
- It is saved to the database while it streams, so a reload or another browser finds the text written so far.
- Any client can attach to it later with `GET /api/chat/:id/stream`, and several clients can follow it at once.
- There is at most one run per conversation.

A run ends when `llama-server` finishes the reply, when someone stops it, when it fails, or when llama-webui stops or
reloads.

## Run lifecycle

`send(conversationId, content)` and `regenerate(conversationId)` both check the conversation first (`prepare()`), and
refuse before writing anything:

| Check                                             | Error                                                         |
| ------------------------------------------------- | ------------------------------------------------------------- |
| The conversation exists                           | `404` `Conversation not found`                                |
| No run is in progress for it                      | `409` `A reply is already in progress in this conversation`   |
| A server can answer (`target()` is not `null`)    | `409` `llama-server is not ready`                             |

`target()` is provided by `server/index.ts` and reads the [supervisor](/developers/server/supervisor/) state: a
`ready` managed server gives its port, profile and model path (from `profilePaths()`), an `external` server gives its
port with no profile or model path, and every other state gives `null`.

Then:

1. **`send()`** trims the content (`400` `Empty message` if nothing is left) and adds the user message with status
   `done`. If the conversation still has its default title (`isDefaultTitle()`) and this is its first user message, it
   is renamed with `autoTitle()`: the first 6 words, 48 characters at most.
2. **`regenerate()`** finds the last user message (`409` `Nothing to regenerate` without one) and deletes every
   message after it (`deleteFrom()`). The new run has no user message.
3. **`start()`** records the target's model on the conversation if it has none yet (a conversation keeps the model it
   started with), reads the history, inserts an empty assistant message with status `streaming` and the target's
   model path, and creates the `Run` against `http://127.0.0.1:<port>/v1/chat/completions`.
4. The `Run` streams the reply, then writes the final message and emits `done`. Its `done` promise removes it from
   the map.

A message's `status` is one of `streaming`, `done`, `stopped` and `error` (`MessageStatus`).

## The request sent to llama-server

`buildChatRequest(conversation, history)` builds the body of `POST /v1/chat/completions`:

```ts title="server/chat/request.ts"
const sampling = Object.fromEntries(Object.entries(conv.sampling).filter(([, v]) => v !== undefined && v !== null));
return { messages, stream: true, ...sampling, chat_template_kwargs: { enable_thinking: conv.thinking } };
```

- **System prompt**: a first `system` message when the conversation's prompt is not blank.
- **History**: only messages with status `done` or `stopped` and non-empty content. The reasoning of earlier replies
  is never sent back, and failed replies are left out.
- **Alternating roles**: a failed reply leaves two user messages in a row, so consecutive messages with the same role
  are merged, separated by a blank line. Strict chat templates (Gemma, Mistral…) require alternating roles.
- **Sampling**: only the keys the conversation sets (`SamplingSchema`: `temperature`, `top_p`, `top_k`, `min_p`,
  `presence_penalty`, `repeat_penalty`, `max_tokens`, `seed`). A missing key keeps the value `llama-server` was
  started with, that is the profile's.
- **Thinking**: `chat_template_kwargs.enable_thinking` follows the conversation's `thinking` switch.

## Reading the stream

`Run.run()` posts the body with an `AbortController` and reads the response with `SseParser`:

- An HTTP error (or a response without a body) is turned into a message by `llamaErrorMessage()` when the body is a
  `llama-server` error object, else `llama-server: HTTP <status> — <text>`.
- Each `data:` event is parsed as JSON (an event that does not parse is skipped). An `error` field ends the run with
  that error. `choices[0].delta.content` and
  `choices[0].delta.reasoning_content` are appended to the reply and its reasoning, and emitted as a `delta` event.
- The time to the first token (`ttftMs`) is taken at the first non-empty content or reasoning delta, so it includes
  the reasoning.
- The last `timings` object seen is kept for the stats.
- `data: [DONE]` ends the stream normally. A stream that ends without it is an error.

`llamaErrorMessage()` rewrites a context overflow (`type: 'exceed_context_size_error'`) as `Conversation too long for
the model's context (<prompt> / <context> tokens): start a new conversation or use a profile with a larger context.`
Other errors become `llama-server: <message>`.

## Streaming to subscribers

A `Run` keeps the full content and reasoning in memory. `subscribe(listener)` replays what is already there, then
follows live:

1. a `start` event with the user message (`null` for a regeneration) and the assistant message;
2. one `delta` with everything written so far, if anything;
3. `done` with the final message if the run has already ended; otherwise the listener is added and receives the next
   events.

The events are a `ChatEvent` (`shared/src/chat.ts`):

```ts title="shared/src/chat.ts"
export type ChatEvent =
  | { type: 'start'; user: ChatMessage | null; assistant: ChatMessage }
  | { type: 'delta'; content?: string; reasoning?: string }
  | { type: 'done'; message: ChatMessage };
```

`sse()` in `server/routes/chat.ts` serves a run as `text/event-stream`. Each event is written by `formatSse()` as a
named event whose data is the whole `ChatEvent` as one line of JSON:

```text
event: start
data: {"type":"start","user":{"id":41,"role":"user",…},"assistant":{"id":42,"role":"assistant","status":"streaming",…}}

event: delta
data: {"type":"delta","content":"The answer"}

event: done
data: {"type":"done","message":{"id":42,"status":"done","stats":{…},…}}
```

- Bun closes a connection that stays silent for 10 seconds, so `sse()` calls `server.timeout(req, 0)` and writes a
  `: ping` comment every `PING_MS` (15,000 ms): a long prompt can be processed without a single token.
- The stream closes right after `done`.
- A client that disconnects only unsubscribes (`cancel()`); the run goes on.

Three routes return such a stream: `POST /api/chat/:id/messages` (body `{ "content": "…" }`),
`POST /api/chat/:id/regenerate`, and `GET /api/chat/:id/stream`, which attaches to the running reply or answers `204`
when there is none. The web app (`web/src/lib/chat.ts`) attaches with `/stream` when it opens a conversation whose
`live` flag is true, and parses the stream with the same `SseParser`.

## Persistence

`ConversationsRepo` stores the reply in the `messages` row created by `start()`:

- While streaming, `content` and `reasoning` are written at most once every `flushMs` (1,000 ms), on the next delta
  after that delay.
- At the end, one `updateMessage()` writes `content`, `reasoning`, `status`, `error` and `stats`.
- Every message update also refreshes the conversation's `updated_at`, which orders the conversation list.

If the conversation was deleted in the meantime, the final write fails and the run keeps the final message in memory
only. `DELETE /api/chat/:id` stops the run and waits for it before deleting the conversation.

### Stats

`statsFromTimings(timings, ttftMs, durationMs)` maps the `timings` of the last `llama-server` chunk (`LlamaTimings`) to
`MessageStats`. `stats` stays `null` when no chunk carried `timings`, for example after a stop.

| `MessageStats` field | From                                    |
| -------------------- | --------------------------------------- |
| `ttftMs`             | Measured by the run (first delta)       |
| `promptTokens`       | `prompt_n`                              |
| `cachedTokens`       | `cache_n` (`0` when absent)             |
| `genTokens`          | `predicted_n`                           |
| `ppTps`              | `prompt_per_second`                     |
| `tgTps`              | `predicted_per_second`                  |
| `draftN`             | `draft_n` (`null` when absent)          |
| `draftAccepted`      | `draft_n_accepted` (`null` when absent) |
| `durationMs`         | Measured by the run (send to end)       |

## Stop and failures

How a run ends decides its status and error:

| What happened                                                       | `status`  | `error`                                                         |
| ------------------------------------------------------------------- | --------- | --------------------------------------------------------------- |
| `llama-server` sent `[DONE]`                                         | `done`    | `null`                                                          |
| `POST /api/chat/:id/stop` (the request is aborted)                  | `stopped` | `null`                                                          |
| The request failed before any response (connection refused…)        | `error`   | `llama-server unreachable: …`                                   |
| An HTTP error, or an `error` event in the stream                    | `error`   | The worded `llama-server` error (see [Reading the stream](#reading-the-stream)) |
| The stream broke or ended without `[DONE]` (server stopped, crashed) | `error`  | `llama-server cut the reply short (stopped or crashed)`         |

In every case the text received so far is kept. `POST /api/chat/:id/stop` answers `409` `No reply in progress` when
the conversation has no run.

## Shutdown and reload

The database must not be written after it is closed, so every running reply is settled first. `ChatRuns.dispose()`
calls `detach()` on each run: it aborts the request, saves the reply right away with status `stopped`, emits `done` so
that the SSE streams close, and blocks any later write from that run.

- **llama-webui stops** (`SIGINT`, `SIGTERM`): `server/index.ts` prepends a handler that disposes the chat runs (and
  the benchmark runner and the download queue) before the runtime's handler stops `llama-server`. Without that order,
  the replies would see `llama-server` disconnect and end as `error`.
- **`bun --hot` reload**: `ChatRuns` is created by `server/index.ts`, not kept in the runtime, so it does not survive.
  The previous module's dispose function calls `chatRuns.dispose()` before closing its database handle: a reply in
  progress ends as `stopped`, and the new module starts with no run.
- **Bun killed** (`SIGKILL`, crash): nothing runs. At the next start, `conversations.stopOrphans()` turns every message
  left `streaming` into `stopped`.

## Tests

`server/chat/runs.test.ts` drives `ChatRuns` with a fake `fetch` and an in-memory database: a run that goes on and is
saved after its listener leaves, a stop that keeps the partial answer, a late subscriber that receives what was
already written, a stream that breaks, and `dispose()` closing the streams. `server/chat/request.test.ts` covers
`buildChatRequest()` and `llamaErrorMessage()`.
