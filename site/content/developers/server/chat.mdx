title: Chat runs

A chat reply is generated by the llama-webui server, not by the browser. `ChatRuns` (`app/server/chat/ChatRuns.ts`)
sends the request to `llama-server`, accumulates the streamed reply, saves it to the database as it goes, and lets any number of
HTTP clients follow it over Server-Sent Events (SSE).

| File                                       | Role                                                                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `app/server/chat/ChatRuns.ts`              | `ChatRuns`, the service of the replies being written (one per conversation at most), each in a fiber of its own.      |
| `app/server/chat/request.ts`               | `buildChatRequest()`, the body sent to `llama-server`, and `failureMessage()`, a failure worded for the conversation. |
| `app/server/chat/target.ts`                | `chatTarget`, the `llama-server` a reply is asked of.                                                                 |
| `app/server/chat/http.ts`                  | `ChatHandlers`, the handlers of the `chat` group.                                                                     |
| `app/server/chat/ConversationsRepo.ts`     | `ConversationsRepo`: the `conversations` and `messages` tables.                                                       |
| `app/server/llama/chatStream.ts`           | `streamChat()`, the streamed `/v1/chat/completions` through `LlamaHttp`, and its failures.                            |
| `app/server/http/Sse.ts`                   | `sseResponse()`, a stream served as `text/event-stream`.                                                              |
| `packages/webui-shared/src/chat.ts`        | `Conversation`, `ChatMessage`, `ChatEvent`, `MessageStats`, `statsFromTimings()`, their schemas.                      |
| `packages/webui-shared/src/api/ChatApi.ts` | `ChatApi`, its errors, and `ChatSseEvent`, a `ChatEvent` as one server-sent event.                                    |

The routes are documented in [Chat](/developers/api/chat/), the user-facing behavior in [Chat](/docs/chat/).

## Why the server owns generations

`ChatRuns` keeps the running replies in a `SynchronizedRef` of a map keyed by conversation ID. A run is forked in the
service's scope, not in the request's, so it does not belong to the request that started it:

- It goes on when its client disconnects. Closing the SSE stream only unsubscribes that client.
- It is saved to the database while it streams, so a page reload or another browser finds the text written so far.
- Any client can attach to it later with `GET /api/chat/:id/stream`, and several clients can follow it at once.
- There is at most one run per conversation: the check and the registration happen in one step under the map's
  lock, so two sends at once give one reply and one `409`.

A run ends when `llama-server` finishes the reply, when someone stops it, when it fails, or when llama-webui stops.

## Run lifecycle

`send(id, content)` and `regenerate(id)` both go through `starting()`, which checks, under the map's lock and
uninterruptibly, before writing anything:

| Check                                                                         | Error                                                                         |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| The conversation exists                                                       | `404` `ConversationNotFound` `Conversation not found`                         |
| No run is in progress for it                                                  | `409` `ReplyInProgress` `A reply is already in progress in this conversation` |
| llama-webui is not stopping, and a server can answer (`chatTarget` gives one) | `409` `ServerNotReady` `llama-server is not ready`                            |

`chatTarget` (`app/server/chat/target.ts`) reads the [supervisor](/developers/server/supervisor/) state: a managed
server that takes requests (`servesRequests()`: `ready`, `sleeping`, or `starting` with `waking`) gives its `--host`,
port, profile and model path (from `resolveProfilePaths()`, `null` when the profile is gone), an `external` server
gives its port on loopback with no profile or model path, and every other state gives none. A request sent to a
sleeping server wakes it, and one sent during a wakeup waits in `llama-server` until the model is back.

Then:

1. **`send()`** trims the content (`400` `EmptyMessage` `Empty message` if nothing is left, before any other check)
   and adds the user message with status `done`. If the conversation still has its default title (`isDefaultTitle()`)
   and this is its first user message, it is renamed with `autoTitle()`: the first 6 words, 48 characters at most.
2. **`regenerate()`** finds the last user message (`409` `NothingToRegenerate` without one) and deletes every message
   after it (`deleteFrom()`). The new run has no user message.
3. **`begin()`** records the target's model on the conversation if it has none yet (a conversation keeps the model it
   started with), reads the history, inserts an empty assistant message with status `streaming` and the target's
   model path, and forks the run against `http://<host>:<port>/v1/chat/completions`, in a root span `ChatRuns.reply`.
4. The run consumes the reply, then saves the final message and publishes `done`. It leaves the map before its
   `done`, so a client that sends again on `done` finds no reply in progress.

A message's `status` is one of `streaming`, `done`, `stopped` and `error` (`MessageStatus`).

## The request sent to llama-server

`buildChatRequest(conversation, history)` builds the body of `POST /v1/chat/completions`:

```ts title="app/server/chat/request.ts"
const messages = Arr.reduce(Arr.filter(Arr.sort(history, byId), sent), system, appendTurn);
const sampling = Rec.filter<string, number | undefined>(conversation.sampling, Predicate.isNotNullish);
return { messages, stream: true, ...sampling, chat_template_kwargs: { enable_thinking: conversation.thinking } };
```

- **System prompt**: a first `system` message when the conversation's prompt is not blank.
- **History**: only messages with status `done` or `stopped` and non-empty content. The reasoning of earlier replies
  is never sent back, and failed replies are left out.
- **Alternating roles**: a failed reply leaves two user messages in a row, so consecutive messages with the same role
  are merged, separated by a blank line. Strict chat templates (Gemma, Mistral…) require alternating roles.
- **Sampling**: only the keys the conversation sets (`Sampling`: `temperature`, `top_p`, `top_k`, `min_p`,
  `presence_penalty`, `repeat_penalty`, `max_tokens`, `seed`). A missing key keeps the value `llama-server` was
  started with, that is the profile's.
- **Thinking**: `chat_template_kwargs.enable_thinking` follows the conversation's `thinking` switch.

## Reading the stream

The run consumes `streamChat(baseUrl, body)` (`app/server/llama/chatStream.ts`), raced against its `stopped`
signal. `streamChat` posts the body through `LlamaHttp`, a `node:http` client with no time limit on the headers or the
body: a long prompt can take minutes before its first token. The request belongs to the stream, so ending or
interrupting the stream aborts it. The body is decoded with Effect's SSE decoder, each `data:` read by `readChatEvent()`
of `llamacpp-js/client` (the reader the package's `streamChatCompletion()` uses), and
its failures are tagged errors that `failureMessage()` words for the conversation:

| Failure             | When                                                                                   | Message                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `LlamaUnreachable`  | The request got no answer (nothing listens, the connection failed before the headers). | `llama-server unreachable: <cause>` (`connect ECONNREFUSED …`)                                     |
| `LlamaHttpFailed`   | An error status.                                                                       | The worded `llama-server` error when the body is one, else `llama-server: HTTP <status> — <body>`. |
| `LlamaStreamFailed` | An event with an `error` field.                                                        | The worded `llama-server` error.                                                                   |
| `LlamaStreamCut`    | The body ends or breaks before `data: [DONE]`.                                         | `llama-server cut the reply short (stopped or crashed)`                                            |

- An event whose data is not JSON is skipped. A chunk is read field by field: a field of another type is left out and
  the others are kept (`timings` without their four counts are dropped alone, and the chunk keeps its delta); an
  `error`, in an event or in an HTTP error body, keeps its fields of their type.
- `choices[0].delta.content` and `choices[0].delta.reasoning_content` are appended to the reply and its reasoning,
  and published as a `delta` event.
- The time to the first token (`ttftMs`) is taken at the first non-empty content or reasoning delta, so it includes
  the reasoning.
- The last `timings` object seen is kept for the stats.

A `llama-server` error is worded by `llamaErrorMessage()`: a context overflow (`contextOverflow()` from
`llamacpp-js/errors` reads its sizes) becomes `Conversation too long for the model's context (<prompt> / <context>
tokens): start a new conversation or use a profile with a larger context.`, any other error `llama-server: <message>`.

## Streaming to subscribers

A run keeps the full content and reasoning in memory (`written`, a `SynchronizedRef`) and publishes its events on a
`PubSub`. A client's stream (`ChatReply.events`) takes the replay and the subscription in one step, then follows
live:

1. a `start` event with the user message (`null` for a regeneration) and the assistant message;
2. one `delta` with everything written so far, if anything;
3. `done` with the final message if the run has already ended; otherwise the next events as they are published.

The stream ends with `done`.

The events are a `ChatEvent` (`packages/webui-shared/src/chat.ts`):

```ts title="packages/webui-shared/src/chat.ts"
export const ChatEvent = Schema.Union([
  Schema.Struct({ type: Schema.Literal('start'), user: Schema.NullOr(ChatMessage), assistant: ChatMessage }),
  Schema.Struct({
    type: Schema.Literal('delta'),
    content: Schema.optionalKey(Schema.String),
    reasoning: Schema.optionalKey(Schema.String),
  }),
  Schema.Struct({ type: Schema.Literal('done'), message: ChatMessage }),
]);
```

The handlers serve a reply with `sseResponse()` (`app/server/http/Sse.ts`), each event encoded by `ChatSseEvent`
(`packages/webui-shared/src/api/ChatApi.ts`) as a named event whose data is the whole `ChatEvent` as one line of
JSON:

```text
event: start
data: {"type":"start","user":{"id":41,"role":"user",…},"assistant":{"id":42,"role":"assistant","status":"streaming",…}}

event: delta
data: {"type":"delta","content":"The answer"}

event: done
data: {"type":"done","message":{"id":42,"status":"done","stats":{…},…}}
```

- `sseResponse()` writes a `: ping` comment after 15 s of silence: a long prompt can be processed without a single
  token, and a proxy may drop a silent connection.
- The stream closes right after `done`.
- The response carries `Connection: close`: the connection is not kept alive for another request once the stream
  ends, so it cannot hold up the HTTP server's close at shutdown.
- A client that disconnects interrupts its stream, which only unsubscribes; the run goes on.

Three routes return such a stream: `POST /api/chat/:id/messages` (body `{ "content": "…" }`),
`POST /api/chat/:id/regenerate`, and `GET /api/chat/:id/stream`, which attaches to the running reply or answers `204`
when there is none. The web app (`app/src/lib/chat.ts`) attaches with `/stream` when it opens a conversation whose
`live` flag is true, and reads the stream with `callStream()`, which decodes it with the same `ChatSseEvent`.

## Persistence

`ConversationsRepo` stores the reply in the `messages` row created by `start()`:

- While streaming, `content` and `reasoning` are written at most once every `flushInterval` (1 s, the option of
  `ChatRuns.layerWith`), on the next delta after that delay.
- At the end, `save()` writes once, under the run's `written` lock (a reply already saved is not saved again):
  one `updateMessage()` writes `content`, `reasoning`, `status`, `error` and `stats`.
- Every message update also refreshes the conversation's `updated_at`, which orders the conversation list.

If the conversation was deleted in the meantime, the final write finds no row (`MessageNotFound`) and the run builds
the final message in memory. `DELETE /api/chat/:id` stops the run and waits for its end (`stopAndWait()`) before
deleting the conversation.

### Stats

`statsFromTimings(timings, ttftMs, durationMs)` maps the `timings` of the last `llama-server` chunk (`LlamaTimings`, from `llamacpp-js/client`) to
`MessageStats`. `stats` stays `null` when no chunk carried `timings`, for example after a stop, and when a value is
not finite (a rate divided by zero).

| `MessageStats` field | From                                    |
| -------------------- | --------------------------------------- |
| `ttftMs`             | Measured by the run (first delta)       |
| `promptTokens`       | `prompt_n`                              |
| `cachedTokens`       | `cache_n` (`0` when absent)             |
| `genTokens`          | `predicted_n`                           |
| `ppTps`              | `prompt_per_second`                     |
| `tgTps`              | `predicted_per_second`                  |
| `draftN`             | `draft_n` (`null` when absent)          |
| `draftAccepted`      | `draft_n_accepted` (`null` when absent) |
| `durationMs`         | Measured by the run (send to end)       |

## Stop and failures

How a run ends decides its status and error:

| What happened                                                                    | `status`  | `error`                                                                         |
| -------------------------------------------------------------------------------- | --------- | ------------------------------------------------------------------------------- |
| `llama-server` sent `[DONE]`                                                     | `done`    | `null`                                                                          |
| `POST /api/chat/:id/stop` (the stream is interrupted, so the request is aborted) | `stopped` | `null`                                                                          |
| The request failed before any response (connection refused…)                     | `error`   | `llama-server unreachable: …`                                                   |
| An HTTP error, or an `error` event in the stream                                 | `error`   | The worded `llama-server` error (see [Reading the stream](#reading-the-stream)) |
| The run died on a defect (a bug)                                                 | `error`   | `llama-webui: internal error` (the cause is logged)                             |
| The stream broke or ended without `[DONE]` (server stopped, crashed)             | `error`   | `llama-server cut the reply short (stopped or crashed)`                         |

In every case the text received so far is kept. `POST /api/chat/:id/stop` answers `409` `NoReplyInProgress` `No reply
in progress` when the conversation has no run; it does not wait for the save.

## Shutdown

The replies must be saved while the clients are still connected and before the database closes. `ChatRuns` registers
a shutdown step (`shutdown.before`, `app/server/runtime/Shutdown.ts`), which runs before the HTTP server closes: under
the map's lock it sets `closing`, so a send that comes after it is refused with `ServerNotReady`, then saves every
reply in progress `stopped` with its text so far, which publishes its `done` and ends the clients' streams, and
stops it. A run stopped after its save writes nothing more.

- **llama-webui stops** (`SIGINT`, `SIGTERM`, or in development a save of a file the server imports, which restarts
  it): the step runs with the other shutdown steps, then the HTTP server closes, then the services are released in
  the reverse order of their construction, `llama-server` (stopped by the supervisor) and the database last
  ([Architecture](/developers/architecture/#shutdown)). Without that order, the replies would see `llama-server`
  disconnect and end as `error`. The end of the service's scope interrupts what is left.
- **llama-webui killed** (`SIGKILL`, crash): nothing runs. When the layer is built at the next start,
  `stopOrphans` turns every message left `streaming` into `stopped`.

## Tests

`app/server/chat/ChatRuns.test.ts` runs `ChatRuns` on the test services (`ServicesTest`, an in-memory database) with
`layerWith({ flushInterval, target })` and a stub `llama-server` (`chatStub` of `app/server/testing/llama.ts`): a run
that goes on and is saved after its listener leaves, a stop that keeps the partial answer, a late subscriber that
receives what was already written, a stream that breaks, the shutdown step closing the streams and refusing later
sends, two sends at once, a run that dies, and the wording of each failure. `app/server/chat/request.test.ts` covers
`buildChatRequest()` and `failureMessage()`, `app/server/llama/chatStream.test.ts` the stream reader, and the
[contract suite](/developers/contributing/testing/) reads the SSE of a real reply from the production build.
