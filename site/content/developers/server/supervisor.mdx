title: Supervisor
description: How llama-webui starts, watches and stops llama-server, the state machine behind it, external server detection, and how the process stops it on shutdown.

The supervisor owns the one `llama-server` process llama-webui manages: it starts it from a built command, follows it
to readiness, stops it, and publishes its state to the rest of the server. It is the `Supervisor` service
(`app/server/supervisor/Supervisor.ts`), built once with the app's services and stopped when they are undone.

| File                                     | Role                                                                                                                          |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `app/server/supervisor/Supervisor.ts`    | `Supervisor`: the state machine, the launch, the output, the health poll, the stop.                                           |
| `app/server/supervisor/command.ts`       | `buildCommand()`, `commandOf()`, `profilePaths()`, `launchLines()`: from a profile to a `BuiltCommand`.                       |
| `app/server/supervisor/ExternalWatch.ts` | `ExternalWatch`: detects a `llama-server` llama-webui did not start.                                                          |
| `app/server/supervisor/http.ts`          | `ServerHandlers`: the `server` group (start, switch, restart, stop, state, props).                                            |
| `app/server/process/followed.ts`         | `followProgram()`: a long-running program in a scope of its own, followed until it exits.                                     |
| `app/server/llama/probes.ts`             | `health()`, `isLlamaServer()`, `props()`, `readProps()`: requests to `llama-server` through `LlamaHttp`.                      |
| `app/server/llama/modelsSse.ts`          | `streamModelsSse()`, `sanitizeLoadProgress()`: `GET /models/sse` stream over `LlamaHttp` (`ModelsSseUnsupported` on 404/503). |
| `app/server/llama/procScan.ts`           | `findLlamaServerPid()`: the PID of a `llama-server` read from `/proc`.                                                        |
| `app/server/flags/Flags.ts`              | `Flags`: the flag catalog of the binary, cached per path.                                                                     |
| `app/server/logs/LogRing.ts`             | `LogRing`: the numbered lines of the server's output, published as `log` messages.                                            |
| `packages/webui-shared/src/server.ts`    | `ServerState`, `ServerView`, `serverView()`, `activeProfileId()`, shared with the web app.                                    |

`probeUrl()` (`llamacpp-js/client`) and `parseHelp()` (`llamacpp-js/flags`) come from
[llamacpp-js](/developers/llamacpp-js/); the requests and the programs themselves are made by the app, through
`LlamaHttp` and `effect/process`.

The HTTP endpoints that drive it (`/api/server/start`, `/switch`, `/restart`, `/stop`) are documented in
[Server, state and logs](/developers/api/server/). The user-facing behavior is on the [Server page](/docs/server/).

## States

The state is a union on `kind`, a schema of `packages/webui-shared/src/server.ts` that the web app decodes too:

```ts title="packages/webui-shared/src/server.ts"
export const ServerState = Schema.Union([
  Schema.Struct({ kind: Schema.Literal('idle') }),
  Schema.Struct({
    kind: Schema.Literal('starting'),
    ...launched,
    since: Schema.Int,
    progress: Schema.optionalKey(LoadProgress),
    waking: Schema.optionalKey(Schema.Literal(true)),
  }),
  Schema.Struct({ kind: Schema.Literal('ready'), ...launched, since: Schema.Int }),
  Schema.Struct({ kind: Schema.Literal('sleeping'), ...launched, since: Schema.Int }),
  Schema.Struct({ kind: Schema.Literal('stopping'), ...launched }),
  Schema.Struct({
    kind: Schema.Literal('crashed'),
    profile: Schema.String,
    profileId: Schema.Int,
    exitCode: Schema.NullOr(Schema.Int),
    signal: Schema.NullOr(Schema.String),
    at: Schema.Int,
    message: Schema.optionalKey(Schema.String),
  }),
  Schema.Struct({
    kind: Schema.Literal('external'),
    pid: Schema.NullOr(Schema.Int),
    port: Schema.Int,
    status: Schema.optionalKey(ExternalStatus),
    progress: Schema.optionalKey(LoadProgress),
  }),
]);
```

`launched` is `{ profile, profileId, pid, host, port }`. `idle` is shown as **Stopped** in the interface. `since` and
`at` are times in milliseconds, read from Effect's `Clock`. `message` is only set when the launch itself failed (the
process never ran).

### Transitions

| From                            | Event                                                                                          | To                                            |
| ------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `idle`, `crashed`               | `start`: the process is spawned                                                                | `starting`                                    |
| `idle`, `crashed`               | `start`: the profile's `cwd` does not exist, or the spawn fails                                | `crashed` (with `message`)                    |
| `idle`, `crashed`               | `start`: a `llama-server` already answers on the profile's port                                | `external` (and `start` fails)                |
| `idle`, `crashed`               | the external watch finds a `llama-server` on the settings port or the last command's port      | `external`                                    |
| `starting`                      | `/models/sse` sends `status_change` (`loaded`), or `/health` answers `200` during cold startup | `ready`                                       |
| `ready`, `starting`             | `/models/sse` sends `status_change` (`sleeping`) (`--sleep-idle-seconds`)                      | `sleeping`                                    |
| `sleeping`                      | `/models/sse` sends `status_change` (`loading` on wakeup)                                      | `starting` (with `waking: true`, `progress?`) |
| `starting`, `ready`, `sleeping` | `stop` or `switchTo`                                                                           | `stopping`                                    |
| `stopping`                      | the process exits                                                                              | `idle`                                        |
| `starting`, `ready`, `sleeping` | the process exits without being asked to                                                       | `crashed`                                     |
| `crashed`                       | `stop`                                                                                         | `idle`                                        |
| `external`                      | the recorded PID is dead or unknown, and the port no longer answers                            | `idle`                                        |
| `external`                      | `start`, and the port no longer answers                                                        | `idle`, then the normal start                 |

Every transition goes through one `change()` under the lock of the state (a `SynchronizedRef`): it stores the state,
publishes it as a `server-state` WebSocket message (the `ServerView`) and to the `changes` stream, in the order of the
changes. Each exit is logged as `[llama-webui] llama-server exited (code …)` in the log ring, with the signal when
there is one.

## Building the command

`buildCommand({ profile, settings })` in `command.ts` reads the home folder, llama-webui's working folder and whether
`GGML_CUDA_P2P` is in its environment (`p2pInEnvironment()`: whatever its value, an empty one too, since llama.cpp
only looks for the variable and `llama-server` inherits it), then `commandOf()` turns the profile and the settings (`binary`, `host`,
`port`, `env`) into a `BuiltCommand`:

```ts title="app/server/supervisor/command.ts"
export interface BuiltCommand {
  /** `setpriv --pdeathsig KILL --`, then the server's command: llama-server dies with llama-webui. */
  readonly argv: ReadonlyArray<string>;
  /** The server's command, shell-quoted, without the `setpriv` prefix. */
  readonly display: string;
  readonly cwd: string;
  /** The settings' variables, then the profile's: what is laid over llama-webui's own environment. */
  readonly env: Readonly<Record<string, string>>;
  /** `GGML_CUDA_P2P` is set, in `env` or in llama-webui's environment. */
  readonly p2p: boolean;
  readonly host: string;
  readonly port: number;
  readonly profileName: string;
  readonly profileId: number;
}
```

The `llama-server` part of `argv` is assembled in this order:

```ts title="app/server/supervisor/command.ts"
const server = [
  expandHomeIn(settings.binary, home, path),
  '-m',
  expandHomeIn(profile.model, home, path),
  ...mmproj,
  ...profile.args,
  ...(setsVerbosity(profile.args, env) ? [] : ['-lv', DEFAULT_VERBOSITY]),
  '--host',
  host,
  '--port',
  `${port}`,
  '--metrics',
  '--slots',
  '--props',
];
```

- **Binary**: the `binary` setting (`llama-server` by default), `~` expanded. Every caller that runs it or
  `llama-bench` next to it (flags, setup, tuning, benchmarks) expands it the same way.
- **Model and projector**: `-m` and, when the profile has one, `-mm`.
- **Profile arguments**: `profile.args`, as stored, one array element per argument. They never go through a shell.
- **Address**: `host` is `profile.host ?? settings.host` and `port` is `profile.port ?? settings.port`.
- **Verbosity**: `-lv 4`, the first level at which `llama-server` logs the buffer sizes the
  [placement](/developers/server/monitor/#model-placement) reads, unless the profile sets its own (`-lv`,
  `--verbosity`, `--log-verbosity`, `-v`, `--verbose`, `--log-verbose`, or `LLAMA_ARG_LOG_VERBOSITY` in the settings'
  or the profile's `env`).
- **Flags llama-webui adds**: `--metrics`, `--slots` and `--props`, which the [monitor](/developers/server/monitor/)
  and the Server page read. A profile cannot set these, nor `--host`, `--port`, `-m`, `--model`, `-mm` or `--mmproj`:
  `ProfileInput` (`packages/webui-shared/src/profile.ts`) rejects them through `RESERVED_FLAGS`.

The final `argv` prefixes that list with `setpriv --pdeathsig KILL --`. `setpriv` (util-linux) sets the parent-death
signal and then executes `llama-server`, so the kernel kills `llama-server` if llama-webui dies without stopping it.
`display` is the shell-quoted `llama-server` part only (`shellQuote()` from `packages/webui-shared/src/shell.ts`): it
is what the Server page shows as the effective command and what the launch log line contains.

### Paths and `~`

`llama-server` runs without a shell, so nothing expands `~` for it. The command replaces a leading `~` or `~/` with
the home folder and leaves every other path unchanged (`expandHomeIn` of `app/server/config/Home.ts`, the pure half
of the `expandHome` the rest of the server uses).

- In `argv`, the model and projector are only `~`-expanded: a relative path stays relative, and `llama-server`
  resolves it against its own working folder.
- `cwd` is the profile's `cwd`, `~`-expanded, or llama-webui's own working folder when the profile has none.
- `profilePaths({ profile, home, cwd, path })` returns the same files as `llama-server` will open them: `cwd`, and
  `model` and `mmproj` made absolute against that `cwd`. The rest of the server uses it whenever it needs the real file
  (chat model path, model disk for the monitor, benchmarks, model usage).

### Environment

`env` is the `env` setting (the global variables of Settings) with the profile's `env` over it: a profile variable
overrides a global one. The spawn lays it over llama-webui's own environment (`extendEnv: true`), so both override an
inherited variable. Nothing else is added.

## Starting and readiness

`start(cmd)` runs `doStart` as [one operation](#one-operation-at-a-time):

1. If the state is `external`, it probes that port again. If it still answers, it fails with `PortInUse`
   `port in use by an external server (PID …)`; otherwise it goes back to `idle`.
2. If it already has a process, it fails with `ServerAlreadyRunning` `a server is already running`.
3. If something answers on `cmd.host`:`cmd.port`: when it is a `llama-server` (`isLlamaServer()`), it switches to
   `external` and fails with the same `PortInUse`; any other service fails with `PortInUse`
   `port <port> is in use by another service`, the state unchanged. All three are `409`.
4. It records `cmd` as the last command and checks that `cmd.cwd` exists, then starts the program with
   `followProgram()`: `ChildProcess.make(binary, args, { cwd, env, extendEnv: true, stdin: 'ignore' })`, its output
   piped. A spawn that fails (`spawn setpriv ENOENT` when `setpriv` is not installed) or a missing folder logs
   `[llama-webui] launch failed: …` and sets `crashed` with that message (`directory not found: <cwd>` for the
   folder). A `llama-server` binary that is missing or not executable is reported by `setpriv` on its standard error,
   which exits with an error code: the state is `crashed` with that code.
5. Once spawned, before any output is read, it pushes the lines of `launchLines(cmd)` to the log ring: the launch
   line, `LAUNCH_LOG_PREFIX` (`[llama-webui] launch:`) followed by `display`, then `P2P_LOG_LINE` when `cmd.p2p` is
   set (llama.cpp enables peer-to-peer as soon as the variable exists, whatever its value, and logs nothing about it).
   The [placement tracker](/developers/server/monitor/) looks for the prefix to find the start of the current load,
   and for the second line to know that peer-to-peer was requested.
6. Both output streams are split into lines (`linesOf()`, `app/server/logs/lines.ts`), the idle noise
   (`update_slots: all slots are idle`) left out, and pushed to the `LogRing` (10,000 lines kept in memory).
7. The state becomes `starting`. One fiber in the program's scope polls `/health` every `healthPoll` (500 ms).
   A second fiber connects to `GET /models/sse` and retries while the socket is binding. Either
   `/health` returning `200` or SSE reporting `loaded` makes the server ready during cold startup. The SSE watcher
   supplies live `starting.progress`, records `data.memory` in `supervisor.memory`, and tracks sleep and wakeup for
   the life of the process. Builds that return `404` or `503` from `/models/sse` use the health poll for startup.
   Once the stream has answered for a process, a non-2xx answer to a reconnect is transient: the watcher tries again
   every `healthPoll`, since only the stream sees the end of a wakeup.
   For external servers, `watchExternal()` checks `/props` before subscribing to SSE, and asks again every
   `healthPoll` when `/props` fails (a `503` during the first load, a slow or failed answer; a server that no longer
   answers `/health` is rechecked and leaves `external`). A `401` or `403` (a server started with `--api-key`) ends
   the watch instead: the stream would be refused too. A router stays in the generic `external` state because its
   events describe individual models. A single-model server can report `status`, `progress`, and
   `supervisor.memory` once its properties are available. A round of either watcher that dies on a defect is logged
   (`following /models/sse of llama-server`, `… of an external llama-server`) and the next one runs.

Stage-only SSE announcements, such as the start of projector loading, reuse the last stage order from the current load.

`start` returns once the process is spawned, not once it is ready: the endpoints answer `202` and the client follows
the state over the WebSocket.

`health(target)` (`app/server/llama/probes.ts`) sends `GET <probeUrl(host, port)>/health` through `LlamaHttp` with a
timeout of 800 ms and gives the status code, or none when nothing answers in time. `probeUrl()` reaches the address
the server listens on: loopback for a wildcard (`0.0.0.0` → `127.0.0.1`, `::` → `[::1]`) or no host, the address
itself otherwise (a LAN address refuses loopback connections), with brackets for IPv6. The `starting`, `ready` and
`stopping` states carry the `host`, so the monitor, `/api/server/props` and chat reach the server the same way
(`stateHost()`); an external server is reached on loopback. `llama-server` answers `503` while it loads and `200`
once the model is loaded. The first `200` during the process's cold startup sets `ready` and ends the poll. Wakeup
uses SSE because `/health` also answers `200` during sleep. A wakeup is a `starting` with `waking: true`:
`llama-server` already answers and queues requests until its model is back, so `servesRequests(state)` (chat target,
`/api/server/props`, the chat composer) counts it with `ready`, `sleeping` and `external`, the monitor does not read
`/slots` during it (nor while the server sleeps or stops), and the startup metric only measures launches. The supervisor can stay in `starting` for minutes
while a large model loads. The benchmark uses the same probe for port occupancy (any status) and readiness (`200`).

## Following a program

`followProgram()` (`app/server/process/followed.ts`) is how every long-running program is run (`llama-server`,
`llama-bench`, the benchmark's trial server, `nvidia-smi`, the NVML sampler). It spawns the command in a scope of its
own, forked from the caller's (`parent`), and:

- runs `onSpawn` first, so the caller names the process in its state before any output is read and an exit seen at
  once still finds it;
- reads its output (`read`) in the program's scope;
- once it exits, waits for the readers (`DRAIN_TIMEOUT`, 1 s, so the last output is not lost), runs `onExit` with how
  it ended (`endingOf()`: its code, or the signal that ended it), then closes its scope;
- bounds every close: a scope closed on a live program sends `SIGKILL` 1 s after the first signal
  (`FORCE_KILL_AFTER`), and the close waits 1 s at most for the program to be gone (`CLOSE_BOUND`, `closeWithin()`).
  A program stuck in a driver call does not die on `SIGKILL` until the call returns: past the bound the close is
  logged and goes on without it.

## Stopping

`stop` never touches an external server. It waits for the operation in progress, then sets `stopping` (from
`starting` or `ready`), sends `SIGTERM`, and waits for the process to exit for up to `killTimeout` (5 s). After that
it logs `[llama-webui] not stopped after 5000 ms, SIGKILL` and sends `SIGKILL`. Once the exit is handled, the state is
`idle`. Called without a process, `stop` clears a `crashed` state to `idle` and does nothing otherwise. A stop runs in
a fiber of the supervisor, not of the request: a client that goes away does not cut it short.

`switchTo(cmd)` stops the current process and starts `cmd` as one operation. `POST /api/server/restart` is a
`switchTo` with the command rebuilt from the database, so profile edits saved since the last launch apply
(`NoProfileToRestart` when there is no last command, `ProfileNotFound` when its profile is gone).

### When llama-webui exits

The supervisor's layer has a finalizer: when the app's services are undone (a shutdown, or a restart in development),
it takes the operation lock, logs `stopping llama-server…` when a managed process runs, and stops it as `stop` does.
The services are undone in the reverse order of their construction, so the chat replies, the benchmark and the
download are saved before it, and the database closes after it; the order is in
[Architecture](/developers/architecture/#shutdown).

- A second `SIGINT` or `SIGTERM` during the shutdown exits at once, and `setpriv`'s parent-death signal kills
  `llama-server`.
- An exit without the finalizers (an uncaught error) still kills it: the supervisor keeps the PID of the live process
  in a plain variable, and a synchronous `exit` handler sends it `SIGKILL`.
- If llama-webui is killed outright, the parent-death signal takes care of `llama-server`.

## One operation at a time

Overlapping start, restart and switch operations could spawn two servers, so the supervisor holds a semaphore of one
permit:

- `start` and `switchTo` go through `exclusive()`, which fails at once with `OperationInProgress`
  `operation in progress, try again` (`409`) when the permit is taken. The operation runs in a fiber of the
  supervisor, so it ends even when the request is interrupted.
- `stop` and the layer's finalizer do not fail: they wait for the permit, then run.

The errors are the tagged errors of `ServerApi` (`packages/webui-shared/src/api/ServerApi.ts`), which the handlers
answer as they are. Before any of them, the handlers refuse with `BenchRunning` `A benchmark is running` (`409`) while
the [bench runner](#benchmarks-and-the-gate) is busy.

## External servers

An external server is a `llama-server` that answers on a port llama-webui would use, while llama-webui has no process
of its own. `isLlamaServer(target)` tells it apart from any other HTTP service: its `/health` answers JSON,
`{"status":"ok"}` once loaded or `{"error":{"type":"unavailable_error",…}}` while loading, within 800 ms.

`ExternalWatch` (`ExternalWatch.ts`) is a fiber of its layer's scope that looks once as soon as it is built, without
holding the start of the app, then every 2 seconds, one look at a time:

- While the bench runner is busy, it does nothing: the benchmark's own `llama-server` on the settings port is not an
  external server.
- In `idle` or `crashed`, it calls `detectExternal(port)` for the `port` setting, then for the last command's port,
  and stops at the first hit: the state becomes `external`. After a crash, a `llama-server` started by hand on the
  port is thus seen without waiting for another state change.
- In `external`, it calls `recheckExternal`: when the recorded PID is still alive the state stays, even if the port is
  silent (a hung server is still a server); when the PID is dead or unknown and the port no longer answers, the state
  goes back to `idle`.
- In any other state it does nothing.

A look that dies on a defect (the database failing…) is logged (`a look for an external llama-server failed`) and the
next one runs: the watch lasts as long as the app.

`findLlamaServerPid({ port, root })` (`app/server/llama/procScan.ts`) reads `/proc/<pid>/cmdline` for every process
and gives the first whose program is named `llama-server` and whose `--port` (or `--port=`, `8080` when absent) equals
`port`. The PID is none when nothing matches, for example a server started under another name or in a container.

An external server can be read (chat, monitoring, `/props`) but never stopped: `start` refuses while it answers.

## The flag catalog

`Flags` (`app/server/flags/Flags.ts`) reads what the installed `llama-server` accepts, for the profile editor's
completion and warnings:

- `catalog` runs `<binary> --help` (the `binary` setting, `~` expanded) within 5 seconds, at most 16 MiB of output,
  and parses its standard output with `parseHelp()` (`llamacpp-js/flags`). It fails with `FlagsUnavailable`
  `llama-server --help failed (<binary>)` when the binary cannot run, exits with a non-zero code, or lists no flag.
- The result is kept in a `Cache` per binary path for the life of the app; a failure is not kept, so the next call
  runs `--help` again.

`GET /api/flags` returns `{ flags }`, or `503` `FlagsUnavailable`. The catalog never blocks anything: an argument it
does not know is only flagged in the editor.

## Following the state

`changes` gives a `Stream` of every new state from the subscription on (a `PubSub`). The `Placement` tracker of the
monitor subscribes to it to recompute the model placement. The `server-state` WebSocket message is published by the
supervisor itself, on every change, with the `ServerView` as payload ([WebSocket](/developers/api/websocket/)).

Other services read `state` when they need it instead of subscribing: the monitor on every tick, `ChatRuns` to find
the server to talk to, the bench gate, the external watch, and the endpoints.

Two pure helpers of `packages/webui-shared/src/server.ts` read the state:

- `serverView({ state, last })`: the `ServerView` sent to clients, `{ state, command, profileId }` (the supervisor's
  `view`). `command` is the last `display` (without the `setpriv` prefix). `profileId` comes from the state, or from
  the last command after a stop.
- `activeProfileId(state)`: the profile of the managed server while it is `starting`, `ready`, `sleeping` or
  `stopping`, else `null`.
- `servesRequests(state)`: whether `llama-server` takes requests: `ready`, `sleeping`, `starting` with `waking`, or
  `external`. Deleting the running profile is refused with it (`ProfileRunning`), and the chat uses it as its default
  profile.

The `bootId` of `/api/health` and of the WebSocket's `hello` is made by `AppInfo` (`app/server/config/AppInfo.ts`),
a fresh UUID each time the services are built: the client ties its log numbering to it. In development, a save of a
file the server imports restarts it (`node --watch`): the services are undone like at a shutdown, so `llama-server`
stops, and built again with a new `bootId`. A save under `app/src/` is HMR and keeps both.
[Architecture](/developers/architecture/#development-restarts) describes the development loop.

## Benchmarks and the gate

A benchmark needs the GPUs to itself, and it does not use the supervisor to run its programs: `app/server/bench/`
spawns its own `llama-bench` (`execute.ts`) and trial `llama-server` (`trial.ts`, on `127.0.0.1` and the settings
port). The gate (`app/server/bench/gate.ts`), made by the `BenchRunner`, coordinates the two:

- `acquire({ stopServer })` refuses with `409` `ExternalServerRunning` when the state is `external`, and with `409`
  `ServerRunning` (`llama-server is running (profile …): it will be stopped during the benchmark, then restarted`)
  when the managed server is `starting` or `ready` and `stopServer` is false: the client asks for confirmation. It
  waits up to 60 seconds for a `stopping` state to finish (`ServerStopTooSlow` after that). With `stopServer`, it
  records the last command and forks the stop; `ready` waits for it.
- `release(rebuild)` restarts the stopped server with `supervisor.start` and frees the gate, also when the restart
  fails. `rebuild` (given by the runner) builds the command again from the profile as it is now, so edits saved during
  the benchmark apply; the recorded command is used when it gives none. A failed restart is logged as
  `could not restart llama-server: …`.
- While the runner is busy, the server endpoints refuse every lifecycle call with `409 A benchmark is running`, and
  the external watch is paused.

[Benchmarks and sweeps](/developers/server/bench/) covers the runner.
