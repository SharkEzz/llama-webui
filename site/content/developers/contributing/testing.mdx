Tests run on Node with [Vitest](https://vitest.dev) and sit next to the code they test, except those of
[llamacpp-js](/developers/llamacpp-js/), which use Node's own runner, `node:test`
([Tests of llamacpp-js](#tests-of-llamacpp-js)). The server's tests are effects, run by
[`@effect/vitest`](https://effect.website) on the services of the app with an in-memory database. They cover logic
rather than screens: parsers fed with real captured outputs from `testdata/`, the estimator, the repositories on
SQLite, the endpoints over HTTP, the supervisor and the benchmark runner driving fake `llama-server` and `llama-bench`
binaries, and the production build started as a user starts it.

## Run the tests

From the root of the repository:

```bash title="Terminal"
pnpm test
```

It runs two suites one after the other, and is the command CI runs:

| Script                  | Command                         | Runs                                                                                                                    |
| ----------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `test:unit`             | `vitest run`                    | Every `*.test.ts` of `app/server/`, `app/build/`, `scripts/`, `packages/webui-shared/`, `app/src/` and `site/`, on Node |
| `test` of `llamacpp-js` | `node --test 'tests/*.test.ts'` | The tests of `packages/llamacpp-js/`, on Node                                                                           |

`vitest.config.ts` at the root defines one Vitest project per code base: `server` (`app/server/`, `app/build/` and
`scripts/`), `shared`, `web` (`app/src/`, with the `@/` alias to it) and `site` (with its own `@/` alias). Imports are
explicit (`import { expect, test } from 'vitest'`, or `@effect/vitest` for an effect), and `oxc.target` is `esnext` so
that `using` stays native.

The `server` project has a `globalSetup`, `app/server/testing/build.ts`: before its first test, it runs one
production build (`pnpm run build`, into `app/.output`), which the suites that start the app share (contract,
lifecycle, build output). `LLAMA_WEBUI_TEST_BUILD=0` skips it and reuses the build already there, to rerun a test
quickly after a change that does not touch the build.

| Command                                                                      | Runs                                                        |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `pnpm exec vitest run app/server/bench`                                      | Test files whose path contains `app/server/bench`           |
| `LLAMA_WEBUI_TEST_BUILD=0 pnpm exec vitest run app/server/lifecycle.test.ts` | One file, on the existing build                             |
| `pnpm exec vitest run --project web`                                         | The tests of one project                                    |
| `pnpm exec vitest run -t 'sweep'`                                            | Tests whose name matches the regular expression             |
| `pnpm exec vitest run --changed`                                             | Test files that import a file changed since the last commit |
| `pnpm exec vitest`                                                           | Watch mode: reruns the tests a change affects               |
| `VITEST_ENABLE_CONSOLE_LOG=1 pnpm exec vitest run app/server/bench`          | The same files, with what their tests write on the console  |

The report hides what a test writes on the console (`onConsoleLog` in `vitest.config.ts`), so that failures stay
readable: `VITEST_ENABLE_CONSOLE_LOG=1` shows it. Each file is listed with the heap it used (`logHeapUsage`).

<Callout type="warning">

`--changed` and watch mode follow imports only. The suites that start the production build (contract, lifecycle, build
output) and `vite dev` (`app/server/dev.test.ts`) do not import the server: a change to a route or a service does not
select them. Use them as a quick loop while working, and run the full `pnpm test` before every commit.

</Callout>

A test has 5 seconds by default. The tests that start `vite dev` pass a longer timeout as the last argument of
`test()` (`}, 90_000);` in `app/server/dev.test.ts`); an effect that waits bounds its own wait with `Effect.timeout`.

## Where tests live

A test file sits next to its module: `app/server/bench/parse.test.ts` tests `app/server/bench/parse.ts`, and
`app/server/<domain>/http.test.ts` the endpoints of a domain. The library `llamacpp-js` keeps its tests apart, in
`packages/llamacpp-js/tests/` (`tests/metrics.test.ts` tests `src/metrics.ts`), so that `src/` holds only what a
published package ships.

| Folder                   | What the tests cover                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/server/`            | Parsers (`nvidia-smi`, AMD sysfs and fdinfo, `perf`, startup logs, PCI topology), GGUF reading and the model scan, `llama-server` command lines, the supervisor and external-server detection, tuning, repositories and migrations, the bench runner and gate, chat runs, Hugging Face downloads, the guard and request errors, the configuration and command line, the setup report, the endpoints of each domain, the HTTP contract, the production build, shutdown and the development loop |
| `app/build/`             | The build plugin that writes `THIRD-PARTY-LICENSES.md` (`licenses.test.ts`)                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `packages/webui-shared/` | Pure logic used on both sides: benchmark parameters, profile import, sweeps, chat stats and titles, logs, topology, models, setup checks, Hugging Face inputs, `defer`; and the schemas (settings, profiles, the messages of `/ws`)                                                                                                                                                                                                                                                            |
| `packages/llamacpp-js/`  | The llama.cpp client: flags from `--help`, the SSE parser, `/metrics` and `/slots`, `llama-bench` output, the health probes, `/props` and the streamed chat completion, `/proc` discovery, and the package's own contract (`tests/package.test.ts`: no app import, `.ts` import paths, one export per module, tree-shaking)                                                                                                                                                                    |
| `app/src/`               | Pure UI logic: the typed client (`app/src/lib/api.ts`), the Topology page's flows, geometry, placements, streaks and view preference (`app/src/features/topology/`), the benchmark form mapping (`app/src/lib/bench.ts`), the profile draft, the error texts of a page and the chat's Markdown rendered by blocks (`features/chat/Markdown.test.ts`, with `react-dom/server`)                                                                                                                  |
| `site/`                  | The link checker helpers, the sidebar and content routes, the landing page's telemetry simulation                                                                                                                                                                                                                                                                                                                                                                                              |

`scripts/` holds the tests of the repository itself: the published package's fields (`package.test.ts`) and the
versions of every `package.json` (`release.test.ts`).

There are no component or browser tests (no DOM library is installed). When a page has logic worth testing, it lives in
a plain module next to the page, as `flows.ts` does for the Topology page.

## Write a test

A server test is an effect. `it.effect` of `@effect/vitest` runs it, with its services provided by a layer, and
asserts with `assert` from the same package:

```ts title="app/server/settings/SettingsRepo.test.ts"
/** A repository on a new in-memory database, with its client for what the test stores itself. */
const Fresh = SettingsRepo.layer.pipe(Layer.provideMerge(Db.layerAt(':memory:')));

/** `test` on its own new database. */
const fresh = <A, E>(test: Effect.Effect<A, E, SettingsRepo | SqlClient.SqlClient>) =>
  Layer.build(Fresh).pipe(
    Effect.flatMap((context) => Effect.provideContext(test, context)),
    Effect.scoped,
  );

describe('SettingsRepo', () => {
  it.effect('settings: defaults, then a persisted patch', () =>
    fresh(
      Effect.gen(function* () {
        const repo = yield* SettingsRepo;
        const initial = yield* repo.get;
        assert.deepStrictEqual(initial, DEFAULT_SETTINGS);
        const patched = yield* repo.patch({ port: 9000 });
        assert.strictEqual(patched.port, 9000);
        const read = yield* repo.get;
        assert.strictEqual(read.port, 9000);
        const refused = yield* Effect.flip(repo.patch({ pollIntervalMs: 10 }));
        assert.strictEqual(refused._tag, 'SettingsInvalid');
      }),
    ),
  );
```

- **Names** are English sentences that state the behavior: `a deleted profile's id is never given to a new profile
(#38)`, `isOomError recognizes the current and the legacy out-of-memory errors`. A `describe` block, or the name a
  `layer(…)` gives its tests, groups the tests of one module.
- **The services** come from layers, never from a mocked module. `layer(L)('Name', (it) => { … })` builds `L` once
  for the tests of its block and runs its finalizers after them; a test that needs its own state builds its layer
  inside the test (`fresh` above). `ServicesTest` (`app/server/testing/services.ts`) is the app's services as
  `App.ts` builds them, on an in-memory database, with the stub monitor (no collector, no snapshot) and shorter
  durations through each service's `layerWith`; `ServicesWithoutBench` and `ServicesWithoutQueue` are its lower
  tiers, for a test that builds its own runner or download queue on them.
- **Time**: `it.effect` runs on the `TestClock`, where a `sleep` waits until the test moves the clock
  (`TestClock.adjust`). A test on real time (a process, a socket, a schedule) takes `it.live`, or
  `layer(L, { excludeTestServices: true })` for a whole block.
- **Errors** are asserted by their tag: `Effect.flip` turns the failure into the value, then
  `assert.strictEqual(error._tag, 'ProfileNotFound')`.
- **Endpoints** are tested over real HTTP: `serve(ApiRoutes)` on `ServicesTest` and `ServerTest`
  (`app/server/testing/http.ts`: a Node server on `127.0.0.1` and a free port, with a client bound to it), through the
  typed client (`HttpApiTest.groups(Api, ['<group>'])`) or raw requests for what the client would never send
  ([Add an endpoint](/developers/contributing/how-to/#add-an-endpoint)).
- **Temporary folders and files** come from `FileSystem` (`fs.makeTempDirectoryScoped({ prefix })`, deleted with the
  test's scope). Outside an effect, `tempDir(prefix)` (`app/server/testing/tempDir.ts`) with `using` does the same.
- **`/proc` and `/sys` readers** take the root to read from, so a test writes a small tree in a temporary folder:
  `readProcAmdVram(pid, { procRoot, skipNodes })` reads `<procRoot>/<pid>/fdinfo/*`.
- **Programs and HTTP peers**: `app/server/testing/llama.ts` gives the paths of the fake binaries (`FAKE`,
  `FAKE_BENCH`), `freePort`, `pidAlive(pid)`, `httpStub` (a `node:http` server that answers what the test says),
  `chatStub` (a fake `llama-server` stream the test feeds chunk by chunk) and `fakeOutside` (a `llama-server` started
  by someone else). `app/server/testing/hub.ts` is a fake Hugging Face Hub and CDN, with `Range` support and scripted
  faults. A test that starts a process checks that it is dead at the end.
- **Ports**: a test takes a free port, never 7860, 7861 or 8080 (where the user's own app and `llama-server` run):
  `freePort` draws it from a block of ports of its Vitest worker, below Linux's ephemeral range, so that neither
  another worker nor an outgoing connection takes it before the program listens on it.
- **Environment variables** a test sets are owned by its scope (`ownVariable(name, value)`), so they are restored
  when it ends.
- **Promises**, in a plain Vitest test, are awaited: `await expect(p).rejects.toThrow()`. The lint enforces it:
  `vitest/valid-expect` reports a `.resolves` or `.rejects` assertion left unawaited (Vitest fails the test too), and
  `typescript/no-floating-promises` any other promise neither awaited, returned, handled nor discarded with `void`.
- **Nothing is left pending**: `detectAsyncLeaks` (`vitest.config.ts`) reports a promise never settled, a timer or a
  handle that a test file leaves behind, and the `failOnAsyncLeaks` reporter next to it fails the run on one (Vitest
  alone prints the leak and exits 0). A leak may show only when its test runs alone (`-t`): in a full file, a later
  test can outlast the timer. Three habits keep a file clean:
  - the body of a `fetch` reply is read (`json()`, `text()`) or cancelled (`await res.body?.cancel()`), even when
    only the status matters: an unread body keeps its stream pending;
  - a wait with a limit is `orAfter(promise, ms, late)` (`app/server/testing/orAfter.ts`), which cancels its timer,
    not a bare `Promise.race([promise, sleep(ms)])`, whose timer stays pending when the promise wins;
  - a retried assertion is `vi.waitFor(() => expect(…))`, not `expect.poll`: a poll that passes leaves Vitest's own
    timeout promise pending.

### Build, shutdown and development loop

The tests that need the whole app start the production build in a process of its own, as a user does:
`launch({ dataDir, port?, env? })` (`app/server/testing/launch.ts`) runs `app/.output/llama-webui.mjs` with
`--host 127.0.0.1`, a free port and the data directory, from the data directory, without the `CI`, `TEST`,
`NODE_ENV` and `LLAMA_WEBUI_DEV` variables that a user never sets. A data directory without a database gets one whose
`port` setting is a free port (`seedWatchPort`, `app/server/testing/seed.ts`), so the build never looks at 8080. It
waits for `/api/health`, and stops the app with `SIGTERM` when disposed (`await using`). These files are plain Vitest
tests:

- `app/server/lifecycle.test.ts`:
  - a second instance on a taken port exits with code 1 and names the port, without touching the data directory of
    a first instance on the same folder;
  - `.env` sets a variable, the environment wins over it, and `--env-override` lets `.env` win;
  - a `SIGTERM` stops the app in under 2 seconds with the UI open (close code 1001), with `llama-server` running
    (stopped), with a chat reply streaming (ended with `done`, saved `stopped`), during a benchmark (saved
    `interrupted`, `llama-bench` killed) and during a download (its `.part` kept, resumed by the next start);
  - an exit without its finalizers leaves no `llama-server`;
  - a data directory of the Nitro server opens untouched, and the build never connects to the Effect DevTools.
- `app/server/build.test.ts` reads the build of the `globalSetup`: the launcher starts from an empty folder outside
  the repository, the server requires nothing but Node built-ins (the build is self-contained), the client imports no
  `node:` module and each page is a chunk of its own, a deep URL gets the shell, `THIRD-PARTY-LICENSES.md` ships next
  to the server, and `nvml-worker.mjs` sits next to the module that names it and starts from the bundle.
- `app/server/collectors/nvml/Nvml.test.ts` drives the NVML sampler: its readings, a sampler that never answers (given
  up after the ready timeout and killed), one stuck in a native call, one that exits, and the real worker with a
  missing library (`null`, the `nvidia-smi` fallback).
- `app/server/dev.test.ts` starts `vite dev` on a free port, in a copy of `app/` under the repository's `.cache/`
  (ignored by git; `node_modules` linked entry by entry, `devCopy()` of `app/server/testing/devCopy.ts`), so the
  checkout's files and a `pnpm dev` you run meanwhile are left alone: saving a server file restarts the server (a new
  `bootId`), saving a web file keeps it, one `SIGINT` (with a page open too), two quick ones and a `SIGHUP` stop
  `vite dev` and the server, `.env` is read and the environment wins over it, and the server connects to the
  DevTools address in development only. `app/build/devServer.test.ts` covers the plugin's link to the server on its own
  (`serverLink()`): it waits for a server that starts, keeps one connection instead of one per request, drops with the
  server, and gives up after its wait when nothing listens.

### Tests of llamacpp-js

[llamacpp-js](/developers/llamacpp-js/) targets Node 24 or later, so its tests are written with Node's
own runner, `node:test` and `node:assert/strict`, with no dependency: `pnpm --filter llamacpp-js test`
(`node --test 'tests/*.test.ts'`) runs them on the TypeScript sources as they are. CI runs them on Node 26 in the main
job and on Node 24, the lowest supported version, in a job without any install.

```ts title="packages/llamacpp-js/tests/metrics.test.ts"
import assert from 'node:assert/strict';
import { describe, test } from 'node:test';
import { parseSlots } from '../src/metrics.ts';
import { fixture } from './helpers.ts';

describe('parseSlots', () => {
  test('idle slot', async () => {
    const s = parseSlots(JSON.parse(await fixture('slots-idle.json')))[0]!;
    assert.equal(s.processing, false);
    assert.equal(s.nDecoded, 0);
    assert.equal(s.idTask, null);
  });
});
```

- They use web and `node:*` APIs only: a local server comes from `serve(handler)` (`node:http`), a file from
  `fixture()`, the directory from `import.meta.dirname`. The package's project (`tsconfig.json`, sources and tests)
  has the Node types only, so any other runtime's API does not type check.
- `tests/helpers.ts` adds the two assertions `node:assert` lacks: `closeTo(actual, expected, digits)` and
  `matchObject(actual, expected)` (the properties of `expected`, deeply equal).
- The bundling checks of `tests/package.test.ts` bundle an import of the package with Rolldown (a devDependency of
  `llamacpp-js`) for the browser: tree-shaking keeps only what one function needs, and the browser-safe modules pull no
  Node built-in. Without an install, as in the Node 24 job, they pass `{ skip }` and Node reports them as skipped.

## Fake binaries

`testdata/fake/` holds two stand-ins for the llama.cpp binaries. Each is a shell script that runs its TypeScript
counterpart with `node` from the `PATH` (a plain Node script: erasable TypeScript, `node:*` APIs only), so a test can
use it wherever the app expects a binary path. `app/server/testing/llama.ts` exports their paths, `FAKE` and
`FAKE_BENCH`.

### Fake llama-server

`fake-llama-server` takes `llama-server`'s flags, prints log lines on stderr, and serves on `127.0.0.1` at the `--port`
it was given:

- `/health` answers `503` while it "loads" the model, then `{"status":"ok"}`.
- `/completion` and `/v1/chat/completions` answer with timings. A streamed chat reply sends reasoning (unless thinking
  is off), then Markdown, one chunk at a time; a prompt larger than the simulated context gets `llama-server`'s
  context-size error.
- `/slots`, `/metrics` and `/props` serve `slots-busy.json`, `metrics-after.txt` and `props.json` from `testdata/fake/`.
- With `FAKE_SSE=1`, `GET /models/sse` streams `llama-server`'s `status_change` events (`loading` with its progress,
  `loaded` with a `memory` report, `sleeping`), the last one first to a new connection. `POST /test/sleep` puts the
  server to sleep, and `GET /test/sse-refused` counts the streams refused (`FAKE_SSE_REFUSE_AFTER_SLEEP`).
- Asleep, it behaves as `llama-server` does: `/health`, `/metrics` and `/props` still answer, and a request that
  needs the model (`/slots`, `/completion`, `/v1/chat/completions`) wakes it and waits until the model is back,
  without a `503`.
- `--version` prints a fake build line and exits; `--help` prints a one-flag catalogue and exits.

The supervisor, the bench runner, the profiles' endpoints, the contract suite and the lifecycle tests use it, as the
`binary` setting.

Environment variables shape its behavior:

| Variable                                | Effect                                                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `FAKE_LOAD_MS`                          | Loading time before `/health` is ready (default 300 ms)                                         |
| `FAKE_SLOW_ARG`, `FAKE_SLOW_MS`         | A longer load (default 5000 ms) when that argument is present                                   |
| `FAKE_FAIL_ARG`                         | Logs a CUDA out-of-memory and exits with 1 when that argument is present                        |
| `FAKE_EXIT_LINES`                       | Logs these `\|`-separated lines, then exits with 1                                              |
| `FAKE_TAIL`                             | Writes this last line without its newline                                                       |
| `FAKE_ECHO_ENV`                         | `A,B`: logs one line per variable, with its value as the fake sees it                           |
| `FAKE_CRASH_ON_PREDICT`                 | Dies mid-request on a `/completion` with that `n_predict`                                       |
| `FAKE_PP`, `FAKE_TG`, `FAKE_DRAFT`      | Reported prompt and generation speeds, draft statistics when `1`                                |
| `FAKE_N_CTX`                            | Simulated context size (default 40192 tokens)                                                   |
| `FAKE_CHAT_DELAY_MS`, `FAKE_CHAT_LINES` | Delay between streamed chunks (default 60 ms), extra reply lines                                |
| `FAKE_IGNORE_TERM`                      | Ignores `SIGTERM` when `1`                                                                      |
| `FAKE_EXIT_AFTER_MS`, `FAKE_EXIT_CODE`  | Exits on its own after a delay, with that code (default 1)                                      |
| `FAKE_SSE`                              | Serves `GET /models/sse` and `POST /test/sleep` when `1` (a `404` otherwise, as an older build) |
| `FAKE_SSE_STAGES`                       | The loading stages announced, comma-separated (default `text_model`)                            |
| `FAKE_SSE_STAGE_ONLY`                   | When `1`, `mmproj_model` starts with a stage-only event (`{ stage }`, no list, no value)        |
| `FAKE_SSE_FAIL`                         | When `1`, the load ends with `unloaded` (`exit_code: 1`) and the process exits with 1           |
| `FAKE_SSE_STALL`                        | `headers`: the stream never answers; `events`: it answers, then sends no event                  |
| `FAKE_SSE_REFUSE_AFTER_SLEEP`           | When `1`, a sleep cuts the streams and the next `/models/sse` answers `503`                     |
| `FAKE_SLEEP_IDLE_MS`                    | Sleeps after that long without a request that needs the model, as `--sleep-idle-seconds` does   |
| `FAKE_SLOTS_IDLE`                       | When `1`, `/slots` serves `testdata/slots-idle.json` (an idle slot, as `/metrics` says)         |

### Fake llama-bench

`fake-llama-bench` sits next to the fake server, as `llama-bench` sits next to `llama-server`: `benchBinary()`
(`llamacpp-js/node`) turns `testdata/fake/fake-llama-server` into `testdata/fake/fake-llama-bench`. It prints
`llama-bench`'s progress lines on stderr and the JSON of `testdata/llama-bench/ok.json` on stdout, and answers
`--list-devices` with `list-devices.txt`.

| Variable             | Effect                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `FAKE_BENCH_STEP_MS` | Pause between progress steps (default 100 ms)                                                                              |
| `FAKE_BENCH_OOM`     | `1`: fails like an out-of-memory load (`oom-stderr.txt`, exit code 1)                                                      |
| `FAKE_BENCH_OOM_ARG` | Same failure when the arguments contain that fragment                                                                      |
| `FAKE_PP`, `FAKE_TG` | Overrides the prompt and generation speeds                                                                                 |
| `FAKE_TG_BY_ARG`     | `-ncmoe 8=30;-dev CUDA0,CUDA1=55`: the generation speed of the first fragment found (the fake receives `-dev` with commas) |

### Use them in a test

A test points the `binary` setting at the fake server, on a free port. The `env` setting (or a profile's) reaches the
spawned fakes, as it reaches the real binaries:

```ts title="app/server/bench/BenchRunner.test.ts"
/** The fake as llama-server (llama-bench next to it), with these variables; the trial's port is free. */
const useFake = Effect.fn(function* (env: Record<string, string> = {}) {
  const settings = yield* SettingsRepo;
  const port = yield* freePort;
  yield* settings.patch({ binary: FAKE, host: '127.0.0.1', port, env }).pipe(Effect.orDie);
});
// …
      yield* useFake({ FAKE_BENCH_OOM: '1' });
```

Such a test runs on real time (`it.live`), waits for a state with a bounded `Effect.repeat`, and checks that the
processes it started are gone at the end (`pidAlive`).

## Fixtures

Modules and files that build inputs for the tests that need a model, a machine or an old database:

- **`app/server/testing/tuning.ts`**
  - `fakeModel(o)` returns a complete `ModelInfo`, tensors included, with the sizes you pass: 48 layers by default, an
    embedding and an output of 300 MiB, 100 MiB of attention per layer, and expert tensors (`ffn_gate_exps`,
    `ffn_up_exps`, `ffn_down_exps`, 300 MiB per layer) when `experts` is above 0.
  - `hw3(o)` returns a `TuningHardware`: two 16 GiB CUDA cards, an RX 9070 XT on Vulkan, an iGPU, the Vulkan duplicates of
    the NVIDIA cards and BLAS, with 61 GiB of RAM (55 GiB available unless `ramAvailableGiB` says otherwise).
  - The estimator, placement, system checks and setup tests use them.
- **`app/server/testing/gguf.ts`**: `writeGguf(path, kv, tensors)` writes a real GGUF v3 file: header, typed key/value
  pairs (`u32`, `u64`, `f32`, `string`, `u32[]`), tensor infos aligned on 32 bytes, then zero bytes for each tensor. The
  GGUF reader, model scan and contract tests parse these files instead of shipping models.
- **`app/server/testing/bench.ts`**: `benchSpec()` and `sweepSpec()`, valid specs to override field by field.
- **`app/server/testing/fixtures/`**: small programs a test runs with `node` to watch a process from outside: an app

- **`app/server/db/fixtures/`**: two databases written by the Nitro server, described in its `README.md`

## HTTP contract suite

`app/server/contract/` records what the API answers, over real HTTP, so that a change of server framework or runtime
has to give the same replies. `contract.test.ts` prepares a temporary data directory (a home of its own with one
small model, the fake `llama-server` as the `binary` setting), then starts the production build on it with
`launch()`. Two test settings, read by the services, replace what depends on the machine:
`LLAMA_WEBUI_TEST_MONITOR=stub` gives a monitor without collectors (`Monitor.layer`), and
`LLAMA_WEBUI_TEST_OFFLINE=1` makes every Hugging Face request fail as offline (`HfHttp.layer`), hence the `502`
`HfUnreachable` of the Hub's routes. It sends every case, then compares each reply with
`app/server/contract/golden.json`.

<FileTree>

- `app/server/contract/`
  - `wire.ts`: raw HTTP/1.1 client on `node:net` (`request`, `readSse`): a request carries the headers a browser
    sends, not the ones a `fetch` implementation adds
  - `cases.ts`: the cases (`cases()`, with the matrix of the API definition), `normalize()`, `runContract()` and
    `runStreams()`
  - `contract.test.ts`: prepares the data, launches the build, runs the cases, compares with the golden
  - `golden.json`: the recorded replies, one entry per case, in run order

</FileTree>

The cases come in three parts:

- **the matrix**, generated from the API definition (`HttpApi.reflect(Api, …)`):
  - every method a path lacks (a `404` `RouteNotFound`: there is no `405`);
  - for each `:param`, an id that is not a number (`abc`) and one no row has (`999999`);
  - for each endpoint that reads a body: malformed JSON, a JSON value that is not an object, no body with and without
    `Content-Type: application/json`, and a `text/plain` body;
- **the cases written by hand**, each with its kind: `read` and `write` (an endpoint used as the web uses it,
  llama-server's commands, the settings, the profiles, the flag catalogue, the bench, the Hub and the downloads, the
  chat, the models folder, the tuning), `violation` (a payload that breaks the schema), `refusal` (a valid request the
  domain refuses), `guard` (a foreign `Origin` or `Host`, a malformed `Host`), `other` (an unknown path, `/ws`
  without an upgrade, a trailing slash) and `web` (the UI's files: a deep URL, a hashed asset, a missing one);
- **the streams** (`runStreams`): `/ws` (`hello`, then `ping` → `pong`), a profile started on the fake
  `llama-server`, and a chat reply streamed from it, read by `readSse` (headers, the first event, the name of the last
  one).

The calls that change rows run after the reads, on rows the cases made for them. A test checks that a case covers
every endpoint of the API definition: a new endpoint fails it until it has a case (the matrix reaches every endpoint
with a `:param` or a body; write a success for the others). Another checks that no `violation`, `body`, `guard` or `refusal`
case succeeds.

A reply is recorded with:

- its status;
- its `content-type`, `allow`, `cache-control`, `content-disposition` and `location` headers;
- its body (JSON parsed, otherwise text).

Values that change from one run to the next become placeholders: the temporary directory (`<tmp>`), the home
directory (`<home>`), the repository (`<repo>`), ports (`<port>`), timestamps (`<time>`), UUIDs (`<uuid>`), the content
hash of a built asset (`/assets/index-<hash>.js`, which changes with any change to the client), and `bootId`,
`version`, `uptimeMs`, `pid`. An endpoint whose answer depends on the machine (its CPU, its PCI devices) records the
names of its top-level fields, not their values.

When a change of behaviour is intended, regenerate the golden and read its diff before committing it:

```bash title="Terminal"
UPDATE_GOLDEN=1 pnpm exec vitest run app/server/contract/contract.test.ts
git diff app/server/contract/golden.json
```

A failure lists the names of the cases whose reply changed, with the diff of those replies only. `golden.json` is
written by the test and left out of the formatter (oxfmt), so a regeneration changes only the entries that moved. The suite was
recorded on the Nitro server and replayed on the Effect server; the replies that changed on purpose are listed in
`docs/superpowers/poc-effect/behaviours.md` of the repository.

<Callout type="note">

The golden pins no Hugging Face success (the suite has no network) and no value of the machine-dependent endpoints:
check those screens in the running app after a change of framework or runtime.

</Callout>

## Migrations on old data

A migration that rewrites existing data gets a test on a database at the schema it starts from. The databases of the
Nitro server are files of `app/server/db/fixtures/` (`legacy-v16.sqlite`, `legacy-v17.sqlite`, their rows listed in
its `README.md`), written once by that server's own code: no local file of a user, so the tests run in CI and on a
fresh clone. A test opens a copy, never the fixture itself, with `Db.layerAt(file)`, which applies what is missing, as
on a user's machine:

```ts title="app/server/db/Db.test.ts"
  it.effect('an older database is brought up to date: profiles keep their ids and every link to them (#38)', () =>
    Effect.gen(function* () {
      const file = yield* tempFile('legacy-v16.sqlite');
      yield* withDb(file, (sql) =>
        Effect.gen(function* () {
          const version = yield* sql`SELECT version FROM schema_version`;
          assert.deepStrictEqual(version, [{ version: 17 }]);
          // … the same ids, every link to them, no foreign key violation, and the next id after the highest
        }),
      );
    }),
  );
```

`Db.test.ts` also checks that a new database gets the schema of the Nitro server, that a database of the Nitro server
is recognised without replaying anything, that it still opens with the Nitro server afterwards, and that a table
rebuild that breaks a link fails and is rolled back.

## Type checking

```bash title="Terminal"
pnpm check
```

The `check` script is `pnpm -r --parallel --include-workspace-root typecheck`: it runs the `typecheck` script of
every workspace package at the same time. That script is `tsc` in `packages/*`, `tsc && tsc -p server` in `app/`
(its two projects), `tsc -p . && tsc -p scripts` in the root package (its config files, then `scripts/`) and `react-router typegen && tsc` in `site/`. One package alone:
`pnpm --filter <name> typecheck`. `tsc` is TypeScript 7, the native compiler.

There is no TypeScript project reference: each code base has its own `tsconfig.json`, which extends
`tsconfig.base.json` (the shared options, `noEmit` among them), directly or through `tsconfig.effect.json`, and adds
its types and its files. The root `tsconfig.json` covers the config files of the root only (`./*.config.ts`,
`./oxlint.*.ts`), with options of its own, and the root `typecheck` runs it before `scripts/`.

| Project                               | Covers                                                                                                                        | Types                                             |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `packages/llamacpp-js/tsconfig.json`  | The library's sources and its tests (`tests/`), as a Node user compiles them: NodeNext resolution                             | Node only (no DOM): a browser-only API fails here |
| `packages/webui-shared/tsconfig.json` | `@llama-webui/shared` and its tests, with the Effect diagnostics                                                              | Node, no DOM: a browser-only API fails here       |
| `app/server/tsconfig.json`            | `app/server/` and its tests, with the Effect diagnostics                                                                      | Node                                              |
| `tsconfig.json` (root)                | The root config files: `./*.config.ts` and `./oxlint.*.ts` (oxfmt, Vitest, oxlint and its fragments)                          | Node                                              |
| `scripts/tsconfig.json`               | `scripts/`                                                                                                                    | Node                                              |
| `app/tsconfig.json`                   | `app/src/` (tests included), `app/build/` and `app/vite.config.ts`                                                            | DOM and Node                                      |
| `site/tsconfig.json`                  | `site/src/`, `site/content/nav.ts`, `site/scripts/` and the config files, after `react-router typegen` writes the route types | DOM and Node                                      |

A project that imports another package checks the sources it reaches with its own options: the server those of
`llamacpp-js` and `webui-shared`, and `app/tsconfig.json` those of `webui-shared`, whose API definition the typed
client is derived from (the client never imports server code), and those `app/vite.config.ts` imports. That is why
the client project has Node's types next to the DOM's. The production build test (`app/server/build.test.ts`) checks
that no chunk of the client bundle imports a `node:` module. The projects do not enable the same options:

| Option                                                         | `tsconfig.base.json` (packages, `app/server/`, `scripts/`) | `app/` | `site/` |
| -------------------------------------------------------------- | ---------------------------------------------------------- | ------ | ------- |
| `strict`, `verbatimModuleSyntax`, `noFallthroughCasesInSwitch` | yes                                                        | yes    | yes     |
| `noUncheckedIndexedAccess`                                     | yes                                                        | yes    | yes     |
| `noImplicitOverride`                                           | yes                                                        | yes    | no      |
| `exactOptionalPropertyTypes`, `erasableSyntaxOnly`             | yes                                                        | yes    | no      |
| `noUnusedLocals`, `noUnusedParameters`                         | no                                                         | yes    | yes     |

With `verbatimModuleSyntax`, type-only imports must use `import type`. With `exactOptionalPropertyTypes`, an optional
property (`x?: T`) takes no `undefined`: write `x?: T | undefined` (or `Schema.optional`) where a caller passes one on,
or leave the key out. `erasableSyntaxOnly` refuses what Node cannot strip (`enum`, `namespace`, constructor parameter
properties); relative imports keep their `.ts` extension (`rewriteRelativeImportExtensions`, `allowImportingTsExtensions`
in `site/`).

### Effect diagnostics

The projects that hold Effect code (the server and `packages/webui-shared`) extend `tsconfig.effect.json`, which
loads the Effect language service (`@effect/tsgo`, patched into the `tsc` of `node_modules` by the root `prepare`
script at each `pnpm install`). Its diagnostics come out of `tsc` as `effect(<rule>)` lines, with the severities of
`diagnosticSeverity`: they are blocking, warnings included, so `pnpm check` prints no `effect(` line. Among them, the
platform rules refuse `node:*` imports, `fetch`, timers, `JSON` and `process.env` in the server; the few `node:*`
imports it keeps carry a directive and their reason. The test helpers and the suites that drive the build from outside
(`testing/`, `contract/`, `lifecycle.test.ts`, `build.test.ts`, `dev.test.ts`) are exempt from those rules, and the
pure logic of the shared package stays plain TypeScript. `unstableApiUsage` and `apiStabilityLeak` are off: nearly
every Effect module beyond the core is `@stability unstable`, which is why the Effect version is pinned exactly.

The `.mdx` pages are not type checked; the site build compiles them.

## Test the website

The site's unit tests run with the others under Vitest (project `site`):

- `site/src/docs/nav.test.ts` fails when a page under `site/content/` is missing from `site/content/nav.ts`, when an
  entry has no file or appears twice, or when a page sits in the wrong section.
- `site/src/lib/content.test.ts` checks how a file maps to its route.
- `site/scripts/links.test.ts` tests the link checker's helpers.
- `site/scripts/serve.test.ts` drives the preview server (`serveDist()`) on a small `dist/`: trailing-slash redirects,
  content types and cache, gzip for text only, `404.html` and `Not found`, `HEAD`.
- `site/scripts/cli.test.ts` starts `serve.ts` with `-- --port 0`: a script reads its flags after the `--` that pnpm
  passes through.
- `site/src/landing/telemetry.test.ts` checks that the landing page's simulated dashboard is deterministic, so the
  prerendered HTML and the hydrated page start from the same frame.

After a build, the link checker reads every page of `site/dist/`:

```bash title="Terminal"
pnpm site:build
pnpm --filter llama-webui-site check-links
```

It extracts each `href`, `src` and `srcset` URL and fails on a page or file that does not exist, a missing `#anchor` (on
the same page or the target), a page link without its trailing slash, a relative URL or a URL outside `/llama-webui/`.
External links are not fetched. CI runs both commands; [Docs, commits and PRs](/developers/contributing/workflow/) covers
writing pages.
