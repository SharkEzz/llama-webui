Tests run on Node with [Vitest](https://vitest.dev) and sit next to the code they test, except those of
[llamacpp-js](/developers/llamacpp-js/), which use Node's own runner, `node:test`
([Tests of llamacpp-js](#tests-of-llamacpp-js)). They cover logic rather than screens: parsers fed with real captured outputs from `testdata/`, the estimator, the repositories against SQLite, and the
benchmark runner driving fake `llama-server` and `llama-bench` binaries.

## Run the tests

From the root of the repository:

```bash title="Terminal"
pnpm test
```

It runs two suites one after the other, and is the command CI runs:

| Script                           | Command                                                    | Runs                                                        |
| -------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------- |
| `test:unit`                      | `vitest run`                                               | Every `*.test.ts` of `app/server/`, `app/build/`, `scripts/`, `packages/webui-shared/`, `app/src/` and `site/`, on Node |
| `test` of `llamacpp-js`          | `node --test 'tests/*.test.ts'`                            | The tests of `packages/llamacpp-js/`, on Node               |

`vitest.config.ts` at the root defines one Vitest project per code base: `server` (`app/server/`, `app/build/` and
`scripts/`), `shared`, `web` (`app/src/`, with the `@/` alias to it) and `site` (with its own `@/` alias). Imports are
explicit (`import { expect, test } from 'vitest'`), and `oxc.target` is `esnext` so that `using` stays native.

The `server` project has a `globalSetup`, `app/server/lib/testing/build.ts`: before its first test, it runs one
production build (`pnpm run build`, into `app/.output`), which the suites that start the app share (contract,
lifecycle, build output). `LLAMA_WEBUI_TEST_BUILD=0` skips it and reuses the build already there, to rerun a test
quickly after a change that does not touch the build.

| Command                                            | Runs                                                 |
| -------------------------------------------------- | ---------------------------------------------------- |
| `pnpm exec vitest run app/server/lib/bench`        | Test files whose path contains `app/server/lib/bench` |
| `LLAMA_WEBUI_TEST_BUILD=0 pnpm exec vitest run app/server/lifecycle.test.ts` | One file, on the existing build |
| `pnpm exec vitest run --project web`               | The tests of one project                             |
| `pnpm exec vitest run -t 'sweep'`                  | Tests whose name matches the regular expression      |
| `pnpm exec vitest`                                 | Watch mode: reruns the tests a change affects        |

A test has 5 seconds by default. Tests that spawn processes or start the app pass a longer timeout as the third
argument of `test()` or `beforeAll()` (`}, 20_000);` in `app/server/lib/bench/runner.test.ts`, `90_000` for a
`vite dev` of `app/server/dev.test.ts`).

## Where tests live

A test file sits next to its module: `app/server/lib/bench/parse.test.ts` tests `app/server/lib/bench/parse.ts`. The library
`llamacpp-js` keeps its tests apart, in `packages/llamacpp-js/tests/` (`tests/metrics.test.ts` tests
`src/metrics.ts`), so that `src/` holds only what a published package ships.

| Folder     | What the tests cover                                                                                                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/server/`  | Parsers (`nvidia-smi`, AMD sysfs and fdinfo, `perf`, startup logs, PCI topology), GGUF reading and the model scan, `llama-server` command lines, external-server detection, tuning, repositories, the bench runner and gate, chat runs, Hugging Face downloads, the security guard, CLI flags, the setup report, route files, the HTTP contract, the production build, shutdown and the development loop |
| `app/build/`   | The build plugin that writes `THIRD-PARTY-LICENSES.md` (`licenses.test.ts`); the route map's plugin is tested by `app/server/api.gen.test.ts` |
| `packages/webui-shared/`  | Pure logic used on both sides: benchmark parameters, profile import, sweeps, chat stats and titles, logs, topology, models, setup checks, Hugging Face inputs, `defer` |
| `packages/llamacpp-js/`  | The llama.cpp client: flags from `--help`, the SSE parser, `/metrics` and `/slots`, `llama-bench` output, the health probes, `/props` and the streamed chat completion, `/proc` discovery, and the package's own contract (`tests/package.test.ts`: no app import, `.ts` import paths, one export per module, tree-shaking) |
| `app/src/` | Pure UI logic: the Topology page's flows, layout, pacing and smoothing (`app/src/features/topology/`), the benchmark form mapping (`app/src/lib/bench.ts`)                                 |
| `site/`    | The link checker helpers, the sidebar and content routes, the landing page's telemetry simulation                                                                                         |

`scripts/` holds the tests of the repository itself: the published package's fields (`package.test.ts`) and the
versions of every `package.json` (`release.test.ts`).

There are no component or browser tests (no DOM library is installed). When a page has logic worth testing, it lives in
a plain module next to the page, as `flows.ts` does for the Topology page.

## Write a test

```ts title="app/server/lib/db/settings.test.ts"
test('settings: defaults, then a persisted patch', () => {
  using dir = tempDir('lw-');
  using db = openDb(join(dir.path, 'sub', 't.sqlite')); // missing subdirectory
  const repo = new SettingsRepo(db);
  expect(repo.get()).toEqual(DEFAULT_SETTINGS);
  expect(repo.patch({ port: 9000 }).port).toBe(9000);
  expect(new SettingsRepo(db).get().port).toBe(9000);
  expect(() => repo.patch({ pollIntervalMs: 10 })).toThrow();
});
```

- **Names** are English sentences that state the behavior: `a deleted run's id is never handed out again`,
  `isOomError recognizes the current and the legacy out-of-memory errors`. A prefix (`setup: …`) or a `describe` block
  groups the tests of one function.
- **Temporary directories** come from `tempDir(prefix)` (`app/server/lib/testing/tempDir.ts`). With `using`, the directory is
  deleted when the test ends, even when it fails. At module level, where `using` would release it before the tests run,
  call `afterAll(() => dir[Symbol.dispose]())`.
- **Files** are written with `writeFileDeep(path, data)` (`app/server/lib/testing/write.ts`), which creates the parent
  directories (fake `/proc` and `/sys` trees), and read with `node:fs/promises`; `writeFileAtomic(path, text)` (same
  file) replaces a file in one step, as an editor's safe write does. Pauses are `setTimeout` from
  `node:timers/promises`.
- **HTTP servers**: `listen(server)` (`app/server/lib/testing/listen.ts`) binds a `node:http` server to a free loopback port
  and resolves its base URL (a fake `llama-server` endpoint, for example).
- **Databases**: `openDb(':memory:')` gives a fresh database with every migration applied; `openDb()` on a path in a
  temporary directory tests a real file.
- **Dependencies are injected.** Server classes and builders take their collaborators as arguments, so a test passes
  fakes instead of mocking modules (`vi.fn()` only records callbacks, in `app/server/lib/hf/downloader.test.ts`):

  | Code                              | Injected in tests                                                  |
  | --------------------------------- | ------------------------------------------------------------------ |
  | `ChatRuns` (`app/server/lib/chat/runs.ts`) | `fetch`: a fake `llama-server` stream the test feeds chunk by chunk |
  | `HfClient`, `DownloadQueue` (`app/server/lib/hf/`) | `fetch`: a fake Hub and CDN with `Range` support and scripted failures |
  | `NvidiaMonitor` (`app/server/lib/collectors/nvidia.ts`) | `spawn`: canned `nvidia-smi` output                        |
  | `BenchGate` (`app/server/lib/bench/gate.ts`) | A `ServerControl` that records stops and restarts               |
  | `buildSetupReport`, `buildLaunchpad` (`app/server/lib/setup.ts`) | A `SetupDeps` object                                |

- **`/proc` and `/sys` readers** take the root to read from, so a test writes a small tree in a temporary directory:
  `readProcAmdVram(pid, root)` reads `<root>/<pid>/fdinfo/*`.
- **Route files** are tested without a server: `routeApp([[method, path, handler], …])`
  (`app/server/lib/testing/routes.ts`) mounts the default exports of route files on an h3 app of their own, with the
  app's error replies (`errorResponse()`), and `app.request(path, init)` answers a `Response`. The handlers read
  their objects with `deps()`: `provideDeps(deps)` (`app/server/lib/context.ts`, with `using`) makes it answer the
  test's doubles until the block ends, without building a runtime. `app/server/lib/routes.test.ts` does this for
  chat, settings and `/props`, and `app/server/lib/bench/runner.test.ts` for `POST /api/sweeps/:id/validate`.
- **Environment variables** a test sets (the `FAKE_*` switches below) are deleted in an `afterEach`.
- **Promises** are awaited: `await expect(p).rejects.toThrow()`. Vitest fails a test that leaves a `.resolves` or
  `.rejects` assertion unawaited.

### Build, shutdown and development loop

The tests that need the whole app start the production build in a process of its own, as a user does:
`launch({ dataDir, port?, env? })` (`app/server/lib/testing/launch.ts`) runs `app/.output/llama-webui.mjs` with
`--host 127.0.0.1`, a free port and the data directory, without the `CI`, `TEST` and `NODE_ENV` variables that a user
never sets (srvx installs no signal handler under the first two), waits for `/api/health`, and stops it with
`SIGTERM` when disposed (`await using`). `app/server/lib/testing/seed.ts` prepares what they drive:
`seedDataDir(dataDir)` writes settings that run the fake `llama-server` and one profile on a tiny GGUF,
`startLlama(base, profileId)` starts it and resolves its PID, `bootId(base)` reads the `bootId` of the WebSocket's
`hello`, and `isAlive(pid)` tells whether a process still runs. These files run under Vitest like the others:

- `app/server/lifecycle.test.ts`: a `SIGTERM` with the UI's WebSocket open and a chat reply streaming stops the
  process in under 2 seconds, `llama-server` included; a second instance on a taken port exits with code 1 and names
  the port, and leaves alone the streaming reply of a first instance on the same data directory; a missing asset is a
  `404`, not a `500`; pages are revalidated (`cache-control: no-cache`), hashed assets are immutable, and the API sets no cache
  header.
- `app/server/build.test.ts` reads the build of the `globalSetup`: the client is split per page, three.js is only in
  the Topology chunks, no client chunk imports a `node:` module, a deep URL finds every file its page references,
  the server imports nothing but Node built-ins (the build is self-contained), `THIRD-PARTY-LICENSES.md` ships next
  to it, and `nvml-worker.mjs` sits next to the module that names it (where `workerUrl()` looks) and starts from the
  bundle.
- `app/server/api.gen.test.ts`: the route map of `app/server/api.gen.ts` is Nitro's own scan (70 routes), the
  `Body` and `Query` types of each file are read, and in development a route file added or deleted updates the map.
- `app/server/lib/collectors/nvml/monitor.test.ts` starts the real NVML sampler: with a missing library it resolves `null` at
  once (the `nvidia-smi` fallback); on a machine with an NVIDIA driver (`/proc/driver/nvidia/version`; skipped in
  CI) it reads every card; and a sampler stuck in a native call (libc's `sleep()` through `node:ffi`) does not hold
  the exit of the process that stops it.
- `app/server/dev.test.ts` starts `vite dev` on a free port, in a copy of `app/` under the repository's `.cache/`
  (ignored by git; its own Nitro and Vite caches, `node_modules` linked entry by entry), so the checkout's files and
  a `pnpm dev` you run meanwhile are left alone: saving a route file keeps `llama-server` and the `bootId`, saving
  business code rebuilds the runtime and stops the old `llama-server`, one `SIGINT` (and a quick double one) stops
  `vite dev` and `llama-server`, with a page open (`/ws`) too and without the worker force-closed after 5 seconds, `.env.local` is read in development, and `.env` wins over it.

### Tests of llamacpp-js

[llamacpp-js](/developers/llamacpp-js/) targets Node 24 or later, so its tests are written with Node's
own runner, `node:test` and `node:assert/strict`, with no dependency: `pnpm --filter llamacpp-js test`
(`node --test 'tests/*.test.ts'`) runs them on the TypeScript sources as they are. CI runs them on Node 26 in the main
job and on Node 24, the lowest supported version, in a job without any install.

```ts title="packages/llamacpp-js/tests/metrics.test.ts"
import assert from 'node:assert/strict';
import { describe, test } from 'node:test';
import { parseSlots } from '../src/metrics.ts';
import { fixture } from './helpers.ts';

describe('parseSlots', () => {
  test('idle slot', async () => {
    const s = parseSlots(JSON.parse(await fixture('slots-idle.json')))[0]!;
    assert.equal(s.processing, false);
    assert.equal(s.nDecoded, 0);
    assert.equal(s.idTask, null);
  });
});
```

- They use web and `node:*` APIs only: a local server comes from `serve(handler)` (`node:http`), a file from
  `fixture()`, the directory from `import.meta.dirname`. The package's project (`tsconfig.json`, sources and tests)
  has the Node types only, so any other runtime's API does not type check.
- `tests/helpers.ts` adds the two assertions `node:assert` lacks: `closeTo(actual, expected, digits)` and
  `matchObject(actual, expected)` (the properties of `expected`, deeply equal).
- The bundling checks of `tests/package.test.ts` bundle an import of the package with Rolldown (a devDependency of
  `llamacpp-js`) for the browser: tree-shaking keeps only what one function needs, and the browser-safe modules pull no
  Node built-in. Without an install, as in the Node 24 job, they pass `{ skip }` and Node reports them as skipped.

## Fake binaries

`testdata/fake/` holds two stand-ins for the llama.cpp binaries. Each is a shell script that runs its TypeScript
counterpart with `node` from the `PATH` (a plain Node script: erasable TypeScript, `node:*` APIs only), so a test can
use it wherever the app expects a binary path.

### Fake llama-server

`fake-llama-server` takes `llama-server`'s flags, prints log lines on stderr, and serves on `127.0.0.1` at the `--port`
it was given:

- `/health` answers `503` while it "loads" the model, then `{"status":"ok"}`.
- `/completion` and `/v1/chat/completions` answer with timings. A streamed chat reply sends reasoning (unless thinking
  is off), then Markdown, one chunk at a time; a prompt larger than the simulated context gets `llama-server`'s
  context-size error.
- `/slots`, `/metrics` and `/props` serve `slots-busy.json`, `metrics-after.txt` and `props.json` from `testdata/fake/`.
- `--version` prints a fake build line and exits; `--help` prints a one-flag catalogue and exits.

The bench runner and the parser tests use it (`app/server/lib/bench/runner.test.ts`), as the binary setting of a fake
configuration.

Environment variables shape its behavior:

| Variable                                  | Effect                                                                |
| ----------------------------------------- | --------------------------------------------------------------------- |
| `FAKE_LOAD_MS`                            | Loading time before `/health` is ready (default 300 ms)               |
| `FAKE_SLOW_ARG`, `FAKE_SLOW_MS`           | A longer load (default 5000 ms) when that argument is present          |
| `FAKE_FAIL_ARG`                           | Logs a CUDA out-of-memory and exits with 1 when that argument is present |
| `FAKE_EXIT_LINES`                         | Logs these `\|`-separated lines, then exits with 1                     |
| `FAKE_CRASH_ON_PREDICT`                   | Dies mid-request on a `/completion` with that `n_predict`             |
| `FAKE_PP`, `FAKE_TG`, `FAKE_DRAFT`        | Reported prompt and generation speeds, draft statistics when `1`      |
| `FAKE_N_CTX`                              | Simulated context size (default 40192 tokens)                         |
| `FAKE_CHAT_DELAY_MS`, `FAKE_CHAT_LINES`   | Delay between streamed chunks (default 60 ms), extra reply lines      |
| `FAKE_IGNORE_TERM`                        | Ignores `SIGTERM` when `1`                                            |
| `FAKE_EXIT_AFTER_MS`, `FAKE_EXIT_CODE`    | Exits on its own after a delay, with that code (default 1)            |

### Fake llama-bench

`fake-llama-bench` sits next to the fake server, as `llama-bench` sits next to `llama-server`: `benchBinary()`
(`llamacpp-js/node`) turns `testdata/fake/fake-llama-server` into `testdata/fake/fake-llama-bench`. It prints
`llama-bench`'s progress lines on stderr and the JSON of `testdata/llama-bench/ok.json` on stdout, and answers
`--list-devices` with `list-devices.txt`.

| Variable                          | Effect                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------- |
| `FAKE_BENCH_STEP_MS`              | Pause between progress steps (default 100 ms)                                     |
| `FAKE_BENCH_OOM`                  | `1`: fails like an out-of-memory load (`oom-stderr.txt`, exit code 1)             |
| `FAKE_BENCH_OOM_ARG`              | Same failure when the arguments contain that fragment                             |
| `FAKE_PP`, `FAKE_TG`              | Overrides the prompt and generation speeds                                         |
| `FAKE_TG_BY_ARG`                  | `-ncmoe 8=30;-dev CUDA0,CUDA1=55`: the generation speed of the first fragment found (the fake receives `-dev` with commas) |

### Use them in a test

The bench runner tests point the `binary` setting at the fake server. Variables set in `process.env` reach the
spawned fakes; a run can also get them from the profile's environment
(`profile: () => ({ env: { FAKE_BENCH_OOM: '1' } })`).

```ts title="app/server/lib/bench/runner.test.ts"
const FAKE = resolve(import.meta.dirname, '../../testdata/fake/fake-llama-server');
// …
const executor = new RunExecutor({
  settings: () => ({ ...DEFAULT_SETTINGS, binary: FAKE, port }),
  logs,
  gpus: () => [],
  disk: () => null,
  ...deps,
});
```

The tests that start server runs (`kind: 'server'`) give each one its own port (`18089` to `18091`).

## Fixtures

Two modules build inputs in code, for tests that need a model or a machine:

- **`app/server/lib/tuning/fixtures.ts`**
  - `fakeModel(o)` returns a complete `ModelInfo`, tensors included, with the sizes you pass: 48 layers by default, an
    embedding and an output of 300 MiB, 100 MiB of attention per layer, and expert tensors (`ffn_gate_exps`,
    `ffn_up_exps`, `ffn_down_exps`, 300 MiB per layer) when `experts` is above 0.
  - `hw3(o)` returns a `TuningHardware`: two 16 GiB CUDA cards, an RX 9070 XT on Vulkan, an iGPU, the Vulkan duplicates of
    the NVIDIA cards and BLAS, with 61 GiB of RAM (55 GiB available unless `ramAvailableGiB` says otherwise).
  - The estimator, placement, system checks and setup tests use them.
- **`app/server/lib/models/gguf.fixture.ts`**: `writeGguf(path, kv, tensors)` writes a real GGUF v3 file: header, typed key/value
  pairs (`u32`, `u64`, `f32`, `string`, `u32[]`), tensor infos aligned on 32 bytes, then zero bytes for each tensor. The
  GGUF reader and model scan tests parse these files instead of shipping models.

## HTTP contract suite

`app/server/lib/contract/` records what the API answers, over real HTTP, so that a change of server framework or runtime has
to give the same replies. `contract.test.ts` seeds a temporary data directory (the fake `llama-server` as the `binary`
setting, two profiles, conversations, runs and sweeps), then starts the production build on it with `launch()`. Two
test settings, read by `boot()` (`app/server/lib/boot.ts`), replace what depends on the machine:
`LLAMA_WEBUI_TEST_MONITOR=stub` gives a monitor without collectors, and `LLAMA_WEBUI_TEST_OFFLINE=1` a `fetch` that
fails as offline for Hugging Face. It sends every case, then compares each reply with
`app/server/lib/contract/golden.json`.

<FileTree>
- `app/server/lib/contract/`
  - `wire.ts`: raw HTTP/1.1 client on `node:net` (`request`, `readSse`): a request without body carries the headers
    a browser sends, not the ones a `fetch` implementation adds
  - `cases.ts`: the route table (`ROUTES`), the generated cases, `normalize()`, `runContract()` and `runStreams()`
  - `contract.test.ts`: seeds the data, launches the build, runs the cases, compares with the golden
  - `golden.json`: the recorded replies, one entry per case, in run order
</FileTree>

The cases, generated from `ROUTES`:

- every method a path lacks, which must be a 405 with an `Allow` header, and `HEAD` on every path;
- the reads (`GET`) of every route;
- an `:id` that is not a number (`x`) and one no row has (`999999`);
- for each route that reads a JSON body:
  - malformed JSON;
  - a JSON value that is not an object;
  - no body, with and without `Content-Type: application/json`;
  - a `text/plain` body (415);
  - one body that breaks the route's schema;
- a foreign `Origin`, a foreign `Host`, `/api/nope`, a deep SPA URL, `/ws` without an upgrade (426);
- the calls the web sends without a body (`DELETE`, `POST` with `Content-Length: 0`) or with `{}`;
- a WebSocket (`hello`, then `ping` → `pong`);
- a chat reply streamed from the fake server (headers, the first event, and the name of the last one).

The calls that change rows run last, on rows seeded for them.

A reply is recorded with:
- its status;
- its `content-type`, `allow`, `cache-control` and `content-disposition` headers;
- its body (JSON parsed, otherwise text).

Values that change from one run to the next become placeholders: the temporary directory (`<tmp>`), the home
directory (`<home>`), the repository (`<repo>`), ports (`<port>`), timestamps (`<time>`), UUIDs (`<uuid>`), the content
hash of a built asset (`/assets/index-<hash>.js`, which changes with any change to the client), and `bootId`,
`version`, `uptimeMs`, `pid`. A route whose answer depends on the machine (`/api/system/info`, `/api/topology`,
`/api/tuning/hardware`, `/api/tuning/checks`, `/api/setup`, `/api/launchpad`, `/api/bench/devices`, `/api/flags`)
records the names of its top-level fields, not their values.

A test also checks that `ROUTES` lists every path of the `ROUTES` that `app/server/api.gen.ts` generates from Nitro's
scan. A new route file fails it until its path is added to the table, with a `body` entry (methods and one
schema-breaking body) when it reads JSON.

When a change of behaviour is intended, regenerate the golden and read its diff before committing it:

```bash title="Terminal"
UPDATE_GOLDEN=1 pnpm exec vitest run app/server/lib/contract/contract.test.ts
git diff app/server/lib/contract/golden.json
```

A failure lists the names of the cases whose reply changed, with the diff of those replies only. Three replies differ
from those of the Hono server the suite was first recorded on, on purpose: `Host: a b` gets the guard's JSON `400`, the
pages are the real `index.html` (`text/html; charset=utf-8`), and the chat stream carries h3's own `cache-control`. `golden.json` is written by the test
and left out of Biome's formatter, so a regeneration changes only the entries that moved.

<Callout type="note">
The golden pins no Hugging Face success (the suite has no network) and no value of the machine-dependent routes: check
those screens in the running app after a change of framework or runtime.
</Callout>

## Migrations on old data

A migration that rewrites existing data gets a test on a database at the schema it starts from, built in the test: no
local file, so it runs in CI and on a fresh clone. `runMigrations(db, n)` stops at version `n`; the test fills that
old schema, then `openDb()` applies the rest, as on a user's machine:

```ts title="app/server/lib/db/sweeps.test.ts"
test('the migration keeps every run of a J5 database: ids, values and the next id', () => {
  using dir = tempDir('lw-mig-');
  const file = join(dir.path, 'db.sqlite');
  {
```

## Type checking

```bash title="Terminal"
pnpm check
```

The `check` script is `pnpm -r --parallel --include-workspace-root typecheck`: it runs the `typecheck` script of
every workspace package at the same time. That script is `tsc` in `packages/*`, `tsc && tsc -p server` in `app/`
(its two projects), `tsc -p scripts` in the root package and `react-router typegen && tsc` in `site/`. One package alone:
`pnpm --filter <name> typecheck`.

There is no root `tsconfig.json` and no TypeScript project reference: each code base has its own `tsconfig.json`,
which extends `tsconfig.base.json` (the shared options, `noEmit` among them) and adds its types and its files.

| Project                               | Covers                                     | Types                                       |
| ------------------------------------- | ------------------------------------------ | ------------------------------------------- |
| `packages/llamacpp-js/tsconfig.json`  | The library's sources and its tests (`tests/`), as a Node user compiles them: `erasableSyntaxOnly`, `exactOptionalPropertyTypes`, NodeNext resolution | Node only (no DOM): a browser-only API fails here |
| `packages/webui-shared/tsconfig.json` | `@llama-webui/shared` and its tests        | Node, no DOM: a browser-only API fails here |
| `app/server/tsconfig.json`            | `app/server/` (route files, middlewares, plugins, `lib/`), tests included | Node              |
| `scripts/tsconfig.json`               | `scripts/`                                 | Node                                        |
| `app/tsconfig.json`                   | `app/src/` (tests included), `app/build/` and `app/vite.config.ts` | DOM and Node        |
| `site/tsconfig.json`                  | `site/src/`, `site/content/nav.ts`, `site/scripts/` and the config files, after `react-router typegen` writes the route types | DOM and Node |

A project that imports another package checks the sources it reaches with its own options: the server those of
`llamacpp-js` and `webui-shared`, and `app/tsconfig.json` those of the server that the client reaches through the
types of `app/server/api.gen.ts` (`import type` only: the client never imports server code at runtime), and those
`app/vite.config.ts` imports. That is why the client project has Node's types next to the DOM's, so a Node API type
checks in the client's code. The production build test
(`app/server/build.test.ts`) checks that no chunk of the client bundle imports a `node:` module. The projects do not
enable the same options:

| Option                                                          | `tsconfig.base.json` (packages, `app/server/`, `scripts/`) | `app/` | `site/` |
| --------------------------------------------------------------- | --------------------------- | ------ | ------- |
| `strict`, `verbatimModuleSyntax`, `noFallthroughCasesInSwitch`  | yes                         | yes    | yes     |
| `noUncheckedIndexedAccess`                                      | yes                         | yes    | yes     |
| `noImplicitOverride`                                            | yes                         | yes    | no      |
| `noUnusedLocals`, `noUnusedParameters`                          | no                          | yes    | yes     |

With `verbatimModuleSyntax`, type-only imports must use `import type`.

The `.mdx` pages are not type checked; the site build compiles them.

## Test the website

The site's unit tests run with the others under Vitest (project `site`):

- `site/src/docs/nav.test.ts` fails when a page under `site/content/` is missing from `site/content/nav.ts`, when an
  entry has no file or appears twice, or when a page sits in the wrong section.
- `site/src/lib/content.test.ts` checks how a file maps to its route.
- `site/scripts/links.test.ts` tests the link checker's helpers.
- `site/scripts/serve.test.ts` drives the preview server (`serveDist()`) on a small `dist/`: trailing-slash redirects,
  content types and cache, gzip for text only, `404.html` and `Not found`, `HEAD`.
- `site/scripts/cli.test.ts` starts `serve.ts` with `-- --port 0`: a script reads its flags after the `--` that pnpm
  passes through.
- `site/src/landing/telemetry.test.ts` checks that the landing page's simulated dashboard is deterministic, so the
  prerendered HTML and the hydrated page start from the same frame.

After a build, the link checker reads every page of `site/dist/`:

```bash title="Terminal"
pnpm site:build
pnpm --filter llama-webui-site check-links
```

It extracts each `href`, `src` and `srcset` URL and fails on a page or file that does not exist, a missing `#anchor` (on
the same page or the target), a page link without its trailing slash, a relative URL or a URL outside `/llama-webui/`.
External links are not fetched. CI runs both commands; [Docs, commits and PRs](/developers/contributing/workflow/) covers
writing pages.
