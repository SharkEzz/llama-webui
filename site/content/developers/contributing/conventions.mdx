These rules apply to `app/`, `packages/` and `site/`. They come from `CLAUDE.md` at the root of the repository
(written in French); `oxfmt.config.ts`, the `oxlint.config.ts` files, the `tsconfig*.json` files, the Effect
diagnostics and CI enforce the mechanical ones. The server's own rules, each with its example (where each part of a
domain goes, requests and replies, programs, long processes, SQL, caches), are in
`docs/superpowers/poc-effect/conventions.md`.

## Language

Everything is in English (en-US):

- the UI and the website;
- server messages: HTTP errors, the messages of the schemas' checks, logs and `--help`;
- code comments and test names;
- commit messages and pull requests.

Comments explain why rather than what: exported functions and non-obvious choices carry a `/** … */` comment. The
server logs through `Effect.log` and its levels (`Effect.logWarning`…); the lines it adds to `llama-server`'s log
ring start with `[llama-webui]`.

### Numbers, dates and units

The web app formats every number, date and unit through `app/src/lib/format.ts`, with the `LOCALE = 'en-US'` of
`packages/webui-shared/src/format.ts`. Do not hard-code a locale in a component: use a helper, or add one to that file. A server
message that shows a number (an error, a log line) uses `fmtInt()` from `packages/webui-shared/src/format.ts` the same way,
and `fmtBytes()` of the same file for a size (`12.3 GiB`, `512 MiB`; `MiB` and `GiB` are there too).

| Helper                                            | Output                                                        |
| ------------------------------------------------- | ------------------------------------------------------------- |
| `num(max, min = max)`                             | Cached `Intl.NumberFormat` with that many fraction digits     |
| `fmt(v, max = 1)`                                 | Up to `max` decimals: `fmt(3.14159, 1)` gives “3.1”           |
| `plural(n, one, other)`                           | `plural(1, 'line')` gives “line”, `plural(0, 'line')` “lines” |
| `formatBytes(n, digits = 1)`                      | Base 1024 with `B`, `KiB`, `MiB`, `GiB`, `TiB`: “12.3 GiB”    |
| `formatBps`, `formatRate`                         | “1.2 GiB/s”, “42.7 tok/s”                                     |
| `formatPct`, `formatInt`, `formatParams`          | “37%” (one decimal below 10), “32,768”, “27.3 B”              |
| `formatTemp`, `formatStddev`                      | “54 °C”, “ ± 0.4”                                             |
| `formatDuration`, `formatTime`, `formatShortDate` | “12 min 05 s”, “14:03:27”, “Nov 7, 14:03”                     |

Missing values (`null`, `undefined`, not finite) render as “—” in the helpers that accept them. The website has its own
`site/src/lib/format.ts` with the same `LOCALE`.

### Never compare a server message

The web app never branches on the text of a server message. Each error an endpoint answers is a
`Schema.TaggedError` of the API definition, with its status, and its body is `{ "_tag": "…", "message": "…" }`:

```ts title="packages/webui-shared/src/api/ProfilesApi.ts"
export class ProfileNameTaken extends Schema.TaggedError<
  ProfileNameTaken,
  { readonly ProfileNameTaken: unique symbol }
>()('ProfileNameTaken', { message: Schema.String }, { httpApiStatus: 409 }) {}
```

The server builds it with its message (`ProfileNameTaken.make({ message: … })`, never `new`), and the typed client
of the web (`app/src/lib/api.ts`) rejects with it; the UI reads its tag with `errorTag()`:

```ts title="app/src/lib/bench.ts"
        if (errorTag(e) === 'ServerRunning') return 'confirm';
```

Text stored in the database that the UI has to recognize goes through a helper in `packages/webui-shared/`, which also knows the
wording of earlier versions (the app used to be in French, and old rows keep their text):

- `isOomError(error)` (`packages/webui-shared/src/bench.ts`): a run's error starts with `OOM_ERROR = 'Out of memory'` or the legacy
  prefix.
- `isDefaultTitle(title)` (`packages/webui-shared/src/chat.ts`): the conversation still has `DEFAULT_TITLE = 'New conversation'` or the
  legacy default title.

## Formatting and lint

[oxfmt](https://oxc.rs) formats and [oxlint](https://oxc.rs) lints. Both are pinned devDependencies (`oxfmt` 0.79.0,
`oxlint` 1.94.0, with `oxlint-tsgolint` 7.0.2008 for the rules that read types, and the JS plugin
`oxlint-plugin-react-doctor` 0.9.23 for ten React rules), configured in TypeScript files.

### Format

oxfmt formats, sorts imports and sorts the keys of every `package.json`. Its config, `oxfmt.config.ts`, holds the
style:

| Setting        | Value                                                                      |
| -------------- | -------------------------------------------------------------------------- |
| Indentation    | 2 spaces                                                                   |
| Line width     | 120 columns                                                                |
| Quotes         | Single quotes in TypeScript, double quotes in JSX attributes, CSS and YAML |
| Semicolons     | Always                                                                     |
| Imports        | Sorted by oxfmt, no blank line between groups                              |
| `package.json` | Keys sorted by oxfmt                                                       |

oxfmt formats TypeScript, JavaScript, JSON, CSS, YAML, HTML, every `.md` file (the root `docs/` included) and the
site's `.mdx` pages. In Markdown and MDX, the code of fenced blocks stays as written (`embeddedLanguageFormatting`
off). It skips what `.gitignore` lists, `repos/`, `testdata`, `pnpm-lock.yaml`, the generated
`app/server/contract/golden.json` and the generated shadcn components.

### Lint

oxlint lints the TypeScript and TSX of every package; CSS, Markdown and MDX are formatted, not linted. It runs the
rules of its `correctness`, `suspicious` and `perf` categories (minus the few that are wrong for this code, off by
name) and a selection of other rules picked by name, all in `error`. The type-aware ones
(`options.typeAware`) read the types through the `tsconfig.json` of each file. Every rule that is off or has options
carries a one-line comment with its reason in the config: that is where to read why.

Five families of the rules picked by name shape how the code is written:

| Family                            | Rules                                                                                                                                                                   | The code                                                                                                                                                                                     |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unsafe `any`                      | `typescript/no-unsafe-assignment`, `no-unsafe-member-access`, `no-unsafe-argument`, `no-unsafe-return`, `no-unsafe-call`, `no-unsafe-type-assertion`                    | What `JSON.parse`, a `catch` or an untyped import gives is decoded or typed before use; a cast is a decode, a guard, a `satisfies` or a narrower declaration (tests may cast their fixtures) |
| Discarded promises                | `typescript/no-floating-promises`, `no-misused-promises`, `no-confusing-void-expression`, `require-await`                                                               | A promise is awaited, returned, handled, or discarded on purpose with `void`; a function that returns one is not passed where a `void` callback is expected (an event handler)               |
| Interface functions as properties | `typescript/method-signature-style`                                                                                                                                     | `fn: (x: T) => U`, not `fn(x: T): U`: the parameters are checked strictly, and the function can be read off its object                                                                       |
| React state and effects           | `react/hooks`, `react/exhaustive-deps`, `react/exhaustive-effect-dependencies`, `react/set-state-in-effect`, `react/immutability`, `react/refs`, the react-doctor rules | See [React](#react): a value derived or reset during render rather than copied in an effect, a ref for what is never rendered, Zustand read through selectors                                |
| Test assertions                   | `vitest/no-conditional-expect`, `require-mock-type-parameters`, `require-to-throw-message`, `prefer-to-have-length`, `prefer-called-times`                              | An `expect` never sits under an `if` (a loop over the cases instead); `vi.fn<T>()` is typed; `toThrow` names the error it expects; `toHaveLength(n)`, `toHaveBeenCalledTimes(1)`             |

The root and four projects (`app/server`, `app/src`, `site`, `packages/llamacpp-js`) each have an `oxlint.config.ts`,
and a file takes the nearest one above it. That config replaces the root one instead of adding to it, so a project
config extends `base` and the fragments it needs:

| File                                    | Lints, or holds                                                                                                                                                                                                                                                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `oxlint.config.ts`                      | Its named export `base`: the plugins (`eslint`, `typescript`, `unicorn`, `oxc`, `import`, `promise`), the `correctness`, `suspicious` and `perf` categories, the rules by name. Its default export, `base` and the Vitest rules, lints `scripts/`, `app/build/`, `app/bin/`, `packages/webui-shared/` and the root files |
| `app/server/oxlint.config.ts`           | The server: `base` and the Vitest rules, with `require-yield` off (a generator of `Effect.gen` or `Effect.fn` does not always yield) and `no-console` on (a log goes through `Effect.log*`)                                                                                                                              |
| `app/src/oxlint.config.ts`              | The web app: `base`, the React rules and the Vitest rules, with `no-console` on                                                                                                                                                                                                                                          |
| `site/oxlint.config.ts`                 | The website: `base`, the React rules and the Vitest rules                                                                                                                                                                                                                                                                |
| `packages/llamacpp-js/oxlint.config.ts` | `llamacpp-js`: `base` alone, since its tests run on `node:test`                                                                                                                                                                                                                                                          |
| `oxlint.react.ts`                       | The React fragment: the `react` and `jsx-a11y` plugins, and the `react-doctor` JS plugin with nine of its rules (the site config adds the tenth). Accessibility is limited to the rules that pass today; the others of `jsx-a11y` are off by name                                                                        |
| `oxlint.tests.ts`                       | The Vitest fragment: an override for `**/*.test.ts` and `**/*.test.tsx` with the `vitest` plugin                                                                                                                                                                                                                         |
| `scripts/oxlint/directives.ts`          | The local plugin of `directives/require-reason` (see [Never disable a rule](#never-disable-a-rule)), tested by `scripts/oxlint/directives.test.ts`                                                                                                                                                                       |

A project config is short:

```ts title="app/src/oxlint.config.ts"
export default defineConfig({
  extends: [base, react, tests],
  rules: {
    // The page logs nothing to the console but what it cannot show (a suppression says which)
    'no-console': 'error',
  },
  // shadcn components keep their default code
  ignorePatterns: ['components/ui/**'],
});
```

`ignorePatterns` do not travel through `extends`, and they are relative to the config that declares them: each
project config repeats those under its directory. Besides what `.gitignore` lists, oxlint skips `repos/`, the root
`docs/`, `testdata`, the generated `app/server/contract/golden.json`, the generated shadcn components and the build
outputs. `.eslintignore` holds `/repos/`: oxlint reads it before it looks for nested configs, and only it keeps
oxlint from loading `repos/effect/.oxlintrc.json`, whose plugin is not installed here. Given a path under `repos/`
explicitly, oxlint still loads that config and fails with a configuration error; `pnpm lint`, which walks the
repository, does not. The VS Code extension does not read `.eslintignore`: `pnpm install` leaves `repos/effect/.oxlintrc.json` out of
the submodule's checkout (`scripts/vendored.ts`).

The Effect diagnostics are not oxlint's: `tsc` reports them in `pnpm check`
([Effect diagnostics](/developers/contributing/testing/#effect-diagnostics)).

| Command         | Runs                                                                         | Effect                                                                      |
| --------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `pnpm lint`     | `oxfmt --check && oxlint --deny-warnings --report-unused-disable-directives` | Format, imports and lint, read-only; a warning or an unused directive fails |
| `pnpm lint:fix` | `oxlint --fix && oxfmt`                                                      | Applies oxlint's safe fixes, then formats                                   |
| `pnpm format`   | `oxfmt`                                                                      | Formats only                                                                |

`oxlint --fix` applies safe fixes only: an unused import, for example, stays for you to remove.
`pnpm exec oxlint --fix-suggestions` removes it too; review its diff.

To see the rules that apply to a project, print its config:

```bash title="Terminal"
pnpm exec oxlint -c app/src/oxlint.config.ts --print-config
```

`--print-config` followed by a file path ignores the path and prints the root config.

In VS Code, install the oxc extension (`oxc.oxc-vscode`): it formats with oxfmt and shows oxlint's reports. Make it
the formatter and let it apply oxlint's fixes when you save:

```json title=".vscode/settings.json"
{
  "editor.defaultFormatter": "oxc.oxc-vscode",
  "editor.codeActionsOnSave": { "source.fixAll.oxc": "explicit" }
}
```

`.vscode/` is ignored by Git, so each contributor sets it.

Before a commit, a pull request or the end of a milestone, `pnpm lint` must report zero errors and zero warnings
(see [the quality gate](/developers/contributing/workflow/#the-quality-gate)).

### Never disable a rule

Do not turn a rule off or lower it to `warn` to get the lint through. When a rule reports a false positive, suppress
it on that one line with a directive that names the rule and gives the reason after `--`:

```tsx title="app/src/features/chat/CodeBlock.tsx"
// oxlint-disable-next-line react/no-danger -- HTML produced by shiki from the text (escaped), not the reply's HTML
dangerouslySetInnerHTML={{ __html: html }}
```

Among JSX children, the directive is a JSX comment:

```tsx title="site/src/root.tsx"
{/* oxlint-disable-next-line react/no-danger -- static theme bootstrap, must run before paint */}
<script dangerouslySetInnerHTML={{ __html: THEME_INIT_SCRIPT }} />
```

Name the rule as oxlint's report prints it, with a `/` for its parentheses and without the `eslint` prefix of a core
rule: `react-hooks(exhaustive-deps)` is written `react-hooks/exhaustive-deps`, `eslint(no-control-regex)` is written
`no-control-regex`.
`pnpm lint` fails on a directive without a reason (`directives/require-reason`, the local plugin), on one that names
no rule (`unicorn/no-abusive-eslint-disable`), and on one that suppresses nothing
(`--report-unused-disable-directives`).

## React

The web app and the site use React 19. The lint enforces the idioms below: the React Compiler-based rules of oxlint's
`react` plugin (`react/hooks`, `react/exhaustive-effect-dependencies`, `react/set-state-in-effect`,
`react/immutability`, `react/refs`, all on in `error`, next to `react/exhaustive-deps`) and ten rules of
[react-doctor](#react-doctor).

- **Trigger dependencies.** Two rules read an effect's dependency array:
  - `react/exhaustive-deps` (named `react-hooks/exhaustive-deps` in its reports and directives) reports, in any hook,
    a value the hook reads but does not list, and an effect with no array that sets state. In a `useMemo` or a
    `useCallback` it also reports a dependency that is listed but not read. In an effect it does not.
  - `react/exhaustive-effect-dependencies` reports an effect's array: "Found missing effect dependencies" for a value
    read but not listed, and "Found extra effect dependencies" for a value listed but not read. A deliberate trigger
    is the second case, and every suppression in the code is that case.

  When the dependency is a deliberate trigger (the effect must run again when it changes), keep it. Suppress the
  report with the rule it names, above the dependency array, with a reason that says what it triggers:

  ```tsx title="app/src/features/chat/Thread.tsx"
  useLayoutEffect(() => {
    stick.current = true;
    // oxlint-disable-next-line react/exhaustive-effect-dependencies -- current.id is a trigger: re-pin to the bottom on every conversation change
  }, [current?.id]);
  ```

  The directive above a dependency array silences every report of that rule for the hook, a missing dependency
  included, although the report prints the line where the value is used. Suppress a deliberate list, never a missing
  dependency that is a real bug. A hook with no array (an effect that runs after every render) takes the directive
  above the hook.

  A value an effect reads but must not re-run it for is not left out with a suppression: read it through
  `useEffectEvent` (next point). Do not suppress `react-hooks/exhaustive-deps` either: a `react-hooks/…` directive
  makes the React Compiler-based rules (`react/hooks`, `react/exhaustive-effect-dependencies`,
  `react/memo-dependencies`, `react/set-state-in-effect`, `react/immutability`…) skip the whole component, as the
  React Compiler itself does. The code has none.

- **Read the latest value without re-running the effect.** Use `useEffectEvent` rather than leaving the value out of
  the dependencies with a suppression:

  ```tsx title="app/src/features/tuning/TuningPage.tsx"
  // Only a change of ?sweep opens one; openId is read fresh without re-running the effect.
  const openWanted = useEffectEvent((id: number) => {
    if (id !== openId) void useTuning.getState().open(id);
  });
  useEffect(() => {
    if (wanted !== null) openWanted(wanted);
  }, [wanted]);
  ```

- **State is not copied or reset in an effect.** `react/set-state-in-effect` reports a `setState` in an effect's body,
  and react-doctor's `no-mirror-prop-effect` and `no-reset-all-state-on-prop-change` report an effect that copies a prop
  into state or clears state when a prop changes. Derive the value during render; reset a whole component with a `key`;
  adjust a piece of state in the render that sees the new input; move the update to the event that causes it. An
  effect keeps only what synchronizes with something outside React (a fetch, a subscription):

  ```tsx title="app/src/features/chat/SamplingPanel.tsx"
  // key: switching conversations remounts the form (fields and errors start from scratch).
  return <SamplingForm key={current.id} current={current} props={props} />;
  ```

  A field whose draft follows a saved value takes `useDraft(value)` (`app/src/lib/useDraft.ts`): the draft resets in
  the render that sees a new `value`, without a remount, so the field keeps its focus. `value` is a primitive or a
  stable reference (it is compared with `Object.is`).

- **What is never rendered is a ref.** `react/immutability` reports a value made during render and mutated afterwards,
  and react-doctor's `rerender-state-only-in-handlers` a state that only handlers read: hold either in a `useRef`. A ref
  passed down as a prop is named `…Ref` (the rule recognises it by its name: `pacerRef` in
  `features/topology/TopologyScene.tsx`).

- **Zustand is read through selectors.** Two rules apply:
  - `react/hooks` reports `useStore.getState()` called where the component renders: its body, or a `useMemo` callback.
    It does not report a call in a handler or an effect.
  - react-doctor's `zustand-no-whole-store-destructure` reports a component that takes the whole store.

  Select each field and each action (`useBench((s) => s.remove)`). `getState()` stays for handlers and effects.

[react-doctor](https://github.com/millionco/react-doctor)'s oxlint plugin, `oxlint-plugin-react-doctor`, is a pinned

## The platform and Effect

The app runs on Node.js (26.13 or later). The server is written with [Effect](https://effect.website) (`effect`
and its `@effect/*` packages, pinned to one exact version), and reaches the platform through Effect's services rather
than through `node:*` or other npm packages:

| Need                     | Used                                                                                        | Where                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| HTTP server and routes   | `HttpApi` of `effect/http-api` on `NodeHttpServer` (`node:http`)                            | `packages/webui-shared/src/api/`, `app/server/<domain>/http.ts`, `app/server/http/` |
| WebSocket                | The upgrade of `effect/http` (`Socket`)                                                     | `app/server/ws/WsHub.ts`                                                            |
| Requests to llama-server | `LlamaHttp` (`node:http` through `@effect/platform-node`, no time limit on headers or body) | `app/server/llama/LlamaHttp.ts`: chat stream, benchmark trials, `/props`            |
| Requests to Hugging Face | `HfHttp` (HTTP/1.1 on its own agents, the environment's proxy)                              | `app/server/hf/HfHttp.ts`: the Hub's API and the downloads                          |
| SQLite                   | `SqlClient` of `@effect/sql-sqlite-node` (`node:sqlite`)                                    | `app/server/db/Db.ts`, the `*Repo.ts` of each domain                                |
| Files and paths          | `FileSystem` and `Path`                                                                     | Collectors, hardware readers, models, downloads                                     |
| Programs                 | `ChildProcess` of `effect/process`, `followProgram()` for one that lasts                    | `app/server/process/`: supervisor, bench, `nvidia-smi`, the NVML sampler            |
| NVML                     | `node:ffi` in an Effect program run as a child process                                      | `app/server/collectors/nvml/`                                                       |
| Configuration            | `Config` (`AppConfig`), `.env` parsed by `parseEnv()` of `node:util`                        | `app/server/config/`                                                                |
| Pauses and repeats       | `Effect.sleep`, `Schedule`, `Effect.timeout`                                                | Everywhere: never a timer                                                           |
| Front end, server bundle | Vite (`vite dev`, `vite build`), Rolldown for the server and the NVML sampler               | `app/vite.config.ts`, `app/build/server.ts`                                         |
| Tests                    | Vitest, `@effect/vitest` for effects                                                        | Every `*.test.ts` but those of `packages/llamacpp-js/`                              |

The language service of Effect enforces it: `pnpm check` refuses a `node:*` import, `fetch`, a timer, `JSON` or
`process.env` in the server ([Effect diagnostics](/developers/contributing/testing/#effect-diagnostics)). Four `node:*`
imports remain, each with a directive and its reason: `node:http` (the server factory `NodeHttpServer` takes),
`node:crypto` (a model's hash as it streams), and `node:fs/promises` twice (`statfs` and `rmdir`, which `FileSystem`
lacks). There is no Express, Hono, `better-sqlite3`, `execa`, `dotenv` or zod, and no Jest. The build bundles every
package the server imports: it needs no `node_modules` at run time. Two exceptions: `site/` is built with Vite and
React Router (its scripts, run by Node, use `node:*`); `packages/llamacpp-js/` targets Node 24 or later, so its
sources use only web and `node:*` APIs (`fetch`, `node:child_process`, `node:fs/promises`), and its tests use
`node:test` with no dependency ([llamacpp-js](/developers/llamacpp-js/#rules-of-the-package)).

### Code idioms

- **A domain has a fixed layout.** Its schemas in `packages/webui-shared/src/<domain>.ts`, its endpoints and errors
  in `packages/webui-shared/src/api/<Domain>Api.ts`, its service in `app/server/<domain>/<Name>.ts`, its handlers in
  `app/server/<domain>/http.ts` ([How-to guides](/developers/contributing/how-to/#add-an-endpoint)).
- **A service is a `Context.Service` class** keyed by its path (`'@llama-webui/app/server/settings/SettingsRepo'`),
  with its layers as statics (`layer`, `layerWith(options)` for the durations a test shortens). What it starts runs
  in the scope of its layer, so the app undoes it when it stops: there is no `dispose()` to call.
- **Functions are `Effect.fn`.** A named `Effect.fn('Service.method')(function* (…) { … })` traces its span; a
  helper that needs no span is `Effect.fnUntraced`.
- **Errors are typed.** A failure the caller can act on is a `Schema.TaggedError` in the error channel; a broken
  invariant is a defect (`Effect.orDie`). An endpoint's handler returns the service's error when it is one of the
  endpoint's errors; a defect is logged and answers `500` without its message.
- **Inputs are schemas.** A handler never reads a body, a parameter or a query itself: the endpoint declares them, and
  `Api` decodes them strictly. A number is `Schema.Finite` or `Schema.Int`, never `Schema.Number`.
- **`packages/webui-shared/` stays portable.** The browser bundle imports it, so its modules import nothing but
  `effect`, the browser-safe modules of `llamacpp-js` and each other: no Node API. The server and the web import it
  as `@llama-webui/shared`; inside `app/` and `site/`, `@/` points to their own `src/`. The web imports nothing from
  `app/server/`.
- **Cleanup with `using` in the web app.** `defer(fn)` (`packages/webui-shared/src/dispose.ts`) returns a
  `Disposable`, so `using _saving = defer(() => setSaving(false));` replaces a `try`/`finally`. The server releases
  through scopes (`Effect.acquireRelease`, `Effect.ensuring`).

## Generated shadcn components

`app/src/components/ui/**` and `site/src/components/ui/**` hold stock [shadcn/ui](https://ui.shadcn.com) components
(configured by `components.json` in each package). oxfmt and oxlint ignore them entirely (no format, no lint, no
import sorting) so they stay comparable with shadcn updates; the type-aware rules still read their types where the
rest of the code imports them. Leave them untouched: put the project's changes in a wrapper outside `ui/`, as
`app/src/components/Select.tsx` does for the select list.

## Development restarts

`pnpm dev` (`vite dev` in `app/`) serves the UI with HMR, and runs the server from its sources in a child process,
`node --watch server/main.ts` (`app/build/devServer.ts`). What a save does depends on the file:

- A save of a file the server imports (`app/server/`, `packages/`) restarts the server process, as any stop does:
  the managed `llama-server` stops, a running chat reply is saved as `stopped`, a benchmark run and its sweep as
  `interrupted` (Resume button), a download resumes from its `.part`. The new process has a new `bootId`. Edit the
  server between benchmarks rather than during one.
- A save under `app/src/` is a hot module replacement of the UI: the server and `llama-server` are kept.
- Nothing survives a restart but the database and the files: state across requests lives in a service, built again
  with the process.
- What a part of the server starts, it starts in the scope of its layer, and what it must save before the stop, it
  registers as a shutdown step (`Shutdown.before`).
- Vite plugins are declared once, in `app/vite.config.ts`: development and `pnpm build` both use them.

[Architecture](/developers/architecture/#development-restarts) describes the restart and the shutdown order.
