A change to llama-webui ships with its documentation, passes the same checks as CI, and lands as one pull request. This
page covers that workflow; [Conventions](/developers/contributing/conventions/) covers the code itself.

## Keep the docs in sync

Any change to a feature, the UI, an API route, a WebSocket message, a CLI flag, a setting or the architecture updates
the matching pages of `site/content/` **in the same pull request**. The API reference is written by hand: it drifts as
soon as a change forgets it.

## Write a docs page

The website lives in `site/`, a package of the pnpm workspace (Vite, React Router with prerendering, Tailwind, MDX),
installed by the root `pnpm install` and run on Node.js: its scripts are `node scripts/<name>.ts`. Every `.mdx` file under `site/content/docs/` or
`site/content/developers/` becomes a prerendered page: `docs/getting-started/installation.mdx` is
`/docs/getting-started/installation/`, and an `index.mdx` is the page of its folder.

<Steps>
  <Step title="Create the file">

Start with a YAML front matter. Both fields are required, and the build fails without them:

```mdx title="site/content/docs/server.mdx"
---
title: Server
description: Start, stop, restart or switch llama-server, follow its state, read what it reports through /props, and see the exact command llama-webui launched.
---
```

The layout renders the title as the page heading and the description under it (it is also the meta description), so the
body has no `#` heading. Its `##` and `###` headings build the "On this page" table of contents.

  </Step>
  <Step title="Add it to the sidebar">

Add `{ path, title }` to its section and group in `site/content/nav.ts`, in reading order. The path is the route
without slashes (`docs/server`, `developers` for `developers/index.mdx`). `site/src/docs/nav.test.ts` fails when a page
is missing from the sidebar or an entry has no file.

  </Step>
  <Step title="Write the content">

The components of `site/src/docs/mdx-components.tsx` need no import:

| Component                   | Use                                                                                     |
| --------------------------- | --------------------------------------------------------------------------------------- |
| `Callout`                   | A note with `type` `note`, `tip`, `warning` or `important`, and an optional `title`     |
| `Steps`, `Step`             | A numbered procedure, one `title` per step                                              |
| `Tabs`, `Tab`               | Alternatives (one tab per backend, per shell…)                                          |
| `Screenshot`                | A capture by `name`, with `alt` and an optional `caption`; click to enlarge             |
| `Kbd`                       | A key: `<Kbd>Ctrl</Kbd>`                                                                |
| `Endpoint`                  | The method and path of an API route, under the heading that names it                    |
| `FileTree`                  | A folder tree written as a Markdown list, names in backticks, a trailing `/` for folders |
| `ArchitectureDiagram`       | The overview diagram of the [Architecture](/developers/architecture/) page              |

Leave a blank line after an opening tag and before the closing tag when the content is Markdown. A code fence always
takes a language, and a title after it for a snippet from a file or a terminal: `bash title="Terminal"`,
`ts title="server/http.ts"`.

Internal links use the route with its trailing slash and without the `/llama-webui` base, which React Router adds:
`[Server](/docs/server/)`, `[States](/docs/server/#server-states)`. An anchor is the heading text in lowercase, spaces
turned into hyphens, punctuation dropped.

  </Step>
  <Step title="Preview it">

After `pnpm install` at the root (it installs the site too), run the site from the root of the repository:

```bash title="Terminal"
pnpm site:dev
```

`site:dev` serves the site with hot reload on port 5173 on every interface: open `http://<host>:5173/llama-webui/`.

  </Step>
  <Step title="Build and check the links">

```bash title="Terminal"
pnpm site:build
pnpm --dir site check-links
pnpm site:preview
```

`site:build` prerenders every page, then `scripts/postbuild.ts` writes `site/dist/`: the pages, a `404.html`, the
`sitemap.xml` and the search index. `check-links` fails on any broken internal link or anchor
([Test the website](/developers/contributing/testing/#test-the-website)). `site:preview` serves `site/dist/` on port 4173
the way GitHub Pages does (under `/llama-webui/`, with the trailing-slash redirect and the 404 page); search only works
there, since its index only exists after a build.

  </Step>
</Steps>

Pages are in English and describe the code as it is: check names, defaults and limits in the source rather than in
another page.

## Screenshots

Captures live in `site/public/screenshots/` as `<name>-dark.webp` and `<name>-light.webp` (1600 px wide), plus an
800 px version of each; `<Screenshot name="server" … />` picks the right one. When a UI change alters a captured
screen, capture it again in the same pull request.

<Steps>
  <Step title="Start a demo instance">

Captures come from a demo instance, never from the one you use every day. It runs on port 7861 with a neutral home so
that no personal path or account appears:

```bash title="Terminal"
env -u HF_TOKEN HOME=/home/demo PATH="/home/demo/llama.cpp/build/bin:$PATH" pnpm start --host 0.0.0.0 --port 7861
```

`/home/demo/models` points to the models folder, and `/home/demo/llama.cpp/build/bin` holds hard links to the llama.cpp
binaries: the app resolves the binary's real path, so a symbolic link would show the original location.

  </Step>
  <Step title="Fill it">

```bash title="Terminal"
pnpm --dir site demo-seed setup bench sweep start chat
```

`site/scripts/demo-seed.ts` drives the real API: settings and profiles (`setup`), `llama-bench` and server runs
(`bench`), a validated sweep (`sweep`), a running server (`start`) and a conversation (`chat`). It loads real models on
the GPUs, so free them first.

  </Step>
  <Step title="Capture">

```bash title="Terminal"
pnpm --dir site screenshots            # every screen but the live and manual ones, or: screenshots server logs
pnpm --dir site demo-seed generate
pnpm --dir site screenshots --live     # Dashboard, System and Topology, during a generation
```

`site/scripts/screenshots.ts` opens each screen in headless Chromium (`/usr/bin/chromium`), switches the theme through
`PATCH /api/settings` to capture it in dark and light, and restores the theme at the end. `--base` points it at another address.
`site/scripts/shots.ts` lists the screens and how each is staged; a `manual` shot (the setup checklist) is only taken
when you name it.

  </Step>
  <Step title="Update what depends on them">

After a new Dashboard capture, run `pnpm --dir site og` to render the Open Graph image (`site/public/og.png`). The
landing page also redraws some app screens in React with their real values (the hero's live Dashboard, the argument
editor, the Tuning recommendation, in `site/src/landing/`): update them when those screens change.

  </Step>
</Steps>

## Commit messages

The history uses a type prefix and a capitalized subject that names the change, in English, without a final period:

```text
build: Prerender every static path except the 404 splat route
docs: User documentation for the website (site M6)
feat: Download GGUF models from Hugging Face on the Models page (#11)
feat: First-run setup checklist and profile launch pad on Home (#10)
```

- **Types** seen in the history: `feat` (a feature), `docs` (documentation only), `build` (build and tooling), `ref` (a
  rework of existing code or UI).
- **Body**: after a blank line, wrapped at about 72 columns, say what changed and why, in prose or as `-` bullets (one
  per area for a large change).
- **Pull request number**: pull requests are squash-merged, and the resulting commit's subject ends with `(#N)`.

## Pull requests

- **Branch** from `master`, named after the type and the topic: `feat/hf-downloads`, `docs/readme`, `chore/biome`.
- **Title**: the subject of the future squashed commit, `feat: Download GGUF models from Hugging Face on the Models page`.
- **Body**:
  - `## Summary`: what the change does and why, as the user sees it, then the notable choices.
  - `## Layout` for a large change: the new or changed files, by area.
  - `## Test plan`: a checklist of what you ran (the quality gate below, the site build) and checked by hand.
  - When a pull request builds on another one, say so ("Stacked on #20"). Problems found along the way but not fixed
    get their own list or an issue.
- **Docs**: the pages from [Keep the docs in sync](#keep-the-docs-in-sync) and the screenshots are part of the same pull
  request.

## The quality gate

Before a commit, a pull request or the end of a milestone, these must pass from the root of the repository:

```bash title="Terminal"
pnpm lint
pnpm check
pnpm test
```

- `pnpm lint`: Biome with zero errors and zero warnings (format, lint, sorted imports).
- `pnpm check`: the type checks of every project (`tsc -b`: `packages/*`, `server/`, `scripts/`, `web/`), then
  `site/`.
- `pnpm test`: every Vitest project, `web/src/` and `site/` included, then the `llamacpp-js` tests on `node --test`
  ([Run the tests](/developers/contributing/testing/#run-the-tests)).

When the change touches the server, the build or the package, also run `pnpm build`, then `node scripts/smoke.ts`
and `node scripts/smoke.ts --tarball`, as CI does.

When the change touches `site/`, including its pages, also run `pnpm site:build`, then
`pnpm --dir site check-links`.

## Continuous integration

`.github/workflows/ci.yml` runs on every pull request and every push to `master`, on Ubuntu with Node.js 26.13 and
pnpm:

| Step                                         | Command                                              |
| -------------------------------------------- | ---------------------------------------------------- |
| Install the dependencies (site included)     | `pnpm install --frozen-lockfile`                     |
| Lint                                         | `pnpm lint`                                          |
| Type check                                   | `pnpm check`                                         |
| Tests                                        | `pnpm test`                                          |
| Build the app                                | `pnpm build`                                         |
| Smoke-test the build (help, version, UI, WebSocket) | `node scripts/smoke.ts`                       |
| The same, on the package installed from its tarball | `node scripts/smoke.ts --tarball`             |
| Build the site                               | `pnpm site:build`                                    |
| Check the site's links                       | `pnpm --dir site check-links`                        |

A second job runs the tests of `packages/llamacpp-js/` on Node.js 24, the lowest version it supports, without any
install. `--frozen-lockfile` fails when the lockfile is out of date: commit `pnpm-lock.yaml` with any dependency
change.

`.github/workflows/site-deploy.yml` publishes `site/dist/` to GitHub Pages: on every push to `master` that changes
`site/` (or the workflow itself), and when started by hand from the Actions tab (`workflow_dispatch`). A pull request
never deploys: the site changes it brings go live when it is merged.

## Releases

Every `package.json` (root, `server`, `shared`, `llamacpp-js`, `web`, `site`) carries the version of the last release, and the tag
must match it. A release takes two steps:

```bash title="Terminal"
# 1. Set the version everywhere, then commit it through a pull request
pnpm release 0.2.0
# 2. Once it is merged, tag master
git fetch origin
git tag v0.2.0 origin/master
git push origin v0.2.0
```

`scripts/release.test.ts` fails when the `package.json` versions differ, and `.github/workflows/release.yml`, which
runs when a `v*` tag is pushed, first checks that they match the tag (`node scripts/release.ts --check v0.2.0`). The
build reports the tag as its version (`git describe`, shown in the status bar and by `/api/health`).

A build from an untagged commit reports the last tag, the number of commits since and the short hash instead
(`v0.2.0-3-gfa823b5`), and `-dirty` when built with uncommitted changes.

The workflow then builds, packs the root package (`pnpm pack --pack-destination release`), installs the tarball with
npm into an empty prefix and smoke-tests the installed command (`node scripts/smoke.ts --tarball`), writes
`SHA256SUMS`, and creates the GitHub Release with generated notes and those two files
([Distribution](/developers/architecture/#distribution)). The [Installation](/docs/getting-started/installation/) page
installs from a release.
