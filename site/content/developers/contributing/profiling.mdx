title: Profiling
description: Measure what the app costs (server, NVML sampler, browser, llama-server's throughput) with pnpm profiling, check a fix by running the same scenario before and after it, measure a branch against its base in one run or from a pull request comment, and read a comparison of two runs.
---

`pnpm profiling` measures the app as a person uses it: it builds it, starts it on your machine, opens its pages in
Chromium, launches a profile on your GPUs, and writes the figures to an HTML report. It measures; it does not conclude.
The report states CPU per process, page work, load times, API latency and throughput, with the reference value and the
difference when you compare two runs. Which figure is a problem and what to change stays your call.

The tool lives in `scripts/profiling/`. No test launches it: the suites only cover its options, its undo, its
comparison, its report and the comment command's parser, on small fixtures.

## What it needs

- **Linux**: the figures come from `/proc`, sysfs and `fincore`.
- **Chromium**: `/usr/bin/chromium` by default, another binary with `--chrome <path>`. It runs headless with GPU
  compositing (ANGLE on EGL).
- **The instance's port free**: the tool starts its own server on `127.0.0.1:7860` and refuses to run when something
  answers there. Stop your instance first, or pick another `--host`/`--port`.
- **The GPUs**, for a scenario with a model: it launches the profile given by `--profile <id>`, else the instance's
  default profile, and keeps it running until its last scenario. The tool refuses to start one while a process named
  `llama-server` runs on the machine, whoever started it: stop it first.

The server uses your data directory (`--data-dir` for another one): the profiles, models and settings the tool sees are
yours. With `--base`, each side works on its own copy of it.

## Commands

```bash title="Terminal"
pnpm profiling --list                              # the scenarios, with what they need and their length
pnpm profiling dashboard aurora --name before      # two scenarios, the run named "before"
pnpm profiling all --name baseline                 # every scenario: about an hour
pnpm profiling chat --compare baseline             # a run compared with an earlier one
pnpm profiling chat --base master                  # master, then the working tree compared with it
pnpm profiling:report before --compare baseline    # rewrite a report from its results.json
```

| Option             | Effect                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| `--name <run>`     | The run's folder under `.cache/profiling/`; the date and time when absent. An existing name is refused.       |
| `--compare <run>`  | Compare with an earlier run; a run whose results have another format version is refused.                      |
| `--base <ref>`     | Measure a git ref first, then the working tree compared with it. Not with `--compare` nor `--no-build`.       |
| `--profile <id>`   | The profile the model scenarios launch, instead of the default one.                                           |
| `--data-dir <dir>` | The server's data directory.                                                                                  |
| `--host`, `--port` | The server's address, `127.0.0.1:7860` by default.                                                            |
| `--chrome <path>`  | The Chromium binary.                                                                                          |
| `--no-build`       | Reuse `app/.output` instead of building. The page's functions then keep their minified names in its profiles. |

By default the tool runs the normal production build with hidden source maps, moves the `.map` files into the run, and
starts the server from the result: `app/.output` ends as after `pnpm build`.

## Scenarios

| Scenario     | Model | Browser | Minutes | What it measures                                                                                                  |
| ------------ | ----- | ------- | ------- | ----------------------------------------------------------------------------------------------------------------- |
| `startup`    |       |         | 1       | Spawn to `/api/health` and SIGTERM to exit, five launches; one CPU profile of a launch                            |
| `idle`       |       |         | 1       | The server and the NVML sampler with no page: CPU per process and thread, event loop                              |
| `load`       |       | yes     | 1       | The Dashboard's load, cold and warm cache, three each: TTFB, FCP, LCP, script time, requests, bytes               |
| `launch`     | yes   | yes     | 1       | The profile's start with the Dashboard open: time to ready, log lines, `/ws` messages, server CPU                 |
| `dashboard`  | yes   | yes     | 3       | The Dashboard at rest: a clean window, a profiled window (server and page), a trace, a census of the page's work  |
| `soak`       | yes   | yes     | 6       | The Dashboard open five minutes: JS heap after GC, DOM nodes, listeners, `/ws` traffic, the server's RSS and heap |
| `aurora`     | yes   | yes     | 3       | The Dashboard under six CSS variants (aurora animation, backdrop blur, transitions)                               |
| `generation` | yes   | yes     | 3       | The Dashboard while a reply is generated through the app's chat API                                               |
| `chat`       | yes   | yes     | 4       | The Chat page streaming a long Markdown reply: three successive windows, a census, long tasks                     |
| `pages`      | yes   | yes     | 5       | Every page loaded cold, its API calls, then 12 s of presence                                                      |
| `api`        | yes   | yes     | 2       | Every GET the pages make, replayed 20 times: median, 95th percentile, size                                        |
| `tps`        | yes   | yes     | 3       | llama-server's own throughput (fixed request and seed) with no page, the Dashboard, a static page                 |
| `collectors` | yes   |         | 1       | Each NVML call and each `/proc` or sysfs read of a monitor tick                                                   |

A few scenarios leave things as they find them only on the way out:

- `launch` evicts the profile's GGUF files from the page cache before it starts the profile, so the start reads them
  from the disk as after a reboot; the report shows the share of the model still cached at the start.
- `generation` and `chat` create conversations titled `Profiling (temp)` and delete them at the end.
- `collectors` is a breakdown, not a verdict. Its NVML table times only the calls, in the tool's own process: the
  sampler process also runs Node, encodes and sends each sample and collects its garbage. The reader reads the PCIe
  throughput, the power limit and the persistence mode again only once their period has passed, by the time the tool
  gives it: after a first round that reads everything (dropped, with the values the sampler keeps: identity, maxima,
  driver versions), the tool alternates full samples (every period passed) and light ones (none), one per second. The
  table is the cost of each call in a full sample, labelled with how often it runs at 1 Hz (counted over a minute of
  samples on a reader of its own); the tiles give a full sample, a light one and the average at 1 Hz (a light sample
  plus the calls it leaves out, as often as they run). The NVML sampler's whole cost is its row in the windows of
  `idle` or `dashboard`. The list of `/proc` and sysfs reads is kept in the tool,
  written from `app/server/collectors/`: it does not follow the code. It holds what a tick reads again each time:
  not what the app keeps once read (an AMD card's link maximum), nor the cards the instance hides, and
  for llama-server's descriptors their `/proc/<pid>/fd` links (a `readlink` each) then the fdinfo of those open on a
  DRM node, only when an AMD card is read.

## Check a fix

Run the scenario that shows the cost, make the fix, run the same command again against the first run:

<Steps>

<Step title="Measure before">

```bash title="Terminal"
pnpm profiling aurora --name before
```

</Step>

<Step title="Make the fix">

Change the code; the next run builds it.

</Step>

<Step title="Measure after, compared">

```bash title="Terminal"
pnpm profiling aurora --name after --compare before
```

</Step>

</Steps>

Use the same command on both sides. A full pass (`all --name baseline`) gives the overall picture; it is not the
reference to check one fix against, as the next section explains.

## Measure a branch against its base

`--base <ref>` takes both measures in one run: the ref first (a branch, a tag, a commit), then the working tree, with
the same scenarios, profile, address and Chromium. It answers what a branch changes without a baseline measured
earlier, which the machine's state makes unreliable from one hour to the next.

```bash title="Terminal"
pnpm profiling chat dashboard --base master --name my-branch
```

<Steps>

<Step title="The base is checked out and installed">

The ref is checked out in a git worktree under the base run's folder (`.cache/profiling/my-branch.base/src`), then
installed there with `pnpm install --frozen-lockfile --ignore-scripts --prefer-offline`.

</Step>

<Step title="Both sides are built">

The base in its worktree, then the working tree: a build that fails stops the command before any measure. The profile
to launch is then read once, for both sides.

</Step>

<Step title="The base is measured, then the working tree">

The base is an ordinary run named `<name>.base`; the working tree is the run `<name>`, compared with it. The copy of
the tool in the working tree measures both, so a difference comes from the app, not from the tool.

</Step>

</Steps>

Three things differ from a run without `--base`:

- **The data directory is copied.** Each side starts its server on its own copy of the data directory (the one
  `--data-dir` names, else the one the server would use), made before the first measure and removed with the run. Both
  sides start from the same data, and a migration the branch brings never reaches your data. The copy is taken as the
  directory is: one a branch has already migrated may not open with the base's older code, so give `--data-dir` a
  directory from before.
- **The server's working directory stays the repository** on both sides: its `.env` is the one both read.
- **`collectors` loads the NVML reader of the side it measures.** When the base's reader does not export what the
  scenario calls, its NVML table is skipped on the base and shown without comparison on the working tree.

Stopping the command (Ctrl+C, SIGTERM) removes the worktree and the copies; so does the next `pnpm profiling` after a
kill.

## Read a comparison

With `--compare`, the report opens on **What changed**: the figures whose difference exceeds the noise of their kind,
largest first. A full pass lists a few hundred of them: the field above the table keeps the rows whose label contains
what you type (`chrome-gpu`, `/topology`), and **Group by measured window** puts them under the window they were
measured in. Every other figure shows the reference value and the difference, and a figure under its noise is shown
as unchanged. The noise is a fixed threshold per kind of figure: a difference is a change when it exceeds both the
share of the reference and the floor; a figure of a profiled window has twice that threshold. They were set from two
runs of the same scenarios on unchanged code: two runs give a spread, not a distribution. A smaller difference may
still be real, such as a small process's CPU: read the raw difference, or repeat both runs.

A compared run also writes `summary.md` next to its report: the two versions, the figures outside the noise (the 40
with the largest excess), the scenarios that failed on either side and the comparison's notes, in Markdown. It names no
path and nothing of the machine but what a failed scenario's message holds.

| Kind of figure                      | Share of the reference     | Floor   |
| ----------------------------------- | -------------------------- | ------- |
| CPU of a process or thread (points) | 10 %                       | 0.75 pt |
| Share of a thread's time (points)   | —                          | 1 pt    |
| Tokens per second                   | 1 %                        | —       |
| Duration                            | 15 %                       | 1 ms    |
| Size                                | 10 %                       | 1 KiB   |
| Count                               | 5 %                        | 1       |
| AMD `gpu_busy_percent`              | indicative, never a change | —       |

Three things to keep in mind:

- **A run alone against a full pass.** A scenario starts from the same browser state alone or inside `all`, but not
  from the same server: inside `all` the server has run longer and the monitor's history (300 s, in memory) is full.
  When the server's uptime or the history's length differs by more than a factor of two between the two sides, the
  report prints a note next to the scenario. Compare two runs of the same command.
- **Profiled windows.** A window measured under a profiler or a trace is tagged `profiled`: the profiler inflates its CPU
  and the server's event loop, so its figures compare only with another profiled window. The overview shows only the
  windows measured without one.
- **Software rendering.** When Chromium composites in software, a red banner says so at the top of the report: the
  page and GPU-process figures then overstate blur and animation costs several times over and do not stand for a
  desktop browser.

## Where a run lives

<FileTree>

- `.cache/profiling/<run>/`
  - `run.json` options, scenarios, versions, machine, Chromium's GPU status, start and end
  - `state.json` what must be undone (pids, conversation ids, the default profile to restore)
  - `data/<scenario>/` windows, `.cpuprofile` files, traces
  - `sourcemaps/` the client's maps of this build
  - `results.json` the figures of the report, with a format version
  - `report.html` the report, one file with no external resource
  - `summary.md` the comparison in Markdown, for a compared run
  - `datadir/` with `--base`, this side's copy of the data directory, while the run lasts
- `.cache/profiling/<run>.base/` with `--base`, the base's run: the same files, and
  - `src/` the base's worktree, while the run lasts

</FileTree>

`.cache/` is ignored by git, the formatter and the linter. `pnpm profiling:report` reads `results.json` only, so a
report can be rewritten, or compared, without the raw data. The report follows the system's light or dark theme; its
switch (**Auto**, **Light**, **Dark**) picks one, which the browser keeps.

## What the tool undoes

Everything the tool starts or creates is written to `state.json` when it starts or creates it, each process with its
start time. The end of the command (failed scenarios included), Ctrl+C and SIGTERM run the same undo: delete the
temporary conversations, stop llama-server through the API, restore the default profile, close Chromium, then stop the
server and wait for its exit; with `--base`, the base's worktree and each side's copy of the data directory are removed
last. A step that fails is printed and the next ones still run. The API is called, and a
process stopped, only while the process recorded in `state.json` still runs: a pid reused since, or an instance started
on the port after the run, is left alone, and what could not be undone is printed. A second Ctrl+C quits at once.

A run killed before its undo (`kill -9`, a crash) leaves its `state.json`: the next `pnpm profiling` undoes it before
it starts, and prints what it cleaned. A run whose `pnpm profiling` still runs is left as it is.

## Measure a pull request from a comment

A comment on a pull request starts a pass on the maintainer's machine and gets the comparison as an answer:

```text title="Comment"
/profiling chat dashboard --profile 6
```

The first line holds the command: scenario names or `all` (the default when none is named), and `--profile <id>`.
Anything else is answered with the usage. `.github/workflows/profiling.yml` then runs
`pnpm profiling <scenarios> --base origin/<base branch>` on the pull request's last commit, and posts the run's
`summary.md` with the commit it measured and a link to the workflow run. A pass that is refused or fails answers with
the end of its output, the runner's paths replaced by placeholders.

| Rule                 | Detail                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| Who can start a pass | The repository's owner and its collaborators; a comment from anyone else starts nothing.                        |
| Forks                | A pull request from a fork is refused with an answer: push the branch to the repository to measure it.          |
| One pass at a time   | A new comment waits for the pass in progress; a third one replaces the second while the first still runs.       |
| The report           | Not uploaded: it names the machine. It is copied to `PROFILING_REPORTS_DIR` on the runner when that is set.     |
| Changes to the job   | A workflow started by a comment runs from `master`: a change to `profiling.yml` takes effect once it is merged. |

### Set up the runner

The pass needs the GPUs, so it runs on a [self-hosted runner](https://docs.github.com/en/actions/hosting-your-own-runners)
with the label `profiling`, installed on the machine that has them:

<Steps>

<Step title="Require approval for outside contributors' workflows">

In the repository's **Settings › Actions › General**, under the approval of fork pull request workflows, require
approval for all external contributors. A workflow started by a pull request runs the pull request's own copy of the
workflow files: without that approval, a fork could name the `profiling` label in a workflow of its own and run code on
the machine. Read the workflow changes of a fork's pull request before you approve its runs.

</Step>

<Step title="Register the runner">

**Settings › Actions › Runners › New self-hosted runner** gives the commands. Add the label `profiling` when
`config.sh` asks for labels, and run the runner as your own user, not as root: it needs `git`, `gh`, Chromium, the
GPUs, and the model files the profile names.

</Step>

<Step title="Give it a data directory">

Set the repository variable `PROFILING_DATA_DIR` (**Settings › Secrets and variables › Actions › Variables**) to a data
directory on the machine that holds the profile to launch as its default one. Each pass copies it, so it is never
changed. Without the variable, the pass copies the data directory of the runner's user.

</Step>

</Steps>

| Repository variable     | Effect                                                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------------------------------- |
| `PROFILING_DATA_DIR`    | The data directory each pass copies; the runner's user's own when unset.                                       |
| `PROFILING_PORT`        | The port of the pass's server, 7870 when unset: it must be free.                                               |
| `PROFILING_REPORTS_DIR` | A folder on the machine where each pass leaves its `report.html`, `results.json`, `run.json` and `summary.md`. |

A pass uses the GPUs for as long as its scenarios last (`all` is about twenty minutes a side) and is refused while a
llama-server runs. Check the first report for the software rendering banner: a runner started as a service must still
reach the GPU for Chromium's compositing.
