Each guide lists the files a common change touches, in the order you usually write them, and ends with the
documentation pages to update in the same pull request ([Keep the docs in sync](/developers/contributing/workflow/#keep-the-docs-in-sync)).
[Conventions](/developers/contributing/conventions/) and [Testing](/developers/contributing/testing/) apply to all of
them.

## Add a page to the web app

<Steps>
  <Step title="Write the page">

Create `app/src/features/<page>/<Name>Page.tsx` and export the component by name. Pages render their own `<h1>` and
build on the glass components of `app/src/components/glass/` (`GlassCard`) and the shadcn primitives. Keep logic you
want to test in a plain module next to it.

  </Step>
  <Step title="Add the route">

Add an entry to the router's children in `app/src/app/router.tsx`. `page()` turns it into a lazy route, so the page is
its own chunk, loaded on first visit:

```tsx title="app/src/app/router.tsx"
{ path: 'bench', ...page(() => import('@/features/bench/BenchPage'), 'BenchPage') },
```

Keep the `import()` literal: the bundler can only split a chunk it can see. The server answers every path that is not
an API route with the app (Nitro's renderer serves `index.html`), so a reload on the new URL works without a server
change.

  </Step>
  <Step title="Add it to the sidebar">

Add `{ path, label, icon, group }` to `ROUTES` in `app/src/app/routes.ts`, with a [Lucide](https://lucide.dev) icon,
next to the other entries of its group (`overview`, `run`, `monitor` or `tune`). The sidebar
(`app/src/app/Sidebar.tsx`) lists `ROUTES` in order, draws a line between two groups (`navGroups()`), and pins
**Settings** (group `settings`) at the bottom. `app/src/app/routes.test.ts` fails if a group's entries are not
contiguous.

  </Step>
  <Step title="Load its data">

Put the API calls and the store of the page's domain in `app/src/lib/<domain>.ts` (a zustand store, `api(…)` from
`app/src/lib/api.ts`). If the page follows WebSocket messages that only it needs, start their subscription when it
mounts, as `BenchPage` does with `startBenchSync()`.

  </Step>
  <Step title="Check it">

`pnpm dev` picks up the new files. To check the production split, run `pnpm start` (it builds the app with
`vite build` first) and open the page.

  </Step>
</Steps>

**Docs to update**: a user page `site/content/docs/<page>.mdx` with its entry in `site/content/nav.ts`, a screenshot
(an entry in `site/scripts/shots.ts`, then a capture, see [Screenshots](/developers/contributing/workflow/#screenshots)),
and the [Web app](/developers/frontend/) page for the router and sidebar.

## Add an API route

<Steps>
  <Step title="Define the shapes">

A request body or a response the web app also builds or reads gets a zod schema and its type in
`packages/webui-shared/src/<domain>.ts` (a new module is re-exported from `packages/webui-shared/src/index.ts`). Validation messages are in English.
A shape only the route reads can stay in the route file, like `EstimateRequest` in `app/server/routes/api/tuning/estimate.post.ts`.
`z.strictObject` rejects unknown fields.

```ts title="packages/webui-shared/src/hf.ts"
export const DownloadRequestSchema = z.strictObject({
  repo: z.string().regex(HF_REPO_RE, 'Repository id expected (org/name)'),
  revision: z.string().regex(/^[0-9a-f]{40}$/, 'Commit sha expected'),
  /** Keys of the variants to download (HfVariant.key). */
  keys: z.array(z.string().min(1).max(1024)).min(1).max(16),
});
export type DownloadRequest = z.infer<typeof DownloadRequestSchema>;
```

  </Step>
  <Step title="Write the route file">

Nitro maps each file under `app/server/routes/api/` to a route, one file per method: the path comes from the folders,
`[id]` is a parameter, and the suffix is the method (`profiles/[id]/index.put.ts` is `PUT /api/profiles/:id`). The
file's default export is a `defineHandler()` of `nitro`; it reads the app's objects with `deps()`
(`app/server/lib/context.ts`), which the middleware `00.ready.ts` makes available once startup is done. The guard, the
`405` table, the `404` of an unknown route and the error responses are applied to every route by
`app/server/middleware/01.guard.ts` and `app/server/error.ts`: there is nothing to wrap.

```ts title="app/server/routes/api/topology.get.ts"
export default defineHandler(async () =>
  reply({ graph: await readPciTopology(), placement: deps().placement.current }),
);
```

Nitro's router matches a static segment before a `[param]` one, whatever the order of the files:
`downloads/clear.post.ts` is never taken for `downloads/[id]/`.

The helpers of `app/server/lib/http.ts` cover the usual cases:

| Helper                                      | Use                                                                        |
| ------------------------------------------- | -------------------------------------------------------------------------- |
| `reply<T>(data, status = 200)`              | A JSON response; `T` is what the typed client returns                      |
| `noContent()`, `attachment(filename, body)` | A `204`, a JSON download                                                   |
| `readBody(event, Schema)`                   | The JSON body validated by a zod schema: `400 Invalid JSON`, `400 JSON object expected`, then the `ZodError` (`Invalid data: …` + `issues`) |
| `readJson(event, check)`                    | A JSON body passed through your own check (`object`: any object; `passthrough`: as sent), for custom messages |
| `idParam(event, 'Download')`                | A positive integer `:id`, otherwise `404 Download not found`; read it before the body |
| `queryOf(event, 'key', …)`                  | The first value of each query key present (it refuses nothing)             |
| `notFound('Profile')`                       | `404 Profile not found`                                                    |
| `new HttpError(409, message, code)`         | Any refusal; add a `code` when the web app must react to it                |

A file that reads a body or a query exports its type, `export type Body` or `export type Query` (`QueryOf<'key'>`):
that is what the typed client checks a call against.

```ts title="app/server/routes/api/downloads/index.post.ts"
export type Body = z.input<typeof DownloadRequestSchema>;

export default defineHandler(async (event) => {
  const { hf, downloads, settings } = deps();
  const body = await readBody(event, DownloadRequestSchema);
  const items = await downloads.enqueue(await downloadInputs(hf, body, expandHome(settings.get().modelsDir)));
  return reply({ items }, 202);
});
```

When the handler must look something up (and answer `404` or `409`) before the body is checked, do not validate the
body ahead of it: read it with `readJson(event, object)` after the lookup, or pass it as sent
(`readJson(event, passthrough)`) to a repository that validates it.

  </Step>
  <Step title="Register the route">

There is nothing to mount: Nitro scans the file, and `app/build/apiTypes.ts` writes the route into
`app/server/api.gen.ts` (the client's types and the `405` table) at the start of `pnpm dev`, on every save under
`app/server/routes/api/` and at every build. A new dependency goes into `AppDeps` and is built in `createDeps()`
(`app/server/lib/deps.ts`). Add the route to `ROUTES` in `app/server/lib/contract/cases.ts` (the contract suite fails
otherwise), then regenerate the golden (see [Testing](/developers/contributing/testing/#http-contract-suite)).

  </Step>
  <Step title="Call it from the web app">

The typed client sees the route as soon as `api.gen.ts` lists it:
`api('POST /api/downloads', { body: { repo, revision, keys } })` (`app/src/lib/api.ts`, with `params: { id }` for an
`:id` and `query` for the query) returns the type of the handler's `reply(…)` and throws an `ApiError` with `status`,
`issues` (zod details on a `400`) and `code`. Branch on `code`, never on the message. The body and the query of the
call are checked against the file's `Body` and `Query` (see [Typed client](/developers/api/overview/#typed-client)).

  </Step>
  <Step title="Test it">

Test the logic behind the route without HTTP (a builder like `buildSetupReport` in `app/server/lib/setup.ts`, a
repository on `openDb(':memory:')`). To test the route file itself, mount it with `routeApp()` and give it test doubles
with `provideDeps()` ([Write a test](/developers/contributing/testing/#write-a-test)).

  </Step>
</Steps>

**Docs to update**: the API reference page of the domain (`site/content/developers/api/<domain>.mdx`, written by
hand: every route, body, response and error code), and the user page of the feature. The common rules (guard, error
shape) live on the [API overview](/developers/api/overview/).

## Add a WebSocket message

<Steps>
  <Step title="Declare it">

Add a variant to the `WsMessage` union in `packages/webui-shared/src/ws.ts`, with a payload type from `packages/webui-shared/`:

```ts title="packages/webui-shared/src/ws.ts"
| { type: 'download-progress'; payload: DownloadLive | null } // throttled; null when the queue is idle
```

  </Step>
  <Step title="Broadcast it">

Services do not import the hub: they take callbacks, and `createDeps()` connects them to `hub.broadcast()`
(`app/server/lib/ws/hub.ts`), which sends the message to every client:

```ts title="app/server/lib/deps.ts"
const downloads = new DownloadQueue({
  repo: downloadsRepo,
  hf,
  onItem: (i) => hub.broadcast({ type: 'download', payload: i }),
  onLive: (l) => hub.broadcast({ type: 'download-progress', payload: l }),
  onDeleted: (ids) => hub.broadcast({ type: 'download-deleted', payload: { ids } }),
});
```

Events of the runtime (the supervisor, the log ring, the monitor) are forwarded in `boot()` (`app/server/lib/boot.ts`),
as `monitor.onSnapshot((s) => hub.broadcast(…))` does: the subscription lasts as long as the runtime. Routes that
change state themselves can broadcast through `deps().hub`, as the delete routes of `app/server/routes/api/bench/` do
for `bench-deleted`.

  </Step>
  <Step title="Receive it">

In the store's file in `app/src/lib/`, subscribe with `onWs()` inside a `start<Domain>Sync()` function that runs once.
Messages are not replayed after a disconnection, so the same function reloads the state over REST on every
(re)connection:

```ts title="app/src/lib/downloads.ts"
onWs('download-progress', (m) => useDownloads.setState({ live: m.payload }));
// …
useWs.subscribe((s, prev) => {
  if (s.status === 'open' && prev.status !== 'open') void useDownloads.getState().load();
});
```

Call it from `app/src/main.tsx` when the whole app needs it (status bar, toasts), or when a page mounts when only that
page does.

  </Step>
</Steps>

**Docs to update**: the [WebSocket](/developers/api/websocket/) reference (type, payload, when it is sent) and the user
page of the screen that shows it.

## Add a database migration

<Steps>
  <Step title="Append the SQL">

Add an entry at the end of `MIGRATIONS` in `app/server/lib/db/migrations.ts`, with a comment that gives its version and
purpose. Never edit, reorder or remove an entry that has shipped:

```ts title="app/server/lib/db/migrations.ts"
/** One entry per schema version; never change a migration that has shipped, add a new one. */
export const MIGRATIONS: string[] = [
```

The database only stores a version number, the count of entries already applied (`schema_version`). `runMigrations()`,
called by `openDb()` at startup, runs each missing entry in a transaction together with the version bump, so a database
that already ran an entry never sees a later edit to it. Existing entries hold one statement each; a table rebuild
takes several (versions 10 to 14 rebuild `bench_runs` and copy its rows).

  </Step>
  <Step title="Update the repository">

Each table has a repository in `app/server/lib/db/` (`settings.ts`, `profiles.ts`, `benchRuns.ts`, `downloads.ts`…) that maps
rows to the types of `packages/webui-shared/`. Change its queries and row mapping, and the shared type if the API exposes the column.

  </Step>
  <Step title="Test it">

`openDb(':memory:')` applies every migration, so the repository tests exercise the new schema. When the migration
rewrites existing data, also test it on a copy of a real database, as the skipped J5 test does
([Skipped tests](/developers/contributing/testing/#skipped-tests)).

  </Step>
</Steps>

**Docs to update**: [Database](/developers/server/database/) (tables, columns, migration list).

## Add a collector

<Steps>
  <Step title="Write the sampler">

Add the reader in `app/server/lib/collectors/<name>.ts`: a class or function that returns a typed sample, or `null` when the
source is unavailable. Keep parsing in pure functions tested against captured output in `testdata/`, and take the
`/proc` or `/sys` root, the `spawn` function or the binary path as parameters so tests can replace them.

  </Step>
  <Step title="Type the sample">

Declare the sample type in `packages/webui-shared/src/monitor.ts`, as `SystemSample` and `DiskSample` are, and add a nullable field to
`Snapshot`. Add its history keys to `SERIES` if it is charted.

  </Step>
  <Step title="Register it">

`Collectors` (`app/server/lib/collectors/registry.ts`) owns every source. Create the new one in `start()` or `configure()` and
expose it through a getter that is `undefined` while its switch is off, as `system` and `disk` are; stop it in `stop()`.
A GPU source honors the `GpuNeeds` of `app/server/lib/collectors/needs.ts`: `gpuSkipped(needs, busId)` is true for a hidden
card, which is identified but never read.

  </Step>
  <Step title="Sample it on each tick">

In `Monitor.doTick()` (`app/server/lib/monitor/monitor.ts`), start the read alongside the others and catch its errors as they
do (`.catch(() => null)`): an exception would drop the whole snapshot of that tick. Put the result in the snapshot and
feed its series with `push()`, or `known()` when the value can be missing (the series gets a gap).

  </Step>
  <Step title="Show it">

Read it in the page with `useMonitor((s) => s.snapshot?.<field>)` and chart a series with `TimeSeriesChart` and its
`SERIES` key (`app/src/components/charts/`). If it gets an on/off switch, add it to `collectors` in the settings (see
[Add a setting](#add-a-setting)).

  </Step>
</Steps>

**Docs to update**: [Monitor and collectors](/developers/server/monitor/), the [WebSocket](/developers/api/websocket/)
page for the new `Snapshot` field, and the user pages that show it ([Dashboard](/docs/dashboard/),
[System](/docs/system/), [Topology](/docs/topology/)).

## Add a setting

<Steps>
  <Step title="Add it to the schema">

Add a field with its limits and a `.default()` to `SettingsSchema` (`packages/webui-shared/src/settings.ts`). `DEFAULT_SETTINGS` and the
`Settings` type follow from it.

```ts title="packages/webui-shared/src/settings.ts"
historySeconds: z.number().int().min(30, 'Between 30 and 1800 s').max(1800, 'Between 30 and 1800 s').default(300),
```

No migration is needed: the `settings` table stores one JSON value per key, and `SettingsRepo.get()`
(`app/server/lib/db/settings.ts`) starts from the defaults, so a new key gets its default and a stored value that no longer
validates falls back to it. A switch inside `collectors` goes into both the inner object and the outer `.default({…})`.

  </Step>
  <Step title="Use it on the server">

Read it with `settings.get()` when it is used (modules receive a getter such as `settings: () => settings.get()`), so a
change applies without a restart. `PATCH /api/settings` (`app/server/routes/api/settings.patch.ts`) also calls `monitor.configure()`: a setting
the monitor or the collectors depend on belongs in `MonitorSettings` and `CollectorSettings`.

  </Step>
  <Step title="Add it to the Settings page">

`app/src/features/settings/SettingsPage.tsx` has three tabs (**General**, **Monitoring**, **Appearance**). Add a field
from `fields.tsx` (`TextField`, `SwitchRow`) to the right section and save it with `save({ key: value })` from
`useSettingsEditor()` (`app/src/lib/settings.ts`). When the server refuses the value, `errors.<key>` holds the zod
message, which `TextField` shows under the field. The first-run checklist (`app/src/features/home/`) shares the editor
and the fields.

  </Step>
</Steps>

**Docs to update**: [Settings](/docs/settings/) (the setting, its default and limits), [Health and
settings](/developers/api/app/) (`PATCH /api/settings`), the Settings screenshots, and
[First run](/docs/getting-started/first-run/) if the checklist shows it.
