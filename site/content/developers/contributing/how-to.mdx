---

Each guide lists the files a common change touches, in the order you usually write them, and ends with the
documentation pages to update in the same pull request ([Keep the docs in sync](/developers/contributing/workflow/#keep-the-docs-in-sync)).
[Conventions](/developers/contributing/conventions/) and [Testing](/developers/contributing/testing/) apply to all of
them. The server's own rules, with an example of each, are in `docs/superpowers/poc-effect/conventions.md` of the
repository: read it before writing server code.

## Add a page to the web app

<Steps>
  <Step title="Write the page">

Create `app/src/features/<page>/<Name>Page.tsx` and export the component by name. Pages render their own `<h1>` and
build on the glass components of `app/src/components/glass/` (`GlassCard`) and the shadcn primitives. Keep logic you
want to test in a plain module next to it.

  </Step>
  <Step title="Add the route">

Add an entry to the router's children in `app/src/app/router.tsx`. `page()` turns it into a lazy route, so the page is
its own chunk, loaded on first visit:

```tsx title="app/src/app/router.tsx"
{ path: 'bench', ...page(() => import('@/features/bench/BenchPage'), 'BenchPage') },
```

Keep the `import()` literal: the bundler can only split a chunk it can see. The server answers every path that is not
under `/api`, `/ws` or `/assets` with the app's `index.html` (`app/server/http/Static.ts`), so a reload on the new URL
works without a server change.

  </Step>
  <Step title="Add it to the sidebar">

Add `{ path, label, icon, group }` to `ROUTES` in `app/src/app/routes.ts`, with a [Lucide](https://lucide.dev) icon,
next to the other entries of its group (`overview`, `run`, `monitor` or `tune`). The sidebar
(`app/src/app/Sidebar.tsx`) lists `ROUTES` in order, draws a line between two groups (`navGroups()`), and pins
**Settings** (group `settings`) at the bottom. `app/src/app/routes.test.ts` fails if a group's entries are not
contiguous.

  </Step>
  <Step title="Load its data">

Put the API calls and the store of the page's domain in `app/src/lib/<domain>.ts`: a zustand store, and calls through
`call()` of `app/src/lib/api.ts` (see [Typed client](/developers/api/overview/#typed-client)). If the page follows WebSocket messages that only it needs, start their subscription when it
mounts, as `BenchPage` does with `startBenchSync()`.

  </Step>
  <Step title="Check it">

`pnpm dev` picks up the new files. To check the production split, run `pnpm start` (it builds the app with
`vite build` first) and open the page.

  </Step>
</Steps>

**Docs to update**: a user page `site/content/docs/<page>.mdx` with its entry in `site/content/nav.ts`, a screenshot
(an entry in `site/scripts/shots.ts`, then a capture, see [Screenshots](/developers/contributing/workflow/#screenshots)),
and the [Web app](/developers/frontend/) page for the router and sidebar.

## Add an endpoint

<Steps>
  <Step title="Define the shapes">

The data an endpoint reads or answers gets an Effect `Schema` in `packages/webui-shared/src/<domain>.ts`, shared by the
server and the web (a new module is re-exported from `packages/webui-shared/src/index.ts`). A field's message is the
`message` of its check, in English. A payload's schema carries the input rules; the reply's schema has the same fields
without them, because a reply carries what is stored, and a stored row that a newer rule refuses must still be listed
(`ProfileInput` and `Profile` of `packages/webui-shared/src/profile.ts`). A number is `Schema.Finite` or `Schema.Int`,
never `Schema.Number`.

```ts title="packages/webui-shared/src/profile.ts"
export const ProfileInput = Schema.Struct({
  name: Required,
  model: Required,
  mmproj: Schema.optionalKey(Schema.String),
  cwd: Schema.optionalKey(Schema.String),
  host: Schema.optionalKey(Schema.String),
  port: Schema.optionalKey(Port),
  args: Args.pipe(Schema.withDecodingDefaultKey(Effect.succeed([]))),
  env: Schema.Record(Schema.String, Schema.String).pipe(Schema.withDecodingDefaultKey(Effect.succeed({}))),
}).annotate({ messageUnexpectedKey: 'unknown key' });
```

  </Step>
  <Step title="Declare the endpoint and its errors">

The endpoint goes into its domain's group, `packages/webui-shared/src/api/<Domain>Api.ts`, with everything it reads
as schemas: `params` (an id is `IdParam` of `api/params.ts`), `payload`, `query`, and its `success` and `error`. An
error it answers is a `Schema.TaggedError` with its status (`httpApiStatus`), exported from the package's index; the
web tells it by its `_tag`.

```ts title="packages/webui-shared/src/api/ProfilesApi.ts"
export class ProfileNotFound extends Schema.TaggedError<ProfileNotFound, { readonly ProfileNotFound: unique symbol }>()(
  'ProfileNotFound',
  { message: Schema.String },
  { httpApiStatus: 404 },
) {}

const Created = Profile.pipe(HttpApiSchema.status(201));
const params = { id: IdParam };

  HttpApiEndpoint.post('duplicate', '/api/profiles/:id/duplicate', {
    params,
    success: Created,
    error: ProfileNotFound,
  }),
```

An endpoint without `success` answers `204`. A file to download is `success: <its schema>` with `attachment(schema)`
of `app/server/http/attachment.ts`; a stream of server-sent events is `HttpApiSchema.StreamSse` with `sseResponse` of
`app/server/http/Sse.ts`. A new group is added to `Api` (`packages/webui-shared/src/api/Api.ts`) above its last two
lines: the `RequestErrors` middleware only reaches the groups added before it.

There is nothing to validate in the handler: `Api` decodes payloads strictly (an unknown key is an issue), and a
payload, a query or a header that does not decode answers `400` `RequestInvalid`, a path parameter `404`
`RouteNotFound` ([Validation errors](/developers/api/overview/#validation-errors)).

  </Step>
  <Step title="Write the handler">

The handlers of a group are one `HttpApiBuilder.group(Api, '<group>', …)` in `app/server/<domain>/http.ts`. They take
the services they need from the context and call them; a service's typed error becomes the endpoint's reply when it
is one of the endpoint's errors.

```ts title="app/server/profiles/http.ts"
      .handle('get', ({ params }) => repo.get(params.id))
      .handle('update', ({ params, payload }) => repo.update({ id: params.id, input: payload }))
      .handle('remove', ({ params }) => Effect.provideContext(removeProfile(params.id), services))
      .handle('duplicate', ({ params }) => repo.duplicate(params.id))
```

A new group's handlers go into the `Layer.mergeAll(…)` of `ApiRoutes` in `app/server/http/HttpLive.ts`. The guard,
the `404` of an unknown route and the error bodies apply to every endpoint of `Api`: there is nothing to wrap. A route
added outside `Api` with `HttpRouter.add` is not guarded until its layer is provided `Guarded`
(`app/server/http/Guard.ts`), as `WsHub.route` is.

  </Step>
  <Step title="Add its contract cases">

The contract suite (`app/server/contract/`) builds its matrix from `Api` (`HttpApi.reflect`): every method a path
lacks, a bad and an unknown id for each `:param`, and five broken bodies for each payload, with nothing to write. By
hand, in `cases()` of `app/server/contract/cases.ts`, add a success for an endpoint the matrix does not reach (the
coverage test fails otherwise), a `violation` for a body the schema refuses and a `refusal` for what the domain refuses
beyond an unknown id. Then regenerate the golden record and read its diff
([HTTP contract suite](/developers/contributing/testing/#http-contract-suite)).

  </Step>
  <Step title="Call it from the web app">

The web calls the endpoint through the typed client of `app/src/lib/api.ts`, which derives everything from `Api`:

```ts title="app/src/lib/profiles.ts"
export const duplicateProfile = (id: number) => call((api) => api.profiles.duplicate({ params: { id } }));
```

The promise resolves with the decoded reply, or rejects with the endpoint's tagged error (`ApiUnreachable` when no
answer came). Branch on `errorTag(error)`, never on the message. A type error in a call is fixed in the shared schema,
not with a cast ([Typed client](/developers/api/overview/#typed-client)).

  </Step>
  <Step title="Test it">

`app/server/<domain>/http.test.ts` runs the handlers on the services of `ServicesTest` with `layer(…)` of
`@effect/vitest`, through the typed client (`HttpApiTest.groups(Api, ['<group>'])`), and over raw HTTP for what the
client would never send (a body the schema refuses):

```ts title="app/server/profiles/http.test.ts"
    it.effect('duplicate answers the copy', () =>
      Effect.gen(function* () {
        const client = yield* makeClient;
        const source = yield* client.profiles.create({ payload: input('Dup', { port: 8085 }) });
        const copy = yield* client.profiles.duplicate({ params: { id: source.id } });
        assert.strictEqual(copy.name, 'Dup (copy)');
        assert.strictEqual(copy.port, 8085);
        assert.notStrictEqual(copy.id, source.id);
        const missing = yield* Effect.flip(client.profiles.duplicate({ params: { id: 999 } }));
        assert.strictEqual(missing._tag, 'ProfileNotFound');
      }),
    );
```

See [Write a test](/developers/contributing/testing/#write-a-test).

  </Step>
</Steps>

**Docs to update**: the API reference page of the domain (`site/content/developers/api/<domain>.mdx`, written by
hand: every endpoint, body, response and error), and the user page of the feature. The common rules (guard, error
shape) live on the [API overview](/developers/api/overview/).

## Add a service

<Steps>
  <Step title="Declare it">

A service is a `Context.Service` class in `app/server/<domain>/<Name>.ts`, keyed by its path, with its interface as
the class's type parameter:

```ts title="app/server/ws/WsHub.ts"
export class WsHub extends Context.Service<
  WsHub,
  {
    /** Sends a message to every connected client. */
    readonly publish: (message: WsMessage) => Effect.Effect<void>;
    /** The number of connected clients. */
    readonly size: Effect.Effect<number>;
    /** The life of one client on its upgraded socket, until it closes: what the `/ws` route runs. */
    readonly attach: (socket: Socket.Socket) => Effect.Effect<void>;
  }
>()('@llama-webui/app/server/ws/WsHub') {
```

  </Step>
  <Step title="Build it as a layer">

Its layers are statics of the class: `layer` for the app, and `layerWith(options)` when its durations or limits
differ in tests. The layer builds the state, forks the fibers of the service in its own scope (they end with it), and
registers its finalizers and its shutdown step.

```ts title="app/server/bench/BenchRunner.ts"
  static readonly layer = BenchRunner.layerWith({
    killTimeout: '5 seconds',
    pause: '1 second',
    stoppingTimeout: '60 seconds',
    liveThrottle: '250 millis',
  });
```

Never `node:child_process`, `fetch`, `JSON` or a timer in a service: a program runs through `effect/process`
(`followProgram()` when it lasts), a request to llama-server through `LlamaHttp`, one to Hugging Face through `HfHttp`,
a file through `FileSystem`, and a wait through `Effect.sleep` or a `Schedule`.

  </Step>
  <Step title="Add it to the app">

Add its layer to `Services` in `app/server/App.ts`, in the tier above everything it needs (the database is built
first, `ExternalWatch` last): the services are built tier by tier, and undone in the reverse order when the app stops.
Add it the same way to `ServicesTest` (`app/server/testing/services.ts`), with `layerWith` and shorter durations.

  </Step>
</Steps>

**Docs to update**: the server page of its domain, and [Architecture](/developers/architecture/) when it adds a tier
or a shutdown step.

## Add a shutdown step

A step saves what a service is doing before the app stops: a chat reply saved `stopped`, a benchmark `interrupted`,
the last message of the hub. It is registered while the service is built:

```ts title="app/server/downloads/Downloads.ts"
        yield* shutdown.before(
          Effect.gen(function* () {
            const running = yield* SynchronizedRef.modifyEffect(state, (s) =>
              Effect.as(Ref.set(closing, true), [s.loop, s] as const),
            );
            if (Option.isSome(running)) yield* Fiber.interrupt(running.value);
          }).pipe(Effect.withSpan('Downloads.shutdown')),
        );
```

The steps run on `SIGINT` or `SIGTERM`, last registered first, before the HTTP server stops serving; a step that fails
is logged and the next ones still run. A wait inside a step is made `Effect.interruptible` before its
`Effect.timeout`. A step that saves what `llama-server` is doing belongs to a service built above the supervisor, so it
runs while the process still answers. It saves first, then stops the work, and the work writes nothing once its result
is saved. **Docs to update**: the shutdown table of [Architecture](/developers/architecture/#shutdown) and of the
domain's page.

## Add a WebSocket message

<Steps>
  <Step title="Declare it">

Add a `Schema.Struct` with its `type` literal and its `payload` to `packages/webui-shared/src/ws.ts`, and add it to the
`WsMessage` union:

```ts title="packages/webui-shared/src/ws.ts"
export const WsDownloadProgress = Schema.Struct({
  type: Schema.Literal('download-progress'),
  payload: Schema.NullOr(DownloadLive),
});
```

  </Step>
  <Step title="Publish it">

The service that changes the state publishes the message on the hub, `WsHub.publish`, which sends it to every client:

```ts title="app/server/downloads/Downloads.ts"
            yield* hub.publish({ type: 'download-progress', payload: live });
```

The hub encodes it once for every client. A message that does not encode is not sent (nor kept as the snapshot a
new client gets), and logged once as an error (`a <type> message does not encode: not sent`): make a reading finite
before it reaches a schema.

  </Step>
  <Step title="Receive it">

In the store's file in `app/src/lib/`, subscribe with `onWs()` inside a `start<Domain>Sync()` function that runs once.
Messages are not replayed after a disconnection, so the same function reloads the state over HTTP on every
(re)connection:

```ts title="app/src/lib/downloads.ts"
  onWs('download-progress', receive);
  onWs('download', receive);
  onWs('download-deleted', receive);
  useWs.subscribe((s, prev) => {
    if (s.status === 'open' && prev.status !== 'open') void useDownloads.getState().load();
  });
```

Call it from `app/src/main.tsx` when the whole app needs it (status bar, toasts), or when a page mounts when only that
page does, as `BenchPage` does with `startBenchSync()`.

  </Step>
</Steps>

**Docs to update**: the [WebSocket](/developers/api/websocket/) reference (type, payload, when it is sent) and the user
page of the screen that shows it.

## Add a database migration

<Steps>
  <Step title="Append it">

Add an entry at the end of `MIGRATIONS` in `app/server/db/migrations.ts`, keyed by its number and name
(`0018_<name>`), with a comment that gives its purpose. Never edit, reorder or remove an entry that has shipped:

```ts title="app/server/db/migrations.ts"
export const MIGRATIONS: Record<string, Migration> = {
  // key/value settings
  '0001_settings': statements(`CREATE TABLE settings(key TEXT PRIMARY KEY, value_json TEXT NOT NULL);`),
```

`statements(…)` runs its SQL one statement at a time; a table rebuild goes through `rebuild({ version, sqls })`, which
also checks that no foreign key points to a missing row. `SqliteMigrator` (`app/server/db/Db.ts`) runs each missing
entry in a transaction when the database opens ([Database](/developers/server/database/)).

  </Step>
  <Step title="Update the repository">

Each table has a repository in its domain's folder (`settings/SettingsRepo.ts`, `profiles/ProfilesRepo.ts`,
`bench/BenchRunsRepo.ts`, `downloads/DownloadsRepo.ts`…), a service on `SqlClient` that maps rows to the schemas of
`packages/webui-shared/`. Change its queries and row mapping, and the shared schema if the API exposes the column. A
number fed to a JSON function or an untyped column is written `CAST(? AS INTEGER)`: `node:sqlite` binds a JS number as
REAL otherwise.

  </Step>
  <Step title="Test it">

`Db.layerAt(':memory:')` (under `ServicesTest`) applies every migration, so the repository tests exercise the new
schema. When the migration rewrites existing data, also test it from the schema it starts from, filled with rows
([Migrations on old data](/developers/contributing/testing/#migrations-on-old-data)).

  </Step>
</Steps>

**Docs to update**: [Database](/developers/server/database/) (tables, columns, migration list).

## Add a collector

<Steps>
  <Step title="Write the reader">

Add the reader in `app/server/collectors/<name>.ts`: an effect that gives a typed sample. Keep parsing in pure
functions tested against captured output in `testdata/`, and read files through `FileSystem` and programs through
`effect/process`, so a test can give its own files and programs.

  </Step>
  <Step title="Type the sample">

Declare the sample's schema in `packages/webui-shared/src/monitor.ts`, as `SystemSample` and `DiskSample` are, and add
a nullable field to `Snapshot`. Add its history keys to `SERIES` if it is charted. Its numbers are `Schema.Finite` or
`Schema.Int`: `app/server/monitor/finite.ts` makes a reading finite before it reaches the snapshot.

  </Step>
  <Step title="Register it">

`Collectors` (`app/server/collectors/Collectors.ts`) owns every source. Expose the new one as an
`Effect<Option<Source>>` that is none while its switch is off, as `system` and `disk` are, and start or stop it in
`configure`, which applies the settings.

  </Step>
  <Step title="Read it on each tick">

`Monitor` (`app/server/monitor/Monitor.ts`) reads every source of a tick in one `Effect.all`, each read with its own
fallback (`orElse(null)`): a read that fails gives no value, never a lost snapshot. What the tick does with the
readings is the pure `endTick` of `app/server/monitor/tick.ts`: put the sample in the `TickReading`, then in the
snapshot, and feed its series. Test the rule in `tick.test.ts`, as a plain function.

  </Step>
  <Step title="Show it">

Read it in the page with `useMonitor((s) => s.snapshot?.<field>)` and chart a series with `TimeSeriesChart` and its
`SERIES` key (`app/src/components/charts/`). If it gets an on/off switch, add it to `collectors` in the settings (see
[Add a setting](#add-a-setting)).

  </Step>
</Steps>

**Docs to update**: [Monitor and collectors](/developers/server/monitor/), the [WebSocket](/developers/api/websocket/)
page for the new `Snapshot` field, and the user pages that show it ([Dashboard](/docs/dashboard/),
[System](/docs/system/), [Topology](/docs/topology/)).

## Add a setting

<Steps>
  <Step title="Add it to the schema">

Add the default to `DEFAULTS` and a field with its limits and its decoding default to `Settings`
(`packages/webui-shared/src/settings.ts`):

```ts title="packages/webui-shared/src/settings.ts"
  historySeconds: IntBetween(30, 1800, 'Between 30 and 1800 s').pipe(
    Schema.withDecodingDefaultKey(Effect.succeed(DEFAULTS.historySeconds)),
  ),
```

No migration is needed: the `settings` table stores one JSON value per key, and `SettingsRepo.get`
(`app/server/settings/SettingsRepo.ts`) decodes each stored value on its own, so a new key gets its default and a
stored value that no longer validates falls back to it, with a warning in the log.

  </Step>
  <Step title="Use it on the server">

Read it with `SettingsRepo.get` when it is used, so a change applies without a restart. The `PATCH /api/settings`
handler (`app/server/settings/http.ts`) hands a patch to `monitor.configure` when it changes what the monitor follows:
a setting the monitor or the collectors depend on also goes into `MonitorSettings` and `monitorSettingsOf`
(`app/server/monitor/Monitor.ts`).

  </Step>
  <Step title="Add it to the Settings page">

`app/src/features/settings/SettingsPage.tsx` has three tabs (**General**, **Monitoring**, **Appearance**). Add a field
from `fields.tsx` (`TextField`, `SwitchRow`) to the right section and save it with `save({ key: value })` from
`useSettingsEditor()` (`app/src/lib/settings.ts`). When the server refuses the value (`SettingsInvalid`), `errors.<key>`
holds the message of its issue, which `TextField` shows under the field. The first-run checklist
(`app/src/features/home/`) shares the editor and the fields.

  </Step>
</Steps>

**Docs to update**: [Settings](/docs/settings/) (the setting, its default and limits), [Health and
settings](/developers/api/app/) (`PATCH /api/settings`), the Settings screenshots, and
[First run](/docs/getting-started/first-run/) if the checklist shows it.
