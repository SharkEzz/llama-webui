title: Topology
description: The route that returns the machine's PCIe graph read from sysfs and the placement of the loaded model read from llama-server's logs.
---

`GET /api/topology` returns what the [Topology](/docs/topology/) page draws: the hardware graph (CPU, memory, GPUs,
NVMe drives, chipsets and their PCIe links) and how the loaded model is split across devices. The endpoint is declared
in `MonitorApi` (`packages/webui-shared/src/api/MonitorApi.ts`) and handled in `app/server/monitor/http.ts`; the types and the pure helpers are in `packages/webui-shared/src/topology.ts`, the graph reader in
`app/server/hardware/pci.ts` (the links' speeds read by `pcieLink.ts`, the device names by `pciLabels.ts`), the placement tracker `Placement` in `app/server/monitor/Placement.ts`.

The guard and the error shape follow the common rules of the [API overview](/developers/api/overview/).

## Get the topology

<Endpoint method="GET" path="/api/topology" />

The graph is read again on every call: the current state of a PCIe link changes with power states. The placement is
the tracker's latest value. Only the Topology page asks for it: once when it is shown (on a cold load, once the
WebSocket opens), then on each reconnect while it is; the `placement` messages keep the placement up to date in
between.

**Response**: `200` with `{ graph: TopologyGraph, placement: ModelPlacement | null }`.

```bash title="Terminal"
curl http://127.0.0.1:7860/api/topology
```

## The hardware graph

`readPciTopology()` reads sysfs only, never `lspci`, which wakes up suspended cards. It always starts with the CPU and
memory nodes and their `cpu-ram` link, then walks `/sys/bus/pci/devices` for display controllers (class `0x03`, GPUs)
and NVMe controllers (class `0x0108`). Each device is linked to the CPU directly (root port), or through a chipset node
when the first bridge below the root port has the root port's vendor, is not marked removable, and is not a
Thunderbolt or USB4 bridge (a PCIe switch from another vendor, on an NVMe card or a riser, is not a chipset). A GPU
inside the processor gets an `internal` link without figures: one whose link reports no speed (on the root bus), or
one right under a root port that shares its PCI device with functions of the root port's vendor and is not of that
vendor itself (a Ryzen's Radeon, vendor `0x1002`, sits beside the processor's security processor and USB controllers,
vendor `0x1022`, behind an internal bridge that reports Gen4 x16 like a slot). Any failed
read degrades to unknown: at worst the graph holds the CPU and memory only. The CPU node comes from the CPU info the
server keeps (`CpuInfo`, the one [System](/docs/system/) shows), not from a new read of `/proc/cpuinfo`. The devices
are read one after the other in bus id order, which is the order of the nodes and links.

`TopologyGraph`:

| Field   | Type             | Description                  |
| ------- | ---------------- | ---------------------------- |
| `nodes` | `TopologyNode[]` | Devices.                     |
| `links` | `TopologyLink[]` | Connections between them.    |
| `at`    | number           | When it was read (epoch ms). |

### Nodes

`TopologyNode`:

| Field    | Type                                                     | Description                                                                                                                                           |
| -------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`     | string                                                   | `cpu`, `ram`, `pci:<busId>` (GPU, NVMe) or `chipset:<busId of the switch>`.                                                                           |
| `kind`   | `"cpu"` \| `"ram"` \| `"nvme"` \| `"gpu"` \| `"chipset"` |                                                                                                                                                       |
| `label`  | string                                                   | Display name: the CPU model shortened, `Memory`, the name from `pci.ids` (the bracketed name when there is one), the NVMe model, or the chipset name. |
| `busId`  | string                                                   | PCI address (`0000:01:00.0`), the same format as `GpuSample.busId` and the `hiddenGpus` setting. Missing for `cpu` and `ram`.                         |
| `vendor` | `"nvidia"` \| `"amd"` \| `"intel"` \| `"other"`          | GPUs and NVMe drives only.                                                                                                                            |
| `block`  | string                                                   | NVMe only: its block device (`nvme0n1`), the key of `DiskSample.perDisk` and `model.disk` in the [Snapshot](/developers/api/monitor/#disk).           |
| `detail` | `Record<string, string \| number \| null>`               | Static facts for the block and its details; null is unknown.                                                                                          |

What `detail` holds per kind:

| Kind      | Keys                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------- |
| `cpu`     | `model`, `physicalCores`, `logicalThreads`, `numaNodes`                                                   |
| `ram`     | `totalBytes`; `dimms` and `tempC`: the number of `spd5118` sensors (DDR5 modules) and the hottest reading |
| `nvme`    | `sizeBytes`                                                                                               |
| `gpu`     | none                                                                                                      |
| `chipset` | none                                                                                                      |

### Links

`TopologyLink`:

| Field      | Type                                   | Description                                                                                                                                |
| ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`       | string                                 | `cpu-ram`, `cpu-chipset:<busId>`, or `<from>-pci:<busId>`.                                                                                 |
| `from`     | string                                 | Node id on the CPU side (upstream).                                                                                                        |
| `to`       | string                                 | Node id downstream.                                                                                                                        |
| `kind`     | `"pcie"` \| `"memory"` \| `"internal"` | `memory` for `cpu-ram`; `internal` for a GPU inside the processor, or a link that reports no PCIe speed at all: its four figures are null. |
| `genMax`   | number \| null                         | Link capability: the lower of both ends' maximum generation.                                                                               |
| `widthMax` | number \| null                         | Link capability: the lower of both ends' maximum width.                                                                                    |
| `genCur`   | number \| null                         | Current generation.                                                                                                                        |
| `widthCur` | number \| null                         | Current width.                                                                                                                             |

For recent Radeon cards, which sit behind a PCIe switch on the card itself, the link is read at the card's upstream
port (`slotLink()`): the GPU's own link to that switch always reads its full width. A width outside 1 to 32 (a
suspended card can answer `0xFFFF` to a config read) is treated as unknown.

## The model placement

`ModelPlacement` comes from `llama-server`'s startup logs, since `llama-server` does not expose these figures through
its API (`parsePlacement()` in `app/server/monitor/placementLog.ts`). The tracker reads the log ring from the last
`[llama-webui] launch:` line: the `using device … (<busId>)` lines, the `… model|KV|RS|compute buffer size = N MiB`
lines and `offloaded N/M layers to GPU`. A second `offloaded` line opens the draft model and ends the reading of the
buffers; the projector's buffers and the fitting probes of `-fit` are skipped. NCCL's lines, written with
`NCCL_DEBUG=INFO`, are read over the whole launch: they give the PCI address of each CUDA device and say whether
peer-to-peer is in use. The sizes are only logged from `-lv 4` on, which
llama-webui adds to a profile that sets no verbosity.

`placement` is null when no server runs, while a model sleeps or a managed model wakes up, or before any placement is known. For a managed
server with `-lv 4` (the default), startup logs remain primary because they carry PCI `busId`s, layer counts and P2P
status. When startup buffer logs are absent (an external single-model server or a profile with `-lv < 4`), `Placement`
falls back to the `data.memory` report from `/models/sse` (`source: 'sse'`). It resolves local PCI `busId` values when
unambiguous. After ring eviction or sleep, the cached log placement can still be restored for the same PID.

| Field       | Type                                                     | Description                                                                                                  |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `launchSeq` | number                                                   | Sequence number of the `[llama-webui] launch:` log line it comes from (`0` for SSE fallback without logs).   |
| `layers`    | `{ offloaded, total }` \| null                           | From `offloaded N/M layers to GPU`; null until that line has gone by (or when read from `/models/sse`).      |
| `buffers`   | `PlacementBuffer[]`                                      | One per device that has buffers.                                                                             |
| `p2p`       | `'active'` \| `'unavailable'` \| `'requested'`, optional | Peer-to-peer between the GPUs of a backend, see below. Absent when neither requested nor reported.           |
| `source`    | `'logs'` \| `'sse'`, optional                            | Where the buffer breakdown came from (`'sse'` when derived from `/models/sse` `data.memory`; absent = logs). |

`PlacementBuffer`:

| Field          | Type             | Description                                                                                                                                                              |
| -------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `device`       | string           | ggml device name: `CUDA0`, `ROCm0`, `Vulkan1`, `CPU`, `CPU_Mapped`, `CUDA_Host`…                                                                                         |
| `busId`        | string \| null   | PCI address from the `using device` line, or from NCCL's `cudaDev N … busId X` for a CUDA device it does not cover (`-sm tensor`); null for the host or when not logged. |
| `modelBytes`   | number           | Weights on the device.                                                                                                                                                   |
| `kvBytes`      | number           | KV cache, plus the recurrent state (`RS`) of hybrid models.                                                                                                              |
| `computeBytes` | number           | Compute buffers, summed over the contexts (an MTP's adds to the model's); a context reserved again keeps only its last size.                                             |
| `estimated`    | `true`, optional | Spread from the `Meta()` buffers of `-sm tensor`, which only give the largest part: by `-ts`, equal parts without it. Absent otherwise.                                  |

`p2p` says what the logs tell about direct transfers between GPUs. What the driver allows between two cards is not
part of it: it comes with each card of the [snapshot](/developers/api/monitor/) (`p2p` of a GPU), and the Topology page
uses it to settle a `requested`.

| Value         | Read from                                                                                                                                                                                     |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `active`      | An NCCL line `Channel … via P2P/…`: a channel goes from GPU to GPU. Does not need `GGML_CUDA_P2P` (NCCL enables peer access itself).                                                          |
| `unavailable` | The launch set `GGML_CUDA_P2P` (llama-webui's own line, right after the launch line), and NCCL logs `P2P is disabled between connected GPUs` or a channel `via SHM/…`: the driver refuses it. |
| `requested`   | The launch set `GGML_CUDA_P2P` and NCCL says nothing (not built in, or without `NCCL_DEBUG=INFO`): llama.cpp enables peer-to-peer where the driver allows, silently.                          |

Every change is pushed as the `placement` message of the [WebSocket](/developers/api/websocket/), with the same
`ModelPlacement | null` payload.

## Helpers in shared

`packages/webui-shared/src/topology.ts` holds the pure logic the UI uses with this payload:

| Export              | What it does                                                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `hostDevice()`      | True for host-side (RAM) buffers: `CPU`, `CPU_*` (`CPU_Mapped`, `CPU_REPACK`…), `*_Host` and `Host` (`/models/sse`).           |
| `placementTotals()` | `modelBytes`, `gpuModelBytes` and `hostModelBytes` of a placement.                                                             |
| `phaseOf()`         | `stopped`, `loading`, `sleeping`, `idle`, `prompt` or `generating`, from the supervisor state and the latest snapshot's slots. |
| `pcieBps()`         | Payload capacity of a link per direction (bytes/s) from its generation and width; null if either is unknown.                   |
