llama-webui has one HTTP API. Its own web app uses it, and so can your scripts and integrations. The route table is
in `server/app.ts`, the routes themselves in `server/routes/` (one file per domain), the handler wrapper and errors in
`server/http.ts`, and the request guard in `server/security.ts`. Types and zod schemas come from `shared/src/`
(`@llama-webui/shared`).

## Base URL

One Bun process serves the API, the WebSocket and the web app on one address, `http://127.0.0.1:7860` by default
(`DEFAULT_HOST` and `DEFAULT_PORT` in `server/cli.ts`). `--host` and `--port`, or `LLAMA_WEBUI_HOST` and
`LLAMA_WEBUI_PORT`, change it: see [Launch options](/docs/configuration/).

- REST routes are under `/api/`.
- The WebSocket is `/ws`.
- Any other path serves the web app (the SPA fallback `/*`, so reloading `/chat` works).

There is no authentication and no API key: anyone who can reach the port can call every route. The examples on these
pages use `http://127.0.0.1:7860`.

## Channels

| Channel            | Where                                                                                        | Carries                                                                                                                        |
| ------------------ | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| REST               | `/api/*`                                                                                     | Reads and commands, JSON in and out.                                                                                           |
| WebSocket          | `/ws`                                                                                        | Events pushed by the server: monitor snapshots, log lines, server state, benchmark, sweep and download progress.              |
| Server-sent events | `POST /api/chat/:id/messages`, `POST /api/chat/:id/regenerate`, `GET /api/chat/:id/stream` | The events of a chat reply while it is generated (`event: <type>` then `data: <json>`, a `: ping` comment every 15 seconds). |

The WebSocket only sends `hello` when a client connects, then events as they happen. A client reads the current state
over REST and applies the messages on top of it: see [WebSocket](/developers/api/websocket/). The chat streams are
described on [Chat](/developers/api/chat/).

## The request guard

Every `/api/*` route and the `/ws` upgrade go through `guard()` (`server/security.ts`) before their handler runs. The
API is unauthenticated and local, so the guard protects it from other websites open in your browser. It does not
protect it from people on your network. It applies three checks, in this order:

| Check          | Rule                                                                                                                                      | Refusal                                                          |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `Host`         | The header (or the URL's host) parses, and its hostname is `localhost`, ends in `.localhost`, or is an IPv4 or IPv6 literal.             | `403` `Invalid host` or `403` `Host not allowed`                 |
| `Origin`       | When the header is present, it equals `<scheme>//<Host header>` exactly.                                                                  | `403` `Origin not allowed`                                       |
| `content-type` | For `POST`, `PUT`, `PATCH` and `DELETE`: a `content-type`, when sent, is `application/json` (parameters such as `; charset=utf-8` allowed), and a request with a body sends it. | `415` `JSON body expected (content-type: application/json)` |

- The `Host` rule stops DNS rebinding: a domain name can be made to resolve to `127.0.0.1`, an IP address cannot. The
  API therefore refuses requests addressed by host name, such as `http://myserver.lan:7860`.
- The `Origin` rule stops cross-site requests, a WebSocket opened by another site included. `curl` and most
  non-browser clients send no `Origin`, so they pass.
- The `content-type` rule stops "simple request" CSRF: another site can make the browser post a form or a plain-text
  body without asking, but `application/json` needs a CORS preflight, which llama-webui never grants. A write without
  a body and without a `content-type` passes (`curl -X POST http://127.0.0.1:7860/api/server/stop`).

A refusal has the usual error shape, without a `code`:

```bash title="Terminal"
curl -i http://127.0.0.1:7860/api/health -H 'Origin: http://example.com'
```

```text
HTTP/1.1 403 Forbidden
content-type: application/json;charset=utf-8

{"error":"Origin not allowed"}
```

The API sends no CORS headers either, so a browser does not let another site read its responses. The reasons behind
each rule are on [Security](/developers/server/security/), and the user-facing summary on
[Security](/docs/security/).

## Errors

Every `/api/*` error is a JSON object with an `error` message, and a `code` when the route sets one:

```json
{ "error": "A profile named “Qwen3 32B” already exists", "code": "name-taken" }
```

`guarded()` catches whatever a handler throws and turns it into a response with `errorResponse()`
(`server/http.ts`):

| Thrown                                           | Status         | Body                                                     |
| ------------------------------------------------ | -------------- | -------------------------------------------------------- |
| `HttpError(status, message, code?)`              | `status`       | `{ error: message }`, plus `code` when there is one       |
| `ZodError` (a schema refused the input)          | `400`          | `{ error: "Invalid data: <first issue> (<path>)", issues }` |
| `SyntaxError` (the body is not valid JSON)       | `400`          | `{ error: "Invalid JSON" }`                              |
| Anything else                                    | `500`          | `{ error: "Internal error" }`, and the error is logged on the server console |

Match on the status and the `code`, never on the `error` text: messages are written for people and can change. The
web app follows the same rule (`ApiError` in `web/src/lib/api.ts` keeps `status`, `issues` and `code`).

### Validation errors

When a zod schema refuses a body, the response is a `400` with the first issue in `error` (its path in parentheses,
when it has one) and every issue in `issues`, as zod reports them (`code`, `path`, `message`, and the fields specific to
the issue):

```json
{
  "error": "Invalid data: Expected a number (port)",
  "issues": [{ "expected": "number", "code": "invalid_type", "path": ["port"], "message": "Expected a number" }]
}
```

This one comes from `PATCH /api/settings` with `{"port":"abc"}`. The web app shows each issue under the field its
`path` names.

### Error codes

A few refusals carry a machine-readable `code`:

| `code`                                                                       | Status            | When                                                                                                               |
| ---------------------------------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| `name-taken`                                                                 | `409`             | Creating or renaming a profile with a name another profile has ([Profiles](/developers/api/profiles/)).           |
| `server-running`                                                             | `409`             | Starting a benchmark or a sweep while `llama-server` runs, without `stopServer` ([Benchmarks](/developers/api/bench/)). |
| `hf-gated`, `hf-not-found`, `hf-unauthorized`, `hf-rate-limited`, `hf-unreachable` | `403`, `404`, `401`, `429`, `502` | Hugging Face refused or failed a request ([Hugging Face](/developers/api/hf/)).                                    |
| `already-queued`, `not-finished`                                             | `409`             | Queueing a download that is already queued, retrying one that has not failed or been canceled ([Hugging Face](/developers/api/hf/)). |
| `disk-full`                                                                  | `507`             | Queueing or retrying a download that does not fit on the disk ([Hugging Face](/developers/api/hf/)).              |

Every other error has no `code`.

## Status codes

| Status | Meaning in this API                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `200`  | Success, with a JSON body.                                                                                                                              |
| `201`  | A resource was created (profile, duplicate, conversation, profile from a benchmark run); the body is the new resource.                                 |
| `202`  | The operation started and goes on in the background (server start, switch and restart, benchmark run, sweep, download); follow it over the WebSocket. |
| `204`  | Success without a body (deletions, cancellations, a chat stream with no reply in progress).                                                            |
| `400`  | Invalid body, JSON or query parameter.                                                                                                                  |
| `401`  | Hugging Face rejected the token (`hf-unauthorized`).                                                                                                    |
| `403`  | Refused by the guard (`Host`, `Origin`), or a gated Hugging Face repository.                                                                           |
| `404`  | Unknown route, unknown id, or missing file.                                                                                                             |
| `405`  | A known path called with a method it does not define; the `Allow` header lists the ones it does.                                                       |
| `409`  | The request conflicts with the current state: a name is taken, an operation is in progress, a benchmark holds the GPUs, a server is running…           |
| `415`  | Refused by the guard: a write that is not `application/json`.                                                                                           |
| `422`  | The file exists but cannot be read as a GGUF.                                                                                                           |
| `426`  | `/ws` requested without a WebSocket upgrade (plain-text body `WebSocket upgrade expected`).                                                            |
| `429`  | Hugging Face rate limit reached (`hf-rate-limited`).                                                                                                    |
| `500`  | An unexpected exception (`Internal error`).                                                                                                             |
| `502`  | An upstream service failed: `llama-server` (`/props`) or Hugging Face.                                                                                  |
| `503`  | `llama-server --help` failed (`/api/flags`).                                                                                                            |
| `507`  | Not enough disk space for a download.                                                                                                                   |

## How routes are registered

`createApp()` in `server/app.ts` starts a single `Bun.serve()` with a `routes` table. Each domain module in
`server/routes/` exports a function that takes its dependencies and returns its part of the table,
`{ path: { METHOD: handler } }`, and every handler is wrapped in `guarded()`:

```ts title="server/routes/models.ts"
export function modelRoutes({ db, settings }: { db: Database; settings: SettingsRepo }) {
  // …
  return {
    '/api/models': {
      GET: guarded(async () => {
        // …
        return Response.json(list);
      }),
    },
```

`createApp()` defines the health route itself, spreads the domain tables (the settings ones from
`server/routes/settings.ts`), then adds the catch-alls, all wrapped in `withMethodNotAllowed()`:

```ts title="server/app.ts"
      ...setupRoutes(deps),
      '/api/*': guarded(() => Response.json({ error: 'Unknown route' }, { status: 404 })),
      '/ws': guarded((req, server) => {
        if (server.upgrade(req)) return undefined;
        return new Response('WebSocket upgrade expected', { status: 426 });
      }),
      // Any other path serves the app (SPA fallback `/*`: reloading /chat works).
      ...deps.web,
```

- An unknown path under `/api/` gets `404` `{ "error": "Unknown route" }`.
- A known path called with a method it does not define gets `405` `{ "error": "Method not allowed (POST)" }` with
  `Allow: POST`. Without it, Bun would fall through to the next route that matches the path: `GET
  /api/profiles/import` would reach `/api/profiles/:id` and answer `Profile not found`. `withMethodNotAllowed()`
  (`server/http.ts`) fills in a guarded `405` handler for each missing `GET`, `POST`, `PUT`, `PATCH` and `DELETE` of
  every `/api/…` route defined by methods.
- Path parameters are read with `idParam(req, what)`: anything but a positive integer gives `404` `<what> not found`,
  the same answer as an id that does not exist.
- A body that must be an object is read with `jsonObject(req)`: valid JSON that is not an object gives `400`
  `JSON object expected`.
- `notFound(what)` is the shared `404` `<what> not found`.

To add a route, see [How-to guides](/developers/contributing/how-to/).

## Conventions

- **JSON everywhere.** Bodies are JSON, sent with `content-type: application/json`. Responses are JSON, except a `204`
  (no body), the chat event streams (`text/event-stream`), the profile exports (a JSON file sent as an attachment) and
  the `426` of `/ws` (plain text).
- **Ids** are SQLite integer ids (`id INTEGER PRIMARY KEY`), positive integers in paths (`/api/profiles/3`).
- **Times** are epoch milliseconds, from `Date.now()`: `createdAt`, `updatedAt`, `finishedAt`, `since`, `at`,
  `scannedAt`, `serverTime`.
- **Durations** carry their unit in their name: `uptimeMs`, `durationMs` and `pollIntervalMs` are milliseconds,
  `historySeconds` is seconds, `promptSec` and `genSec` are seconds.
- **Sizes** are bytes, named `…Bytes` (`fileBytes`, `vramBytes`, `rssBytes`), and rates are bytes per second, named
  `…Bps` (`readBps`, `diskReadPeakBps`). The exceptions are in MiB and say so: `BenchDevice.totalMib` and
  `BenchDevice.freeMib` (as `llama-bench --list-devices` reports them) and `BenchRun.vramPeak[].mib`.
- **`null` and absent fields.** A field typed `T | null` is always present, and `null` means unknown, not applicable
  or not set (`SetupReport.binary.path`, `ServerView.command`, `LaunchpadEntry.fit`). A field typed `field?: T` is left
  out when it has no value, never sent as `null`: the optional fields of a profile (`mmproj`, `cwd`, `host`, `port`),
  `Flag.value` for a switch, `error` in the llama-tui check when the file reads fine. A few monitor fields accept both
  (`GpuSample.fanPct?: number | null`): missing or `null` both mean unknown.
- **Paths** are absolute paths on the machine that runs llama-webui. The server expands `~` in the models folder
  setting and in a profile's `model`, `mmproj` and `cwd`.
