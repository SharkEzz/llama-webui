# N9 — NVML on `node:ffi`: task plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** NVIDIA monitoring reads NVML again, on Node: `node:ffi` in a `node:worker_threads` worker, in development
(`.ts` worker under native type stripping) and in production (`dist/server/nvml-worker.js`), with nvidia-smi as the
fallback when NVML cannot start; `@types/bun` leaves the app's projects.

**Architecture:** the worker protocol and `NvmlMonitor` stay as they are (`start` / `configure` / `ready` / `error` /
`sample`, freshness, `WorkerLike`); only the binding (`bun:ffi` → `node:ffi`, handles `number` → `bigint`) and the
worker host (`Worker` global → `node:worker_threads`, adapted to `WorkerLike`) change. The worker is built by its own
Vite environment (`nvml`, build only) into `dist/server/`, because Rolldown refuses a second input when
`codeSplitting` is `false` (measured: `INVALID_OPTION … multiple inputs are not supported`).

**Tech Stack:** Node 26.13 (`node:ffi`, experimental, no flag; `--disable-warning=ExperimentalWarning` in the worker's
`execArgv`), `@types/node` 26.6.6 (typed `dlopen`), Vite 8.3.8 environments.

**Spec:** [`2026-11-12-node-migration.md`](./2026-11-12-node-migration.md), section N9; spike N0(b) (`6af73b0`,
`server/spike/nvml/`), N0(d).

## Findings that shape this plan (read on this tree, 2026-11-12)

- Bun is left only in comments of `server/` (`proc.ts`, `db/sqlite.ts`: parity notes, they stay) and in
  `server/collectors/nvml/{symbols,worker,monitor}.ts`. `scripts/` uses no `Bun.*`.
- `web` already has no `types` (DOM only, `env.d.ts` declares `import.meta.hot`) since N8: the plan's "`vite/client`
  only" is not needed.
- `@types/node` is a dependency of `web` and `llamacpp-js` only; `server`, `scripts`, `packages/webui-shared` resolve
  their types from the root `node_modules/@types`, which has only `bun`.
- `LLAMA_WEBUI_NVIDIA_SMI` (registry) already exists "to test the tool missing" and is documented in
  `developers/getting-started.mdx` and `developers/server/monitor.mdx`.
- The worker graph: `worker.ts` → `read.ts`, `symbols.ts`, `../needs.ts`; `read.ts` → `../gpu.ts`, `../needs.ts`;
  `gpu.ts` imports only a type from `@llama-webui/shared` (erased).

## Global Constraints

- Behaviour-identical: same readings, same fallback rule (NVML unusable → `null` → nvidia-smi), same protocol;
  `server/contract/golden.json` byte-identical.
- Biome zero errors / zero warnings; `pnpm lint`, `pnpm check`, `pnpm test`, `pnpm build`, `node scripts/smoke.ts`.
- English for code, comments, tests, commits; docs in sync (CLAUDE.md mapping table).
- Ports 7860/7861 belong to the user; manual runs on 7862, `http://192.168.0.20:7862`.

## Review Focus

- NVML present but `nvmlInit_v2` fails (driver mismatch): the worker posts `error`, the monitor resolves `null`,
  nvidia-smi takes over (covered by the broken-path test: same `error` path).
- The worker throws at load (bad import in the bundle): `error` event → `null`, not a hang (the 3 s ready timeout
  bounds it).
- `stop()` while the worker is mid-call: `terminate()` returns a promise on Node, nothing awaits it; the process must
  still exit (worker `unref`).
- A handle above 2^53: kept as `bigint` end to end, never `Number()`.
- Production: `main.js` resolves `nvml-worker.js` next to itself, not `worker.ts`.

### Task 2: NVML on `node:ffi` and `node:worker_threads`

**Files:** `server/collectors/nvml/{symbols,read,worker,monitor,monitor.test}.ts`, `server/collectors/{gpu,needs}.ts`
(import extensions only), `server/collectors/registry.ts`.

**Interfaces:**

- `openNvml(path?: string): NvmlSymbols` — `dlopen(path, defs).functions`, assigned to `NvmlSymbols` without a cast
  (the typed `dlopen` checks the interface against the definitions); handles `bigint`, out-params `'buffer'`.
- `deviceHandles(lib): bigint[]`, `readNvml(lib, handles: bigint[], filter)`.
- Worker messages unchanged, plus an optional `lib?: string` in `start` (library path; absent → `libnvidia-ml.so.1`).
- `workerUrl(moduleUrl = import.meta.url): string` — `./worker.ts` next to a `.ts` module, `./nvml-worker.js` next
  to a bundle.
- `NvmlMonitor.start({ …, lib?: string })` passes it to the worker; the registry passes
  `process.env.LLAMA_WEBUI_NVML_LIB || undefined` (to test NVML missing, like `LLAMA_WEBUI_NVIDIA_SMI`).

- [ ] Tests first (`server/collectors/nvml/monitor.test.ts`):
  - `workerUrl: worker.ts next to the module in development, nvml-worker.js next to the bundle` —
    `workerUrl('file:///x/server/collectors/nvml/monitor.ts')` → `file:///x/server/collectors/nvml/worker.ts`;
    `workerUrl('file:///x/dist/server/main.js')` → `file:///x/dist/server/nvml-worker.js`; the default exists on disk.
  - `a real worker with a missing NVML library resolves null (the nvidia-smi fallback)` —
    `NvmlMonitor.start({ intervalMs: 1000, lib: '/nonexistent/libnvidia-ml.so.1' })` → `null`, in well under the
    3 s timeout (the `error` message, not the timer).
  - `a real worker reads NVML when the library is here` — skipped unless `libnvidia-ml.so.1` opens: `start` resolves
    a monitor, a sample arrives within 3 s, every GPU has a `key` starting `nvidia:GPU-` and a `busId`; `stop()`.
- [ ] Run → Expected: the two real-worker tests fail (no `Worker` global: `null` for the wrong reason is possible for
      the first one — check it fails on timing or passes only after the port; the third fails), `workerUrl` fails.
- [ ] Port: `symbols.ts` (spike), `read.ts` (`bigint`), `worker.ts` (`parentPort`, `.ts` imports, `lib`), `gpu.ts` /
      `needs.ts` relative imports with `.ts`; `monitor.ts`: `defaultWorker` = `new Worker(new URL(workerUrl()), {
  execArgv: ['--disable-warning=ExperimentalWarning'] })`, `unref()`, `message` → `onmessage({ data })`, `error` →
      `onerror(err)`, `terminate()` with its promise ignored (`void`).
- [ ] Run → Expected: all pass on this machine (2 GPUs), the NVML test skipped in CI.
