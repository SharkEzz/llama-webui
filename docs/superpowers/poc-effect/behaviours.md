# Behaviours of the Nitro server

The checklist of E0: what each milestone of the Effect rewrite (E1 to E8) brings back, read from the Nitro server as it
stands at commit 6327201a3 (`app/server/`, `app/bin/`, `app/build/` and `packages/`). Each later plan copies its
acceptance list from its section. Every item names the file it was read from; "Not covered by a test" lists what no
entry of `test-inventory.json` exercises.

## E1: Foundation

Closed by E1 (commits up to `chore(poc): Close E1`). Each line is ticked with what proves it (a test, the contract
record `app/server/contract/golden.json`, or a run of the build), struck with `dropped: <reason>`, or moved to its
milestone. A line that changed with the Effect server says how it behaves now.

## E2: Profiles

### Endpoints

- [ ] `GET /api/profiles`: returns every profile as an array sorted by name case-insensitively (`ORDER BY name COLLATE NOCASE`), each `{ id, name, model, args, env, source, createdAt, updatedAt }` plus `mmproj`, `cwd`, `host`, `port` only when stored non-NULL, `createdAt`/`updatedAt` in epoch milliseconds; errors: none (`app/server/routes/api/profiles/index.get.ts`, `app/server/lib/db/profiles.ts`).
- [ ] `POST /api/profiles`: reads the body with `req.json()` (no `readBody`, so a non-object is a zod error, never `JSON object expected`), validates it with `ProfileInputSchema` (strict object: `name` and `model` non-empty strings, optional `mmproj`/`cwd`/`host` strings, optional integer `port` 1 to 65535, `args` string array defaulting to `[]` where no item may be a reserved flag `--host`, `--port`, `--metrics`, `--slots`, `--props`, `-m`, `--model`, `-mm`, `--mmproj` alone or in `--flag=value` form, `env` string-to-string record defaulting to `{}`, unknown keys refused), inserts it with `source: 'ui'` and `createdAt = updatedAt = now`, and answers 201 with the stored profile; errors: 400 `Invalid JSON` (empty or malformed body); 400 `Invalid data: <first issue> (<path>)` with `issues` (schema, e.g. `cannot be empty (name)`, `required (model)`, `port between 1 and 65535 (port)`, `<flag> is managed by llama-webui (use the profile fields) (args.<i>)`, `Invalid input: expected object, received array` for a non-object); 409 `A profile named “<name>” already exists` (code `name-taken`, exact case-sensitive name match) (`app/server/routes/api/profiles/index.post.ts`, `app/server/lib/db/profiles.ts`, `packages/webui-shared/src/profile.ts`).
- [ ] `GET /api/profiles/export`: answers 200 a JSON attachment `{ profiles: [...] }` of every profile in list order in import format (id, source and dates stripped, optional fields only when set), indented by 2 spaces with a trailing newline, `content-type: application/json` and `content-disposition: attachment; filename*=UTF-8''llama-webui-profiles.json`; errors: none (`app/server/routes/api/profiles/export.get.ts`, `app/server/lib/http.ts`, `app/server/lib/db/profiles.ts`).
- [ ] `POST /api/profiles/import`: reads any JSON value (body passed as sent), accepts a whole llama-tui config `{ profiles: [...] }` (other keys ignored), an array of profiles or a single profile object (one with a `name` or `model` key), validates each item on its own with `ProfileInputSchema`, keeps the first of two items with the same name, inserts the valid ones whose name is not already taken with `source: 'import'` in one transaction (never overwriting), and answers 200 `{ imported: Profile[], skipped: { name, reason }[] }` with the parse rejections first (`(file)` / `no profile found in this JSON` when no profile shape is found, `<name or (unnamed)>` / `<first zod message> (<path>)` for an invalid item, `duplicate name in the file`) then the `already exists` skips; errors: 400 `Invalid JSON` (empty or malformed body), a JSON value of the wrong shape is a 200 with its rejection, not a 400 (`app/server/routes/api/profiles/import/index.post.ts`, `packages/webui-shared/src/profile.ts`, `app/server/lib/db/profiles.ts`).
- [ ] `GET /api/profiles/import/llama-tui`: reads the llama-tui config file (`$XDG_CONFIG_HOME/llama-tui/config.json`, else `$HOME/.config/llama-tui/config.json`, else `os.homedir()`) and answers 200 `{ path, exists, names, error?, dismissed, profileCount }` where `names` are the valid profile names it would import, `exists` is false for a missing file or a directory, `error` is `Invalid JSON: <message>` when the file cannot be read or parsed (omitted otherwise), `dismissed` is the `llamaTuiImportDismissed` setting and `profileCount` the number of profiles in the database; errors: none (`app/server/routes/api/profiles/import/llama-tui.get.ts`, `app/server/lib/llamatui.ts`).

## E3: Supervisor

### Endpoints

- [ ] `GET /api/server/state`: answers the `ServerView` `{ state, command, profileId }` of the supervisor, where `state` is the `ServerState` union (`idle`; `starting` and `ready` with `profile`, `profileId`, `pid`, `host`, `port`, `since`; `stopping` with the same fields but no `since`; `crashed` with `profile`, `profileId`, `exitCode`, `signal`, `at` and an optional `message`; `external` with `pid` (or null) and `port`), `command` is the shell-quoted display of the last launched command (without the `setpriv` prefix, kept after a stop, null before any launch) and `profileId` is the state's profile, else the last command's, else null; errors: none (`app/server/routes/api/server/state.get.ts`, `app/server/lib/runtime.ts`, `packages/webui-shared/src/server.ts`).
- [ ] `POST /api/server/start`: reads a JSON object body `{ profileId }` (coerced with `Number()`, so `"1"` and `true` both select profile 1), rebuilds the profile's launch command from the database and the settings, launches llama-server through the supervisor, sets the `defaultProfileId` setting to that profile when it differs, and answers 202 with the `ServerView` (state `starting`, or `crashed` with a `message` when the launch itself failed, which is still a 202 and still remembers the profile); errors: 400 `Invalid JSON` (empty or malformed body), 400 `JSON object expected` (not an object), 404 `Profile not found` (missing, non-integer or unknown `profileId`, checked before the benchmark), 409 `A benchmark is running` (bench runner busy), 409 `operation in progress, try again` (another start, switch, restart or stop is running), 409 `a server is already running` (a managed llama-server process exists), 409 `port in use by an external server (PID <pid or unknown>)` (a llama-server not started by llama-webui answers on the profile's port, or the detected external server still answers), 409 `port <port> is in use by another service` (a service that is not llama-server answers HTTP on `/health` of that port) (`app/server/routes/api/server/start.post.ts`, `app/server/lib/supervisor/control.ts`, `app/server/lib/supervisor/supervisor.ts`).
- [ ] `POST /api/server/switch`: same body, coercion and 202 reply as the start route, but in one exclusive supervisor operation it first stops the managed llama-server (SIGTERM, SIGKILL after 5 s) and then launches the given profile, and sets `defaultProfileId` to it when it differs; errors: 400 `Invalid JSON`, 400 `JSON object expected`, 404 `Profile not found`, 409 `A benchmark is running`, 409 `operation in progress, try again`, 409 `port in use by an external server (PID <pid or unknown>)`, 409 `port <port> is in use by another service` (the last two after the old server was already stopped) (`app/server/routes/api/server/switch.post.ts`, `app/server/lib/supervisor/control.ts`, `app/server/lib/supervisor/supervisor.ts`).
- [ ] `POST /api/server/restart`: reads no body, takes the profile of the current state or else of the last launched command (so it works after a stop, after a crash, or in the external state once something was launched), rebuilds that profile's command from the database (profile edits apply), runs the same stop-then-launch operation as the switch route and answers 202 with the `ServerView`, without touching `defaultProfileId`; errors: 409 `No profile to restart` (neither the state nor a last command has a profile), 404 `Profile not found` (that profile was deleted), 409 `A benchmark is running`, 409 `operation in progress, try again`, 409 `port in use by an external server (PID <pid or unknown>)`, 409 `port <port> is in use by another service` (`app/server/routes/api/server/restart.post.ts`, `app/server/lib/supervisor/control.ts`, `app/server/lib/runtime.ts`).
- [ ] `POST /api/server/stop`: reads no body, waits for any lifecycle operation in progress (it never refuses one), then stops the managed llama-server (state `stopping`, SIGTERM, SIGKILL after 5 s, state `idle` once it exited) or, with no process, turns a `crashed` state into `idle`, never touching an external server (an `external` state stays), and answers 200 with the `ServerView` after the process has exited (the last `command` and `profileId` are kept); errors: 409 `A benchmark is running` (`app/server/routes/api/server/stop.post.ts`, `app/server/lib/supervisor/control.ts`, `app/server/lib/supervisor/supervisor.ts`).
- [ ] `GET /api/server/props`: in the `ready` or `external` state, fetches llama-server's `/props` (2 s timeout, Node's global `fetch`) on the state's host (loopback for a wildcard address and for an external server) and answers its JSON untouched (the web narrows it with `isRecord`/`serverPropsOf` of `app/src/lib/props.ts`, keeping `model_path` and `default_generation_settings.n_ctx`/`params` only when they have the right type); errors: 409 `Server not ready` (any other state, `starting` included), 502 `llama-server /props: HTTP <status>` (an error status), 502 `llama-server /props: the reply is not JSON`, 502 `llama-server is not responding on /props` (no connection or timeout) (`app/server/routes/api/server/props.get.ts`, `packages/llamacpp-js/src/client.ts`).
- [ ] `GET /api/state`: answers `{ server, logSeq, bootId }`, the `ServerView`, the number of the next log line and this boot's id, the snapshot the web reads on (re)connection; errors: none (`app/server/routes/api/state.get.ts`).
- [ ] `GET /api/logs`: answers `{ lines, seq, bootId }` with the ring's lines still in memory whose number is at least the `since` query (0 when absent or not a finite number; a negative value returns the whole ring), the next line number and the boot id; errors: none (`app/server/routes/api/logs.get.ts`, `app/server/lib/logs/buffer.ts`).
- [ ] `GET /api/launchpad`: answers one entry per profile (in `profiles.list()` order) with `profileId`, `name`, `modelPath` (absolute, `~` expanded, relative paths from the profile's cwd), `model` (`name`, `quant`, `fileBytes` from the GGUF), `modelError` (`Expected an absolute path to a .gguf file`, `Model not found`, `Projector not found` or the GGUF reader's message, with `model` and `fit` then null), `lastBench` (`ppTps`, `tgTps`, `at` of the profile's latest successful one-off run, sweep items excluded, else null) and `fit` (`verdict`, `reason`, `vramBytes` summed over the cards, `ramBytes`, from the `fit`-preset estimate with the profile's pinned args and context, null when the estimate fails or when llama-bench lists no device while the monitor sees GPUs), the tuning hardware being read once per request from the llama-bench next to the `binary` setting and the monitor's latest memory and GPUs; errors: none (`app/server/routes/api/launchpad.get.ts`, `app/server/lib/setup.ts`, `app/server/lib/tuning/models.ts`, `app/server/lib/db/benchRuns.ts`).

### WebSocket messages

- [ ] `server-state`: broadcast to every connected client on each supervisor state change (every internal `set()`: launch, ready, stopping, idle, crash, launch failure, external server detected at start or by the watch, external server gone), synchronously and unthrottled, with the `ServerView` `{ state, command, profileId }` as payload; it is not sent on connect (a client gets `hello` and reads `GET /api/state`) (`app/server/lib/boot.ts`, `app/server/lib/supervisor/supervisor.ts`).
- [ ] `log`: broadcast with a batch of new `LogLine` `{ seq, text, level, kind }`, one message for all the lines pushed to the ring within one microtask, whoever pushed them (llama-server's stdout and stderr, the supervisor's `[llama-webui]` lines, the bench's `[bench]` lines); the web merges batches by `seq` (deduplicated, sorted, capped, `mergeLogs`) and starts over on another `bootId` (`onBoot`, hiding reset) (`app/server/lib/boot.ts`, `app/server/lib/logs/buffer.ts`, `packages/webui-shared/src/logs.ts`).

### Startup and shutdown

- [ ] `createRuntime()` builds the supervisor in the `idle` state, the log ring of 10 000 lines numbered from 0, a new random UUID `bootId` per boot and the bench gate; no llama-server is launched at boot, not even the `defaultProfileId` one (`app/server/lib/runtime.ts`).
- [ ] `boot()` subscribes the `server-state` and `log` broadcasts, runs the external-server check once at startup, then every 2 s (`app/server/lib/boot.ts`).
- [ ] `boot()` registers `supervisor.stop()` on its stack right after opening the database, so at shutdown it runs after the external-watch interval is cleared and after chat runs, bench runner, downloads, WebSocket hub (1001), placement and monitor are undone, and before the database closes: llama-server gets SIGTERM, then SIGKILL after 5 s (`app/server/lib/boot.ts`, `app/server/lib/supervisor/supervisor.ts`).
- [ ] `stop()` of the runtime logs `[llama-webui] stopping llama-server…` to the console when a managed llama-server is alive, then disposes the stack once (a later call waits for the same undo) (`app/server/lib/context.ts`).
- [ ] A `process.on('exit')` handler, registered once per process, synchronously SIGKILLs the live runtime's managed llama-server (and clears its health poll) as a last resort when the process exits without its stack, e.g. on an uncaught error (`app/server/lib/context.ts`, `app/server/lib/supervisor/supervisor.ts`).
- [ ] Every launch runs llama-server under `setpriv --pdeathsig KILL --`, so the kernel kills it when its parent dies (`app/server/lib/supervisor/args.ts`).
- [ ] In dev, saving a route file keeps the runtime and llama-server (same `bootId`), while saving business code disposes the runtime (llama-server stopped) and builds a new one with a new `bootId` and a log ring starting from 0 (`app/server/lib/context.ts`).

- [ ] From E1: no llama-server is left alive by a stop of the app: SIGTERM of the build with the UI open (the half of `SIGTERM with the UI open and a reply streaming stops in under 2 s`), one SIGINT of `vite dev`, two quick SIGINTs, and a save of a server file in dev (the halves of the `dev.test.ts` tests that named llama-server, rewritten in E1 without it) (`app/server/lifecycle.test.ts`, `app/server/dev.test.ts`).

### Background work

- [ ] llama-server is a child process started by `spawnProc(argv, { cwd, env })` with stdin ignored and stdout and stderr piped, `argv` being `setpriv --pdeathsig KILL -- <binary> -m <model> [-mm <mmproj>] <profile args> [-lv 4] --host <host> --port <port> --metrics --slots --props`, with `~` expanded in the binary, model, mmproj and cwd (relative paths stay relative to the cwd), the profile's `host`/`port` winning over the settings', and `-lv 4` added unless the profile args hold `-lv`, `--verbosity`, `--log-verbosity`, `-v`, `--verbose` or `--log-verbose` (with or without `=value`) (`app/server/lib/supervisor/args.ts`, `app/server/lib/supervisor/supervisor.ts`).
- [ ] Before a launch the supervisor probes `/health` of the profile's port on its host (800 ms): any HTTP answer means the port is taken (a llama-server there sets the state `external` with its pid before the 409, any other service is a plain 409); the last command is then recorded, a missing cwd ends in state `crashed` with message `directory not found: <cwd>` and a spawn failure in `crashed` with `spawn <binary> ENOENT|EACCES|UNKNOWN`, both with the ring line `[llama-webui] launch failed: <message>` (`app/server/lib/supervisor/supervisor.ts`, `app/server/lib/proc.ts`).
- [ ] After a spawn the supervisor writes `[llama-webui] launch: <display>` to the ring, plus `[llama-webui] GGML_CUDA_P2P is set: direct transfers between GPUs requested` when the launch environment has `GGML_CUDA_P2P` (whatever its value, empty included), then sets the state `starting` with the pid and `since` (`app/server/lib/supervisor/supervisor.ts`, `app/server/lib/supervisor/args.ts`).
- [ ] llama-server's stdout and stderr are split into lines across chunks, ANSI escape sequences, a trailing `\r` and trailing whitespace removed, empty lines dropped, lines ending in `update_slots: all slots are idle` dropped (the `-lv 4` idle-loop noise), and the last partial line flushed when the stream ends (`app/server/lib/supervisor/supervisor.ts`, `app/server/lib/logs/lines.ts`).
- [ ] While `starting`, a `setInterval` every 500 ms probes `/health` (800 ms timeout) on the host llama-server listens on (loopback for `0.0.0.0`, `::1` for `::`, a specific address as is, #28): a 200 sets `ready` with a new `since` and clears the interval, a 503 or no answer keeps polling with no deadline (`app/server/lib/supervisor/supervisor.ts`, `packages/llamacpp-js/src/client.ts`).
- [ ] When llama-server exits, the supervisor clears the health poll, writes `[llama-webui] llama-server exited (code <code or ->[, <signal>])` to the ring and sets `idle` if it was stopping, otherwise `crashed` with `exitCode`, `signal` and `at` (`app/server/lib/supervisor/supervisor.ts`).
- [ ] A stop sets `stopping` (from `starting` or `ready`), sends SIGTERM, waits up to 5 s on an unref'd timer (no timer outlives the stop), then writes `[llama-webui] not stopped after 5000 ms, SIGKILL`, sends SIGKILL and waits for the exit (`app/server/lib/supervisor/supervisor.ts`).
- [ ] The supervisor runs one lifecycle operation at a time: start, switch and restart are refused while one runs, a stop waits for the running one, and the bench gate's stop and restart go through the same lock (`app/server/lib/supervisor/supervisor.ts`).
- [ ] The external-server watch runs at boot and every 2000 ms (`setInterval`, cleared first at shutdown), skips a tick while the previous check still runs or while the bench gate is held or the bench runner is busy, and in `idle` or `crashed` probes the settings port then the last command's port (deduplicated, missing ones dropped, stopping at the first detection), or in `external` rechecks that server (`app/server/lib/supervisor/external.ts`, `app/server/lib/boot.ts`).
- [ ] External detection needs no managed process and a `/health` on loopback answering JSON with a string `status` or an `error.type` of `unavailable_error`, and the state still `idle` or `crashed` after the probe; it then sets `external` with the port and the pid of the first `/proc` process whose `argv[0]` is named `llama-server` with that `--port` (8080 when it has none), or null (`app/server/lib/supervisor/supervisor.ts`, `packages/llamacpp-js/src/client.ts`, `packages/llamacpp-js/src/node.ts`).
- [ ] The external recheck keeps the `external` state while its known pid is alive (signal 0), even if the port is silent (a hung server), and otherwise sets `idle` once `/health` on loopback gets no answer and the state has not changed meanwhile (`app/server/lib/supervisor/supervisor.ts`).
- [ ] The bench gate (owned by E7) relies on the supervisor's `state`, `lastCommand`, `stop()` and `start()`: it stops the managed server for a benchmark (ring line `[bench] stopping llama-server for the benchmark`), refuses with 409 while an external server runs, and restarts the stopped server afterwards with the command rebuilt from the profile, through `start()` (so without updating `defaultProfileId`) (`app/server/lib/bench/gate.ts`, `app/server/lib/deps.ts`).
- [ ] The launchpad's logic, `buildLaunchpad()`, lives in `app/server/lib/setup.ts`, an E8 file, and so does its hardware read `readTuningHardware()` (`app/server/lib/tuning/hardware.ts`); it builds one entry per profile, independently and in parallel (a model that cannot be read only sets `modelError`, a failed estimate only drops `fit`); its two tests in `app/server/lib/setup.test.ts` are filed under E8 in the inventory, but E3 owns the route and must keep them green (`app/server/lib/setup.ts`, `app/server/routes/api/launchpad.get.ts`).
- [ ] `activeProfileId()` (used by other domains through `deps`) is the profile of the managed server while `starting`, `ready` or `stopping`, and null when idle, after a crash or for an external server (`app/server/lib/runtime.ts`).
- [ ] `llamaFetch` (used by chat and bench, not by the supervisor, whose probes and `/props` use Node's global `fetch`) is a `fetch` over `node:http`/`node:https` without Node's 300 s limits (no limit for response headers or between body chunks, the caller's signal is the only timeout), with its own connection per request and no proxy (`agent: false`), never following a redirect (the 3xx is the response) (`app/server/lib/llamaFetch.ts`).

## E4: Monitoring

### Endpoints

- [ ] `GET /api/monitor/history`: returns the in-memory history dump `{ intervalMs, capacity, at, times, series, bootId }` (one value per tick, oldest first, `times` the tick timestamps, every series left-padded with `null` to the length of `times`, NaN gaps as `null`, `at` the last tick time or `Date.now()` when empty, `bootId` of this process), and with the stub monitor `{ intervalMs: 1000, capacity: 0, at: 0, times: [], series: {} }` plus `bootId`; errors: none (`app/server/routes/api/monitor/history.get.ts`, `app/server/lib/monitor/history.ts`, `app/server/lib/testing/stubMonitor.ts`).
- [ ] `GET /api/monitor/snapshot`: returns the last tick's `Snapshot` (the same object the `snapshot` WebSocket message carries), or JSON `null` before the first tick has finished and always with the stub monitor; errors: none (`app/server/routes/api/monitor/snapshot.get.ts`, `app/server/lib/monitor/monitor.ts`).
- [ ] `GET /api/system/info`: returns `{ cpu, gpus, nvidiaSource }` where `cpu` is the `CpuInfo` read from `/proc/cpuinfo` and `/sys/devices/system/node` (model, distinct physical cores at least 1, logical threads at least 1, flags, NUMA nodes counted from `node<N>` entries and 1 when unreadable) read once per process and memoized, `gpus` is `{ key, name, vendor, busId, vramTotalBytes }` of every card in the last snapshot's `allGpus` (empty before the first tick and with the stub; hidden and suspended cards have `vramTotalBytes` 0), and `nvidiaSource` is `nvml` or `nvidia-smi` (always `nvml` with the stub); errors: none (`app/server/routes/api/system/info.get.ts`, `app/server/lib/hardware/cpu.ts`).
- [ ] `GET /api/topology`: returns `{ graph, placement }` where `graph` is the PCIe hardware graph re-read from sysfs on every call (never `lspci`; nodes `cpu` with model, cores, threads and NUMA nodes, `ram` with MemTotal, DIMM count and the hottest `spd5118` temperature, one `pci:<busId>` node per GPU of class `0x03` and per NVMe controller of class `0x0108` with its block device, model and size, a `chipset:<busId>` node for a first bridge from the root port's vendor that is not removable and not Thunderbolt/USB4; links `cpu-ram` of kind `memory`, then each device's link of kind `pcie` with gen/width max as the smaller of both ends and current values, or `internal` without link attributes, a width of 0 or above 32 read as unknown; `at` the read time; any failed read degrades to unknown, at worst CPU and RAM only) and `placement` is the placement tracker's current `ModelPlacement` or `null`; errors: none (`app/server/routes/api/topology.get.ts`, `app/server/lib/hardware/pci.ts`, `app/server/lib/monitor/placement.ts`).

### WebSocket messages

- [ ] `snapshot`: broadcast unthrottled to every connected client at the end of every successful monitor tick (every `pollIntervalMs`, a tick skipped while the previous one is still running, nothing sent when a tick throws or with the stub monitor), carrying the full `Snapshot` (`at`, `tick` number, `health` null without an active server or `down` when llama-server does not answer, `rates` genTps/ppTps, `slots`, `kv` used/total tokens, `queue` processing/deferred/busySlots from the metrics, `lastRequest`, `spec`, `recentRequests` most recent first, `gpus` the cards whose llama-server process VRAM exceeds 64 MiB sorted by busId, `allGpus` every card sorted by busId including hidden and suspended ones, `proc` cpuPct/rssBytes/dramBps of llama-server, `system`, `disk`, `points` the values appended to the history on this tick with NaN as null, `history` `{ intervalMs, capacity }` whose change invalidates the client's copy) (`app/server/lib/boot.ts`, `app/server/lib/monitor/monitor.ts`, `packages/webui-shared/src/monitor.ts`).
- [ ] `placement`: broadcast to every client each time the tracked placement changes (compared by its JSON, so an identical recompute sends nothing; recomputed on every supervisor state change, synchronously, and on every microtask batch of log lines that holds a relevant line: launch line, `GGML_CUDA_P2P`, `using device`, `buffer size =`, `offloaded N/M layers`, `- device N:`, NCCL channel/P2P/`ncclCommInitAll`), carrying the `ModelPlacement` (`launchSeq`, `layers`, `buffers` per device with busId, model/KV/compute bytes and `estimated`, optional `p2p`) or `null` when no managed server runs (idle, crashed, external) (`app/server/lib/boot.ts`, `app/server/lib/monitor/placement.ts`, `packages/webui-shared/src/ws.ts`).

### Startup and shutdown

- [ ] At boot, after the database and the runtime are built, the monitor is started from the stored settings and awaited (`startMonitor`, at most one Monitor per runtime), unless `LLAMA_WEBUI_TEST_MONITOR=stub` puts the stub monitor in its place (`app/server/lib/boot.ts`, `app/server/lib/runtime.ts`).
- [ ] Starting the collectors waits for the NVML child to answer `ready` (up to 3 s, or its `error` message, or its exit) when `collectors.nvml` is on, falls back to a `nvidia-smi` stream otherwise, discovers the AMD cards once from `/sys/class/drm` (vendor `0x1002`, names from pci.ids, DRM nodes, slot link), applies the system/disk switches (starts `perf`, lists the physical disks), then starts nvidia-smi if it is the source (`app/server/lib/collectors/registry.ts`, `app/server/lib/collectors/nvml/monitor.ts`, `app/server/lib/collectors/amdgpu.ts`).
- [ ] The first tick is fired without being awaited and the poll interval is armed right after, so the API is ready before any snapshot exists (`GET /api/monitor/snapshot` answers `null` and `GET /api/system/info` lists no GPU until it lands) (`app/server/lib/monitor/monitor.ts`).
- [ ] Boot gives the monitor a model path resolver (profile id to the profile's absolute model path, from the profiles repository), which also clears the per-profile model disk cache (`app/server/lib/boot.ts`, `app/server/lib/monitor/monitor.ts`).
- [ ] The placement tracker is built with the other dependencies and replays the log ring at construction (the placement of a server already starting or running is known at once, without a `placement` message), then boot subscribes the hub to `onSnapshot` and `onChange` (`app/server/lib/deps.ts`, `app/server/lib/monitor/placement.ts`, `app/server/lib/boot.ts`).
- [ ] At shutdown the stack, in reverse order, closes the hub (1001), then disposes the placement tracker (unsubscribes from logs and supervisor, drops listeners), then stops the monitor (clears its interval and listeners, kills the NVML child with SIGKILL or the nvidia-smi stream, stops the perf streams), and only then stops llama-server (`supervisor.stop()`) and closes the database (`app/server/lib/boot.ts`, `app/server/lib/monitor/monitor.ts`, `app/server/lib/collectors/registry.ts`).
- [ ] The NVML sampler child never keeps the server process alive (child and IPC channel `unref()`'d) and a sampler stuck in a native call does not hold the exit, since it is a forked process killed with SIGKILL rather than a worker thread (`app/server/lib/collectors/nvml/sampler.ts`).
- [ ] The sampler child exits by itself when its IPC channel disconnects (server gone, even killed) (`app/server/lib/collectors/nvml/worker.ts`).
- [ ] The production build ships the sampler as `.output/server/nvml-worker.mjs` (built by Rolldown at the `compiled` hook, only `node:*` imports), and the module that names it must sit next to it, not in a chunk subfolder, or the monitor silently falls back to nvidia-smi (`app/vite.config.ts`, `app/server/build.test.ts`, `app/server/lib/collectors/nvml/monitor.ts`).

### Background work

- [ ] The monitor ticks every `pollIntervalMs` on a `setInterval`, whether clients are connected or not; a tick never overlaps the previous one, a failing tick is logged `[llama-webui] monitoring tick:` and a throwing subscriber is logged `[llama-webui] monitoring subscriber:` without stopping the others (`app/server/lib/monitor/monitor.ts`).
- [ ] Each tick with an active server (`starting`, `ready`, `stopping`, `external`) reads llama-server through `fetchLlama` (`/health`, then `/slots` and `/metrics` once loaded, 800 ms timeout each, global `fetch`) at the state's host and port, the GPUs, the process `/proc/<pid>/stat` and `status` (CPU % from utime+stime at 100 ticks/s, RSS) and the machine, and derives rates, KV usage, queue, last request, speculative stats and the recent requests list (`app/server/lib/monitor/monitor.ts`, `app/server/lib/collectors/proc.ts`).
- [ ] When the llama-server PID changes (restart, another profile, stop) the monitor resets its previous raw reading, metrics, last request, speculative stats and recent requests, so no rate is computed across two processes (`app/server/lib/monitor/monitor.ts`).
- [ ] A tick without an active server still reads every GPU (no process VRAM) and the machine, pushes 0 for tokens/s, CPU, KV, queue and busy slots, and repeats the last speculative acceptance value (`app/server/lib/monitor/monitor.ts`).
- [ ] Every tick appends one point to each history series (llama tokens/s, spec acceptance, process CPU and DRAM, per-GPU util/VRAM %/PCIe rx/tx/power/temp, system CPU/memory %/temperature, DRAM read/write, disk read/write and model disk read, KV %, requests processing/deferred, busy slots), a series is created at its first known value, an existing series not fed on a tick gets a gap, GPU util is a gap for a hidden or suspended card, and a collector turned off leaves gaps (`app/server/lib/monitor/monitor.ts`, `packages/webui-shared/src/monitor.ts`).
- [ ] The history keeps `ceil(historySeconds × 1000 / pollIntervalMs)` points per series in fixed-capacity rings (300 by default), in memory only, lost at restart (`app/server/lib/monitor/history.ts`, `app/server/lib/monitor/ring.ts`).
- [ ] With nvidia-smi as the source, the per-process VRAM (compute apps query, 3 s timeout then SIGKILL, one query at a time, previous mapping kept on timeout or failure) is refreshed and awaited on the first tick of a new PID and refreshed in the background every 5th tick (`app/server/lib/monitor/monitor.ts`, `app/server/lib/collectors/nvidia.ts`).
- [ ] The model disk of the running profile (stat of the model file, `/sys/dev/block/<major>:<minor>`, a partition resolved to its disk, null for tmpfs/btrfs/NFS) is looked up in the background once per profile so a dead mount never blocks a tick, retried every 30 s while not found, and is null for an external server, a crashed one, or with the disk collector off (`app/server/lib/monitor/monitor.ts`, `app/server/lib/collectors/disk.ts`).
- [ ] The NVML child (`fork` of `worker.ts` in development and tests, `nvml-worker.mjs` next to the server bundle in production, `--disable-warning=ExperimentalWarning`, advanced serialization) dlopens NVML through `node:ffi`, samples every interval (floor 100 ms, drift-compensated) and sends GPU readings, processes and driver/CUDA versions; hidden cards are only identified and PCIe throughput is read only when needed (`app/server/lib/collectors/nvml/sampler.ts`, `app/server/lib/collectors/nvml/worker.ts`, `app/server/lib/collectors/nvml/read.ts`, `app/server/lib/collectors/nvml/monitor.ts`).
- [ ] NVML readings older than 3 sampling intervals are treated as stale (no GPU, no process VRAM), the old interval staying valid after a change until the child has sampled at the new one (`app/server/lib/collectors/nvml/monitor.ts`).
- [ ] If the NVML child reports an error or exits after `ready`, its readings are cleared for good: no restart and no switch to nvidia-smi until the process restarts (`app/server/lib/collectors/nvml/monitor.ts`).
- [ ] A process VRAM NVML or nvidia-smi cannot report (`NVML_VALUE_NOT_AVAILABLE`, `[N/A]`) counts the card's whole VRAM in use, so the card still shows as used by the server (`app/server/lib/collectors/nvml/monitor.ts`, `app/server/lib/collectors/nvidia.ts`).
- [ ] The nvidia-smi fallback runs one long-lived `nvidia-smi --query-gpu=… -lms <interval>` stream, groups its lines into cycles, keeps the last values when the stream dies (not restarted), and is disabled for good when the binary cannot be spawned (`app/server/lib/collectors/nvidia.ts`).
- [ ] AMD cards are read from sysfs and hwmon each tick (util, VRAM, temperature, power, memory busy, clocks, fan, power cap, PCIe link of the slot bounded by its port, max kept once known), a runtime-suspended card is listed but not read so it is not woken up, a hidden card is listed but not read, and process VRAM comes from `/proc/<pid>/fdinfo` deduplicated per client id while skipping descriptors on hidden or suspended cards (`app/server/lib/collectors/amdgpu.ts`, `app/server/lib/monitor/monitor.ts`).
- [ ] With the system collector on, two `perf stat` processes measure DRAM bandwidth (whole machine `umc_cas_cmd.rd/wr`, llama-server's PID `ls_any_fills_from_sys.dram_io_all`, 64 bytes per event, stale after 3 intervals), a failing or dead stream is retried at most every 60 s, a PID perf could never attach to is not retried, and the process stream follows the PID on every tick (`app/server/lib/collectors/membw.ts`).
- [ ] The system sampler reads `/proc/stat` (total and per-core CPU %), `/proc/meminfo`, `/proc/loadavg`, the mean `scaling_cur_freq` and the first `k10temp`/`coretemp` hwmon sensor found once, each failure degrading to null (`app/server/lib/collectors/system.ts`).
- [ ] The disk sampler reads `/proc/diskstats` each tick and gives read/write rates per physical disk (from `/sys/block`, excluding loop/ram/zram, listed once when the collector is switched on), their sum and the model disk's read rate, 0 on the first sample (`app/server/lib/collectors/disk.ts`).
- [ ] pci.ids names are looked up in `/usr/share/hwdata/pci.ids`, `/usr/share/misc/pci.ids` then `/usr/share/pci.ids` and memoized per file and vendor:device for the process lifetime (a missing file not remembered), the bracketed name preferred (`app/server/lib/hardware/pci.ts`).
- [ ] The placement is parsed from the log ring after the last `[llama-webui] launch:` line: devices and bus ids from `using device` (or NCCL rank lines), model/KV(+RS)/compute buffers in MiB summed per device, compute per context with the last reservation winning, mmproj buffers and `-fit` probes skipped, parsing ended by a second `offloaded N/M layers` (draft), `-sm tensor` `Meta()` buffers spread over the member devices by `-ts` (equal parts without it) and marked estimated, and `p2p` `active`/`unavailable`/`requested` from NCCL and the `GGML_CUDA_P2P` line (`app/server/lib/monitor/placement.ts`).
- [ ] When the launch line has been evicted from the ring, the last placement read stays valid while the same PID runs (`app/server/lib/monitor/placement.ts`).

### Settings and environment

- [ ] `pollIntervalMs` (integer, 250 to 60000 ms, default 1000) sets the tick interval, the NVML sampling interval, the nvidia-smi `-lms` and the perf `-I` interval; a change re-arms the tick timer, restarts the nvidia-smi and perf streams and posts `configure` to the NVML child (`packages/webui-shared/src/settings.ts`, `app/server/lib/monitor/monitor.ts`, `app/server/lib/collectors/registry.ts`).
- [ ] `historySeconds` (integer, 30 to 1800 s, default 300) sizes the history; a change of it or of `pollIntervalMs` resizes every ring keeping the most recent points and changes the `history` shape carried by the next snapshots (`packages/webui-shared/src/settings.ts`, `app/server/lib/monitor/monitor.ts`, `app/server/lib/monitor/history.ts`).
- [ ] `hiddenGpus` (array of PCI addresses, default empty) lists cards that are identified but never read (no util, VRAM, temperature, power, process VRAM), applied live to NVML, AMD and nvidia-smi readings (`packages/webui-shared/src/settings.ts`, `app/server/lib/collectors/needs.ts`, `app/server/lib/monitor/monitor.ts`).
- [ ] `collectors.nvml` (default true) picks NVML or nvidia-smi once at startup only, so changing it has no effect until the process restarts (`packages/webui-shared/src/settings.ts`, `app/server/lib/collectors/registry.ts`).
- [ ] `collectors.system` (default true) switches the CPU/memory sampler and the perf DRAM bandwidth streams live (off kills perf and leaves `system` null), and `collectors.disk` (default true) switches the disk sampler live (off leaves `disk` null, on lists the disks again) (`packages/webui-shared/src/settings.ts`, `app/server/lib/collectors/registry.ts`).
- [ ] After a settings patch the route calls `monitor.configure(next)`, which applies the collectors first (calls serialized) and makes the new settings current only once they accepted them; a failure still saves the settings and answers 200 with `warning: Saved, but the monitor could not apply it: <message>`, logged with the `[llama-webui]` prefix (`app/server/routes/api/settings.patch.ts`, `app/server/lib/monitor/monitor.ts`, `app/server/lib/collectors/registry.ts`).
- [ ] `LLAMA_WEBUI_TEST_MONITOR=stub` (exact value) replaces the monitor with a stub without collectors: no snapshot, an empty history, `nvidiaSource` `nvml`, `nvmlSystem` null, `configure` a no-op (`app/server/lib/boot.ts`, `app/server/lib/testing/stubMonitor.ts`).
- [ ] `LLAMA_WEBUI_NVML_LIB` names the NVML library the child opens (default the system's `libnvidia-ml.so.1`, an empty value counts as unset), read at startup, to test its absence (`app/server/lib/collectors/registry.ts`, `app/server/lib/collectors/nvml/worker.ts`).
- [ ] `LLAMA_WEBUI_NVIDIA_SMI` names the nvidia-smi binary of the fallback (default `nvidia-smi`, an empty value counts as unset), read at startup, to test its absence (`app/server/lib/collectors/registry.ts`).

### WebSocket messages

- [ ] `download-progress`: payload `DownloadLive` `{ id, phase: 'downloading' | 'verifying' | 'retrying', file, bytesDone, totalBytes, bps, retryAt }` or null, broadcast to every client when an item starts (bytes of its finished files, `bps` 0), at the start of each file attempt and when its response starts (`downloading`, bytes so far), when an existing `.part` is re-hashed (`verifying`, `bps` 0), before each retry pause (`retrying`, `retryAt` = now + delay, `bps` 0), and during the transfer at most once per 250 ms (`bps` smoothed as 0.7 × previous + 0.3 × instantaneous), then null once the item ends (done, error or canceled); nothing is sent after `dispose()` (`app/server/lib/hf/downloader.ts`, `app/server/lib/deps.ts`, `packages/webui-shared/src/ws.ts`).
- [ ] `download`: payload the full `DownloadItem`, broadcast on every status change: each row created by `POST /api/downloads` (`queued`), a retried item (`queued`), an item the queue picks up (`downloading`, sent again for an item resumed in that state), an item that ends (`done`, `error` with `error` and `code`, `canceled`), and a queued item canceled through the API; not sent when one file of an item completes, nor after `dispose()` (`app/server/lib/hf/downloader.ts`, `app/server/lib/deps.ts`, `packages/webui-shared/src/ws.ts`).
- [ ] `download-deleted`: payload `{ ids }`, broadcast when a finished item is removed (`DELETE /api/downloads/:id`, one id) and when `POST /api/downloads/clear` deletes at least one row (ids ascending) (`app/server/lib/hf/downloader.ts`, `app/server/lib/deps.ts`, `packages/webui-shared/src/ws.ts`).

### Background work

- [ ] The download queue processes one item at a time in a loop started by `enqueue`, `retry` and `resume` (and started again when work was added while it ran, unless disposed), always picking an item left `downloading` first then the oldest `queued` one; `enqueue` and `retry` are serialized so their already-queued and disk space checks see each other's rows (`app/server/lib/hf/downloader.ts`, `app/server/lib/db/downloads.ts`).
- [ ] Each file is fetched with `downloadFetch` (`node:https`, HTTP/1.1, Node's global agents so the environment's proxy applies) from `<endpoint>/<repo>/resolve/<sha>/<path segments URL-encoded>` with `user-agent: llama-webui`, following up to 6 redirects by hand and sending the token only to the Hugging Face endpoint's origin, never to the CDN; more redirects fail the item with 502 `Too many redirects from Hugging Face` (code `hf-unreachable`) (`app/server/lib/hf/downloader.ts`, `app/server/lib/llamaFetch.ts`, `app/server/lib/hf/client.ts`).
- [ ] Each file is written to `<dest>.part` and resumed with `Range: bytes=<offset>-`: a 206 whose `content-range` does not start at the offset deletes the `.part` and retries, a 200 to a ranged request rewrites the file from the start (hash reset), a 416 deletes the `.part` and retries from zero, a `.part` larger than the file is deleted before the request, and a file already in place with the right size is skipped (`app/server/lib/hf/downloader.ts`, `app/server/lib/hf/paths.ts`).
- [ ] Files with an LFS sha256 are hashed as they are written; the hash state is kept across attempts when it covers exactly the `.part`, else the `.part` is re-read from disk in 1 MiB chunks (phase `verifying`); on a size match the digest is compared and a mismatch deletes the `.part` and fails the item with 422 `Checksum mismatch for <path>: the file was deleted` (code `checksum-mismatch`), else the `.part` is renamed into place and the file marked done in the row (`bytesDone` = sizes of finished files) (`app/server/lib/hf/downloader.ts`, `app/server/lib/db/downloads.ts`, `app/server/lib/proc.ts`).
- [ ] Each attempt has a stall timer of 60 s reset on every chunk (`setTimeout`): no data for 60 s aborts the attempt as retryable `no data for 60 s` (`app/server/lib/hf/downloader.ts`).
- [ ] Transient failures (network error `Hugging Face unreachable: …`, status 408, 429 or 5xx from the Hub or the CDN, stall, body shorter than the file which keeps the `.part`, body longer which deletes it, empty body, bad range, 416, any write error other than ENOSPC) are retried after abortable pauses of 2, 4, 8, 16 then 30 s (logged `[llama-webui] download <repo>/<file>: <message>, retrying`), the count reset after an attempt that received data; once spent the item fails with 502 and the last message (code `hf-unreachable`) (`app/server/lib/hf/downloader.ts`).
- [ ] Non-transient failures end the item at once as `error` with message and code: Hub errors (`hf-gated`, `hf-not-found`, `hf-unauthorized`), ENOSPC as 507 `Disk full` (code `disk-full`), checksum mismatch, and any other error as its message with code `download-failed`, logged `[llama-webui] download <repo>/<key> failed: <message>` (`app/server/lib/hf/downloader.ts`).
- [ ] Canceling the running item aborts its request; the queue then deletes its `.part` files, the files it had put in place (or with the right size), and the folders left empty deepest first (shard subfolders, the repo folder, the org folder), then marks it `canceled` (`app/server/lib/hf/downloader.ts`).
- [ ] The disk space check (`enqueue`, `retry`) takes the free space (`statfs`, `bavail × bsize`) of the destination folder or its nearest existing parent and refuses when it is below the bytes still to write (sizes minus existing `.part` bytes) plus what the active items still have to write plus a 1 GiB margin; an unknown free space skips the check (`app/server/lib/hf/downloader.ts`).
- [ ] An unexpected error escaping the queue loop (the database failing) is logged `[llama-webui] download queue stopped:` and the item is picked up again on the next start of the loop (`app/server/lib/hf/downloader.ts`).
- [ ] Hub API calls (search, repo files, whoami) use Node's `fetch` with a 10 s `AbortSignal.timeout`, combined with the client request's signal for search and repo; a 200 that is not JSON is a 502 `Hugging Face sent an invalid response (<path>)`, or `Hugging Face unreachable: …` when the client aborted (`app/server/lib/hf/client.ts`).
- [ ] The model scan walks the models folder recursively (names starting with `.` skipped, directory symlinks not followed, a `.gguf` symlink kept when it points to a regular file, unreadable folders skipped), groups `-0000k-of-0000N.gguf` shards (an incomplete set is an `ok: false` entry `missing shard: <names>`), reads all GGUFs in parallel, reuses a `model_cache` row when the stamp (`mtimeMs:size` of every part) is unchanged, caches each successful read (failures never cached), and deletes the cache rows of files no longer found (`app/server/lib/models/scan.ts`, `app/server/lib/db/modelCache.ts`).
- [ ] `readModel` keeps the last 8 parsed GGUFs in memory keyed by path and the stamp of every part (a changed shard re-reads it), using `@huggingface/gguf` with parameter count (`app/server/lib/models/gguf.ts`).

- [ ] `DELETE /api/sweeps/:id`: deletes the sweep and its runs (cascade), broadcasts `bench-deleted` with the deleted run ids (even an empty list) then `sweep-deleted` `{ id }`, and answers 204; errors: 404 `Sweep not found`; 409 `This sweep is still running: cancel it first` (`app/server/routes/api/sweeps/[id]/index.delete.ts`, `app/server/lib/sweeps/access.ts`, `app/server/lib/db/sweeps.ts`).
- [ ] `POST /api/sweeps/:id/cancel`: cancels the running sweep with this id (its queued items become `cancelled`, the running item is cancelled and its child killed, a `sweep` broadcast), after which the loop ends the sweep as `cancelled` with its best run and restarts the server it stopped; answers 204, no body read; errors: 404 `Sweep not found`; 409 `This sweep is not running` (not the running sweep, or already cancelled) (`app/server/routes/api/sweeps/[id]/cancel.post.ts`, `app/server/lib/bench/runner.ts`).
- [ ] `POST /api/sweeps/:id/resume`: looks the sweep up and refuses a running one before reading the body, reads a JSON object where only `stopServer === true` counts (no schema: other keys and non-boolean values are ignored), checks the sweep's model and projector, takes the gate, requeues its `interrupted` items (results cleared), sets the sweep `running` with `finishedAt` null, runs its queued items and answers 202 with the sweep; errors: 404 `Sweep not found`; 409 `This sweep is still running: cancel it first`; 400 `Invalid JSON` (malformed or empty body); 400 `JSON object expected`; 409 `A benchmark is running`; 400 `Model not found: <path>` / `Projector not found: <path>` (#37, before anything stops); the gate's three 409s; 409 `Nothing to resume: no interrupted or queued item` (checked after the gate is taken, the gate then released) (`app/server/routes/api/sweeps/[id]/resume.post.ts`, `app/server/lib/bench/runner.ts`, `app/server/lib/db/benchRuns.ts`).
- [ ] `POST /api/sweeps/:id/validate`: looks the sweep up and refuses a running one before reading the body, reads a strict `{ n?: integer 1–5 default 3, stopServer?: boolean }`, ranks the sweep's successful `bench` items with its preset at the sweep context (the last `-c`/`--ctx-size` of its server flags, `=` forms included, otherwise the preset's minimum) and enqueues the top `n` as `server` items (`params` of the ranked run, the sweep's server flags with `-c <sweep context>` appended when they set none (#24), the sweep's `p`/`n`/`r`, label `validation · <item label or base>`, the item's fit or `fits`), also requeueing interrupted items, then runs them like a resume and answers 202 with the sweep; errors: 404 `Sweep not found`; 409 `This sweep is still running: cancel it first`; 400 `Invalid JSON`; 400 `JSON object expected`; 400 `Invalid data: …` (schema, unknown keys refused); 409 `No successful run to validate` (checked before the busy check); 409 `A benchmark is running`; 400 `Model not found: <path>` / `Projector not found: <path>`; the gate's three 409s (`app/server/routes/api/sweeps/[id]/validate.post.ts`, `packages/webui-shared/src/sweep.ts`, `app/server/lib/bench/runner.ts`).

### WebSocket messages

- [ ] `bench-progress`: carries the current `BenchLive` (`runId`, `kind`, `phase`, `step`, `startedAt`, last 20 lines) or null, sent unthrottled when a run becomes current (phase `stopping-server` while the gate's stop is in progress, else `loading`), on every executor phase change (`loading`, `warmup`, `measure` with step `i/r` for a server run; `prompt`/`generation` with step `(test-1)*runs+run` of `tests*runs` on each llama-bench progress line), on other output lines at most every 250 ms, on cancellation, on `restarting-server` (one-off runs only, when the gate stopped a server), and null once a one-off run has restarted the server or as soon as a sweep item is saved (before the sweep's final restart, so a sweep never shows `restarting-server`); nothing after shutdown (`app/server/lib/bench/runner.ts`, `app/server/lib/bench/execute.ts`, `app/server/lib/deps.ts`).
- [ ] `bench-run`: carries a full `BenchRun`, sent when a one-off run is created (`running`), when a sweep item begins (`running`, command and hardware frozen, `createdAt` reset), when any run's result is saved, and again when a failed server restart is appended to the last run's error; never on enqueue, requeue, `cancelQueued` or the shutdown save (`app/server/lib/bench/runner.ts`, `app/server/lib/deps.ts`).
- [ ] `bench-deleted`: carries `{ ids }`, sent by `DELETE /api/bench/:id` (one id), by the failed-runs purge only when it deleted something, and by a sweep deletion with the ids of its runs (possibly empty) just before `sweep-deleted` (`app/server/routes/api/bench/[id]/index.delete.ts`, `app/server/routes/api/bench/runs.delete.ts`, `app/server/routes/api/sweeps/[id]/index.delete.ts`).
- [ ] `sweep-progress`: carries `{ sweepId, runId, index, total, stage }` before each sweep item starts (`index` = total − queued + 1, 1-based, `stage` `validate` for a server item, `explore` otherwise), and null once the sweep has ended and the server restart has been attempted; nothing after shutdown (`app/server/lib/bench/runner.ts`, `app/server/lib/deps.ts`).
- [ ] `sweep`: carries the full `Sweep` (status, counts, best), sent when a sweep starts, resumes or starts its validation (`running`), after each item is saved (fresh counts), on `cancelSweep` (queue already cancelled) and at the end (`done` or `cancelled` with `bestRunId` and `finishedAt`); not when shutdown saves it `interrupted` (`app/server/lib/bench/runner.ts`, `app/server/lib/deps.ts`).
- [ ] `sweep-deleted`: carries `{ id }`, sent only by `DELETE /api/sweeps/:id`, after its `bench-deleted` (`app/server/routes/api/sweeps/[id]/index.delete.ts`).

### Startup and shutdown

- [ ] The bench gate is built per boot inside the runtime with the supervisor (as its `ServerControl`: state, last command, stop, start) and the log ring, and the runner, its executor and repositories are built in `createDeps` (`app/server/lib/runtime.ts`, `app/server/lib/deps.ts`).
- [ ] Opening the database migrates `bench_runs` to AUTOINCREMENT ids (a deleted run's id is never handed out again, which `sweeps.best_run_id` relies on), keeping every run of an older (J5) database with its id, values and next id; `bench_runs.sweep_id` cascades on sweep delete and `profile_id`/`best_run_id` are set null when their row goes (`app/server/lib/db/migrations.ts`, `app/server/lib/db/sweeps.test.ts`).
- [ ] At startup, after the conversation orphans and before the downloads resume, every bench run left `running` becomes `interrupted` with error `interrupted (llama-webui stopped)` (an existing error is kept), and every sweep left `running` becomes `interrupted` while its queued items stay `queued`; nothing resumes on its own (Resume button) (`app/server/lib/boot.ts`, `app/server/lib/db/benchRuns.ts`, `app/server/lib/db/sweeps.ts`).
- [ ] At shutdown the stack undoes, in order, the external-watch interval, chat runs, then `benchRunner.dispose()`, then downloads, the hub (1001), placement, the monitor, `supervisor.stop()` and the database, so the benchmark is saved before the sockets close and before the managed llama-server and the database are stopped (`app/server/lib/boot.ts`).
- [ ] `benchRunner.dispose()` (once only) SIGKILLs the current child without waiting, saves the unfinished current run (a sweep item too) as `interrupted` with error `interrupted (llama-webui stopped)` and its elapsed `durationMs`, saves the running sweep as `interrupted` (its queued items untouched), swallows database errors, broadcasts nothing, and does not release the gate, so a server stopped for the benchmark is not restarted (`app/server/lib/bench/runner.ts`, `app/server/lib/bench/execute.ts`).
- [ ] After dispose the runner writes and broadcasts nothing more: the in-flight execution's result is dropped, the sweep loop returns, and live updates are ignored (`app/server/lib/bench/runner.ts`).
- [ ] llama-bench and the trial llama-server run under `setpriv --pdeathsig KILL`, so they die with the Node process (`app/server/lib/bench/execute.ts`, `app/server/lib/supervisor/args.ts`).
- [ ] In dev, saving business code rebuilds the runtime and so disposes the runner (a running sweep becomes `interrupted` with a Resume button), while saving a route file keeps the runtime and the benchmark running (`CLAUDE.md`, `app/server/lib/context.ts`).

### Background work

- [ ] One benchmark at a time: the runner is `busy` while a request is between acceptance and start (file check, gate, hardware), while a run is current, while a sweep runs, or while the gate is held; a one-off run and a sweep loop run in the background after the 202 (`app/server/lib/bench/runner.ts`).
- [ ] While `busy`, the supervisor lifecycle routes (start, stop, restart, switch) answer 409 `A benchmark is running`, the disk speed measurement answers 409 `A benchmark is running: the measurement would be skewed`, and the external-server watch (every 2 s) is paused (`app/server/lib/supervisor/control.ts`, `app/server/routes/api/tuning/disk-speed.post.ts`, `app/server/lib/boot.ts`).
- [ ] The model and projector of the live run and of the running sweep count as in use for model deletion (`app/server/lib/models/access.ts`).
- [ ] The device listing also returns why it is not trusted (`llama-bench --list-devices exited with code <n>`, `llama-bench --list-devices killed by <signal>`, the spawn error, or `<device id> listed without memory`), read by the tuning hardware (the bench devices route drops it) (`app/server/lib/bench/hardware.ts`, `app/server/lib/tuning/hardware.ts`).
- [ ] For the launch pad, `lastOkByProfile()` gives each profile's latest successful one-off run (failed runs, sweep items and runs whose profile was deleted ignored) (`app/server/lib/db/benchRuns.ts`, `app/server/routes/api/launchpad.get.ts`).
- [ ] Gate acquire: a server in `stopping` is polled every 100 ms for up to 60 s (then 409); a `starting` or `ready` managed server with `stopServer` gets the log line `[bench] stopping llama-server for the benchmark`, its last command recorded, and its stop started without being awaited (the run waits for it in `ready()`); an idle or crashed server is left alone (`app/server/lib/bench/gate.ts`).
- [ ] A failed server stop records nothing to restart and fails the first run with `could not stop llama-server: <message>` (or `cancelled` if it was cancelled meanwhile) (`app/server/lib/bench/gate.ts`, `app/server/lib/bench/runner.ts`).
- [ ] Gate release (once per one-off run or per sweep, idempotent, after awaiting a pending stop): restarts the stopped server with the command rebuilt from its profile as it is now (#39), falling back to the recorded command when the profile is gone or the rebuild throws, logs `[bench] restarting llama-server (<profile name>)`; a failure logs `[bench] could not restart llama-server: <message>`, still frees the gate, and is appended to the run's error (`<previous>; <message>`) and re-broadcast (`app/server/lib/bench/gate.ts`, `app/server/lib/bench/runner.ts`).
- [ ] A one-off run or sweep whose start fails after the gate was taken (hardware read, row creation, a resume with nothing to resume) releases the gate, restarting a server it had already begun to stop (`app/server/lib/bench/runner.ts`).
- [ ] llama-bench child: argv `setpriv --pdeathsig KILL -- <llama-bench> -m <model> -o json --progress -r R -p P -n N <fields>` (`-ngl all` as 999, `/` between `-dev`/`-ts` values, `;` between `-ot`, `-ngl auto` omitted, projector not passed), recorded command without the `setpriv` prefix, environment = process env, then the `env` setting, then the source profile's env, `[bench] <command>` logged, a spawn failure = `failed` with its message (`app/server/lib/bench/execute.ts`, `packages/webui-shared/src/bench.ts`).
- [ ] llama-bench result: `ok` with pp/tg when it exits 0 and its JSON has pp or tg, otherwise `failed` with `Out of memory: <allocation line>` (or `Out of memory`) when an OOM line appears, else the last error line, else `llama-bench exited (code <exit or signal>)` (`app/server/lib/bench/execute.ts`, `app/server/lib/bench/parse.ts`).
- [ ] Trial llama-server command: a synthetic profile (model, projector, fields as llama-server flags then the other flags, host 127.0.0.1, the `port` setting, cwd and env of the source profile or the model's directory and `{}`) through `buildCommand` (so `-lv 4` unless verbosity is set, `--metrics --slots --props`, env = process env, then settings env, then profile env) (`app/server/lib/bench/execute.ts`, `app/server/lib/supervisor/args.ts`).
- [ ] Server trial: refuses with `port <port> is used by another server` when the port already answers health, then spawns llama-server and polls its health every 500 ms (failing with `loading > 10 min` after 10 minutes, or with the exit error when it dies), warms up with `POST /completion` (`Write one short sentence about the sea.`, 16 tokens), then makes `r` `POST /v1/chat/completions` requests (a fixed lighthouse text of about `p` tokens at 4 characters each plus a new-story instruction, `max_tokens` n, `ignore_eos`, thinking disabled), all with `cache_prompt: false`, `temperature: 0`, `seed: 42`, `stream: false`, through `llamaFetch` (no 300 s cap) (`app/server/lib/bench/server.ts`, `app/server/lib/bench/prompt.ts`).
- [ ] Server trial errors: each request times out after 10 minutes (`no response after 10 min`), a non-200 is `<path> responded <status>`, and on any failure it waits up to 2 s for the process to exit so the error comes from its own lines (the last 10 error lines kept apart from the 50-line tail, OOM recognised, else `llama-server exited (code <exit>)`) (`app/server/lib/bench/server.ts`, `app/server/lib/bench/parse.ts`).
- [ ] Server trial result: pp and tg = mean and population standard deviation of the per-request `prompt_per_second`/`predicted_per_second` with the last request's token counts, and `draftAcceptPct` = accepted/drafted over all requests rounded to 0.1 (null without drafts) (`app/server/lib/bench/server.ts`).
- [ ] The trial llama-server is always stopped when the trial ends: SIGTERM, then SIGKILL after 5 s with the line `not stopped after 5000 ms, SIGKILL` (`app/server/lib/bench/server.ts`).
- [ ] Cancellation of a run aborts its requests, sends SIGTERM to its child then SIGKILL after 5 s, logs `cancellation requested`, and saves it `cancelled` (`app/server/lib/bench/execute.ts`).
- [ ] Every run's output line is pushed to the log ring as `[bench] <line>`, the last 50 lines become `logExcerpt`, and the executor re-checks the model file at start (`failed` with `Model not found: <path>`) (`app/server/lib/bench/execute.ts`).
- [ ] During a run, a 500 ms interval samples the monitor's GPUs (VRAM above each card's level at launch) and the model disk's read rate, plus a final sample when the run ends (the snapshots themselves refresh at the monitor's `pollIntervalMs`, 1 s by default), giving `vramPeak` (per card, MiB rounded, zero entries dropped) and `diskReadPeakBps` (`app/server/lib/bench/execute.ts`).
- [ ] Fast VRAM probe during a run: a `nvidia-smi --query-gpu=uuid,memory.used --format=csv,noheader,nounits -lms 100` child when an NVIDIA card is present (its lines read as the monitor's keys `nvidia:<GPU uuid>`) and a 100 ms sysfs `mem_info_vram_used` read for AMD cards, each source that fails ignored, stopped with SIGTERM and at most 500 ms of waiting when the run ends (`app/server/lib/bench/vram.ts`).
- [ ] Run hardware frozen at start: CPU model (read once per process), the monitor's GPUs (name, bus id, total VRAM) and the llama-server build `b<build> (<commit>)` from `<binary> --version` (5 s timeout, SIGKILL, cached per file and modification time, null when unreadable); a sweep item whose hardware read fails gets an empty hardware (`app/server/lib/bench/hardware.ts`, `app/server/lib/bench/runner.ts`).
- [ ] Sweep loop: takes the queued items in id order, runs each (a failure, OOM included, does not stop the sweep), broadcasts the sweep after each, pauses 1 s between items while another is queued, and at the end sets `done` (or `cancelled`) with `finishedAt` and the best run (the top-ranked successful `server` validation if any, otherwise the top-ranked `bench` item, null when none succeeded), restarts the server once, and records a failed restart on the last item (`app/server/lib/bench/runner.ts`).

## E8: Tuning and setup

### Endpoints

- [ ] `GET /api/tuning/checks`: reads the optional query key `model` (first value, an empty value counts as absent), then in parallel the tuning hardware, the parsed GGUF of `model` (any `loadModel` failure silently gives `null`, never an error) and the system readings (`readSys`, binary = the `binary` setting with `~` expanded, the in-memory llama-server log lines from `runtime.logs.since(0)`, the monitor's NVML driver info and the bus ids of the monitor's `allGpus`), runs the checks against the latest estimate and disk measurement memoized for that model, and returns `{ checks, summary: { warn, ok, unknown, na }, at }` (`at` = `Date.now()`); errors: none (`app/server/routes/api/tuning/checks.get.ts`, `app/server/lib/tuning/checks.ts`, `app/server/lib/tuning/models.ts`).
- [ ] `GET /api/tuning/hardware`: returns the tuning hardware `{ devices, devicesError, cpu, ramTotalBytes, ramAvailableBytes }`: the `llama-bench --list-devices` devices with their live memory from the monitor, the reason the list is not trusted (or `null`), the CPU info, and RAM from the latest monitor snapshot (otherwise `/proc/meminfo`, otherwise 0); errors: none (`app/server/routes/api/tuning/hardware.get.ts`, `app/server/lib/tuning/memo.ts`, `app/server/lib/tuning/hardware.ts`).
- [ ] `POST /api/tuning/disk-speed`: body `{ modelPath }` (strict object, non-empty string), refuses while the bench runner is busy, validates the model with `loadModel`, then times a sequential read of up to 1 GiB of the file from a random offset and returns `{ bytesPerSec, sampledBytes, path, at }`, which it also memoizes per `modelPath` for the checks; errors: 400 `Invalid JSON`, 400 `JSON object expected`, 400 `Invalid data: …` (body schema), then 409 `A benchmark is running: the measurement would be skewed`, then 400 `Expected an absolute path to a .gguf file`, 404 `Model not found`, 422 `<GGUF read error message>`, then 404 `File not found: <path>` (file gone between the two stats), 400 `File too small to measure (<n> MiB)` (fewer than 64 MiB to read) (`app/server/routes/api/tuning/disk-speed.post.ts`, `app/server/lib/tuning/disk.ts`, `app/server/lib/tuning/models.ts`).
- [ ] `POST /api/tuning/estimate`: body (strict object) `{ modelPath: non-empty string, mmprojPath?: string | null, preset: chat|agent|context|fit|big, pinned?: BenchParams, ctx?: integer 512 to 10,000,000 }`, loads the model, the projector size (0 when `mmprojPath` is missing, null or empty) and the tuning hardware in parallel, runs the rule-based estimator and returns the `Estimate` (`ok`, `reason`, `preset`, `params`, `ctx`, `kv`, `serverArgs`, `rows`, `fit`, `ramOverflowBytes`, `diskReadBytesPerToken`, `warnings`), memoizing it per `modelPath` (also when `ok` is false) for the checks; errors: 400 `Invalid JSON`, 400 `JSON object expected`, 400 `Invalid data: …` (body schema, the preset error being zod's default `Invalid option: expected one of "chat"|"agent"|"context"|"fit"|"big"`), 400 `Expected an absolute path to a .gguf file`, 404 `Model not found`, 422 `<GGUF read error message>`, 404 `Projector not found` (`app/server/routes/api/tuning/estimate.post.ts`, `app/server/lib/tuning/estimate.ts`, `app/server/lib/tuning/models.ts`).
- [ ] `POST /api/tuning/plan`: body `{ spec }` read without a media-type check (`readJson` + `object`), `spec` parsed by `SweepSpecSchema` so its errors keep their own paths (`name`, not `spec.name`), then the model, projector size and tuning hardware loaded in parallel, and returns `{ items: [{ params, label, fit }], excluded, droppedTs, estimatedSeconds }` without storing anything; errors: 400 `Invalid JSON` (empty or malformed body), 400 `JSON object expected`, 400 `Invalid data: …` (spec schema; a body without `spec` gives a message with no path), 400 `Expected an absolute path to a .gguf file`, 404 `Model not found`, 422 `<GGUF read error message>`, 404 `Projector not found` (`app/server/routes/api/tuning/plan.post.ts`, `app/server/lib/tuning/space.ts`, `packages/webui-shared/src/sweep.ts`).
- [ ] `GET /api/setup`: returns the first-run report `{ binary: { setting, path, version }, bench: { path, devices }, models: { setting, dir, exists, count, bytes }, telemetry: { nvidiaSource, perfParanoid }, listen: { host, exposed }, llamaListen: { host, exposed }, ready }`, with `ready` true when the binary is found and the models folder exists; errors: none (`app/server/routes/api/setup.get.ts`, `app/server/lib/setup.ts`).
- [ ] Model loading for estimate, plan and disk-speed (`loadModel`): a path that does not start with `/` or end with `.gguf` is 400 `Expected an absolute path to a .gguf file`, a path that is not a regular file is 404 `Model not found`, and a `readModel` failure (unreadable GGUF, missing shard, permission denied) is 422 with the `ModelReadError` message; the parsed GGUF comes from `readModel`'s cache (8 models, keyed by the size and mtime of every shard) (`app/server/lib/tuning/models.ts`, `app/server/lib/models/gguf.ts`).
- [ ] Projector size (`mmprojBytes`): 0 without a path, the file size of a regular file, otherwise 404 `Projector not found`; the projector path is not checked for being absolute or `.gguf` (`app/server/lib/tuning/models.ts`).
- [ ] Plan body schema (`SweepSpecSchema`): `name` trimmed 1 to 80 characters (`required`, `80 characters at most`), `modelPath` absolute (`expected an absolute path`) and `.gguf` (`expected a .gguf file`), `mmprojPath` string or null (default null), `profileId` integer or null (default null), `p` 1 to 32768 (default 512), `n` 1 to 4096 (default 128), `r` 1 to 20 (default 3), `preset` (`unknown preset`), `base` BenchParams (default `{}`), `space` with each dimension a non-empty list (`at least one value`, default `{}`), `serverArgs` refusing reserved flags and flags covered by a field (`<flag>: use the <short> field`), `includeUnfit` (default false) (`packages/webui-shared/src/sweep.ts`, `packages/webui-shared/src/bench.ts`).
- [ ] `BenchParams` (estimate `pinned`, plan `base`): strict object of `ngl` (0 to 9999, `all` or `auto`), `ot` (`pattern=buffer` strings), `ncmoe` (0 to 9999), `dev` (device names like `CUDA0`), `ts` (non-negative numbers), `sm` (none, layer, row, tensor), `fa` (on, off, auto), `ctk`/`ctv` (f32, f16, bf16, f8_e4m3, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1), `t` (1 to 1024), `b` and `ub` (1 to 1,000,000), each with its own message (`packages/webui-shared/src/bench.ts`).
- [ ] Plan items: the cartesian product of `space` over `base` (`expandSpace`, duplicates removed, `-ts` dropped where `-dev` does not have as many devices, counted in `droppedTs`), each with `itemLabel` and its `fitOf` verdict at the sweep context (`-c` from `serverArgs`, else the preset's `ctxMin`), K cache `ctk ?? f16`, V cache `ctv ?? ctk ?? f16`, micro-batch `ub ?? 512`; items whose verdict is `no` are dropped and counted in `excluded` unless `includeUnfit`; `estimatedSeconds` = round(items × (model file bytes / 1.5 GiB/s + 10 s × `r`)) (`app/server/lib/tuning/space.ts`, `packages/webui-shared/src/sweep.ts`).
- [ ] Presets: `chat` (target 32768, min 8192, f16 KV preferred, ub 512), `agent` (65536, 16384, q8_0, ub 2048), `context` (largest that fits, min 8192, q8_0, ub 512), `fit` (8192, 8192, q8_0, ub 512), `big` (32768, 8192, q8_0, ub 512, experts in RAM across all cards, RAM overflow accepted) (`packages/webui-shared/src/tuning.ts`).
- [ ] Estimator card sets: dedicated GPUs (`deviceRole` = `gpu`: no host, iGPU or Vulkan duplicate of a native card) whose budget is at least 256 MiB, CUDA first in `--list-devices` order; a pinned `-dev` gives only that set, otherwise each CUDA card alone, all CUDA cards, each card alone, then all cards (`app/server/lib/tuning/estimate.ts`, `packages/webui-shared/src/tuning.ts`).
- [ ] Estimator families: outside `big`, every card set all-GPU (`-ngl all`), then for a MoE `-ncmoe` 1 to L on the widest set (or the pinned `ncmoe`), then partial `-ngl` L−1 down to 1 on the widest set (or the pinned `ngl`), then CPU only (`-ngl 0 -dev none`); `big` tries only `-ncmoe` (MoE) and partial on the widest set, then CPU; a candidate is rejected when its verdict is `no` or its RAM exceeds the available RAM (except with `big`) (`app/server/lib/tuning/estimate.ts`).
- [ ] Estimator cache and batch: with pinned `-fa off` the KV candidates are f16 then f8_e4m3 (f16 only when both `ctk` and `ctv` are pinned), with a pinned `ctk` f16 or q8_0, otherwise the preset's preferred type (f16 then q8_0, or q8_0 alone); f8_e4m3 is tried only on sets made of CUDA cards; the micro-batches are the pinned `ub`, otherwise `[512]` or `[preset ub, 512]`; every candidate also carries `-fa on` (unless `-fa off` is pinned), `-ctk`/`-ctv` = the KV type, `-t` = pinned or the physical core count (at least 1), `-b` = pinned or 2048, and the pinned values override the searched ones (`app/server/lib/tuning/estimate.ts`).
- [ ] Estimator context search: the maximum context is max(preset min, model context length rounded down to 1024); for the `context` preset without a pinned `ctx`, each KV type gets the largest context (binary search in 1024 steps) over every GPU family then the other families in order, stopping after the first non-GPU family once any family has fitted, and a fallback KV type wins only with a larger context; otherwise the GPU families are tried first at the target context (min(target, max) or the pinned `ctx`) with the preferred KV, the first `fits` wins, else the first `tight`, else every family × KV type × context (target, then down by 4096 to the preset min) × micro-batch, first that passes (`app/server/lib/tuning/estimate.ts`).
- [ ] Estimator `-ts`: on two cards or more, proportional to each card's budget minus the compute buffers and projector on the first card, in 256 MiB units (at least 1); absent on a single card (`app/server/lib/tuning/estimate.ts`).
- [ ] Estimate when nothing fits: `ok: false`, the simplest configuration (`-ngl all` on the widest set, or `-ngl 0` without cards; q8_0 KV, f16 with `-fa off`; ub 512; context = pinned `ctx` or preset min; pinned values applied last), `reason` = `not enough RAM: <X> needed with weights in RAM, <Y> available` when some candidate fitted the VRAM but not the RAM, else the fit's reason, else `model too large: <X> of RAM needed, <Y> available`, `fit.verdict` forced to `no`, empty `rows`, `diskReadBytesPerToken` 0, `serverArgs` ending with `-c <ctx> --fit off` (`app/server/lib/tuning/estimate.ts`).
- [ ] Estimate when a configuration is found: `serverArgs` = the params as llama-server flags, then `-c <ctx> --fit off`, then `--mlock` when the layers are not all on GPU, some weights are in RAM, RAM does not overflow, at least 2 GiB of RAM stays free and there is no `-ncmoe`, then `--numa distribute` when the CPU has several NUMA nodes; `kv` = the final K cache type (pinned included); `ramOverflowBytes` = RAM needed minus available (at least 0); `diskReadBytesPerToken` = active CPU weights (MoE experts × used/total experts, plus other layer weights) × min(1, overflow / CPU weights) when RAM overflows (`app/server/lib/tuning/estimate.ts`).
- [ ] Estimate rows (`{ flag, value, why }`), in order: `-ncmoe` (with `-ngl all`), `-ngl` (`all`, a layer count, or `0`), `-dev` (unless `none`), `-ts`, `-c` (total estimated bytes, KV label), `-fa` (why depends on quantized KV, `auto` or `off`), `-ctk / -ctv` (`pinned`, `cache halved, negligible loss`, `cache halved, works without flash attention` for f8_e4m3, or `the budget allows it, no loss`), `-t`, `-b / -ub` (`default` only for 2048/512), `--fit off`, then `--mlock` and `--numa distribute` when they apply; f32, f16, bf16 and f8_e4m3 are not counted as quantized (`app/server/lib/tuning/estimate.ts`).
- [ ] Estimate warnings: `dense model: -ncmoe has no effect` (pinned `ncmoe` on a dense model), `slow generation: <n> of <L> layers in RAM`, `<experts of the first N layers> in RAM: slower generation`, `not enough VRAM: everything in RAM`, `overflows RAM by <X>: NVMe read ≈ <Y> per generated token`, the `tight` reason when RAM does not overflow, `a quantized KV cache needs flash attention: -fa off may fail`, `only CUDA and the CPU support an f8_e4m3 KV cache: <devices> may fail`, then every placement issue (`app/server/lib/tuning/estimate.ts`).
- [ ] Placement (`measurePlacement`): the used devices are the pinned `-dev` ids that are listed and not host (`none` ignored, any other unknown id an `unknown device: <id>` issue), otherwise the dedicated GPUs; `-ngl` as a number, else every layer plus the output (0 without a device); the last `ngl` layers go to GPU in contiguous slices proportional to `-ts` (when its length matches and one value is positive) or to each card's free MiB (else total), all on the first card with `-sm none` or a single card (`app/server/lib/tuning/placement.ts`).
- [ ] Placement of each tensor: the first matching `-ot` rule wins (a listed device, or RAM for a host buffer like `CPU`, `CPU_REPACK`, `CUDA_Host`; an unknown target is counted in RAM with the issue `unknown device: <target> (-ot <rule>)`; an invalid regex is the issue `invalid -ot pattern: <pattern>`), then experts of layers below `-ncmoe` go to RAM, `token_embd` to RAM, a layer tensor to its layer's device, other tensors to the last device when the output is offloaded, otherwise RAM; KV of each layer goes with its layer; compute buffers (ub × (embedding × 4 + vocab × 4) + 256 MiB), the projector and the recurrent state go to the first device when a layer is on GPU, otherwise RAM (`app/server/lib/tuning/placement.ts`, `app/server/lib/tuning/memory.ts`).
- [ ] KV cache size: no KV for MTP (nextn) layers, for recurrent layers without a full-attention interval, and for layers off the full-attention interval; sliding-window layers (all but every `swaPattern`-th, pattern from the GGUF, 2 for gpt-oss, 6 otherwise) hold at most `slidingWindow` tokens; bytes = KV heads × (key length × K bytes + value length × V bytes) × tokens, with per-element bytes f32 4, f16/bf16 2, q8_0 1.0625, f8_e4m3 1, q5_1 0.75, q5_0 0.6875, q4_1 0.625, q4_0/iq4_nl 0.5625 (`app/server/lib/tuning/memory.ts`).
- [ ] Fit verdict (`fitOf`): the budget of a device is total − (512 MiB + 4 % of total) − VRAM of other processes (at least 0); `no` with an `unknown device` issue as reason, `no` when a device exceeds its budget (`<dev>: <X> for <Y> usable`), `tight` when RAM needed exceeds RAM available (`RAM: <X> for <Y> available, the rest is re-read from disk`), `tight` above 95 % of a budget (`<dev>: <X> for <Y> usable, thin margin`), otherwise `fits` with a null reason; each `vram` entry carries `device`, `bytes`, `budget`, `totalBytes`, `otherBytes` (`app/server/lib/tuning/placement.ts`, `app/server/lib/tuning/memory.ts`).
- [ ] Live memory of the devices (`withLiveMemory`): each `--list-devices` device matched to a monitored card gets `freeMib` = clamp(card total − used, 0, device total) and `otherUsedMib` = device total − live free − the managed llama-server's own VRAM (at least 0), both rounded; unmatched, suspended or zero-VRAM cards keep the list's values (`app/server/lib/tuning/match.ts`).
- [ ] Card matching (`matchGpus`): hidden cards are left out, cards are taken in bus order, one card per device of a backend (a CUDA device and its Vulkan copy may share one), vendor from the backend (CUDA, ROCm/HIP) or the name, NVIDIA matched by name (Vulkan driver suffixes `(RADV …)`, `(AMDVLK …)`, `(NVK …)`, `(ANV …)` stripped), AMD by VRAM total within 2 %; devices with no memory or no vendor are not matched (`app/server/lib/tuning/match.ts`).
- [ ] Retained cards for the checks (`retainedBusIds`): the bus ids of the cards matched to the latest estimate's `-dev` (minus `none`), or to every dedicated card without `-dev`; with an empty device list, every monitored card (`app/server/lib/tuning/match.ts`).
- [ ] Checks order and scope: NVIDIA checks only when the monitor lists an NVIDIA card (per card: persistence, power limit, PCIe, Resizable BAR; then driver and `nvidia_uvm`), AMD checks only when it lists an AMD card (per card: DPM, PCIe; then HIP backend and ROCm recognition), then CPU (governor, THP, memlock, swappiness, NUMA), build (CUDA, SIMD, age) and kernel (IOMMU, model disk, disk bandwidth, swap) checks; a card that is not retained is `na` with `not applicable (card ignored)` for persistence, power limit, DPM, and HIP/ROCm when no AMD card is retained, while its PCIe and BAR checks still run; "the model spills" means the latest estimate is `ok` with `-ngl` not `all` or a `-ncmoe` (`app/server/lib/tuning/checks.ts`).
- [ ] Check `nvidia.persistence.<busId>`: `unknown` (`not reported by NVML`), `ok` (`enabled`), or `warn` (`disabled`, command `sudo nvidia-smi -i <uuid> -pm 1`, the UUID taken from the card key `nvidia:<uuid>`, else the bus id; persistence `session`) (`app/server/lib/tuning/checks.ts`).
- [ ] Check `nvidia.powerlimit.<busId>`: `unknown` (`unknown limit`), `warn` when the limit is more than 1 W under the default (`<n> W, default <d> W`, command `sudo nvidia-smi -i <uuid> -pl <d>`, session), otherwise `ok` (`<n> W (default)`) (`app/server/lib/tuning/checks.ts`).
- [ ] Check `<nvidia|amd>.pcie.<busId>`: `unknown` without a max link (`unknown PCIe link`) or without a current link (`measured under load: start the server first`), `unknown` when below its max while the card is under 10 % use (`x<w> Gen<g> while idle (max …): measured under load`), `warn` when below its max under load (`…: check the slot, riser or BIOS`, permanent), otherwise `ok` (`x<w> Gen<g> (max x<W> Gen<G>)`) (`app/server/lib/tuning/checks.ts`).
- [ ] Check `nvidia.rebar.<busId>`: `unknown` without a BAR size or VRAM total (`unknown BAR1 size`), `warn` when the largest BAR is smaller than the VRAM (`BAR1 <x> < VRAM <y>: enable Resizable BAR / Above 4G decoding in the BIOS`, permanent), otherwise `ok` (`BAR1 <x>`) (`app/server/lib/tuning/checks.ts`).
- [ ] Check `nvidia.driver`: `warn` when the llama-server logs say `driver version is insufficient` (`too old for the build’s CUDA (driver <v>, CUDA <maj>.<min>): update the driver`, permanent), `unknown` without a driver version, otherwise `ok` (`driver <v>, CUDA <maj>.<min>`, the CUDA part only when NVML gave it); check `nvidia.uvm`: `unknown` when `/proc/modules` is unreadable, `ok` (`loaded`), or `warn` (`missing`, command `sudo modprobe nvidia_uvm`, session) (`app/server/lib/tuning/checks.ts`).
- [ ] AMD checks: `amd.dpm.<busId>` is `unknown` (`power_dpm_force_performance_level unreadable`), `warn` on `auto` (command `echo high | sudo tee <file>`, session) or `ok` with the level; `amd.hip` is `unknown` (`build libraries not found`), `ok` (`present`, a `libggml-hip*` next to the binary) or `warn` (`missing: rebuild llama.cpp with -DGGML_HIP=ON, otherwise Vulkan`, permanent); `amd.rocm-gfx` is always `unknown` (`rocminfo not queried: …HSA_OVERRIDE_GFX_VERSION…`) when an AMD card is retained (`app/server/lib/tuning/checks.ts`).
- [ ] CPU checks: `cpu.governor` `unknown` (`cpufreq unreadable`), `ok` when every core is `performance`, else `warn` with the first other governor and the command `echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor` (session); `cpu.thp` `unknown`, `warn` on `never` (command `echo madvise | sudo tee /sys/kernel/mm/transparent_hugepage/enabled`, session), else `ok` with the mode; `cpu.memlock` `ok` (`--mlock not recommended here`) unless the estimate's args hold `--mlock`, then `unknown`, `warn` under the model size (command `ulimit -l unlimited`, session) or `ok` (`unlimited` or the size) (`app/server/lib/tuning/checks.ts`).
- [ ] CPU checks: `cpu.swappiness` `unknown`, `warn` above 10 while the model spills (command `sudo sysctl vm.swappiness=10`, session), else `ok` with the value; `cpu.numa` `ok` on one node, `ok` when the estimate's args hold `--numa`, else `warn` (`<n> nodes without --numa: add --numa distribute to the profile`, permanent) (`app/server/lib/tuning/checks.ts`).
- [ ] Build checks: `build.cuda` `ok` when a CUDA device is listed or there is no NVIDIA card, `unknown` without backend libraries, `ok` with a `libggml-cuda*`, else `warn` (`missing: rebuild llama.cpp with -DGGML_CUDA=ON`, permanent); `build.simd` `unknown` without a `system_info:` log line (`…start the server first`), `warn` when the CPU has `avx2`/`avx512f` but the line lacks `AVX2 = 1`/`AVX512 = 1` (`…rebuild with -DGGML_NATIVE=ON`, permanent), else `ok`; `build.age` `unknown` without a git checkout, `warn` over 60 days (`<n> days`, command `git pull && cmake --build build`, permanent), else `ok` (`app/server/lib/tuning/checks.ts`).
- [ ] Kernel checks: `kernel.iommu` `unknown` (`/sys/class/iommu unreadable`), `ok` when inactive or in passthrough (`iommu=pt`, `amd_iommu=off`, `intel_iommu=off` on the cmdline), `ok` (`active, single card`) with fewer than two retained cards, else `warn` (permanent); `kernel.disk` `unknown` without a model, `warn` on a spinning disk or a network filesystem (nfs, cifs, smb, fuse, sshfs, 9p, afs, ceph, glusterfs), else `ok` (`<fs>, SSD`); `kernel.disk-speed` `unknown` until measured, `warn` under 2 GiB/s, else `ok`; `kernel.swap` `unknown` without memory info, `warn` when swap is used while the model spills, else `ok` (`app/server/lib/tuning/checks.ts`).
- [ ] System readings (`readSys`), each tolerant (null or empty, never a rejection): governors of `/sys/devices/system/cpu/cpuN`, THP bracketed mode, soft `Max locked memory` of `/proc/self/limits` (`unlimited` = Infinity), `vm.swappiness`, `/proc/cmdline`, `/sys/class/iommu` entries, `/proc/modules`, `libggml-*.so` next to the resolved binary, the last commit date of a git checkout found up to 4 levels above the binary, the driver from NVML else `/sys/module/nvidia/version`, the largest of the first 6 BARs of each monitored card, the DPM level of each `/sys/class/drm/cardN` of a monitored bus id, the last `system_info:` log line, and the model's disk (rotational flag, filesystem of the longest `/proc/mounts` mount point covering it) (`app/server/lib/tuning/sysinfo.ts`).
- [ ] Binary resolution for the checks and the setup (`resolveBinary`): a bare name is looked up in the `PATH` (executable regular files only), a path with a slash is taken as is, a relative one against the working directory, then made symlink-free by `realpath`; `null` when not found (`app/server/lib/tuning/sysinfo.ts`, `app/server/lib/proc.ts`).
- [ ] Setup report details: `binary.path` is the resolved binary only when it is an executable regular file, `binary.version` is `b<build> (<commit>)` from `<binary> --version` (null when unreadable or the binary is not found), `bench.path` is `llama-bench` next to the `~`-expanded binary and `bench.devices` its device list (the last good list or `[]` on failure), `models` counts only readable entries of kind `model` (projectors and unreadable files left out) of `scanModels` on the `~`-expanded `modelsDir` when it is a directory, `telemetry.nvidiaSource` is the monitor's (`nvml` or `nvidia-smi`), `telemetry.perfParanoid` is `/proc/sys/kernel/perf_event_paranoid` parsed (null when unreadable), `listen` is the `--host` llama-webui listens on and `llamaListen` the `host` setting, each `exposed` when not loopback (`^127.`, `::1`, `localhost`, `[::1]`) (`app/server/lib/setup.ts`, `app/server/routes/api/setup.get.ts`, `packages/webui-shared/src/setup.ts`).
- [ ] First-run checklist filter (`isSetupCheck`, shared with the web): drops the checks that need a model or a running server (`cpu.memlock`, `cpu.swappiness`, `kernel.disk`, `kernel.disk-speed`, `kernel.swap`, every `*.pcie.*`, `build.simd`) (`packages/webui-shared/src/tuning.ts`).

### WebSocket messages

None. E8 owns no WebSocket message type (`packages/webui-shared/src/ws.ts`), and its routes broadcast nothing: estimates, plans, checks and disk measurements are only returned to the caller.

### Startup and shutdown

- [ ] E8 registers nothing in `boot()`: the memoized disk measurements and estimates (per model path), the CPU info, the `--list-devices` and `--version` caches and the parsed GGUFs are module-level state in `lib/`, empty at each process start, never persisted and not cleared on stop (`app/server/lib/tuning/memo.ts`, `app/server/lib/tuning/hardware.ts`, `app/server/lib/bench/hardware.ts`, `app/server/lib/boot.ts`).
- [ ] The memos live in `lib/`, not in a route file, so that saving a route file in dev does not reset what `POST /api/tuning/estimate` and `POST /api/tuning/disk-speed` wrote for `GET /api/tuning/checks` (`app/server/lib/tuning/memo.ts`).

### Background work

- [ ] Every tuning-hardware read (`GET /api/tuning/hardware`, `GET /api/tuning/checks`, `POST /api/tuning/estimate`, `POST /api/tuning/plan`) and the setup report spawn `llama-bench --list-devices` (killed with SIGKILL after 15 s), cached per bench binary and modification time; a failed or suspect listing (spawn failure, non-zero exit, signal, a GPU backend device listed with 0 MiB) is not cached and falls back to the last good list of that binary (`[]` if none) with the reason in `devicesError` (`llama-bench --list-devices exited with code <n>`, `… killed by <signal>`, `<id> listed without memory`, or the spawn error), and an empty list is not cached either (no error) (`app/server/lib/bench/hardware.ts`, `app/server/lib/tuning/hardware.ts`).
- [ ] The setup report (`GET /api/setup`) spawns `<binary> --version` (killed with SIGKILL after 5 s) when the binary is found, cached per binary file and modification time (a rebuild is read again), a failure cached as `null` (`app/server/lib/bench/hardware.ts`).
- [ ] Every `GET /api/tuning/checks` whose binary sits in a git checkout spawns `git -C <repo> log -1 --format=%ct` (stderr ignored, no timeout, not cached) for the build date (`app/server/lib/tuning/sysinfo.ts`).
- [ ] The disk measurement (`POST /api/tuning/disk-speed`) reads up to 1 GiB of the model file in 1 MiB chunks inside the request, not tied to the request signal (a disconnected client does not stop it) and not serialized with another measurement; only a running benchmark refuses it (`app/server/lib/tuning/disk.ts`, `app/server/lib/proc.ts`, `app/server/routes/api/tuning/disk-speed.post.ts`).
- [ ] The CPU info of the tuning hardware (`/proc/cpuinfo`, NUMA nodes from `/sys/devices/system/node`) is read once per process and reused (`app/server/lib/tuning/hardware.ts`, `app/server/lib/hardware/cpu.ts`).
